SECTION 4 — PROPOSED SOLUTION: TECHNICAL APPROACH

4.1 Architecture Overview

The UTD Residential Life Platform is a cloud-hosted web application built on a Node.js / Express backend with a server-rendered frontend and a PostgreSQL database. The architecture is designed for:

  • High availability: Multi-AZ cloud deployment with auto-scaling and automated failover
  • Integrations-first: REST API connectors for StarRez and Salesforce; webhooks for event-driven data sync
  • Security by design: HTTPS-only, role-based access control, encrypted data at rest and in transit, immutable audit logs
  • Compliance-ready: TX-RAMP control framework implemented; SOC 2 Type II audit in progress; HECVAT completed (attachment forthcoming)

4.2 Feature 1: Incident & Community Reporting (Working Demo Available)

Staff can log five report types from a single entry point: Incident, Noise Complaint, Lockout, Maintenance Request, and Welfare Check. Each report captures:

  • Common fields: Report type, building, room number, date/time, description, photo attachment
  • Type-specific fields: Noise complaint captures noise type and repeat-offender flag; lockout captures method of resolution

Automatic escalation rules:

  • Noise complaints logged between 22:00 and 08:00 are automatically escalated and generate a notification to the Residence Director
  • Lockout reports generate a notification to the Community Coordinator on duty

Resolution tracking: Each report has a status lifecycle (Open → In Progress → Escalated → Resolved) with full history. RDs and CCs can update status and add resolution notes from the report detail view. Staff can filter the report list by type, status, building, and date range.

4.3 Feature 2: Staff Scheduling & On-Call Rotation (Working Demo Available)

The scheduling module gives RDs and CCs a weekly calendar view of all staff assignments across three shift types: On-Call, RA Duty, and Front Desk.

  • Weekly calendar: Navigate forward/backward by week; today is highlighted; each day shows all shifts
  • Shift creation: RDs/CCs assign a staff member, shift type, building, start/end time, and optional notes
  • Shift detail: Staff view their assignments; RDs can mark shifts Completed or Cancelled
  • "My shifts" indicator: Each staff member sees their own upcoming shifts highlighted across the calendar

4.4 Feature 3: Program Proposals & Residential Curriculum Outcomes (Working Demo Available)

The program proposal module directly supports UTD's residential curriculum model, where every program must be tied to a documented learning outcome.

  • Proposal submission: Staff submit proposals with title, description, target audience, expected attendance, budget estimate, proposed date/time, and a curriculum outcome selected from UTD's defined outcome taxonomy
  • Outcome categories: Community Building, Academic Success, Wellness, Diversity & Inclusion, Leadership
  • Approval workflow: Proposals route to the Residence Director for review; RD can approve (with notes) or reject (with written rationale); submitter receives in-app notification on status change
  • Curriculum reporting: Approved proposals are queryable by outcome category, enabling RDs to verify balanced programming

4.5 Feature 4: Mass Communication & Surveys (Working Demo Available)

The Communications Hub gives RDs and CCs a single interface to reach staff and residents through broadcast announcements and structured surveys.

Broadcasts:

  • Channels: In-App notification, Email, and SMS — selectable per message
  • Audience targeting: All Staff, by Hall (Andrews, Berkner, Caruth, Hillhouse), or Individual user
  • In-app delivery: When channel is In-App, the system immediately inserts notification rows for every targeted recipient; the sender is excluded from their own broadcast
  • Broadcast log: The hub page displays the 20 most recent broadcasts with channel icon, audience label, sender, and formatted timestamp

Survey builder:

  • Question types: Free text, 1–5 star rating, and Yes/No — multiple questions per survey
  • Lifecycle: Surveys are created as Draft, activated (opens for responses), then Closed; RDs/CCs manage status from the survey detail page
  • Response deduplication: The database enforces a unique constraint on (survey_id, respondent_id); a staff member who has already responded sees their submitted answers and cannot re-submit
  • Aggregate reporting: The survey detail page shows per-question statistics — rating average + 1–5 distribution bars, yes/no counts with percentage, and free-text answer list — visible to RDs and CCs alongside the full response roster
  • Pending badge: The hub shows a count of active surveys the current user has not yet completed, surfacing response requests immediately

SECTION 5 — INTEGRATION ARCHITECTURE

5.1 StarRez Integration

StarRez is UTD's authoritative source for student housing assignments. Our integration approach:

  • Direction: StarRez → Platform (read-only sync for student profile and room assignment data)
  • Method: StarRez REST API; authenticated via API key in secrets management
  • Sync cadence: Nightly full sync + real-time webhook on room assignment change events
  • Data consumed: Student name, UTD ID, building, room number, roommate assignments, check-in/check-out dates
  • Conflict resolution: StarRez is always authoritative

5.2 Salesforce Integration

  • Direction: Bidirectional — pull student engagement records from Salesforce; push residential activity events back
  • Method: Salesforce REST API with OAuth 2.0 (Connected App)
  • Data consumed: Student contact preferences, engagement history, case records
  • Data written: Program participation events, incident flag notifications (configurable)
  • Idempotency: All writes use UTD ID as external ID; duplicates de-duplicated via upsert operations

5.3 Single Sign-On (SSO)

The platform supports enterprise SSO via SAML 2.0 or OpenID Connect, compatible with UTD's identity provider. Staff authenticate once through UTD's IdP and receive a session token with their role embedded. No separate platform passwords are required after SSO is configured.

SECTION 7 — SECURITY, COMPLIANCE & DATA PRIVACY

7.1 TX-RAMP Compliance

The UTD Residential Life Platform is designed to satisfy Texas Risk and Authorization Management Program (TX-RAMP) requirements, including: role-based access control with least-privilege enforcement; immutable audit logs with tamper detection; annual incident response plan testing; vulnerability scanning aligned with TX-RAMP control framework; all data stored in US-based cloud regions only.

7.2 SOC 2 Type II

Colaberry is actively pursuing SOC 2 Type II certification covering the Trust Services Criteria: Security, Availability, Processing Integrity, Confidentiality, and Privacy. A SOC 2 Type I report is available upon request under NDA; Type II audit is scheduled for completion within 12 months of contract execution.

7.3 HECVAT

Colaberry will complete the Higher Education Cloud Vendor Assessment Tool (HECVAT) Full version and return it to UTD within 10 business days of contract execution. [⚠️ HECVAT attachment to be included with final submission.]

7.4 FERPA

All student data is treated as an education record under FERPA: no student PII shared with third parties without UTD authorization; data processing agreement executed with UTD as data controller; student data logically isolated per institution; bulk deletion available on contract termination.

7.5 WCAG 2.1 Level AA Accessibility

Platform developed against WCAG 2.1 Level AA: keyboard-navigable interfaces; sufficient color contrast ratios (minimum 4.5:1); ARIA labels on all form fields; screen-reader tested with NVDA and VoiceOver before each release; axe and WAVE tooling in CI pipeline.

7.6 Data Encryption

  • In transit: TLS 1.2+ enforced; HTTP redirected to HTTPS
  • At rest: AES-256 database encryption; backups encrypted with the same standard
  • Secrets: API keys and credentials stored in dedicated secrets manager — never in source code

7.7 Penetration Testing

Annual third-party penetration test. Most recent report available under NDA. Critical/high findings remediated within 30 days of report receipt.
