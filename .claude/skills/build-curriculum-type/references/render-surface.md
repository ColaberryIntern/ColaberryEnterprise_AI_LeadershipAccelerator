# The render surface — where a card actually appears

The mistake that cost the most rework across the Overview / Self Study builds was designing a
**full page** when the student sees a **narrow right-side drawer**. Read this before writing any
`body_html` or designing a layout.

Student renderer: `frontend/src/components/timeline/CardDetailBody.tsx` (+ siblings
`studio/StudentPreview.tsx`, `portal/runtime/RuntimeWorkspace.tsx`).

---

## Physical constraints

- **A right-side drawer, not a page** — roughly **~400–560px wide** (it narrows further on smaller
  viewports). Design for a single narrow column. No multi-column layouts, no wide tables that
  don't wrap, no fixed pixel widths that assume a page.
- **`body_html` renders in a sandboxed iframe: no JavaScript runs.** Anything needing JS
  (scrollspy, tabs, collapsibles, charts) will not work from `body_html`. The runtime prompt
  explicitly demands *"clean self-contained HTML, no scripts."*
- **Token-capped.** Preview caps at 1800 tokens; the persisted student content path
  (`cardContentService`) at 3200. Keep generated content within a tight word budget
  (the shipped prompts target ~150–230 words for Overview, "thorough but drawer-sized" for Self Study).
- **Two styling models depending on the render band** (below): generic types must ship their own
  CSS *inside* `body_html`; bespoke-renderer types must ship **no** CSS/nav/script — the renderer
  owns all of it.

---

## Render bands with a bespoke renderer (these are CODE)

As of `origin/main`, `CardDetailBody` branches on `render_band` for:

| Render band(s) | Bespoke experience | Author implication |
|---|---|---|
| `media`, `live_class`, `video_feedback` | Video player (`isVideo`) | Needs a media source; body is "lesson notes" |
| `skills_jar` | Anthropic Skills course frame (`isSkillsJar`) | External course embed |
| `survey` | Live survey UI + 1–5 scale (`isSurvey`, `CardSurveyExperience`) | Prompt steers ~10 Likert statements + 1 open prompt; the scale is code |
| `quiz`, `evaluation` | Interactive assessment (`isAssessment`, `AssessmentPanel`) | **Questions are auto-generated by `assessmentService`** (blueprint+competency aware); prompt only frames title/summary |
| `warmup` | Immersive reader (`isReader`/`readerDoc`): sticky top nav + scrollspy + progress | `body_html` = **`<section id data-nav>` blocks only, NO `<style>/<nav>/<script>`** — the reader supplies all of it |

`testimonial`, `blog`, `podcast` get external-title handling. **Everything else** falls through to
the **generic content body**: it renders `summary`, `body_html` (in the sandboxed iframe),
`questions`, `reflection`, and gates optional sub-sections (ai_chat, quiz, reflection) on the
type's **capabilities** via `hasPart()`.

### The rule this implies
- Building a type over an **existing** render band (generic or one of the bespoke ones above) =
  pure authoring. Fast.
- Building a type that needs a **new visual behavior** with no renderer = a **frontend PR**, not a
  component edit. You cannot conjure a new interactive experience from `body_html` (no JS). Flag it
  as a separate follow-up and, if needed, add the `render_band` branch in `CardDetailBody` (and its
  siblings) plus any service (like `assessmentService` for scored types). The Self Study reader is
  the reference example of "new render behavior shipped as code."

## The three thumbnail surfaces

A thumbnail shows in **three** places; "the thumbnail isn't showing" usually means one of them was
missed:

1. **Library tile** — the admin grid `<img src={thumbnail_url}>`.
2. **Prompt-driven `renderers.thumbnail`** — an LLM-rendered surface (`render/:surface`). Reference
   the SAME picture by URL inside this prompt (see Overview's `OVERVIEW_THUMBNAIL_RENDERER` in
   worked-examples) so the two never drift.
3. **The student card hero** — what the participant sees on the card.

**Prefer a short static asset path** `thumbnail_url: /thumbnails/curriculum-types/<slug>.jpg`
(files in `frontend/public/thumbnails/curriculum-types/`, regen pipeline
`scripts/curriculum-type-thumbnails/`). Reason (verbatim from the seed): *an LLM can copy a short
URL verbatim into the thumbnail renderer prompt; it cannot reliably reproduce a data-URI.* Use a
`data:image/svg+xml;base64,…` only for a truly one-off self-contained mark. `source:'template'`
falls back to a deterministic band-colored SVG with no image API needed.

## Preview ≠ student runtime (verify in the real shape)

- The Studio **preview** (`runtimePreview`) and the **persisted student content**
  (`cardContentService`) run through **different prompts, token caps, and output schemas** (9 keys
  vs a 5-key subset). A preview that looks right is necessary but not sufficient.
- **The format does not automatically carry from preview to the student workspace** — only what
  the student path emits (`title, summary, body_html, questions[], reflection`) survives, and only
  self-contained, CSS-baked-in `body_html` renders faithfully. When in doubt, check the card in the
  actual portal drawer, not just the Studio preview pane.
- After changing a blueprint or a generation prompt, **regenerate** — old card content is cached and
  will look near-identical until you do.
