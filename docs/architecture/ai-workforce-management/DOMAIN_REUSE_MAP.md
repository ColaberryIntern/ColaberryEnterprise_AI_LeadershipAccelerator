# Domain Reuse Map (Checkpoint A)

For every conceptual object the mission prompt proposed, this is the verdict: **REUSE** (use the real thing as-is), **EXTEND** (real thing exists, needs additive columns/endpoints), or **BUILD NEW** (confirmed absent or confirmed wrong-shaped — a new, additive, `ai_agents.id`-keyed model is required). The mission's own framing said these are "conceptual names, NOT permission to duplicate current tables" — this document is that proof.

| Mission concept | Verdict | Real system | Why |
|---|---|---|---|
| A second AI-agent registry | **N/A — forbidden** | `AiAgent` (`ai_agents`) | Non-negotiable #1. Confirmed canonical, no drift. The separate `orgRegistry.ts` synthetic roster (`docs/architecture/workforce-os/`) is a different, deliberately-isolated system — see `CURRENT_STATE.md` §E — not a second registry to consolidate into this one, just something to never confuse with it. |
| `AgentRoleCharter` | **BUILD NEW** | None | No business-facing "job description" object exists separate from `system_prompt`. `AiAgent` has no `mission`/`responsibilities`/`kpis` fields — those only exist on the *synthetic* `orgRegistry.ts` roster (`mission`, `responsibilities[]`, `kpis[]`, `CURRENT_STATE.md` §E), which is not `ai_agents`-keyed and not reusable. A charter needs its own small table, FK'd to `ai_agents.id`. |
| `AgentManagerSettings` | **BUILD NEW** | None | No per-agent-per-manager settings row exists. Closest analogue is `AiAgent.config` (JSONB), confirmed by repo-wide grep to never hold anything but static operational thresholds — reusing it for manager-authored settings would conflate two different concerns in one untyped bag, violating backend/CLAUDE.md's "every module exposes explicit contracts" rule. |
| `AgentManagerConversation` / `AgentManagerMessage` | **BUILD NEW** | `ChatConversation`/`ChatMessage` (pattern only); `workforce_messages` (wrong key space) | `ChatConversation`/`ChatMessage` are structurally close (conversation + turn-based messages) but hard-FK'd to `visitors` — would need a schema change to support an `org_members.id`↔`ai_agents.id` pair, at which point it's cleaner to model new tables sharing the same *shape*, not the same rows, than to loosen a visitor-identity contract Maya depends on. `workforce_messages` is real and live but keyed on the synthetic `orgRegistry` `employee_slug` — reusing it directly would attribute a real manager's message about Reese to a fictional persona's row. Verdict: new tables, Maya's shape as a design reference, no shared rows. |
| `ManagerDirective` | **BUILD NEW** | `CompanyDirective` (adjacent, wrong originator) | `CompanyDirective` (used by `companyStrategyAgent.ts`) is AI-agent-authored, company-scoped — the reverse direction (agent → human) of what's needed (human manager → agent, restriction-only, versioned, auditable). No existing model fits; must be new, and must enforce non-negotiable #4 (durable instructions injected into runtime context, never written into `system_prompt`). |
| `AgentManagerInboxItem` | **BUILD NEW** | None generic | Every "needs a human's attention" queue found is domain-bound (Basecamp-todo, email-inbox, community-member, or `ApprovalRequest`'s shadow-mode-only state machine). `ProposedAgentAction` is the closest live, enforced approval object (`pending→approved/rejected/expired→applied`, real controller) and should be the model this inbox is built to resemble/extend rather than re-deriving a new state machine from nothing. |
| `AgentReportSubscription` / `AgentReportRun` | **BUILD NEW** | `DepartmentReport`, `KPISnapshot`, `reportingOrchestrationService.ts` (all partial) | No object combines content-scope + recipient + cadence + timezone + channel. `DepartmentReport` persists a report but has no subscription/recipient/cadence concept. `sendRawEmail()` remains the correct send primitive once a subscription fires — reuse the sender, build the subscription. |
| `AgentOneOnOne` / `AgentOneOnOneOutcome` | **BUILD NEW** | None | No 1:1-meeting-with-an-AI-agent object exists anywhere, real or synthetic. The synthetic Workforce OS's "daily leadership meeting" (`workforce_meetings`) is structurally the nearest analogue (agenda-less standup → outcomes) but is keyed to the fictional roster and log-format, not a real manager-initiated 1:1 with a real agent. Reference its shape, not its rows. |
| `AgentGoal` | **BUILD NEW** | `CompanyGoal`, `DepartmentKpi`, `KPISnapshot`, `AgentPerformanceMetric` (all wrong shape) | None let a human set "Agent X's target is Y" and track real progress. `CompanyGoal`/`DepartmentKpi` are company/department-scoped and read-only from an agent's perspective. `KPISnapshot`/`AgentPerformanceMetric` are observed-metric tables with no target column. A new `AgentGoal` needs an explicit target + a real computed-progress link, and per non-negotiable #6 must render `UNMEASURED` rather than a fabricated number when no real metric backs it. |
| `AgentMemoryProposal` / `AgentApprovedMemory` | **BUILD NEW** | `ReportingInsight` (status workflow), `OpenclawLearning` (evidence/confidence) — both partial | No model combines evidence + a real enforced human-approval gate + feedback into runtime behavior. `ReportingInsight.status` (`new→acknowledged→actioned→dismissed`) is the closest real human-workflow precedent to model the approval state machine on. `OpenclawLearning`'s `evidence`/`confidence`/`sample_size` columns are the closest real precedent for what a proposal needs to carry — but its own `applied` flag is confirmed dead (never set, never read for gating), which is the exact anti-pattern non-negotiable #6 and the mission's memory-self-approval stop condition forbid repeating. |
| Manager-vs-admin authorization check | **EXTEND** | `resolveHumanDownstreamAgents()` / `isAgentInHumanDownstream()` (`orgChartHierarchyService.ts:110-141`) | Already real, already live (gates `assignTaskToAgent`), already walks the real `reports_to_type`/`reports_to_id` chain. Needs only a thin new middleware (`requireAgentManagerOrAdmin`) wrapping it with an `OrgMember.email = AuthPayload.email` lookup — see `MANAGER_AUTHORIZATION_MAP.md`. This is the one item on this table that is mostly-already-solved. |
| Durable instruction injection at runtime (not `system_prompt` mutation) | **BUILD NEW**, pattern precedent exists | Maya's context-assembly pipeline (pattern only) | No code assembles "persona + durable instructions + memory + page context" today outside Maya's fully-hardcoded pipeline. The *pattern* (assemble at request time, never persist into the base prompt) is proven and should be followed; the code must be new and generic. |
| Chain of Command display | **REUSE** | `reports_to_type`/`reports_to_id` + `resolveReportsToHuman()` (`ticketCreatorReportsToResolver.ts`) + `AgentDetailPage.tsx`'s existing "Reports to" card | Already fully real, already rendered on the page today (`CURRENT_STATE.md` §A). Checkpoint F should surface it more prominently, not rebuild it. |
| "Ask Agent About This" explainability | **BUILD NEW**, grounded in real data | `ai_events`, `ProposedAgentAction.reason`, `agentAuthorizationService` verdicts/reason codes | No existing UI action does this. The underlying facts to ground it in (event log, stated reason codes, authorization verdicts) are real and already captured — this is a new read-only synthesis view over existing evidence, not a new data-capture system. |
| Trust/INPACT/GOALS scoring | **REUSE (compute), EXTEND (persist)** | `trustMetricsService.ts` | Computation is real and live; history is not persisted (`trust_scores` confirmed absent). If Checkpoint E wants trend-over-time, extend via `KPISnapshot` (already real) rather than building a parallel history table. |
