Know exactly what you are building

Bot. Agent. Agentic. Multi-Agentic.

These four words get used interchangeably, including by people selling you things. They are not the same, and the difference is not model quality. It is authority.

Level 1

Bot

Fixed rules, fixed triggers. If this, then that. No judgment is ever made, because there is nothing in it capable of judging.
Tell: it cannot surprise you. Not in a good way, and not in a bad one.
Level 2

Agent

A model makes one judgment call. It drafts, classifies or recommends. You decide when it runs and what happens to the output.
Tell: no tools, no loop, no consequences. It proposes, you dispose.
Level 3

Agentic

Now it holds tools and authority. It loops: observe, decide, act, read the result, decide again. It owns an outcome rather than a step.
Tell: it can change the world without asking first. That is the whole difference.
We build this
Level 4

Multi-Agentic

Many agentic agents with distinct jobs, talking to each other. They hand work off, cross-task and escalate. The intelligence lives in the organization.
Tell: no single agent can explain the whole outcome on its own.
The jump from Agent to Agentic is not a better prompt. It is authority. And the moment something holds authority it needs exactly what a new employee needs: a job description, a boundary, an approval path, and a record of what it did.

This is not a sandbox

You get real access to the real system.

  • A seat inside enterprise.colaberry.ai. The live application, not a copy with the interesting parts taken out.
  • Your own agent, and full operation of it. Start it, pause it, re-schedule it, read its run history, see every error it has ever thrown.
  • Control of the skills granted to it. You decide which capabilities it holds and which data it may touch. Granting a skill is a decision you will be asked to defend.
  • Claude Code as your build environment. This is where you design it, write it, test it and harden it.

How the work actually goes

Build the happy path until it works.

Break it deliberately. Feed it malformed input. Kill its database mid-run. Fire it twice in one second. Skew its clock.

Harden every break you found, each with a test that reproduces the original failure.

A feature nobody has tried to break is not finished. It is only untested.

Expect to spend more time testing than writing. That ratio is not a sign you are slow, it is the actual job.

The standard we are aiming at

Your agent should behave like a colleague.

You can ask it a question and get a real answer. It opens tickets for work that needs doing. It knows what it is allowed to decide by itself, and what it has to bring to a human.

Job description
The one outcome it owns, written in a sentence, before any code exists.
Scope of authority
What it may do unsupervised, and the hard edge where that stops.
Approval gates
The actions that need a human to say yes first. Anything irreversible belongs here.
Escalation rules
What it does when it is stuck, confused, or asked for something outside its scope. Going quiet is not one of the options.
Record of work
Every run, action and failure, in enough detail to reconstruct a bad decision a month later.
The hardest requirement is this one. If you cannot tell the difference between your agent working and your agent silently failing, you have not built an employee, you have built a rumour. We hit exactly that in the existing fleet this week: a supervisor that could not distinguish "nothing is wrong" from "I was unable to look", and reported both as healthy.

Where it gets genuinely hard

One agent each. One system together.

You own your agent end to end. You will not be working alone, because your agent will not be working alone.

Your agent
meets a request outside its scope
→
Finds the owner
which agent owns this decision
→
Hands it off
files a ticket on their agent
→
Tracks it
and does not drop it on the floor

Agent to agent

Your agent will message other agents directly, pass work across, and cross-task on jobs no single agent can finish alone.

Which means you and the other owners have to agree a protocol, not just write good code separately and hope.

The questions nobody has settled

Who owns a decision that spans two agents? What happens when two agents disagree? How does a handoff get proven rather than assumed?

These are the interesting problems, and they are organizational before they are technical.

One agent is an experiment. Ten agents that can delegate to each other, and be held to account for it, is a company.

Why this matters past your internship

We are writing the manual, and Anthropic will read it.

There is no settled, published answer for what it actually takes to turn a language model into a reliable agentic employee, let alone a team of them that cooperate without dropping work. We are going to find out by doing it, and write down every part of it.

What gets documented

The decisions. The dead ends. The governance that turned out to matter, and the governance that turned out to be theatre. Everything we had to invent because it did not exist yet.

What you walk away with

Not a certificate. A system running in production with your name on it, and a written account of how it was built that an AI lab thought was worth reading.

At the end of this you will be able to point at something real and say: I helped build a digital workforce, and here is the manual we wrote while doing it.
