Grant 2 · the reach

Whose portfolios do they see inside it?

Rows in a new table, granted by an admin. A cohort, or named individuals. Nothing by default.

career_mentor_scopes
Why not just the role? Because a role on its own is a platform-wide grant. Give someone mentor and they would be able to read every learner's career evidence on the platform. “The learners they are over” only means something if something records which learners those are. That is the second table.

Owner / Admin
Every learner. Unscoped by design: they are the ones granting mentor scope, so gating them behind it would be circular.
Everyone
Mentor

Only theirs
Other staff
Support, Revenue, Curriculum, Community Organizer. No review access at all.
Nothing
Clients / employers
No admin token, so they fail at the door. Their only career surface is the frozen public snapshot.

The mistake this was built to avoid

One return value carries the whole thing, and it has a trap in it.

visibleEnrollmentIds(reviewer)

  null   ->  "no filter"      an ADMIN. show every learner.
  []     ->  "filter to none"  a MENTOR with no grants. show NOTHING.
  [ids]  ->  "filter to these" a MENTOR with grants.

null and [] are one keystroke apart and mean opposite things. If an unscoped mentor ever returned null, the queue would read it as “no filter” and hand them every learner on the platform. The failure would look like working software: a full queue, no error, no log line.

So that is the load-bearing test. It asserts a mentor with no grants gets [] and explicitly not null. The queue also short-circuits on an empty scope before it builds a query, so there is no path where an empty filter degrades into an absent one.

Where it is enforced

Passing the door is not the same as being allowed to act.

ActionGateThen also
GET /review-queue requireCareerReviewer Queue filtered to the caller's scope
POST /review/:snapshotId requireCareerReviewer Per-learner check. The snapshot is resolved to its owner and refused with 403 if that learner is outside scope
POST /publication/:id/suspend requireCareerReviewer Same per-learner check
GET/POST/DELETE /mentors/:id/scopes requireAdmin Admin only, even though it sits in the same file
Two deliberate choices there. The decide and suspend routes re-check per learner rather than trusting the gate, because a mentor could otherwise POST a snapshot id belonging to someone else's learner and the gate alone would wave it through. And grant/revoke stay requireAdmin so a mentor can never widen their own scope, which a shared router-level guard would have quietly allowed.

How you grant it

Two shapes of grant, so breadth and precision use the same mechanism.

# "You mentor the whole July cohort"
POST /api/admin/career/mentors/<mentorEnrollmentId>/scopes
     { "scope_type": "cohort", "scope_id": "<cohortId>" }

# "You mentor these four people"
POST /api/admin/career/mentors/<mentorEnrollmentId>/scopes
     { "scope_type": "enrollment", "scope_id": "<enrollmentId>" }

# See what a mentor can currently reach
GET  /api/admin/career/mentors/<mentorEnrollmentId>/scopes

# Take it away
DELETE /api/admin/career/mentors/<mentorEnrollmentId>/scopes
     { "scope_type": "cohort", "scope_id": "<cohortId>" }

Three properties worth knowing

  • Granting twice is a no-op. Re-granting a live scope returns granted: false rather than creating a second row that would then need revoking twice. Enforced by a partial unique index, not by remembering to check.
  • Revoking never deletes. It stamps revoked_at and revoked_by. “Who could see whose portfolio, and when” is exactly the question that gets asked months later, usually by someone who is not pleased.
  • Cohort grants follow the cohort. A grant resolves to that cohort's learners at read time, so a student who joins later is automatically covered and one who leaves is not.

What the new tests actually assert

  • A mentor with no grants gets [], never null
  • A mentor whose token carries no enrollment id gets [] without even querying
  • Cohort grants expand to that cohort's members
  • Cohort and direct grants merge without duplicates
  • A mentor is refused on a learner outside their scope
  • Every non-mentor staff role resolves to no review access
  • Re-granting a live scope creates no second row
  • Revoke stamps the row rather than destroying it
