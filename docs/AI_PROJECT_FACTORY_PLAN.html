Model does the probabilistic work

Decompose a requirement or contract into candidate tasks, normalize them, propose role→executor matches, draft prose. It is allowed to say "don't know."

Code does the deterministic work

Coverage, structural validity, ids, versions, hashes, immutable audit, approval transactions — and the human-or-AI allocation score. The model never grades itself.

The engine that divides the work

Requirement → tasks, built on the NuOrg model

NuOrg's platform parses a procedure someone already wrote; it never generates. We keep its output contract, precedence, gates and review model — and put an LLM exactly where its regex recall stops: the decomposition itself.

Keep from NuOrg — proven

  • Evidence is the unit of truth. Every task cites its source blocks; every block must be cited or classified. Coverage is a query, not a judgment.
  • Written precedence. Explicit > implied > model-added — each task tags which, with a one-line reason.
  • "Don't know" is a value. Unspecified performer, unknown basis, open question — never a guess. The judge penalizes invention, not omission.
  • Three separate decisions. What the task is · which role performs it · which person / team / agent fills the role.
  • Executor is one of person / team / agent, and an agent always needs a human accountable. Enforced twice.
  • A machine gate with named codes. SOURCE_COVERAGE, OVERSIGHT, LOOP, PERFORMER… errors go back to the model, never self-certified.
  • Approval is a transaction. Version, hash, immutable audit, fork-on-edit. Reproducible history for free.

Add beyond NuOrg — where ours is better

  • Actually decompose. One task = one verb, one object, one outcome, one performer — from a goal or narrative, not just numbered steps.
  • Attributes an assignment needs. required_skills, judgment_level, decision_authority, data_sensitivity, interaction_pattern, frequency, confidence.
  • Assignment as a scored pass. Ranked candidates with match_method + confidence; auto-accept only exact-unique; the human-or-AI call is computed in code.
  • Re-derive, don't patch. A changed requirement re-runs the pipeline and shows a diff against the approved version.
  • Confidence + thresholds everywhere the LLM contributes — NuOrg is binary because it is pure rules.
  • Tests as failure modes first. "A block cited by nothing." "A compound sentence that must become two tasks." "An agent on an approval step."
The roadmap

Six phases, each one governed loop-architect run

Sequential. Each phase ends in a reviewable exit you approve before the next starts. The run plans, gets its plan independently audited, builds one task at a time with a fresh-evidence verifier, gates, deploys, and verifies the live release.

1

Process & project contract

The linked-tracks model (proposal + solution build), the process/task schema above, the human/AI allocation matrix, the old→new role map, the workspace design, and the project-identity mapping between domains.

Exit · one complete sample contract project showing both tracks, task ownership, and consolidated human roles — as data plus a rendered review.
loop-architect ▸ discover · contract · plan · audit · build · gate · deploy · verify · handoff
2

Generation pipeline

Update the /build-student-project skill and the real pipeline together — plan contract, decomposition, gates, story prompts, doc renderer, verification. LLM decomposition behind the deterministic validate(); agent-scoping reconciles with explicit assignments.

Exit · a newly generated project produces coherent process, workforce and UI architecture with stories traced to tasks and requirements — and gates reject the incoherent ones.
loop-architect ▸ honors the renderDocs write-allowlist; no silent bypass of the UI-map contract
3

Management workspaces

The Internship Admin Command Center over the whole portfolio, and the human-operator Command Center generated inside each app. Admin authorization, never intern impersonation; "See as intern" stays distinct.

Exit · admin sees the whole project (counts drill into real records); a human operator runs their authorized business work through one login — never a superuser.
4

Evidence & approvals

Page inventory (extending the existing UI-map contract), captures to object storage, review submissions bound to immutable versions, six separate decision types, revision tasks that don't duplicate on retry.

Exit · review, rejection, correction, resubmission — and a stale approval refused: an old screenshot can never sign off a newer unreviewed build.
5

Builder integration · DEP

The AI builder that writes the software, with a caption feed of observable events — each backed by a timestamped, evidence-linked event. Pending is never shown as success; disconnection is shown honestly.

Exit · one real scoped build emits truthful captions and reaches human review; unavailable runtime functions are marked, not faked.
Blocked on ▸ the other-tab builder design (see below). Builds only to the integration contract until then.
6

Migration & acceptance

Backfill known processes and links without fabricating evidence (legacy work labeled unassessed where it can't be proven); page-consolidation and role-migration maps before touching nav or permissions.

Exit · one contract project and one ordinary AI project pass the full workflow; a migration/rollback report and remaining gaps are visible.
Who watches the operation

Three connected command centers

Distinct identities, distinct permissions, distinct activity — never collapsed into one superuser or one impersonation.

A

Internship Admin

One portfolio across interns and projects: proposal readiness, build readiness, verified stories, required approvals, blockers, deadlines — every count drilling into the real records.

B

Human Operator

Generated inside each delivered app: the AI work running, waiting or failed; approval and exception queues by urgency; the controls to direct it — all within one authorized scope.

C

AI Builder

The employee that writes the software, kept separate from the AI employees inside the delivered solution. The intern still understands, supervises, tests and explains the system.
