Explorer Growth OS · Content & messaging

Why there is no weekly digest, and the plan to produce one

The Content tab is confusing because it answers a question nobody asked. It reports which lesson cards could be pointed at. You were looking for what the message says. That message has never existed — not because anything is broken, but because composing it was deliberately deferred to send time, and send time has never arrived.

27 Oct 2026 525 email decisions · 0 sent Diagnosis verified from source Plan: 5 phases

The short answer

Every Explorer sequence step already carries a real subject line and a real written brief. The weekly digest's subject is "This week in AI, for practitioners". Its brief says: lead with the content supplied in the context — usually two or three lessons — and say what each is FOR in one line.

What it does not carry is a body. body_template is an empty string on all 24 steps, by design, with a comment saying so: the engine generates the message at send time from the brief plus the learner's context. Nothing has ever sent, so nothing has ever been generated.

So the digest is not missing. It is a prompt that has never been run. Everything you need to run it — the generator, the validator, the fact guard, the draft store, the approval screen — already exists in this repo and is already tested. None of it has been introduced to the Governor.

Diagnosis — five findings

Each of these is read from source, with the file named. Where something does not exist, it is stated as not existing rather than described.

1

The body was deferred on purpose, and the deferral was never closed

The sequence definitions are explicit about it. This is the comment at the top of the file that defines all 24 steps:

THESE ARE PROMPTS, NOT COPY. body_template is empty on every step by design: the engine generates the message at send time from ai_instructions plus lead context. Only 12 of ~180 steps across the whole production system carry a body template. Writing copy here would duplicate the campaign engine, which the original brief forbade.

backend/src/seeds/explorerGrowth/explorerSequenceDefinitions.ts:8–12

That was a reasonable call. The cost of it is that there is no way to read the message before it sends, which is exactly what you are asking for. The same file is candid that the safety clause appended to every brief is an instruction, not a control: "this is an instruction to a generator, not a filter on its output … the real control on generated copy is the send-time quality gate, which belongs to the epic that wires execution." That epic has not shipped.

explorerSequenceDefinitions.ts:8–12, 32–43, 46–58, 137–147
2

The Governor and the message generator have never been introduced

generateMessage() is a mature service that returns {subject, body} for email, grounded in a campaign system prompt, the lead profile, verified engagement context and live cohort facts. Fifteen places in this repo call it. None of them is Explorer Growth.

The validator built to check its output, validateGeneratedMessage(), already imports the Explorer fact guard. The rails were built for this traffic and left unconnected.

The deeper disconnect: the Governor writes selected_campaign_id, but never traverses campaign → sequence → step. selected_sequence_step is never written by any code in the repository. The 24 subject lines sit in follow_up_sequences.steps and are, today, unreachable from a decision.

aiMessageService.ts:306 (generateMessage), :537 (generatePreview) · messageValidatorService.ts:7, :47 · runGovernor.ts:242–248, 260–294
3

A decision row has nowhere to put a message — except one unused column

explorer_journey_decisions has selected_content_assets (pointers to lessons), channel and reason. There is no subject column, no body column, no html column. The content registry has none either — its own sync file says "explorer_content_assets … has no body column at all."

But there is a scheduled_email_id column, and nothing has ever written to it. It exists precisely for this link. That single fact reshapes the fix — see Phase 1.

ensureExplorerGrowthSchema.ts:60–91, 143–175 · syncTimelineCards.ts:9–16 · ExplorerContentAsset.ts:124–126
4

“Content asset” means “lesson card”, and the tab never says so

The registry holds exactly one kind of thing. Every row is written with asset_type = 'LESSON', projected from published timeline cards. The model's own header lists seven other kinds it was meant to hold — videos, blog posts, podcasts, cohorts, live sessions, open-house events, community rooms — and none of them has a sync or a seeder. That list documents intent, not inventory.

So when the tab says 468 assets support the weekly digest, it means 468 lesson cards could be cited in a digest. It does not mean a digest exists. Of the 525 email decisions in production, 392 “resolved content” — all 392 resolved a pointer to a lesson, not a sentence.

Compounding it: your two screenshotted tables are built from different SQL. The cross-tab filters on active + email-capable only. The coverage table additionally filters on the validity window and the asset type. They are not reconcilable by eye, and nothing on screen warns you.

syncTimelineCards.ts:149–166, 185–199, 220–241 · ExplorerContentAsset.ts:12–26 · explorerDecisionsService.ts:199–231 vs :252–260
5

The message in your screenshot is a stale row, not a live failure

“No content asset was resolved … and the Governor named no gap” fires only when an action that expects content has zero assets and no named gap. With the eight generators as shipped, a newly written row cannot reach that state — the only three candidates that request nothing are a WAIT and two human-task actions, none of which expects content.

Those rows predate the asset wiring. The Governor's own comment records it: "Until EPIC 5 NOTHING anywhere assigned this column, and all 153 rows read []." The upsert is keyed on (enrollment_id, decision_date), so it never backfills an earlier date. The Decisions list hides them (it defaults to the latest run); the Journey drill-down does not. Your own screenshot corroborates this — the learner's scores moved from E 0 / I 1 at the decision to E 5 / I 24 now, which is a lot of drift for a current decision.

There is still a real hole underneath. resolveAllForCandidate returns {assets: [], gaps: []} when handed an empty request list — the loop that produces a gap simply never runs. Any future generator that asks for nothing while selecting an action that expects content reproduces this silence exactly. It needs a guard regardless of the stale rows.

resolveContentAssets.ts:206–222 · runGovernor.ts:274–275, :286 · explorerWhyService.ts:55–61, 118–121 · decideForLearner.ts:95, nurture.ts:24, frictionRecovery.ts:55

The constraint that shapes the fix

The obvious repair — have the Governor compose the email — is the wrong one, and a test will stop it.

The Governor is architecturally forbidden from composing or sending

A structural test sweeps every file under governor/ and content/ and enforces an import whitelist, not merely a denylist. emailService, schedulerService and sequenceService are named forbidden outright. The generator is simply not on the allowed list, so importing it fails the build.

WHY THIS IS A WHITELIST. The plan inherited a denylist of six strings. The plan auditor found that emailService.ts exports twenty-six send* functions, and only one of them is in that list … A new dependency is a deliberate decision that fails this test until someone adds it and says why.

backend/src/services/explorerGrowth/governor/__tests__/noSendPaths.test.ts:6–23

This is a good guard and it should stay. It is also why sequenceService being forbidden matters: the Governor cannot be the thing that reads a sequence step. So the plan does not put generation there. It puts it in a new sibling stage that runs after the Governor, with its own narrower whitelist that still forbids every mailer and queue writer.

noSendPaths.test.ts:25–27 (swept dirs), :116–129 (whitelist), :131–140 (forbidden modules), :219–251 (derived send-fn sweep)

What we already have, and where the words come from

You asked to make it evident what is used to send information and where that information comes from. This is that inventory. Most of the machine is built; the pieces are not connected to each other.

One landmine to name now, because it will bite at the end, not the beginning. Every existing campaign was backfilled to the Colaberry Enterprise brand, but leads have no matching lead_tenant_contexts row. The brand gate resolves that to no_relationship and blocks the send. It does not block drafting and it will not affect any phase below — but the day you decide to actually send, this is what stops you, and it is a separate piece of work.

The plan

Five phases. Phase 1 alone answers your immediate ask and is the smallest of them, because it mostly connects things that already work. Each phase ships behind its own flag and nothing in any phase sends mail.

Phase 1 Generate the message every shadow decision would have sent ~2 days · 1 PR
What ships
A new stage, explorerGrowth/drafts/, that runs after the nightly Governor. For each shadow decision it follows campaign → sequence → step, calls generateMessage() with that step's brief plus the lessons the Governor resolved, runs the validator and the fact guard, and writes the result as a scheduled_emails row with status='agent_draft'. Then it sets decisions.scheduled_email_id — the column that has been waiting. Also writes selected_sequence_step, finally.
Why this shape
It reuses the draft mechanism that is already safe by construction rather than inventing one: the scheduler claims only status='pending', so an agent_draft row is structurally unsendable. No new columns on the decision table. The Governor is not touched, so its purity guard stays green on its existing whitelist.
You will see
For every Explorer, the actual subject and body that would have gone out last night — including the weekly digest, written from real lessons.
Verification
  • The purity test still passes unchanged for governor/ and content/.
  • A new sibling guard proves the drafts stage cannot import a mailer or write a pending row.
  • A test asserts a generated body naming an unresolved date is rejected and recorded, not stored as clean.
  • Idempotency: re-running the stage twice for one learner-day produces one draft, not two.
Cost & risk
Roughly 150 generations per night at current volume, so a hard per-run cap and a dry-run mode ship with it. Risk is spend, not sends. New flag EXPLORER_DRAFT_RENDER_ENABLED, default off.
Phase 2 Rebuild the dashboard around the message ~3 days · 1 PR
What ships
  • Shadow becomes the main tab. Each row shows the subject; opening it shows the full body, the lessons it cited, and any validator findings.
  • Why? gains the message. The Content section stops being a list of lesson titles and shows the draft, with the pointers beneath it.
  • Content tab is renamed Content supply and its subtitle says plainly that these are lesson cards projected from the curriculum. The two tables are reconciled to one query so the numbers agree, and the date filter the endpoint already accepts gets a control.
  • Four fields that are fetched and never displayed — ai_involved, ai_rationale, selected_sequence_step, scheduled_email_id — get surfaced.
  • The first write route. POST /content/refresh, which was specified and never built, becomes a “re-run now” button so the tab stops being a dead end.
Constraint
The page is currently tested to be read-only — “registers exactly fourteen GETs”, “exports no function whose name suggests a write”. Adding the first write is a deliberate amendment to those tests, called out in the PR rather than slipped past them.
Verification
Pinned copy and test-ids survive or change on purpose: suppressed-row, suppressed-count, suppressed-table, “Do not add the cells up”, “No content was needed for this action”. Note CI does not run frontend jest, so tsc --noEmit plus a production screenshot pass is the real gate.
Phase 3 Ground the copy in a knowledge base, and add the AI button ~1 week · 2 PRs
Where we start from
Three unrelated things in this repo are called a knowledge base. The one worth building on is Maya's: admissions_knowledge_entries, retrieved by keyword scoring and injected into the prompt under a “use these facts to answer accurately” header. It works. It has no brand column, no file upload, no chunker and no embeddings.
What ships
  • Ingestion — the genuinely new part. Attach a document or a URL, chunk it, store it with its source so every fact in a draft can be traced back to the file it came from.
  • Retrieval into the draft stage, reusing Maya's scoring rather than a second mechanism.
  • Brand voice finally wired in. brand_governance_rules already holds tone, prohibited claims, protected terms and allowed link domains, and no generator reads it. Phase 3 makes it a prompt input and a post-check.
  • The AI button on the admin page: regenerate this draft, with an editable brief, a diff against the previous version, and the retrieved sources listed.
Borrow, don't invent
composerDraftService already solves the hard part of grounded generation: it forbids invented specifics, requires [placeholder] instead, and runs a second reader that digit-checks every price, date and percentage against the brief. That is the pattern to copy, not re-derive.
Phase 4 Per brand — someone arriving on AI Flotation ~1 week · 2 PRs
Better news than expected
AI Flotation already exists as a seeded tenant and brand, with aiflotation.com, a tracking domain, a build@aiflotation.com sender on its own Mandrill subaccount, a lead-source slug, its own offer policy (Enterprise minus business training, plus six explicit denies) and its own journey program. Content resolution already takes a brand scope — {brand_id, allow_unscoped} is a required argument, not an afterthought.
What is actually missing
  • generateMessage() hard-codes “Colaberry Enterprise AI Division” into its persona and takes no brand. That is the main change.
  • Knowledge-base rows have no brand column, so Phase 3's schema must carry one from day one rather than bolt it on.
  • Sender profiles ship draft and must be activated per brand, with the preflight that refuses to send CPN mail over an AI Flotation envelope.
  • Explorer assets are projected only from the Colaberry curriculum, so a brand with no curriculum has no content to cite — that is a content problem, not a code one.
You will see
A brand selector on the page, and for a given learner: which brand they arrived on, which knowledge base answered, which sender would carry it, and the draft in that brand's voice.
Phase 5 Stage × audience — fix the data, not the taxonomy ~2 days · 1 PR + a decision
Verdict
The taxonomy does not need redesigning. The tagging rule does. Stage and audience are two independent axes, both derived from a card's week number but at different thresholds: week <= 1 sets the stage, week === 0 sets the audience. That second threshold is the whole problem.
The arithmetic
Of 585 published cards, only 23 are week 0, so only those carry the free-preview tag — while 152 of 153 learners are free tier. That is why your cross-tab shows 0 for learning and evergreen in the free column. A free-tier learner past activation has an empty candidate set by construction. Nothing is broken; the rule simply excludes almost everyone from almost everything.
What ships
A change to one function, audienceTagsForWeek, plus the guard from Finding 5 so an empty request list can never again produce a silent non-answer. Also worth fixing in the same pass: a tier lookup that swallows its error and returns full access, so a database hiccup currently widens the pool rather than narrowing it.
Blocked on you
Which lessons a non-paying Explorer may be shown in an email is a commercial decision, not an engineering one. See below.

The one decision I need

What may a free-tier Explorer be shown in an email?

Everything else in this plan I can decide and build. This one sets the paywall, so it is yours. It currently answers itself by accident: week 0 only, which means 23 cards out of 585.

A — Title and one-line summary for any lesson; the link paywalls

The digest can cite any of the 585 lessons and say what each is for. Clicking through still hits the upgrade wall. Maximum useful content, zero given away.

B — Open the first lesson of each module

A deliberate free tier that is more than a single week but less than the catalogue. Needs someone to mark which cards qualify — a content task, not a code one.

C — Leave it at week 0 and accept the consequence

The digest stays effectively undeliverable to 152 of 153 learners. Defensible only if the digest is not the point.

Recommendation: A. It makes the digest work immediately without giving away a single lesson, it needs no content tagging pass, and it matches what the digest's own brief already asks for — “say what each is FOR in one line … this should read as useful on its own even if they never click.” That sentence was written for a paywalled link.
