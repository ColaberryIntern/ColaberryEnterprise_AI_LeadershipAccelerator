# Session CC-20260901-r7m3 — The "94% AI failure rate" page was two abandoned browser tabs

**Date:** 2026-09-01
**Branch:** `fix/reliability-alert-counts-auth-failures` (cut from `origin/main` @ `33faad5`)
**Scope:** The reliability alerter paged at severity 8 claiming a 94% AI event failure rate.
It was false. Real model-call failure rate over the same 24 hours was 0%. Two defects, one
in the alerter and one in the frontend poller that fed it.

---

## The finding

`[reliability_error_rate] Reliability Alert: 94% AI event failure rate (last 15m)` fired at
13:45 UTC. Investigating against production:

| Scope, last 24h | Total | Failures | Rate |
|---|---|---|---|
| All `ai_events` rows (what the alert counted) | 2,523 | 1,657 | 66% |
| Real model calls (`model IS NOT NULL`) | 854 | **0** | **0%** |

Every failure row was `admin_auth_failed` or `participant_auth_failed`, with
`"message": "jwt expired"`. Two clients produced 1,393 of the 1,657 (84%):

| Client | Failures (24h) | Window |
|---|---|---|
| `2607:fb91:4b83:d2a4:...` | 837 | Aug 31 19:47 to ongoing |
| `47.186.92.19` | 556 | Aug 31 20:21 to Sep 1 11:10 |

nginx access logs identified the request exactly: `GET /api/admin/system/safe-mode`, one per
60 seconds, referer `https://enterprise.colaberry.ai/admin/change-password`. That is
`SafeModeBanner`. The declared poll interval is 30s; the observed 60s is Chrome throttling
timers in a background tab, which is how we know these were tabs left open and forgotten.

Ruled out: `JWT_SECRET` is set in the container env (128 chars) and survives restarts, so
this was not deploys invalidating sessions. The tokens genuinely aged out.

- [x] Scope the reliability error rate to real AI events
  - Date: 2026-09-01
  - Session: CC-20260901-r7m3
  - What changed: `backend/src/services/reliabilityAlertingService.ts` counted every row in
    `ai_events` with no filter on event type. But `ai_events` is also where auth telemetry is
    written, and those event types are logged ONLY on failure: they have no success counterpart,
    so they cannot form a rate. Including them makes the "AI failure rate" climb with traffic
    volume no matter how healthy the AI pipeline is. Added an exported
    `FAILURE_ONLY_EVENT_TYPES` constant (the five such types present in production:
    `admin_auth_failed`, `participant_auth_failed`, `sales_or_admin_auth_failed`,
    `delivery_client_auth_failed`, `delivery_client_link_no_membership`) and an
    `AND event_type NOT IN (:failureOnlyEventTypes)` clause bound via sequelize replacements.
    Alert copy now says "AI pipeline events" and states that auth telemetry is excluded.
  - Verification: `reliabilityAlertingService.test.ts` **11 passed** (5 pre-existing + 6 new).
    The pre-existing suite mocked `sequelize.query` wholesale and only ever asserted rate
    arithmetic on hand-fed totals, so it could not have caught this: nothing asserted on WHICH
    ROWS were counted. The new cases do exactly that, plus a locked list of the failure-only
    types so adding a sixth without listing it fails a test instead of paging Ali. Also ran the
    corrected SQL read-only against production: the live 15-minute window returns 11 events, 0
    failures, 0%, versus the 60%+ the old query reported on the same window.
  - Notes: `MIN_SAMPLE_SIZE = 20` was written to stop exactly this kind of noise-driven swing,
    but auth spam inflates the *denominator* past the guard rather than being excluded by it, so
    the guard actively helped the false alarm through. Worth remembering when tuning thresholds:
    a sample-size floor is not a substitute for measuring the right population.

- [x] Stop `SafeModeBanner` polling forever on an expired session
  - Date: 2026-09-01
  - Session: CC-20260901-r7m3
  - What changed: `frontend/src/components/admin/SafeModeBanner.tsx` polled with raw `fetch`,
    bypassing the shared axios client in `utils/api.ts` that already clears the token and
    redirects on 401. It sent `Bearer ${token}` even when `token` was `null`, ignored every
    non-OK response (`if (res.ok)` with no else), swallowed all errors in a bare
    `catch { /* silently ignore */ }`, and never stopped the interval. So an expired session
    produced one logged auth failure per minute, indefinitely, until the tab was closed. The
    silent catch is a direct violation of this repo's own Failure-First Design rule.
    Now: skip the request entirely when there is no token (a guaranteed 401); treat 401/403 as
    terminal by clearing the stale token, logging a structured `console.warn` with
    `error_class`, and stopping the interval permanently; bound genuinely transient network
    errors at 5 consecutive failures then stop, without clearing the token since the session may
    still be valid. Rendering and the Disable Safe Mode button are unchanged.
  - Verification: new `SafeModeBanner.smoke.test.tsx` **7 passed**, covering happy path
    (keeps polling while valid), failure path (401 and 403 both stop after exactly one request,
    where the old code issued one per interval forever), boundary (no token means no request at
    all; network errors stop at exactly 5), and idempotency of the terminal state. Frontend
    `tsc --noEmit` clean, 0 errors across the whole project.
  - Notes: The banner deliberately does NOT force a redirect to `/admin/login`. It is a passive
    component and the referer data shows these tabs sitting on `/admin/change-password`, which is
    a legitimate place to be; the shared axios client already owns the redirect when the user
    makes a real request. Standing down quietly is the correct behaviour for a background poller.

## Not done, and why

**Auth telemetry still lives in `ai_events`.** That table now carries two unrelated concerns:
AI pipeline observability and security telemetry. The alerter fix stops the bleeding but the
conflation is the root cause, and separating them is a schema change (Strategic per CLAUDE.md,
not autonomous). Recommend a dedicated `auth_events` table.

**Pre-existing test failures, untouched:** `requireBuildEntitlement.test.ts` (1) and
`mgmtRbac.test.ts` (2) fail on clean `main` at `33faad5`. Verified by stashing this session's
changes and re-running. Unrelated to this work, not fixed here, flagged for whoever owns them.
