# Session CC-20261107-k7w2 — the gov build grant that failed in silence

Ali, 2026-11-07: "I added Crash project which looks like it made it to his profile, but I
don't see the tab on the admin page."

The build was real. Obi's student project "Crash Records Information System Service
Agreement" (`a563218c`) was materialized on 2026-11-05 16:10 UTC under his enrollment with
22 tasks / 16 stories, on delivery project `7a818ed2`, both contract tracks present. What
was missing was one row: `delivery_project_members` has **zero** rows for that project.
`adminGovContractNavEntries` filters the admin left nav on `hasActiveIntern`, which reads
exactly those rows, so the contract was dropped from the nav. The same rows gate
`requireGovProjectAccess`, so Obi could not open the cockpit for his own project and could
not hand in story evidence either — the symptom Ali saw was the smaller half.

`materializeGovBuildProject` is supposed to write that row (`ensureAssigneeCanBuild`, commit
`4b06cbe2`, 2026-10-27, "fix cockpit 404"), and that call IS present in the image running
now. Why it did not write on 2026-11-05 cannot be established: the host holds only the
`main` tag, pulled 2026-11-07 12:14, and the container was recreated at 12:49, so neither
the Nov 5 image nor its logs survive. Two candidates remain — prod was on a pre-10-27
image, or the insert threw and was swallowed. The second was possible, which is the defect
fixed below; the first is unfalsifiable now.

- [x] Verify the builder grant instead of assuming it
  - Date: 2026-11-07
  - Session: CC-20261107-k7w2
  - What changed: `ensureAssigneeCanBuild` caught the membership create with a bare
    `catch {}`, on the stated assumption that the only possible failure was a concurrent
    insert. Any other failure — a constraint, a column the schema had not grown, a dropped
    connection — was therefore indistinguishable from success, and both callers carried on
    with an unauthorized builder. It now re-reads after a failed create and treats the
    failure as benign ONLY when the row is actually there, which is what the
    story-assignment create 40 lines below it has always done. A genuine failure logs
    `gov_build_membership_grant_failed` with an `error_class` and throws
    `AssignmentError('grant_failed')`. `materializeGovBuildProject` translates that to
    `GovMaterializeError('grant_failed')` so the route answers 503 (retryable) rather than
    a bare 500, and the assign route maps `grant_failed` to 503 rather than 400 because the
    failure is ours, not the caller's.
  - Verification: 4 new tests in `govBuildAssignment.test.ts` (a real race still proceeds
    silently; a genuine failure throws and assigns nothing; the log carries the
    `error_class`; an existing membership stays a silent no-op) + 1 in
    `govProjectMaterialization.test.ts` (a failed grant fails the materialize as
    `grant_failed` and never writes the task rows). 77 tests green across the 4 suites.
    Backend `tsc --noEmit`: the only error reported was a deliberately planted control
    error, which is how the clean run was proved to be checking these files at all.
  - Notes: throwing is safe because materialize is genuinely idempotent — step 3 reuses the
    project already on the `solution_build` track, so a retry after a failed grant cannot
    create a second project. The pre-existing race test was rewritten: it asserted the old
    swallow-everything behaviour by returning `null` from every membership read, which is
    not what a race looks like.

- [x] An untitled pursuit no longer renders as a raw uuid
  - Date: 2026-11-07
  - Session: CC-20261107-k7w2
  - What changed: a pursuit uploaded as a solicitation ZIP can reach approval with no title
    anywhere on its record — the decoupled provenance holds only the workspace uuid and
    there is no OP snapshot to fall back to. `gws:2ac2fdbc` is exactly that, so the funnel
    card title was null and the nav label degraded to
    `gws:2ac2fdbc-9675-4f61-9baa-1020493600e8`. `GovPipelineBuildProgress` now carries the
    materialized project's name and `projectGovPipelineCard` uses it as the last title
    fallback. That name is the title the operator typed at materialize time, which is the
    most human name the system holds for the pursuit.
  - Verification: 4 new tests in `govPipeline.test.ts` (the fallback applies; the pursuit's
    own title still wins; no build means no fallback; an empty name is not an empty title).
  - Notes: the project read is wrapped so an unreadable project row degrades the TITLE and
    never the progress rollup the board exists for. Read-side only — no data was written,
    so every already-built untitled pursuit is fixed by the deploy rather than by a
    backfill. `agency` stays null; the project name carries no agency and inventing one
    would be worse than a blank field.

- [x] Make duplicate solicitation uploads findable
  - Date: 2026-11-07
  - Session: CC-20261107-k7w2
  - What changed: new read-only `auditGovDuplicatePursuits.js` plus the pure grouper
    `lib/govPursuitDuplicates.js`. Every upload of a ZIP mints its own `gws:<uuid>`
    workspace and its own qualification thread, and nothing ever compares a new upload
    against the ones already there — not even by checksum, which is stored. Pursuits are
    grouped as the connected components over three signals: sha256, the leading
    solicitation number of the `<no> - pub - <title>.zip` convention, and the filename
    normalized of the browser's "(1)" suffix.
  - Verification: 13 tests on the pure grouper, fixtured on the real production rows.
    Not yet run against production.
  - Notes: three signals because one is not enough. The Crash pair is two downloads of one
    posting with the SAME byte size (2,850,432) and DIFFERENT sha256, so a checksum-only
    rule misses it; the Salt Lake City trio includes a hand-renamed `slc.zip`, which only
    the checksum catches. The audit nominates the member that looks like the real pursuit
    (built, else approved, else earliest) and retires nothing: `decision` has no
    'duplicate' value, so marking a copy `no_bid` would record that we passed on a
    solicitation we are actively building. That call belongs to a person.
  - Finding, unactioned: the first run found **4 solicitations entered 2-3 times, and two
    of them approved and BUILT twice** — `SNOC26271024` (Snow College Adult Learner) has
    two separate builds off one posting, and `SLCAIR26016` has one built copy plus an
