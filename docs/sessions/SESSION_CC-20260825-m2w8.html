**Made the Export CSV button export the view on screen instead of the whole table, and bounded it.**

2026-08-25
What changedKes reported that Export CSV "exports all data regardless of the applied filters". **Both halves of the path were broken independently**, which is why the failure looked total rather than partial, and why fixing either side alone would have changed nothing. The page called `/api/admin/leads/export` with **no query parameters at all** (`api.get(url, { responseType: 'blob' })`, no `params` key), while the table alongside it sent nine. The controller took `_req`, the request object deliberately unused, and called `generateLeadCsv()`, which **accepted no arguments** and ran a `Lead.findAll` with no `where`. Extracted **`buildLeadWhere(params)`** out of `listLeads` so the table and the export derive their filter from one function; they cannot drift again because there is only one definition left. The export controller now parses the same `leadFilterSchema` and runs the same `resolveWebsiteFilter` as the list handler, so a sales rep's saved and locked website scope applies to their download too rather than being bypassed. On the page, **`buildFilterParams()`** is now the single source both `fetchLeads` and `handleExport` read. Also declared `temperature` on the params interface, which was being read through `(params as any)` and would have silently vanished the first time a typed object was spread into that call.
Verification**81 tests / 5 suites green**, 12 of them new in `leadExportFilters.test.ts`. The new tests pin the filter translation (status, score range, date range with `dateTo` covering the whole day, website group expansion, unknown-key-matches-nothing, temperature, search), **list and export producing the same `where` for the same input** which is the regression itself, the empty result, the bound, and truncation in both directions. `leadSourceGroups`, `leadViewPreference`, `externalLeadIngestService` and `v1LeadController.consent` all still pass. Root cause was confirmed against production before any code was written: `accelerator_prod.leads` holds 24,244 rows, so every click was a full-table dump. PR: https://github.com/ColaberryIntern/ColaberryEnterprise_AI_LeadershipAccelerator/pull/1828

**Diagnosed why 490 leads are invisible to Cora Voice and admissions, and stopped short of the fix on purpose.**

2026-08-25
What changed**Nothing in code, deliberately.** Kes reported that leads from the open house and the training site never appear in the "Colaberry School of Data Analytics" GHL account, so neither Cora Voice nor the admissions team can reach them. Root caused to **two independent blockers**, and the second is the reason no code shipped. **(1) The sync is never invoked.** `enrollmentService.createExplorerEnrollment` writes the open-house lead with a raw `Lead.findOrCreate` and never calls `syncNewLeadToGhl`; `externalLeadIngestService.ingestExternalLead` does the same for the training site; and `leadService.createLead`, the shared helper the generic form ingest funnels through, has no GHL call either. So **inbound web forms are unsynced as an entire class**, not just these two sources. Every existing GHL call site is admin-add, calendar booking, Apollo, CSV import, Maya, the Synthflow webhook, campaigns, automation or the scheduler. **(2) The single stored key points at the wrong sub-account.** `ghlService` uses one global `ghl_api_key` and never reads a location id. Calling `GET /v1/locations/` with the live key returns exactly one location: `JFWwp8q7l6T12NWTIOKG`, **"Agent Cory AI"** - not School of Data Analytics. The `ghl_location_id` that `settingsService` writes is dead config, read by nothing. Escalation written to `tmp/escalation.json` (not committed; `/tmp` is scratch).
VerificationProduction evidence rather than inference. `accelerator_prod.leads` grouped by source: **`open_house` = 490 rows, 0 with a `ghl_contact_id`**, newest one today. `training.colaberry.com` across its three spellings = 3 rows, 0 synced. The control group proves GHL itself is healthy and the failure is specific to these paths: `apollo` **1,981 / 2,102** synced, `ccpp_alumni` 679/689, `ai-pilot-cold` 99/99, `strategy_call` 4/4. `system_settings` reads `ghl_enabled = true`, `ghl_api_key` set, `test_mode_enabled = false`, which rules out the disabled-flag and test-mode-redirect hypotheses outright.
Notes**Not fixed on purpose, and that is the substance of this entry.** Wiring the sync is a two-line change. But with blocker (2) unresolved it would create roughly 490 contacts in the wrong CRM sub-account, and those contacts feed Cora Voice outbound dialing. That is an irreversible, outward-facing write to a live CRM and a live dialer against a population nobody has reviewed, which CLAUDE.md puts on the escalate side of the line rather than the proceed side. Three decisions are needed before code: which sub-account is genuinely the intended destination; whether to build **per-source account routing** (recommended) rather than repointing the single key, since repointing would silently move Apollo, campaigns, Synthflow and calendar bookings into the new account alongside the open-house leads; and whether the 490 already-captured leads get backfilled or the fix is new-leads-only, with a dry-run count first either way. Worth adding `ghl_sync_status` / `ghl_synced_at` to `Lead` when this is built, because today the only sync signal is `ghl_contact_id` being non-null and a failure is otherwise invisible. **Incidental security finding:** GHL's `GET /v1/locations/` returns each location's **full `apiKey` in the response body**, so any script that logs that response leaks a live credential.
