# CC-20261029-f4w2: C125, "Open on your phone" works while viewing as a member, read-only on the phone too

Basecamp: https://app.basecamp.com/3945211/buckets/7463955/todos/10509950234

- [ ] C125: While viewing as a member (read-only), Open on your phone hands the same READ-ONLY view to the admin's phone
  - Date: 2026-11-14
  - Session: CC-20261029-f4w2
  - What changed:
    - **The cause:** `requireParticipant` blocks every non-GET request for a read-only View-as token. Minting the QR code is `POST /api/portal/handoff`, so the panel showed "Could not create a code right now."
    - **`middlewares/participantAuth.ts`:** a one-entry allow-list, `READ_ONLY_ALLOWED_WRITES = {'POST /api/portal/handoff'}`. The match is exact on method and path, with any query string or trailing slash ignored. Every other write stays blocked.
    - **`controllers/portalHandoffController.ts`:** a read-only caller's code is marked with `impersonated_by` (the token's claim, or `admin` if it has none).
    - **`services/portalHandoffService.ts`:**
      - A new nullable column, `portal_handoff_tokens.impersonated_by`, added at boot with `ADD COLUMN IF NOT EXISTS`.
      - `createHandoff` takes `{ impersonatedBy }`, and its result reports `readOnly`.
      - `exchangeHandoff` signs a marked code with `signReadOnlyParticipantJwt`, so the phone gets the same read-only session, with the same "Viewing as ... READ ONLY" banner (`ReadOnlyBanner` reads the JWT claim). It never gets a writable one.
    - **Frontend:** `OpenOnPhone.tsx` says "Opens this same read-only view on your phone". `HandoffCreate` gains an optional `readOnly`.
  - Verification:
    - jest, 21 of 21 (`participantAuth`, `portalHandoffService` and the new `portalHandoffController` test). They cover:
      - a read-only POST to the handoff path passes, including with a query string or trailing slash;
      - 7 look-alike paths and methods stay 403;
      - a normal token is unaffected;
      - a marked code yields `read_only` + `impersonated_by`, and an unmarked code yields neither;
      - the controller marks read-only callers, including tokens without the claim.
    - Mutation check: 3 of 3 deliberate breaks fail a test (allow-list removed, prefix match instead of exact, exchange ignoring the mark).
    - Backend and frontend `tsc --noEmit` are clean, each with a planted control error reported. `checkTestTypecheck` shows only the known local-only `enrichVisitorGeo` (maxmind) noise.
  - Notes:
    - **Security:** without the mark, allowing the POST would have let a read-only viewer scan into a writable session as the member. The mark is what makes the exception safe.
    - **Failure mode:** if the boot `ALTER` failed, the INSERT and RETURNING would fail and no code could be minted at all. That is the same symptom as before the change, never a writable leak. It is checked after deploy.
    - **Side effect to tell Ali:** scanning replaces whatever portal session the phone had with the read-only view. Sign out on the phone, or open a sign-in link, to return to his own.
