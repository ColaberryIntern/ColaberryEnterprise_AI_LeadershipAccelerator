## What the template turned out to be

Seven screens, one per question a person can act on: Fleet, Controls, Failures, Authority,
Safety, Release and data, Direction. Unpacked mechanically rather than read off a screenshot —
every colour, size, spacing value and the four status tones are measured, and the full
reference is committed at `docs/design/PLATFORM_OPERATIONS_SCREENS.md`.

It carries its own palette, not `tokens.css`. That turned out to matter: every
foreground/background pair in the template passes WCAG 2.1 AA with the worst at 5.72:1, while
the admin token `--color-primary: #FB2832` on white is 3.85:1 and fails.

  - Notes (assumptions and deviations, each forced by something measured):
    1. **Live fleet has three states, not the template's two.** `ai_agent_activity_logs` only
       receives a row when a runner calls `instrumentCronJob`, so a registry row with no logs
       is ambiguous: dead, or working and silent about it. 23 of 142 enabled agents had zero
       rows when that was last measured. Those read amber "No report ever"; red is kept for a
       job we know reports and that did not fire. Calling them dead would put two dozen false
       outages on the card every day until nobody read it.
    2. **A coverage line above the cards**, stating the registry count, how many report, the
       timer count and how many are unwatched. Not in the template. It is the basis for the
       whole tab, and without it "everything fired" reads as a much stronger claim than it is.
    3. **`error_class` shows `unclassified`** where only a message and a stack exist. The
       schema has no error class outside `dead_letter_jobs`. An unclassified count is a gap in
       the record and prints as one.
    4. **Actions whose endpoints are a later phase render disabled**, with the phase named in
       the title. `Run check now` and `Try again` are real; the rest are not yet.
    5. **Schedules are shown in words** (`schedule_label`) with the raw expression on `title`.
       A six-field cron, whose first field is seconds, falls through to raw rather than being
       misread as minutes — a bug my own test caught.
    6. **Card basis 440 not 480, and a fourth width for tables.** Inside `AdminLayout` the
       sidebar leaves 936px at 1280, so the template's 480 stacked all four cards into a long
       scroll, and a six-column table at 440 dropped the error-class column off the edge.
    7. Fleet ships **reads only**. The buttons that stop, enable and reschedule things are the
       Controls tab, which is its own phase.

## One defect found and fixed, which the other six tabs will hit

At 390px this page scrolled sideways to 586px while every other admin page stayed at 390.
`AdminLayout`'s content column is a flex item without `min-width: 0`, so it refuses to shrink
below its content's min-content width — and `overflow-x: auto` on a table wrapper does **not**
stop the table reporting that width upward. Bisected in the browser to the "Last run" card and
fixed with `width: 0; min-width: 100%` on the scroll wrapper.

Two earlier versions of the timer scanner are worth recording for the same reason. A regex
scan reported two timers that did not exist, both inside this scanner's own doc comments. A
comment-blanking pass fixed those and introduced a third failure, where a quote character
inside a regex literal put the string tracker into a false state and hid a real line. A
scanner that miscounts its own source cannot be trusted to count the server's, so it parses
with the TypeScript compiler now and both cases are tests.
