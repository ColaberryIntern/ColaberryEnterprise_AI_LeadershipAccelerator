### One card is not always one initiative

This is the decision that shaped the module. Six cards are a single initiative — five
hypotheses and membership — and clicking one asks "what has happened towards this?", which a
timeline answers.

The seventh, `gov_bid_pursuit`, is an **aggregate**. It reports a count of bids carrying the
pursuit flag: twelve on 2026-11-03, including a row named "Snow College Adult Learner - T8
test", one RFP duplicated under two project ids, and three rows with no delivery project.
Clicking it cannot produce one timeline, because there is no single thing it is the history
of.

So a drill-down has two shapes. `single` is a timeline. `roster` is a list of the
initiatives the card aggregates, each with its own evidence count and the flags its own
record shows, each clickable through to its own `single` view at
`?bid=<delivery_project_id>`. Collapsing them would have meant inventing a merged timeline
across twelve unrelated bids, or quietly picking one — and either would have looked fine on
screen.

**The duplicate flag is computed across the roster, not per row.** A per-row check sees each
copy of a duplicated RFP as unique and flags neither. Counting titles first flags both.

### The timeline reads only the spine

It would have been quicker to query Basecamp, email and the proposal tables directly here
and merge the results. That is the design R3 exists to replace: several bespoke queries that
each decide for themselves what counts as an event, with no way to unlink a wrong one and no
record of who linked it. Everything reads `evidence_links`, and anything that wants to
appear earns its place by being linked.

### Why the backfill is in this ticket rather than R5

Between R3 and R4 sat a problem: nothing wrote a link, so every timeline rendered empty and
the page could only be verified against fixtures. A surface checked only against fixtures is
one nobody has seen work.

`gov_proposal_documents` is the one evidence source needing no ingestion — already in this
database, already attached to a `delivery_project_id` by foreign key, and the only signal
that distinguishes a real pursuit from a flagged row. So it is both the cheapest first
producer and the most useful. R5 remains the scheduled Basecamp ingestion and R8 email; this
is a backfill of something already present, not a second sync.

It is safe on every boot because it goes through `linkEvidence`, so R3's guarantees apply
unchanged: the unique index makes a repeat run a no-op, and a document Ali unlinked stays
unlinked. **Refusals are counted and reported, not swallowed** — "nothing to do" and "I was
correctly refused fourteen times" are different facts and only one is boring.

`observed_at` is `COALESCE(drafted_at, created_at)`. The document list is *materialized*, so
`created_at` is when somebody pressed a button, not when the document was written.
`drafted_at` is the event a timeline is asking about. Same discipline as R3's schema, for the
same reason: the R2 diagnosis found a conversion rate counting backwards from exactly this
conflation.

Confidence is **1**, because this is a foreign key rather than an inference — the document
*is* attached to that project by the database. Anything lower would imply a judgment was
made. And `source_url` is left null rather than constructed from a guessed admin route,
because a dead link in front of a reader is worse than no link.

### An empty timeline explains itself

The spine is new and only one producer writes to it, so most timelines are genuinely empty.
That is exactly the point where a page starts lying — by rendering nothing and letting the
reader supply the reason. So three cases are kept apart in words: the table is missing, the
table is present and holds nothing for this initiative, or here is what happened.

### A note on what deploying would reveal

R1, R3 and R4 are all read-only admin surfaces, but the backfill writes. The first boot after
a deploy is when `evidence_links` gets its first rows — on 2026-11-03's data, that would be
**9 proposal documents across 3 projects**, so three bids would show a real timeline and the
other nine would correctly show none. That is the first moment any of this can be checked
against production rather than against fixtures.
