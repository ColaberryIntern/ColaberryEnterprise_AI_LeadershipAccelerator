# CC-20261109-k2w7 — R4 follow-up: nothing ever closed a conversation

**Date:** 2026-11-11
**Ticket:** R4. Maya remembers a person, not a browser —
https://app.basecamp.com/3945211/buckets/7463955/todos/10455593471

## What this change does

Adds a cron that closes chat conversations idle for 30 minutes, so that closing actually
happens at all.

## Why, measured rather than assumed

R4's code shipped in PR #3782 and is in the running production image. That established that
the code shipped, not that the feature works. It does not work, and the reason is upstream of
everything #3782 changed.

`closeConversation()` is the only caller of `saveConversationToMemory()`, which is the only
writer of `admissions_memory.conversation_count`. `closeConversation()` is reachable only
through `POST /api/chat/close`. **Nothing calls that route.** A search of `frontend/` for
`chat/close` returns zero files, while four frontend files reference `/api/chat` — so the
search was aimed correctly and the zero is a real absence, not a mis-aimed query.

Production, measured 2026-11-11:

| Measure | Value |
|---|---|
| chat_conversations | 145, **every one `status='active'`** |
| with `ended_at` set | **0** |
| with a summary | **0** |
| date range | 2026-03-16 to 2026-11-10 |
| conversations with a visitor message | 13 |
| conversations with 3+ visitor messages | 5 |
| `chat_engagement` behavioral signals | **0** |
| admissions_memory rows | 116, **all with `conversation_count = 0`** |
| admissions_memory rows with a `lead_id` | **2** of 116 |

Five conversations were substantive enough that `closeConversation()` would have emitted a
`chat_engagement` signal. There are zero. That is the proof that the function has never run in
production, not an inference from the route search.

So for eight months every downstream effect of closing — the summary, the memory write, the
behavioral signal, the CRM tag, the conversation outcome — has never fired once.

## Why a sweeper and not an unload beacon

The widget restores its conversation id from `sessionStorage` across page loads, and
`sendMessage()` throws `'Conversation is closed'` for any conversation whose status is not
`active`. Closing on `pagehide` would close the conversation during an ordinary navigation and
make the visitor's next message fail on the next page — trading an invisible defect for a
visible one. A sweeper closes only what is genuinely finished.

## Where it lives, and why not in schedulerService.ts

`schedulerService.ts` is 3,871 lines, far past this repo's 500-line ceiling, and CLAUDE.md
says the next change to an oversize file splits before it adds. `services/scheduling/` already
holds focused cron modules (`growthJourneyCrons.ts`, `adSpendCrons.ts`), so the registration
follows that pattern and `startScheduler()` gains two lines.

## Not shipped paused

Every other effect of closing is already written and already guarded. What was missing was
anything to trigger them, so shipping this disabled would leave the defect exactly where it is.
There is no `AiAgent` registry row for `ChatCloseIdleConversations`, and `instrumentCronJob`
runs a job with no row untracked, so it runs on deploy. Seeding a row later adds tracking and
an Admin > Agents pause without a redeploy.

**This job sends nothing to a lead.** Closing writes a summary, a memory row, a behavioral
signal and a CRM tag. The one outbound-looking call, `addMayaInteractionTag`, tags the CRM
record; it does not message the person.
