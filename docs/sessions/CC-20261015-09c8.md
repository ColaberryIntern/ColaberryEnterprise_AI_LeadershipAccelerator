# CC-20261015-09c8 — One student's error report, and the two production faults underneath it

Two student reports, four findings, and each one was found by refusing to stop at the
first plausible cause. The order matters, because none of it was the thing reported:

1. **"Add a story" failed for every student** — a partial unique index added three days
   earlier collided with the order of two statements inside `publishPlan`.
2. **The fix sat merged but undeployed for fourteen hours**, and reached production as a
   passenger on an unrelated team's deploy rather than by intent.
3. **A global kill switch, left on after that morning's deploy, was eating all outbound
   email** — including the alerts that would have reported it.
4. **`auditMiddleware` was writing plaintext staff passwords into `audit_logs`**, 639 rows
   of them, and was still doing so when it was found.

Findings 3 and 4 both came out of one WhatsApp message that said only "I am not getting
any enterprise access link in my mail".

## What the first one asked for, and what landed

Swati reported "Internal server error" from the project interior's **Add a story** form and
had done the triage herself: the project id, the repo, the plan version, the timestamps, and
two suspicions of her own (her wording, and the hand-edited `plan.json`). Both suspicions
were wrong, and the real cause was neither hers nor new to her — the same failure was waiting
for **every** student.

What landed:

- `backend/src/services/sbp/planStore.ts` — inside `publishPlan`'s existing locked
  transaction, the incumbent is **superseded first** and the target version promoted second.
  The order is load-bearing and it is the opposite of what it was.
- `backend/src/services/sbp/addStoryService.ts` — `MAX_STORIES_PER_BUILD` 30 to 50, at the
  DRI's instruction.
- Four tests across `__tests__/planStore.test.ts` and `__tests__/addStoryService.test.ts`
  that pin both, with the publish statements asserted by **content as well as position**.

Swati's own two stories were recovered by hand from her stranded drafts and are live
independently of this code change.

**Now deployed.** It reached production at **6:43 AM CDT on 2026-10-15** as a passenger on
another workstream's deploy of `fb236969e` (PR #3104), not on one of its own. Verified in
the running container rather than inferred from the merge: the compiled `publishPlan`
supersedes at line 204 and promotes at 207, and `MAX_STORIES_PER_BUILD` reads 50.

- [x] **`auditMiddleware` was writing plaintext passwords into `audit_logs`, and still was**
  - Date: 2026-10-15
  - Session: CC-20261015-09c8
  - What changed: `backend/src/middlewares/auditRedaction.ts` (NEW) and one line plus an import in `backend/src/middlewares/auditMiddleware.ts`. The middleware copied the whole of `req.body` into `audit_logs.new_values` with no redaction at all, and the admin login route is a POST whose body is `{email, password}`. Measured in production, not inferred: **639 rows holding plaintext passwords across 13 staff accounts**, earliest 2026-03-08, most recent written at 9:02 AM CDT the morning this was found. The same path had also captured `currentPassword` AND `newPassword` from the password-change flow, plus `ghl_api_key`, `sms_api_key`, `synthflow_api_key` and `smtp_pass`. `redactSecrets` now runs at capture rather than at write, because the body is snapshotted before the handler runs and that snapshot is what gets persisted.
  - Verification: `npx jest --config jest.ci.config.ts src/middlewares/__tests__/auditRedaction.test.ts` reports **45 passed, 45 total**, and the whole middleware directory reports **132 passed across 11 suites**, so nothing else regressed. Two mutations each drive the suite RED and each targets a different failure: removing the `redactSecrets` call from the middleware fails **1** test — the wiring test, which is the only kind that would have caught the original defect, since a pure-function test stays green while the function goes uncalled — and widening `apikey` to a bare `key` substring fails **11**, which is the over-redaction boundary. Both files were restored byte-identically afterwards, sha256 `743ab5ea8c926737` and `141f562fbe7b42c7` matching their pre-mutation values exactly.
  - Notes: THE HARD PART IS PRECISION, NOT DETECTION. A blunt `/key|token|pass/` would have redacted field names that carry real audit meaning, every one of which was observed in the same production table: `keywords`, `content_key`, `step_key`, `stepKey`, `surfaceKey`, `metricKeys`, `idempotency_key`, the three `*_variable_keys`, and `ai_max_tokens` — a model parameter that contains the word "token". Over-redaction is not a safe default when it silently destroys the value of thousands of legitimate rows while looking responsible, so `apikey` is matched as a substring while `key` and `token` are matched only as exact names, and both lists are pinned by tests built from the real field names. THIS ONLY STOPS THE BLEEDING. The 639 existing rows still hold the passwords, and the 13 accounts plus the GHL, SMS, Synthflow and SMTP credentials are still unrotated — a stored secret is a compromised secret under CLAUDE.md's own rule. Both are the DRI's call and neither has been done. MY OWN MISTAKE DURING THIS WORK, recorded because it nearly shipped: I used `git checkout --` to undo a mutation, which reverted the tracked file to HEAD and so deleted my actual fix, while silently failing on the new untracked file and leaving ITS mutation in place. Caught by comparing sha256 against the values captured before the first mutation, which is the only reason it was caught at all. A restore step needs its own verification exactly as much as the change does.
