**Fixed a backfill row-count bug found by production evidence, not by tests**

2026-08-12
What changed`backend/src/scripts/backfillPageEventLeadId.ts` — extracted row counts via a new exported `extractRowCount()` that reads `metadata.rowCount` (the real Postgres shape) as well as bare-number and `affectedRows` shapes, and hardened the loop so a zero-row batch with candidates still outstanding reports `stoppedBecause:'stalled'` with a `BackfillStalled` warning instead of exiting as `complete`. Test mock corrected to Postgres's actual `[results, pgResult]` return shape.
Verification19/19 jest green (was 11). **Proven the tests catch the bug**: reverting to the original extraction fails 3 of them (`stops when a batch updates zero rows`, `respects --max-batches`, `reports the true updated count for a multi-batch run`); restoring passes all 19. Backend tsc = baseline (1 pre-existing).
NotesThe original code did `const [, affected] = result; typeof affected === 'number' ? affected : 0`. For Postgres, `sequelize.query()` resolves to `[results, pgResultObject]`, so that always evaluated to 0. **Not merely cosmetic** — the batch loop terminates on `rows === 0`, so it stopped after ONE batch while still reporting `outcome:'complete'`. The first production run had 65 attributable rows, under a single 5000-row batch, so it completed correctly by luck and the DB confirmed 65/65 attributed with 0 remaining. With more than `batchSize` rows it would have silently left the remainder unattributed and claimed success. **The 11 original tests all passed because the mock resolved `[[], rows]` — a shape this dialect never returns — so the suite asserted my assumption about the driver rather than the driver's behaviour.** Found only by running against the real database and noticing that `candidates:65 -> updated:0 -> remaining:0` cannot all be true.
