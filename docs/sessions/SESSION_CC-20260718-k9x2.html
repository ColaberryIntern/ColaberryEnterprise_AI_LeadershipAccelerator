06

Read progress now truly carries drawer→workspace (the prior host-persistence fix had a race that wiped it)

2026-07-19
What changed`useDeepDiveHost` persisted the guide's progress on every tick by OVERWRITING localStorage with the posted ids. On workspace load the guide's `seen` is empty, so its FIRST render posts `ids:[]` BEFORE the `ready`→`restore` round-trip — which overwrote the stored `[s1,s2,s3]` with `[]`, so restore then sent back nothing and the guide started over. Fix: persistence is now MONOTONIC — the host UNIONs the posted ids with what's already stored (`new Set(prev.seenIds.concat(ids))`) and OR-s `copied`, so an empty initial render can never erase saved progress. Restore then finds the real ids and re-checks the sections.
VerificationDEPLOYED via PR #413 → prod at HEAD d21a7faf; nginx CRA build passed (tsc gate), new bundle main.65df4491.js served with the `dd:progress` persistence key; site 200. Logic verified by trace (empty-first-render no longer clobbers stored ids; restore re-checks). Frontend-only (useDeepDiveHost.ts) — no backend/base64/reseed; guides unchanged. Browser retest of drawer→workspace carry-over is Ali's to confirm.
Notes[[reference_deep_dive_field_guide_platform]] Key lesson: a host that mirrors an iframe's self-reported progress must treat progress as accumulate-only, or the iframe's fresh-load empty state clobbers the restore it is about to receive.
