**Caught my own merged fix failing against the real database, corrected it, applied it to prod, and added a post-condition check so this class of silent schema failure cannot recur**

2026-08-09
What changedImmediately after PR #1281 merged, I ran its DDL against production to unblock persistence without a mid-afternoon backend restart, and it **failed**: `ERROR: cannot drop index student_tasks_unique_req_key because constraint student_tasks_unique_req_key on table student_tasks requires it`. Sequelize's `unique: true` in a model's `indexes` array creates a **CONSTRAINT**, not a bare index, and a constraint-backed index cannot be dropped with `DROP INDEX`. The merged statement was `DROP INDEX IF EXISTS student_tasks_unique_req_key` — and because `ensureStudentTaskMergeSchema()` wraps every statement in a `try/catch` that only `console.warn`s, it would have failed **silently at every boot**, logged one line as "stmt skipped", and left the constraint in place. The fix I shipped would not have fixed anything. My unit tests did not catch it because they mock the models entirely — they exercise `importProject`'s control flow, never the DDL. Corrected in follow-up: `ALTER TABLE student_tasks DROP CONSTRAINT IF EXISTS student_tasks_unique_req_key` first (which removes the backing index too), then the bare `DROP INDEX IF EXISTS` for any DB where it exists without a constraint; both `IF EXISTS`, so the pair is idempotent. Then addressed the root enabler rather than just the instance: added a **post-condition check** after the statement loop that queries `pg_constraint` and `pg_indexes` for the name and, if either still reports it, emits a structured `level:error` line with `error_class: SchemaInvariantViolation`, the impact ("student build imports will abort on the first duplicate requirement_key") and the exact remedial SQL. "It didn't throw" is not evidence a best-effort statement took effect — the check asserts the outcome.
VerificationApplied to production directly and confirmed by re-query: `student_tasks_unique_req_key` is now absent from BOTH `pg_indexes` and `pg_constraint` on `student_tasks`; the correct partial unique `student_tasks_unique_story` remains; all 3 existing task rows intact (no data touched — dropping a uniqueness constraint only widens what is permitted). **Production persistence is unblocked as of this entry.** Backend `tsc --noEmit` (TypeScript 5.7.3): 1 error, the known `@anthropic-ai/sdk` worktree artifact; zero in `server.ts`.
NotesThe honest lesson is that PR #1281's verification was weaker than it read. It claimed a regression test that "reproduces the original failure" — it reproduces the *application-level* failure (a simulated unique violation aborting the import) but never the *schema* change, so a wrong DDL passed every gate: 4 green CI checks, 27 green tests, two clean typechecks. Mocked-model tests cannot verify DDL, and nothing in this repo currently runs migrations against a real Postgres in CI. Worth considering a migration smoke test as follow-up work; not attempted here. Prod DB and the code are now consistent, and the post-check makes a future divergence loud on the next boot rather than invisible.
