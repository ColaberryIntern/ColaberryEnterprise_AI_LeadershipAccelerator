Fix an idempotency defect in authorTimelineCard caught by running the Week 1 seeders twice against production

What changedafter deploying the Week 1 content, the standing "run it twice" check showed two of three cards correctly reporting `already-current` with no write, but the **Claude Code 101** card reporting `applied` on every run. Root cause: `authorTimelineCard.same()` compared values with a plain `JSON.stringify`, and Postgres **`jsonb` does not preserve object key order**. That card is the only one of the three that writes a nested object (`meta.course`), so its authored literal `{name,url,sections}` came back from the DB reordered, compared unequal to itself, and rewrote the card — churning `content_at` — on every single run. Fixed by canonicalising key order recursively before comparing (`canon()`), while deliberately preserving array order, since question order on a card is meaningful. This is an idempotency violation, which this repo classifies as a production defect rather than a nit, so it is fixed rather than noted.
