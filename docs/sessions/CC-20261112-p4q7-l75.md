### Why it was needed

L7.5 asks for generation time and cost. Measured on production, read only: `ai_events` holds
340,173 rows and **not one** can price a decomposition. The two figures the ticket is judged on
did not exist anywhere in the system for either path. The prior pilot report
(`docs/project-lifecycle/pilot-results.md`) names the same two gaps as the ones it could not close.

### The regression this caused, and the fix

The first attempt used a static import. `openaiInstrumented` imports `aiEventService`, which calls
`Model.init` at module load, so a static import dragged a live Sequelize model into the graph of
everything reaching these files. That broke `factoryDecomposeRun.test.ts`, whose own header states
it mocks no database because it needs none.

Fixed by requiring the instrument lazily inside the client factory, which is existing practice in
`advisorySyncQueueService`, `agentAuthorizationService` and `agentPermissionService`. Costs nothing,
because the client is memoised on first real call. The guard test now pins the laziness too, since
it is load-bearing rather than stylistic.

### What this does NOT claim

recoverable, because it was never recorded.

Authorized by Ali on 2026-11-13. Three runs of the SBP generation journey (intake questions,

6 of 6 calls succeeded. Zero rows carry a null cost.

### The instrument was checked against something it does not control

Wall clock was measured independently in the pilot script, because the recorded `duration_ms` is
the figure this change exists to produce and so cannot also be the thing that proves itself.
Across six calls, wall clock totalled 86,183 ms against 86,047 ms recorded: a gap of **136 ms,
0.16%**, which is the function-call overhead outside the model call. The recorded numbers are
trustworthy.

### A real property of the table, found by the first run looking like a failure

Run 1's decompose stage succeeded and its `ai_events` row was **absent** from a SELECT taken
moments later. Two explanations fitted equally: a late write, or a runtime bypass of the
instrument. A second read minutes later, with a control confirming the table was still
receiving rows generally, settled it as the first. **The telemetry write is not awaited**, so
any cost report that queries immediately after a generation under-reports it. Re-running the
pilot would have cost money and distinguished nothing.

### What this does and does not settle

It settles the existing path's cost and time. It does not produce a rival figure for the
lifecycle arm, because `composeBlueprint` makes no model call: governance adds **no model cost**,
and its overhead is validation work that has never run on a real project. The measured figure is
also a **floor**, not an average: the synthetic brief is ~900 characters against a 200,000
character cap, and prompt tokens here are mostly the fixed prompt template.

### The lifecycle never moved, and that is structural

Stage is `discovery` with `updated_at` identical to `created_at`: written once by the
`afterCreate` hook and never touched again. The pipeline derives its work hops from the
non-approve permissions and its single call advances `blueprint_approved` to `planning`, which
`discovery` cannot reach. **L8.3 therefore demonstrates what L7.5 inferred.** L8.4, which
activates lifecycle enforcement for all new-project paths, is already closed.

### The two real hazards, and why neither fired

1. **Repo commit.** Publishing commits docs to the project repo when one is connected, with no
   dry-run switch, and `GITHUB_TOKEN` is set in production. A project created seconds earlier has
   no connection, so the run counted `github_connections` for it and was written to throw rather
   than publish if the count was not zero. `build_intake` settled at `awaiting_repo`, the branch
   that writes nothing.
2. **Failure-path email.** One enabled `alert_subscriptions` row matches a severity-3
   `student_builds` warning and reaches internal staff. It fires only on the generation failure
   branch; the generation succeeded, and `alerts` and `alert_events` are unchanged.

### Two things the run got wrong first

**The first attempt ran the generation and threw it away.** `startBuild` does not await the
generation; it queues it (`void getProvisionQueue().run(...)`) and returns in 57 ms. The script
then closed its pool and exited, killing the generation inside its own process and losing four
telemetry rows to "getConnection was called after the connection manager was closed". That is a
property of driving the orchestrator from a script rather than a defect in it, but it stranded
the build at `generating`, and `STALE_GENERATION_SECONDS` is 3600. The next pass cleared the
stranded row scoped to the fixture, then **polled** until the status left `generating`.

**A premise carried in was wrong.** Lifecycle rows are not created by three entry points; they are
created by two model hooks fired from eight creation sites. And no enrollment with a null cohort
can run this journey at all, because `buildAndActivateProject` requires a program reachable
through the cohort. All 100 synthetic enrollments already on production carry `cohort_id` null, so
the fixture convention existed in `enrollments` but had never been taken through project creation.

### The fixture, and why it is still there

A synthetic cohort (status `completed`, so it cannot appear as joinable), one enrollment at
`e2e-l83-<timestamp>@colaberry-test.local`, and one project. The identity was checked against
`isSyntheticContactEmail` in both directions before anything was written.

Deleting the project cascades to the lifecycle state, readiness rows, tasks and task lists, but
`build_plans`, `build_intake`, `github_connections` and several others are `ON DELETE NO ACTION`
and would block it until removed first. **No teardown script exists in the repo.** The rows are
labelled and harmless where they are, so removing them is left as a decision rather than taken
unilaterally.
