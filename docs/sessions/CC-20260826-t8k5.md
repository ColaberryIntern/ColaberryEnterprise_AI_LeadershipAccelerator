### Per-source GHL sub-account routing, and wiring the two ingest paths that never synced (2026-08-26)

- [x] **Made the destination GHL sub-account a per-source decision, wired the open-house and training-site paths to actually sync, and made an unprovisioned account withhold the push rather than fall back to the wrong CRM.**
  - Date: 2026-08-26
  - Session: CC-20260826-t8k5
  - What changed: Two independent causes, both addressed. **(1) The sync was never invoked.** `enrollmentService.createExplorerEnrollment` wrote the open-house lead with a raw `Lead.findOrCreate` and never called `syncNewLeadToGhl`; `externalLeadIngestService.ingestExternalLead` did the same for training.colaberry.com. Both now push, fire-and-forget, matching every other call site in the codebase. **(2) One global key, wrong account.** `ghlFetch` read a single `ghl_api_key`, and GHL v1 keys are scoped to one sub-account, so the codebase could only ever write to **Agent Cory AI**. New `backend/src/services/leads/ghlAccountRouting.ts` resolves a sub-account per lead source: it maps a **group key** (via `groupForSource`, so all three spellings of training.colaberry.com fold onto one route) to an account name, and reads that account's credential from `ghl_api_key_<account>`. `ghlFetch` and the six helpers `syncLeadToGhl` drives gained an **optional trailing `apiKey`**, so all nine pre-existing call sites (Apollo, campaigns, Synthflow, calendar, CSV import, Maya, automation, scheduler, admin-add) are untouched and stay on the global key.
  - Verification: **14 new tests green** in `ghlAccountRouting.test.ts`, plus `externalLeadIngestService`, `enrollmentService`, `v1LeadController.consent` and `leadSourceGroups` still passing (69 passed across the affected set). The tests deliberately target the withholding rule rather than the happy path, including an assertion that the default key **does not appear anywhere** in a withheld result, so a future "simplification" that reintroduces the fallback fails loudly. Also covered: corrupt routes map falls back to default rather than withholding every lead in the system, whitespace-only key counts as unprovisioned, and a null source does not throw.
  - Notes: **The safety property is the whole design.** A source routed to an account whose key is not on file resolves to `status: 'unconfigured'` and the caller refuses to sync - deliberately *not* a fallback to the default account. Falling back is what makes this dangerous: the default is Agent Cory AI, and those contacts feed Cora Voice outbound dialing. Withholding leaves the leads exactly where they already are, visible in `/admin/leads` and absent from GHL, which is the status quo rather than a new failure. `ghl_account_routes` ships **seeded** with `open_house` and `training_colaberry` pointing at `school_of_data_analytics`, whose key setting ships **empty on purpose**. So merging and deploying this changes nothing observable until someone sets `ghl_api_key_school_of_data_analytics`; that one setting is the switch that turns the whole thing on. Every withheld push writes a `GHL Sync Withheld` activity row naming the account and reason, so "nothing happened" is legible rather than silent. **A defect my own change introduced and then fixed:** adding a top-level `import { syncNewLeadToGhl } from './ghlService'` to both ingest services broke `externalLeadIngestService.test.ts` at load, because it pulls `settingsService -> SystemSetting -> config/database` and constructs Sequelize at module load with no `DATABASE_URL`. Switched both to the lazy-import convention `ghlService` already uses for `aiEventService`, which exists for exactly this reason. **Deliberately deferred:** `ghl_sync_status` / `ghl_synced_at` columns on `Lead`. Sync state is still inferred from `ghl_contact_id` being non-null, so a *failed* push is only visible in activity rows and logs. That needs a migration and a prod run, and keeping this PR migration-free makes it safe to deploy on its own. **Not done and not mine to decide:** the 490 already-captured open-house leads are untouched. Ali chose new-leads-only; a backfill remains a separate, explicitly-approved bulk write with a dry-run count first. **Pre-existing, proven not caused by this change:** `explorerEnrollmentWelcome.test.ts` fails 4 tests at `Enrollment.findAll`.
