    **(1) Provenance read a wire format the server does not send.** `readProvenance`
    in `caseStudySnapshotView.ts` looked for `source` / `sourceType` / `sourceRef` /
    `note` / `generatedBy`. `backend/src/types/caseStudyProvenance.ts` defines
    `CaseStudyProvenanceEntry` as `{ tier, origin, recordedAt }` and none of those keys
    exist on it. Every entry fell through to the `'unknown'` default, so the TRUTH tab's
    Provenance panel — the panel whose whole job is "where did each value come from?" —
    rendered **fourteen rows reading `unknown` / —** on the live pilot record while the
    payload behind them carried the tier, the actor, the note, the repo and the commit
    sha for each. Now reads the real entry shape, describes each `origin` kind in words,
    and keeps the legacy keys as a fallback because pre-entry-type snapshots are still in
    the table. **Internal row ids stay internal** — `metricId`, `evidenceId`,
    `projectId`, `portfolioArtifactId` are described, never printed, following the rule
    `metricAt` already states for `verification.evidenceId`; a commit sha is the opposite
    case and is shown, because it is what makes an extraction checkable.
    **Why nothing caught it:** `caseStudyAdminFixtures.ts` encoded the *old* shape, so the
    suite went on proving the reader could parse a format nothing produces. The fixture
    now carries the production shape, with one deliberately legacy-shaped entry so the
    back-compat branch is exercised rather than assumed.

    **(2) Every write reported its outcome to a tab the operator was not on.**
    `useCaseStudyDesk` funnels all writes through one `act()` setting one `actionNote`
    and one `actionError`; both rendered inside `CaseStudyPublishPanel`, which reaches
    the screen on PUBLISH only. Saving consent on TRUTH produced **no visible response of
    any kind** — success or failure. Same for sync, attach, detach, role change and every
    §34 override. New `CaseStudyActionBand.tsx` renders both above the tab strip on every
    tab, and the two blocks are removed from the publish panel so no id is duplicated.
    This is the argument `CaseStudyGateBand` already made for refusals, applied to the
    outcome of a write; the band returns `null` when there is nothing to say rather than
    holding a row of empty frame on every tab forever.

    **(3) The PREVIEW tab pushed the page 6,305px wide.** Measured on the live page:
    `documentElement.scrollWidth` 1440 on every other tab, **7745** the moment the
    projection rendered, against a 1440 viewport. The JSON `<pre>` grew to 3,686px inside
    a `.col-lg-6` whose `min-width` is `auto`. `overflow: 'auto'` was already set and did
    not prevent it — a box has to be stopped from WIDENING before it can be asked to
    scroll. Added `whiteSpace: 'pre-wrap', overflowWrap: 'anywhere'` to both blocks.

    **(4) An override offered on a record that cannot take one.** `CaseStudyNarrativePanel`
    warns "This candidate has no snapshot yet, so there is nothing to review" and then
    rendered three fully enabled Apply-override buttons underneath it. Pressing one POSTs
    against nothing, 404s, and shows the operator `this override not found.` — on a
    different tab. `CaseStudyOverrideField` gained a `disabledReason` that inerts the
    inputs and the button and states the reason on screen; the narrative panel passes it
    when `hasSnapshot` is false. The panel had already worked out the right answer and
    simply had not acted on it.

    **(5) Two elements, one test id.** The Repository input carries
    `data-testid="cs-analyze-repo"` as a literal and `CASE_STUDY_STUDIO_CONTROLS`
    gave the Analyze **button** the same id. Every lookup resolves the first match — the
    input — so the §18 guard for "analyze repository" was asserting against a text box and
    would have stayed green with the button deleted. The disjointness guard could not see
    it: that check compares two registries, and the collision was with a component literal.
    Registry entry renamed to `cs-analyze-run`. `domHarness` gained `queryAll`, without
    which no suite can see a duplicate id at all.

    **(6) Duplicate metric keys in the chart builder — half fixed, half left open and said so.**
    `metricKeys` is `heroMetrics ++ measurement.metrics`, and the pilot's
    `verified_competencies` is in both, so two checkboxes rendered with one `id` and one
    test id and the second label toggled the first input. De-duplicated. **The deeper half
    is NOT fixed and is recorded rather than papered over:** those keys come from the
    SNAPSHOT while `resolveChart` resolves against `case_study_metrics`, which has zero
    rows for this record — so every offered key resolves to nothing and the panel says so
    ("Renders: nothing"). Closing that needs a metric-listing endpoint the admin API does
    not have; that is a new contract, not a bug fix, and it is not in this brief.
