## Failure-first notes

1. **What happens if this fails?** The account cannot sign in or cannot see the screen. No existing
   access changes either way, because nothing existing was modified — this is one INSERT.
2. **Will it retry?** No. Re-running the script is safe: it refuses when an account for the address
   already exists, and the check is repeated inside the transaction under lock.
3. **Recovery path:** set `IsDeleted = 1` on UserID 48138, which is how CCPP retires an account.
   Nothing else references it.
4. **Handled vs not handled.** Handled: a duplicate account, a username collision (the house
   pattern is three letters plus five random, collision-checked in a loop), a partial insert (the
   transaction rolls back unless exactly one row results). **Not** handled: whether the account can
   actually reach the grading screen, which cannot be determined from the database and needs
   Balamurali or Rob to try it.

### Finding 1: app.colaberry.com does not authenticate against CCPP

It redirects to **Auth0** (`login.refactored.ai`, tenant `refactored-ai.auth0.com`, client
`5PHcR2RRIyINhRqO83mM5OHn4wP1GBDl`). `portal.`, `my.` and `cap.colaberry.com` all redirect to the
same app.

This explains the thing that looked inexplicable yesterday: Rob has no credential row anywhere in
CCPP, and neither do 12,281 other accounts, because **the CCPP row is a profile and the credential
lives in Auth0**. It also means the row created yesterday **does not by itself let anyone log in**.
There are no `AUTH0_*` variables in the backend container and no Auth0 client in this repo, so this
environment cannot create an identity there or sign in as one.

### Finding 2: the profile was probably going to create itself

Of the twenty most recently created accounts that have ever logged in, **twenty logged in the same
day they were created**. Usernames are machine-generated (`robnlamz`, `omomvree`, `baljnugc`), and
every one carries `CreatedByUserID = 684`. That is just-in-time provisioning on first login, not
administrator pre-creation.

And **2,198 of 2,336 accounts created since 2025 (94%) carry a `PreUserID`. The hand-inserted row
does not.** Rob's is 54017. So the row is in the 6% minority shape, missing the link the signup
funnel sets.

### What this means for the actual request

Creating the CCPP row was not wrong, but it was **not the lever**. The lever is an Auth0 identity
for `balamurali@colaberry.com`, which cannot be created from here. Two risks worth stating plainly:

1. If the app's provisioning path matches on email it will adopt the existing row, and he gets a
   profile with a null `PreUserID`.
2. If it matches on something else, first login creates a **second** row for the same person.

**Recommendation:** retire row #48138 (`IsDeleted = 1`) and let the app provision normally on his
first Auth0 login. It is one reversible UPDATE and it puts him on the same path as the other 2,198.
Not done unilaterally - Ali directed the creation, so he should direct the retirement.
