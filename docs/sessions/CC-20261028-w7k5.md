## AF10.6 — let an intern name their own agent

Ticket: https://app.basecamp.com/3945211/buckets/7463955/todos/10424325597

- [x] AF10.6: store the name an intern gives their own agent, with a uniqueness check
  - Date: 2026-10-28
  - Session: CC-20261028-w7k5
  - What changed: new `ai_agents.config.display_name`, written through a guarded PATCH route and
    rendered on My Domain where a raw agent UUID used to be. Four new backend files (schema,
    service, controller, router), the provisioned reader now selects the name, and the My Domain
    page gained an inline naming control.
  - Verification: **63 new tests, all passing** — 52 backend (14 schema, 16 service, 13
    controller, 5 route access, 4 reader exposure) and 11 frontend. No regression: 629 existing
    backend `agentDomain` tests across 24 suites pass, and the two existing My Domain / All
    Domains page suites pass alongside the new one (40 frontend tests across the three). Backend typecheck with **TypeScript 5.9.3**
    (borrowed; this worktree ships only 4.9.5) returns **exactly the two pre-existing
    `@anthropic-ai/sdk` TS2307 errors and nothing else**, byte-identical to the baseline measured
    before any edit. Frontend typecheck, same compiler: **10 errors, none in any file this change
    touches** — all ten are in `TimelineBuilderPanel.tsx` and `TimelineEditorTab.tsx` and cascade
    from `@dnd-kit/*`, which is declared in `frontend/package.json` and not installed in this
    worktree. `scripts/lint-route-auth.js` passes across all 139 admin route files.
  - Notes: three things worth knowing.

    **The uniqueness check must not filter on `enabled`.** A production probe found `Maya` with
    `enabled: false`, and Maya is the name the admissions builder chose. A `WHERE enabled = true`
    would allow exactly the one name this ticket exists to refuse, and would pass any test whose
    fixtures only held enabled rows. Two tests guard it, one behavioural and one that reads the
    generated SQL. The plan's first draft missed this; the independent plan audit caught it.

    **The check covers four name sources, not one.** `agent_name`, `config.display_name`,
    `config.agent_name` (16 rows already carry it) and `admin_users.display_name` — the last
    because that is the name the platform actually renders (`workforce/orgChartService.ts:306`
    prefers it over `agent_name`), so omitting it would let two agents display the same name while
    the check reported clean. Self is excluded, which is what makes Ruth's "Dara" legal while
    Kalkidan's "Maya" is refused.

    **No `as any` was needed.** The house config-merge idiom at
    `reeseBehaviourSwitchService.ts:88` carries one; the typed form compiles here, so this service
    has no bare `any` and needs no justification comment.

    Deliberately out of scope: the platform-wide display-name precedence. Making this name win in
    the org chart and every actor-name render is a cross-module change this ticket does not
    authorize. The resulting inconsistency (My Domain says the chosen name, the org chart still
    says "Product Experience Agent") is recorded in the handoff as a known limitation, and is the
    obvious follow-up ticket.
