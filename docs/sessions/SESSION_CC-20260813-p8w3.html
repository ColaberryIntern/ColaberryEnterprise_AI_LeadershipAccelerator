**A gate-clean build plan now reaches the student by itself — closing the hole that left five students on the browser fallback**

2026-08-13
What changed**The defect.** `runGeneration` ended at `savePlanDraft` + `status='drafted'` and stopped. Publishing is what materialises STORY-000, the cohort due dates and the 3-4k-character Claude Code prompts into `student_tasks`, and **nothing called it**: `publishBuild` had exactly one caller, `POST /api/portal/sbp/builds/:projectId/publish`, which no screen in the product ever hits (`ProjectsPage` imports only `resolveBackendProjectId`, `startBuild`, `pollBuild`). So every gate-clean plan came to rest in `build_plans.status='draft'`, `student_tasks` stayed empty, `enrollments.active_project_id` was never set, and all five students on 2026-08-12/13 spent the evening looking at the browser's local ten-task template. **The fix, in four parts.** (1) `runGeneration` now ends by calling a new `autoPublish()` in the same queued job when `isPublishable(gate.violations)` — it looks up the workspace repo, publishes, and logs `sbp_autopublished`. It passes the just-written draft's `plan_sha256` as `expectedSha`, so a concurrent generation cannot slip a different plan into the promotion. It **cannot throw**: a publish failure is caught, logged as `sbp_autopublish_failed` with an `error_class` and a `recovery` hint, and leaves the build at `drafted` — deliberately NOT `failed`, because `failed` means "regenerate" and telling a student to regenerate a perfectly good plan burns minutes of model time. Kill switch `SBP_AUTO_PUBLISH=off`, defaulting **on**: a second default-OFF flag in front of this would have shipped the fix and left production in exactly the broken state it exists to end. (2) A blocking-violation plan is unchanged — it still fails closed at `gate_failed` — but the poll endpoint now splits `gate.blocking` from `gate.advisory` server-side. The client was taking the first three of the *whole* `violations` array as "why your build was refused", and that array is mostly advisory quality warnings, so a student blocked on an uncovered must-have was being told about a stylistically redundant story. (3) **The student can now tell which build they are looking at.** New `origin: 'local' | 'pipeline'` on `StudentProject`, stamped at birth by `createProjectFromAnswers` and by `backendTreeToProject`, rendered as a chip on the build card and inside the build. The banner explaining a degraded result now renders on **every** Projects view — it previously lived only in the wizard branch, which `handleCreate` leaves on its first line, so it was unmounted before a student could read a word of it. Two of the five never reached the server at all and were told nothing whatsoever. (4) The optimistic placeholder now **claims** its backend project (`pipelineProjectId`, written to localStorage so it survives a reload mid-generation) and `reconcileProjects` supersedes it in place when the real plan lands — guarded on completed work, so a placeholder the student actually ticked something off is kept alongside rather than discarded. Also fixed: `handleCreate`'s post-publish `syncProjectsWithBackend()` was a **no-op**, latched off by the once-per-session guard already tripped on mount, so even a successfully published plan did not appear until a manual reload; new pull-only `refreshProjectsFromBackend()` bypasses the latch. New `services/sbp/workspaceRepo.ts` extracts the repo lookup so the route and the auto path cannot drift.
Verification`npx jest src/services/sbp` — **23 suites / 395 tests green**, including two new files. `sbpOrchestrator.autoPublish.test.ts` holds the three required invariants: a gate-clean plan reaches the student with no human in the loop (`materializePlanAsTasks` called with the real plan, final status `published`/`awaiting_repo`), a `must_uncovered` plan does NOT (no promote, no materialize, no commit, rests at `gate_failed` with the violation naming REQ-002), and a publish failure leaves the build `drafted` and never `failed`. `materializeTasks.idempotency.test.ts` proves "publishing twice is a no-op" against an in-memory fake of the two models rather than call-count assertions — 3 runs create one Command Center, no duplicate lists or tasks, a `complete` task stays complete and is counted in `preservedComplete`, an `in_progress` task is not reset, and `due_baseline_on` survives a cohort date slip while `due_on` moves. Backend `src/services/sbp` + `src/routes` together: **28 suites / 447 tests green** (two route suites flaked once under parallel load and passed in isolation and on re-run — a documented pattern in this repo, unrelated to these files). Frontend: `projectHydrate|sbpApi` **4 suites / 70 tests green**, including the supersede path, its idempotency, and the do-not-discard-completed-work guard. `tsc --noEmit` (5.x, explicit binary) **clean on frontend**; backend clean apart from two pre-existing `@anthropic-ai/sdk` module-resolution errors in files this change does not touch, caused by the junctioned `node_modules` lacking that package.
Notes**Not deployed and no email sent, per the overnight brief.** **The `[review]` step this removes never existed in the product** — the chain comment said `persist(draft) → [review] → publish` but no UI offered either half, so nothing depended on it; the publish route survives for manual retry and for the `SBP_AUTO_PUBLISH=off` case. **Deliberately left alone, and worth someone's attention:** `publishBuild` passes `null` for the existing manifest to `writeDocsToRepo` with a standing `TODO(step 6)`, so `changedFiles` compares against an empty baseline and **every** publish commits all ~16-19 documents. That was tolerable when publish was a rare manual act; auto-publish makes it fire on every regeneration. It is a repo-churn problem, not a correctness one — lists, tasks and completion are all genuinely idempotent — and fixing it means fetching and threading the manifest content plus its own tests, so it is logged here rather than smuggled into this change. **Also stale as of this PR:** the local-only `build-student-project` skill (untracked, not on `origin/main`, so unreachable from this worktree) opens with "PUBLISH IS NOT AUTOMATIC" and lists "publish itself", "the localStorage build is never deleted" and "the degradation banner is unreachable after a create" under *prevented only by someone remembering*. All three are now prevented in code and that runbook will mislead the next operator until it is updated; `.claude/skills/` is DRI-owned so it was not edited here. **One behaviour to be aware of with the kill switch on:** `drafted` is terminal for the poller, so `SBP_AUTO_PUBLISH=off` shows the student the "we could not open it up for you" wording, which is worded for the failure case rather than for a deliberate review mode. That is acceptable for an emergency escape hatch and would need copy if review ever becomes a real product mode.
