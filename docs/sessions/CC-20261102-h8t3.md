## Root cause

AF3.6's backfill wrote `<domain>.STORY-000` into `student_tasks` with six acceptance criteria — the
row the portal renders. The repo side renders from the project's **published BuildPlan**, and
`renderDocs.ts:184` asked `plan.stories.some(s => s.id === COMMAND_CENTER_STORY_ID)` against the
**bare** `'STORY-000'`. No domain plan contains a STORY-000 of either shape, so the test always
missed, the fallback fired, and the Student Build Pipeline's generic **five-line** Command Center
was written into every domain builder's repo: a correct, well-formed file about the wrong
assignment.

Measured read-only in production 1 Nov 2026: **10 of 10** domains have the task row, **0 of 10**
have it in the plan, and **10 of 10 DO have a published plan** — so this was never
`refreshRepoDocuments` bailing at `no_plan`. An earlier investigation concluded it was, and that was
wrong; querying production is what corrected it.

A second sync could not repair it: `repoWriter` is content-addressed, so the stable-and-wrong bytes
produced `sbp_repo_write_noop` and Quincy correctly concluded nothing was happening.

## Finding that came out of the build, and is Ali's to decide

**Criterion 4 of the Command Center story cannot be demonstrated by any builder.** It asks for "a
capability above `autonomy:R2` with no granted tools". Measured across all ten capability records:
**0 of 443 capabilities have a `starting_autonomy` above `autonomy:R2` — every one starts at
`autonomy:R0`.** `effectiveAuthority` applies the `no_tool_grants` cap only when the approved level
is above R2, and a ceiling can only lower it, so the cap cannot fire for anything in the programme.

Found because the first version of that test asserted the opposite and failed. The snapshot now
reports the rule, that its scope is zero, and why — a panel saying "this rule is in force and
currently constrains no capability, because none is approved above R2" is honest, where an empty one
is not. Criterion 3 **is** demonstrable: the ceilings are varied (platform: 14 at R5, 13 at R4, 2 at
R6, 1 at R7).

## The contract rule caught a consumer I had not updated

CI's **Test-file typecheck** failed on `agentFactoryCards.test.ts` — a file this branch never
touched. Correct failure: widening `ProvisionedDomainRow` with six required fields broke a `row()`
fixture that builds a complete literal, which is exactly what CLAUDE.md's "breaking contract change
= failing build" rule is for. Fixed by updating the fixture in the same diff rather than by making
the new fields optional, because all six are always present in the SELECT and optional fields would
let the next consumer forget them.

The six default to `null` there, matching the fixture's `agent_id: null`: null means "no employee
linked", which stays distinct from `0` meaning "an employee holding nothing". Checked that the two
non-test consumers (`agentFactoryCards.ts`, `agentFactoryList.ts`) only read fields, so adding to
the row is safe for them.
