## Root cause

AF3.6's backfill wrote `<domain>.STORY-000` into `student_tasks` with six acceptance criteria — the
row the portal renders. The repo side renders from the project's **published BuildPlan**, and
`renderDocs.ts:184` asked `plan.stories.some(s => s.id === COMMAND_CENTER_STORY_ID)` against the
**bare** `'STORY-000'`. No domain plan contains a STORY-000 of either shape, so the test always
missed, the fallback fired, and the Student Build Pipeline's generic **five-line** Command Center
was written into every domain builder's repo: a correct, well-formed file about the wrong
assignment.

Measured read-only in production 1 Nov 2026: **10 of 10** domains have the task row, **0 of 10**
have it in the plan, and **10 of 10 DO have a published plan** — so this was never
`refreshRepoDocuments` bailing at `no_plan`. An earlier investigation concluded it was, and that was
wrong; querying production is what corrected it.

A second sync could not repair it: `repoWriter` is content-addressed, so the stable-and-wrong bytes
produced `sbp_repo_write_noop` and Quincy correctly concluded nothing was happening.

## Who found it, and how

Quincy's email of 1 November, written from reading the code with no access to the logs: "the
verifier adds plain STORY-000 (storyPoints.ts:46-48). It then finds no task with that id and logs
sbp_verification_task_missing. If so, no commit of mine can verify it, however the id is written."

Production agreed the same day: `sbp_verification_task_missing storyId="STORY-000"` on the platform
project at 15:00:05Z and on marketing at 16:08:35Z, 6 occurrences in 7 days. Measured across the ten
domain boards: bare `STORY-000` rows = **0**, namespaced = **10**. So the verifier was asked to
judge a story that cannot exist, and the first task of the first release on every domain board could
be built, pushed and rendered but never verified — and therefore never paid and never counted toward
a milestone.

## This is AF3.9's contract gap, one consumer further on

AF3.9 fixed `renderDocs.ts` and `sbpRoutes.ts`, both of which compared against the bare constant.
`COMMAND_CENTER_STORY_ID` has twelve consumers. `storyPoints.ts` was the one missed, and it feeds
three surfaces at once — verification, milestones and story XP — so one fix closes all three.

## The half the first draft of this fix got wrong

There are **two** constants named `COMMAND_CENTER_ACCEPTANCE`: the SBP's with five generic lines,
and the agent-domain one with six. Resolving only the id would have had the verifier judge
`platform.STORY-000` against the SBP's five — grading a builder against criteria they were never
shown, which is worse than the missing task it replaced because it fails quietly. My own test
("gives the namespaced story the SAME six criteria") caught it. The id and its criteria now come
from one call and travel together, which is the rule `commandCenterTaskColumns.ts` already carries
for the board row after splitting them left 19 of 20 live builds three versions behind.

## Fails soft, never silent

Any failure in the domain lookup returns the bare spec, which is exactly today's behaviour — a
verifier run must not die because a lookup did. It logs `command_center_spec_lookup_failed` with an
`error_class`, and a test asserts the log fires, because a swallowed catch is a production defect.

## Three mocks had to be widened, and that is the contract working

`milestoneService.test.ts`, `prepPoints.test.ts` and `storyPoints.test.ts` all reached story pricing
without mocking the new lookup. Left alone they would have reached for a database and passed by
falling back — green for the wrong reason. Each now pins "not an agent-domain project" explicitly.

  so the new autonomy story ids reach no repo. This is Quincy's second question, confirmed.

## Two defects, one symptom, both invisible from an owner login

Four builders reported the same 403 on 2 Nov. The text, "You do not have access to this section.",
comes from one place: `mgmtSectionGate`. Two unrelated causes produced it.

**The `agents` section was granted to nobody.** `/api/admin/agent-factory` is gated
`requireSection('agents')`, and across all 802 `community_members` rows no scoped role held
`agents` and no account carried it as an extra. `mgmtRoles.ts` shows this was deliberate -- "NO
scoped role is granted either here" -- with the per-domain grants meant to land alongside the
routes. The route landed; the grant did not. Fixed by writing `agents` into
`mgmt_extra_sections` for the seven builder accounts (owner-authorized, production, per account
rather than per role because five of those roles have a second member). Not a code change, so it
is recorded here for provenance only.

**Seven routes across five prefixes were mounted without being classified.** The gate runs before
a route's own guard, and for a scoped role the final test is
`if (section && allowed.includes(section)) return next();` -- so an unclassified path fails on
`section === null` and reaches the 403 even when the route says `requireSection('dashboard')` and
the caller holds `dashboard`. That was exactly the agent naming save.

The reason neither was ever noticed: a `mgmt_role === 'admin'` caller takes the `isBroad` branch,
which denies only paths that ARE mapped. An unmapped path passes for admin and is refused for
every scoped role, and `owner`/`admin` derive their sections from `ALL_SECTIONS`. Both defects are
therefore invisible from precisely the accounts most likely to be used to check.

## The test found two defects the hand-rolled sweep missed

A throwaway script found five unclassified routes by regex over each router call's text. The
committed test walks back from each `requireSection` to its router call instead, and immediately
found two more -- `/api/admin/agent-domains-builders` and `/api/admin/agent-domains-authorization`
-- whose multi-line route calls the regex had silently skipped. The sweep was wrong in the safe
direction only by luck, which is the argument for the invariant living in a test rather than in a
one-off script.

The floor assertion (`toBeGreaterThanOrEqual(90)`, against 108 found) exists because a parser that
stops matching would otherwise make every other assertion in the file vacuously true.

## Why `/api/admin/agents` classifies a whole subtree

A static prefix cannot express `:agentId/display-name`, so that row covers every
`/api/admin/agents` route. It is narrow in effect rather than broad: each of the other ~20 routes
under it carries its own `requireAdmin` or `requireAgentManagerOrAdmin()`, and the naming service
re-checks ownership itself (`AgentNotYoursError` -> 403). A test asserts that no route under the
prefix is unguarded, so the claim cannot quietly stop being true.

## Found while fixing, not fixed here

- 362 of 1,225 `/api/admin` route paths are unclassified. Most are `requireAdmin`, where the gate's
  refusal of a scoped role is correct, so this is not a defect list -- but it is the reason the
  test is scoped to the `requireSection` contradiction rather than to blanket coverage.
- The grant only reaches a builder on their NEXT sign-in: `mgmtBridgeService` stamps
  `mgmt_extra_sections` into the JWT at mint time and the gate reads the JWT, never the table.
- Quincy also reports `/admin/change-requests` showing "Could not load change requests".
  `AdminChangeRequestsPage` calls both the `-mine` list and the admin-only queue. Which call fails
  for him is unconfirmed, so it stays a hypothesis.

## Criterion 4 could not be satisfied by anybody, and it was the live blocker

`effectiveAuthority` applies the `no_tool_grants` cap only when the APPROVED level is above
`autonomy:R2`, a ceiling can only ever lower that level, and all 443 capability records across all
ten domains start at `autonomy:R0`. So "Given a capability above `autonomy:R2` with no granted
tools" was unreachable by construction.

This was not a new discovery. `agentDomainCommandCenterDoc.test.ts` already carried the sentence
"Criterion 4 of the Command Center story describes a state no builder can currently produce; that
is a finding on AF3.9, not something to paper over here." It was found, written down, and parked.
What made it urgent is that AF3.10 unblocked verification on 2 Nov, and the verifier promptly
graded platform at **5 of 6 with criterion 4 as the single outstanding item** — so the parked
finding became the last thing between ten builders and their first verified story.

`agentDomainSnapshot.ts` had already been built to cope, computing `authority_rule.rule`,
`approved_above_r2` and `binds_nothing` with a note saying to state the zero case in words. The
implementation was right and the criterion never caught up. The rewording asks for exactly those
three fields, and a new drift guard asserts the criterion names nothing the snapshot does not
produce, because that drift is what cost ten people a fortnight.

## No supersession alias, and that was the judgement call

Criteria match by normalised text (`criterionIdentity.ts`), and that file is explicit that editing
`COMMAND_CENTER_ACCEPTANCE` in place turns every existing tick into a rejected claim, drops
`verified` stories back to `submitted`, and lets `mergeProgressFile` write `false` over real work.
The remedy it provides is a permanent `SUPERSEDED_CRITERIA` entry.

One was deliberately NOT added. An alias carries a tick on the old sentence forward onto the new
one, and measured across all ten boards on 2 Nov the old sentence carries **zero ticks and zero
rejected claims** — nine of ten Command Centers had never been graded at all, and platform had
criterion 4 outstanding. There is nothing to carry, and aliasing an undemonstrable criterion would
credit work nobody could have done, which is what criterion 6 exists to forbid. The table's own
doctrine agrees: a reworded criterion with no entry keeps failing, and that is what holds the
gating model together.

## R0's title now answers the question a 96-item list provokes

624 of 1,477 tasks sit on one rung. The rung keeps Ali's own wording from `AUTONOMY_MEANINGS` and
gains one appended clause; the cluster key is untouched, because `release_key` is the stored value
stories hang on while a title is parsed by nothing. The test asserts the clause lands on R0 and on
no other rung — a mutation putting it on R1 fails three assertions, including the one that checks

## Still needed, and not in this change

Both halves are constants, and the ten boards hold their own copies: `student_task_lists.title`
carries the old R0 label and `student_tasks.acceptance` carries the old criterion 4. Grading reads
the constant, so verification changes the moment this deploys, but the text a builder READS comes

Kes asked for "an email notification just like the one we get when we are tagged in Basecamp"
because he only learns of an intern's message once he is already logged in. A notification already
existed, so this is a latency fix rather than a new capability: `dmService.ts:137` writes an in-app
`new_message` row, and `communityDigestService.ts:31` turns it into a count at 08:00 UTC the next
morning. For the manager seven builders are blocked on, tomorrow-as-a-number is not a notification.

`community/replyNotificationService.ts` is the precedent and exists for the same reason one event
earlier — "a reply created a CommunityNotification row and stopped there, so it surfaced ONLY in
the in-app bell." This is its sibling with two deliberate differences.

**The email carries no message content.** A DM is private and email is not; it gets forwarded,
synced and indexed. Kes asked to know *that* someone messaged him, which a content-free notice
answers in full. It also protects the dedup: the idempotency key is
`hash(recipient, subject, business_event_id)`, so a subject carrying a preview would mint a new key
per message and the quiet period would suppress nothing.

**The quiet period is carried by the key, not a scheduler.** `email_send_ledger` already holds a
unique index on `(lower(recipient), subject, business_event_id)`, so putting the window into the
event id — `dm-notify-<room>-<recipient>-<bucket>` — makes the database enforce "at most one per
thread per window". No cron, no new table. Honest limit, recorded in the file: the window is a
fixed wall-clock bucket, so two messages either side of a boundary can produce two emails a minute
apart. A true rolling window means reading the last send before claiming, which is the
check-then-act race `idempotentSend.ts` was built to avoid; a deterministic bucket that is
occasionally generous beats a race.

Two faults of mine worth recording. The first version imported `config/env` as a default export,
which it does not have — and the test passed anyway **because my own mock invented that default
export**, so a mock standing in for a module hid the compile error it was covering. Caught only by
`tsc`. The second: my first reading of the ticket named
`agentManagerConversationService` as the write path. That is a manager talking to an **AI agent**,
roles `'manager' | 'agent'`, and it is admin-authed — which Kes cannot even reach, having no
`admin_users` row. The real path is the portal DM. Building on the first reading would have shipped

# AF11.2 — the duplicate-tool check, with its reason shown

- Date: 2026-11-04
- Session: CC-20261102-h8t3
- What changed: before Ali reads a tool request, the platform has already compared it against
  every registered tool and stored the closest matches, each naming the field that matched.
- Verification: 39 tests in `toolDuplicateCheck.test.ts`, 21 in the schema suite, 17 in the
  catalog-loader suite, 14 new in the service suite; 291 tests across 14 affected suites green
  under `jest.ci.config.ts`, the real CI gate.
- Notes: four of the ticket's own stated facts turned out to be wrong when measured. Each one is
  below, because the corrections are the useful part.

## The ticket says 47 tools. There are 57

`buildToolCatalog()` measured in production on 4 November returns **57**. The dictionary
`TOOL_CAPABILITIES` holds 53, another three appear only in some agent's `tools_granted`, and
**`read_attachments` is in neither** — it reaches the catalog through the `GRANTS` constant in
`agents/tools/agentToolRegistry.ts`.

That last one is worth more than its count. A request duplicating an undocumented tool is exactly
the case this feature exists for, and a catalog missing it would have passed every test while
missing the real thing. A test now asserts all three sources and the total of 57, so the number
gets re-measured rather than aging quietly the way 47 did.

## The ticket says request and catalog share four fields. They share three

`ToolCapability` is `{ reads, produces }` and nothing else. There is no `purpose` on a catalog
tool, which `toolRequestContract.ts` had already recorded in its own header back in AF11.1.

So the request's purpose is compared against the tool's BEHAVIOR text and the matched field is
named `purpose_vs_behavior`. Naming it `purpose` would have claimed a comparison that did not
happen, which is the one thing an approver auditing a match cannot check for themselves.

## Four tools have no behavior text at all, and an empty result now says so

`assignHandoff`, `materializeHandoffs`, `rankQueue` and `read_attachments` carry no `reads` and no
`produces`. They are matchable by name only, so every result lists them in `behaviorless_tools`.
Without that, a request duplicating one of them surfaces nothing and reads as novel.

The same reasoning drives the stored row's shape. Four states have to be distinguishable: no row
(never checked), `catalog_absent` (checked while blind), zero candidates (genuinely novel), and
candidates. A zero that cannot say which kind of zero it is was the failure mode of half this
week's work elsewhere on the platform.

## Both knobs are mutation-proven in both directions, and one of them was not pinned at all

| Mutation | What dies |
|---|---|
| `DEFAULT_THRESHOLD` 0.2 → 0 | **7** — every negative control |
| `DEFAULT_THRESHOLD` 0.2 → 1.01 | **12** — every planted duplicate and every explanation test |
| `COMMON_TOKEN_SHARE` 0.25 → 0 | **12** — behavior matching stops; only name matching survives |
| `COMMON_TOKEN_SHARE` 0.25 → 1.01 | **3** — the half-shared catalog matches all six |

The last row did not exist at first. Loosening the common-word ceiling against the real 57-tool
catalog killed **nothing** except the test pinning the constant's value, because almost no word
crosses 25% of 57 tools. That is the ticket's own "a rule pinned in only one direction passes its
own tests while being unusable", found in my own work. The share is now an argument, so the
direction can be pinned from outside instead of by editing the source.

## The guard does less than I claimed, and the measurement says where

The rarity weight is `log(N/df)/log(N)`, which is **already zero** when a word appears in every
tool. So on a fully uniform catalog the hard drop adds nothing, and my first test for the loosened
direction expected twelve matches and got none. The guard's entire contribution is the band
between its ceiling and 100%: a word in half the catalog would otherwise carry 0.279 and make
every tool using it a candidate. The test now sits in that band.

## The matcher does not know how to refuse or to grant

Both are out of scope by the ticket's own words, and both are structural rather than promised.
`checkForDuplicateTool` has no refusal vocabulary and returns candidates only. The stored row has
no verdict, approver, status or reason-code column, and a test asserts those column names are
absent — because an absence is what a later edit removes without anyone noticing.

## It is written after the transaction, on purpose

The request rides one transaction with its detail row. The check deliberately does not: a failed
write of ADVICE must not roll back the request, because the request is the thing the intern cannot
recreate. The ranking still cannot half-exist, because it is one row and
`chk_adtdc_count_matches` forces the stored count to equal the stored list.

## What the local typecheck proved: nothing

`tsc --noEmit` exited 0 at the shell and reported **267 errors**, every one of them a TypeScript
4.9.5 parser failure on modern `.d.ts` syntax inside `node_modules`. Zero were in repository
source. Backend and frontend both declare TypeScript 5.7.3 and neither is installed in this
worktree, so the real typecheck is CI's. Every changed file was parse-checked individually
instead, which catches syntax and nothing more. Said plainly rather than reported as a pass.

# AF11.0 — somewhere to record that a human confirmed a capability

- Date: 2026-11-05
- Session: CC-20261102-h8t3
- What changed: a Super Admin can now confirm a capability, the confirmation is recorded with the
  human and the evidence, and the draft-only invariant is replaced by one that permits a recorded
  confirmation and still refuses an unrecorded claim.
- Verification: 2,346 tests across 152 suites green under `jest.ci.config.ts`, 30 of them new for
  the contract and 20 for the schema.
- Notes: the keystone. AF3.5 and AF11.4 both refused every possible grant until this existed.

## The problem, in one line

All 443 capabilities were `draft`, nothing could transition one, and `assertDraftOnlyInvariant()`
threw on any non-draft record. So "refuse a tool grant for a draft capability" meant **"refuse
every grant"**, and neither AF3.5 nor AF11.4 could ever show its criterion working.

## Ali answered one of AF6.3's three questions; the other two are decided here

The ruling settled **who**: a Super Admin. The ticket's own comment says the rest is "storage and
evidence, not authority". So:

**What evidence?** A full `EvidenceRecord` from `promotionCriteria.ts`, reused rather than
paralleled, and it may not be one of the four non-promoting signals. That file already learned
this the hard way — its header records a verifier promoting a capability whose only signal was
`elapsed_time`. A confirmation resting on time passing is precisely the fabricated approval the
invariant exists to catch.

**Per capability, or per capability and agent?** Per capability. "This is a real thing we want" is
a statement about the requirement, not about which employee performs it; scoping it per agent
would let the same requirement be real for one agent and not real for another, which is not
something a person can mean. It is also the reversible direction: adding an agent column later is
additive, removing one would strand rows.

## The invariant is replaced by being generalised, not rewritten

`assertConfirmationsAreRecorded(recordedIds)` refuses any non-draft record with no confirmation
behind it. `assertDraftOnlyInvariant()` now calls it **with an empty array** — which is exactly
the old behaviour, because with nothing recorded every non-draft record is refused.

That is the whole trick: the old guard is the empty-set case of the new one, so there is no
window in which the new check permits something the old one refused. A test asserts the two
produce identical results rather than trusting the comment.

## A hole my own test found, which was not the hole I was testing for

I wrote a test asserting that evidence sourced from `system:auto_approve_timeout` is refused. It
failed, and the test was right while my assumption was wrong: `isNonPromotingEvidence` matches the
four signal **names**, so `{ kind: 'manager_review_completed', source: 'system:auto_approve_timeout' }`
sails straight through it — nothing in that record contains `elapsed_time`.

The machine-identity denylist was applied to the **confirmer** and never to the **evidence**. So a
real Super Admin could have confirmed a capability while pointing at something a timer produced
and evaluated: the person real, the evidence complete, and nobody having looked at anything.
Closed with a separate check on the evidence's `source` and `evaluated_by`.

## A boundary pin stopped me reusing the roster, and the pin was right

AF11.0 says to reuse `resolveRecordedHumans` rather than invent a second roster. Importing it
meant importing `agentChangeRequestService`, which failed
`agentChangeRequestNoTrigger.test.ts` — a pin allowing exactly two importers so that nothing can
quietly start acting on approvals.

I did not widen the allowlist. A roster lookup is not change-request logic; it was living in the
first module that happened to need it. It moved to `recordedHumans.ts`, both services import it
from there, and the pin keeps meaning what it meant.

Moving it then broke eleven tests, because `export { x } from './y'` re-exports **without binding
x locally** and the service calls it internally. Import, then re-export.

## What this deliberately cannot do

## Why neither fix she proposed, and this instead

She asked whether the routes could move to `agents`, or `program` be granted to builders. Both
would work and both hand over more than she asked for.

**Moving them to `agents` scopes nothing.** Those handlers take the domain key from the PATH and
check no ownership, so every builder could then read all ten domains and each one's
`accountable_human`. That is the same disclosure wearing a different section.

**Granting `program`** additionally hands over the ten-domain list and the programme-wide reads,
and it is a governance change — widening a role — for what is really a missing route.

`agent-domains-mine` already records the principle in its own header: *"Section access decides
whether you may ask; ownership decides what comes back."* So this adds siblings rather than
re-sectioning the originals, and a test asserts the originals still answer `program` — if that
ever flips, the disclosure has come back through the door this fix avoided.
