  - Notes: **LC-13 is settled, and the answer is not what the code alone would suggest: the application-level CAS does NOT close the race — the database unique index does.** The mandatory positive control proves it. With `uq_blueprint_approval_revision` dropped, two genuinely concurrent approvals of the same revision wrote **2 rows**; with it present, **1**. So `factoryApproval`'s non-transactional read-then-compare is only safe because `uq_contract_proc_doc_version` exists: the index is the actual guarantee, not the code. That is worth knowing before anyone "simplifies" either index away. The plan demanded this be settled by test rather than argument, and it was.
  - Notes: Three things this approval does that the existing ladders do not — the hash binds **tenant** (`factoryApproval.contentHash` covers only `revisionId + doc_json`, so it binds neither tenant nor actor, while the request requires every citation to resolve within the correct project/tenant and revision); separation of duty **refuses a null proposer** rather than short-circuiting on it; and the read-compare-write runs **inside a transaction**, so the losing caller fails cleanly instead of half-writing.
  - Notes: A cross-tenant approval attempt returns the **same** error as a missing manifest, asserted by a test. Telling a caller "it exists but not for yours" is a cross-tenant existence oracle. Tenant is part of the `findOne` where-clause, not a check applied after an unscoped read.
  - Notes: **Four of my own mistakes here, each caught by running it rather than reasoning about it.** (1) I shipped a `jest.integration.config.ts` whose `testMatch` was broad enough to pick up the **two pre-existing** integration suites and run them against my disposable database — one hung for ten minutes and I initially misread it as slowness. (3) I also added a `jest.ci.config.ts` ignore entry, then removed it: the existing integration suite is **not** ignored, it self-skips without `DATABASE_URL` and reports as *skipped*, which is visible where an ignored suite is invisible. Following the repo beat following my own plan, which had specified the ignore entry.   - Notes: One more, in the test's own design: the positive control dropped the unique index, created duplicates, then tried to recreate the index — which Postgres refuses over already-duplicated rows. The duplicates are now deleted before the index is restored. The failure was itself a second confirmation that the duplicate was real, but it would have left the schema wrong for every test after it.
  - Notes: **A real type error of mine that 128 green tests could not see.** `tsc --noEmit` after this task returned **5** errors against a 4-error baseline, and the fifth was mine: `lifecycleStages.ts` built `LEGAL` with `Object.fromEntries(...) as Record<LifecycleStage, …>`, which TS 5.x rejects (`TS2352`) because `fromEntries` widens the key to `string` so the result no longer overlaps the keyed `Record`. **It is invisible to jest because ts-jest runs with `isolatedModules` — suites transpile without type checking.** So in this repo *a fully green jest run is not evidence that the typecheck passes*, and this would have failed the required `Backend typecheck` check in CI. Rebuilt with a typed accumulator rather than silenced with an `as unknown as` double cast. This is the precise case the contract's baseline-relative tsc criterion exists to catch: against a bare "must be clean" bar the 4 pre-existing `playwright` errors would have masked it, and against no bar at all it would have reached CI.
  - Notes: The suite is built so it cannot quietly become decorative: it skips with a loud message when `DATABASE_URL` is absent rather than failing (a failure there would read as a product defect), and its first assertion is that the index actually exists — so the rest of the suite cannot pass by testing nothing.
