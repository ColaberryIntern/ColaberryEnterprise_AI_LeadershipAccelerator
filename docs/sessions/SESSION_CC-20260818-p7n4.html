Portal points earn smoke: move the daily check off the sandboxed cloud routine onto the production host, deterministically

2026-08-18
What changedFounder received "⚠ Portal points smoke FAILED — 2026-08-18" and asked what it was. Traced it to scheduled cloud routine `portal-points-earn-smoke` (`trig_011HVpH5ZaQywE4xDJMm6cif`, created 2026-07-19, `0 13 * * *`), which has **never produced a single valid result**: its July runs died on `rate_limit: rejected (seven_day)` (1-second runs), and every August run sampled (10th, 12th, 17th, 18th) failed with `curl: (56) CONNECT tunnel failed, response 403` because the CCR sandbox's egress proxy does not allowlist `enterprise.colaberry.ai`. Not one request ever reached the API, so every alert described the monitor rather than the product, and the points economy went unwatched for a month behind a monitor that looked alive. Compounding it, runs before ~2026-08-14 had only `create_draft` on the Gmail connector, so those failures were parked silently in Drafts and never delivered; the failure rate did not change on the 14th, only the delivery did. The `www.google.com/url?q=…` wrapper visible in the alert is Outlook/Gmail link rewriting at display time, not what the agent curled (the run log shows the clean URL) — no defect there. Fix: replace the sandboxed LLM agent with a deterministic host-cron script, on the box that already serves the API, with no model in the assertion path. New `backend/src/scripts/pointsEarnSmoke.js` (host-cron runner, matching the existing `cron-env-wrapper.sh` + `backend/src/scripts/*.js` pattern used by ~15 other jobs) runs the same checks 2-6 as `tests/systemV2/pointsEarnFlow.e2e.js` at the API level: mint a throwaway `@colaberry-test.local` guest JWT, baseline `GET /api/portal/points`, load `GET /api/portal/classroom`, complete the first available non-gated point-bearing card, and assert both `points_awarded == the card's rendered badge` and `total rose by exactly that award`. All decision logic is extracted into new pure module `backend/src/scripts/lib/pointsSmokeChecks.js` (`badgeOf`, `selectCandidates`, `evaluateEarn`, `decideAlert`, `nextState`, and the two email formatters) precisely so the part that says "the points economy is broken" is the part CI exercises — the property the predecessor lacked. Failure-First: every request has a hard `AbortController` timeout (default 20s); transport-only retries capped at 2 with fixed 2s backoff on network error/429/5xx; the card-completion POST is explicitly **never** retried because it is the one call with a side effect and a retry could double-award; a harness crash still alerts and exits 2 rather than dying quietly. Alert policy is deterministic and idempotent: passing runs send nothing (no-noise rule), a failing run sends at most ONE email per UTC day keyed on `(date, kind)` in an atomically-written state file, and the first pass after a failure sends exactly one "back to green" notice so silence always means green rather than "the monitor died again". Structured JSON logs with a per-run `correlation_id` and stable `error_class` values (`TimeoutError`, `UpstreamUnavailable`, `ContractViolation`, `HarnessError`, `AlertSendError`) to stdout, per the Observability Framework.
Verification**22 new unit tests, all passing** (`npx jest src/scripts/lib/__tests__/pointsSmokeChecks.test.js` → `Tests: 22 passed, 22 total`), covering the four mandatory shapes: happy path, failure path (badge mismatch, accrual mismatch, and both reported together rather than stopping at the first), boundary cases (empty/absent/malformed feed, missing point buckets, zero-point and gated cards, non-zero baseline), and the idempotency contract (a second failing run on the same UTC day is deduped; the next day alerts again). Suite is collected by the existing CI gate — `backend/jest.config.ts` already matches `**/__tests__/**/*.test.js`. **BUILD-BREAK-HARDEN run against live production**, all five paths executed and recorded: (1) real run `PASS — awarded 10 == badge 10 [warmup]; total 0 -> 10`, exit 0, `alert_sent:false`, 23 cards / 3 candidates, 8.2s; (2) forced-broken endpoint → `FAIL — check(s) 2`, exit 1, `alert_reason:"first failure alert for this UTC day"`, state file written; (3) immediate re-run → `alert_sent:false`, `alert_reason:"failure already alerted today (dedup)"`; (4) recovery → `alert_reason:"transition fail -> pass"` once, and the run after it silent (`"healthy, no-noise rule"`); (5) `POINTS_SMOKE_TIMEOUT_MS=1` → three capped attempts (0,1,2) each logged `error_class:"TimeoutError"`, then exit 2 with an alert rather than a silent hang. Break runs used a scratch state path and no Mandrill key, so no mail was sent. CI guards run locally green: `node scripts/secret-scan.js` → `OK — scanned 4204 tracked files, no secrets found`; `node scripts/lint-route-auth.js` → `OK — all 91 admin route files are auth-guarded`. Independently of the script, the founder's actual question was answered by running all six checks by hand against production first: signup 201, points 200, feed 23 cards, completion 200 awarding 10 == badge 10, total 0 → 10 — the app was healthy the whole time the monitor was red.
NotesRead-only checks aside, each run's real footprint on prod is one throwaway `@colaberry-test.local` guest plus one card completion for that guest, which is the same sanctioned daily footprint the cloud routine was authorised for; guests are unique per run so a re-run cannot corrupt earlier state or double-award anyone. Not handled by this monitor, stated explicitly: a semantically wrong but internally consistent award (if the API awards 10 and the badge also says 10, both being wrong is invisible here) and anything about the browser HUD, which stays with the Playwright e2e. Host crontab installation and disabling the cloud routine are recorded in the follow-up entry below.
