## Root cause

Two independent contract mismatches on the same screen, both silent:

| Surface | Server sent | Page read | Result |
|---|---|---|---|
| `GET /api/admin/visitors/stats` | `visitors_today`, `total_visitors`, … | `todayVisitors`, `visitors30d`, … | every card `undefined ?? 0` → **0** |
| `GET /api/admin/visitors/stats` | *(nothing)* | `liveCount` | no server-side source at all |
| `GET /api/admin/visitors/live` | bare `[…]` | `res.data.visitors` | `undefined \|\| []` → **empty table** |

Neither is reachable by the type checker: the payload crosses the wire as `any`, and `?? 0` converts a missing field into a plausible number. The dashboard did not error, warn, or blank — it rendered a confident zero, which is why it survived so long.

Three smaller defects fell out of the same drift: live rows carried `visitor_id`/`duration_seconds` while the table read `id`/`session_duration`, so every row had an undefined React key and clicking one requested `/api/admin/visitors/undefined/sessions`; and the header cards were only ever fetched on three of seven tabs, so landing on the default Navigation Flow tab showed no cards at all.

## Known limits, stated rather than hidden

- **Bot traffic is not separated.** Nothing in the tracker classifies crawlers, and they dominate: `worldoftaxonomy.com` produced 9,077 sessions from 97 visitors in 7 days, one of them with 1,626 pageviews in a single session. Live rows will therefore include crawlers. The new Site column makes them identifiable at a glance, but filtering them out is a separate decision.
- **The Analytics tab is still wrong** and was left alone as outside this fix. `fetchAnalytics` reads `topPages` and `trafficSources` off the `/visitors/trend` response, which returns a flat array of daily counts and has neither key. `getPagePopularity()` and `getTrafficSources()` exist in the service but are not routed. That needs two new endpoints.
- **Session counts look inflated** — 84,147 sessions against 1,734 visitors — and were not investigated here.

- [x] Analytics tab: fix a query that had never run, and the referrer nobody was sending
  - Date: 2026-09-04
  - Session: CC-20260903-w3k8
  - What changed: Three defects behind the Analytics tab, found by testing the functions against production rather than reading them. (1) `getTopPages` wrote its window as `INTERVAL ':days days'` — placeholder inside a string literal, where Sequelize deliberately does not substitute — so Postgres received the characters `":days days"` and threw `invalid input syntax for type interval` on **every call it has ever received**. Now computes the window in JS and binds a real timestamp. (2) `fetchAnalytics` read `topPages` and `trafficSources` off `/visitors/trend`, which returns a flat array of daily counts and has neither key; it now calls `/visitor-analytics/pages` and a **new** `/visitor-analytics/traffic-sources` route, mapping `page_path`/`view_count` to the `page`/`views` the table renders. (3) `tracker.ts` never sent `referrer_url`, though the ingest has always read it and derives `visitor_sessions.referrer_domain` from it — so the column was NULL for every session the React app ever created and Traffic Sources reported a single row, "direct, 1,018 visitors, 40,954 sessions". Both Top Pages and Traffic Sources now exclude bots by default, consistent with the live view.
  - Verification: 45 tests green across three suites. The **fixed query was executed against the production database**, the same way the original defect was proven: it returns real rows — `/` 735 views / 391 unique, `/start/` 108/87, `/approach/` 79/77 — where the old one returned an exception. Backend `tsc --noEmit` clean.
  - Notes: **The referrer fix cannot be backfilled.** `document.referrer` exists only in the visitor's browser at page load, so every historical session stays `direct` and Traffic Sources only becomes meaningful for traffic arriving from now on. Same-origin referrers are dropped — an internal link is not a traffic source, and counting one would file every visitor under our own hostname. **Why all three hid so well:** each failed into an empty state rather than an error. A 500 caught by `.catch(() => null)`, a missing key resolving to `undefined`, and a NULL column COALESCEd to 'direct' are indistinguishable on screen from a site nobody visited.

- [x] Engaged visitors: separating a hit from a read, after the bot rule failed its own test
  - Date: 2026-09-04
  - Session: CC-20260903-w3k8
  - What changed: Investigating why `ai-flotation` converts at 0.23% showed the traffic is not real — 448 of 454 sessions (98.7%) under ten seconds, 431 fingerprints that never returned, five days, 110 rotating IPs, almost no user-agent variety. The obvious response was a third bot rule. **It was tested against the only ground truth available — visitors who became leads — and it caught one of them.** So it ships as an ENGAGEMENT measure rather than a bot claim: `engagedVisitorSql` marks a visitor engaged if any session exceeded ten seconds or one page, **or if they ever converted**. Both counts are reported and always reconcile to the headline.
  - Verification: 14 tests; both `tsc --noEmit` clean. Measured on production with the carve-out in place: 1,045 visitors → **337 engaged**, 24 converted, and **0 converted visitors excluded** — the false positive is gone.
  - Notes: **The finding changes the advice.** "ai-flotation converts at 0.23%" reads as a landing-page problem, and acting on it would have meant redesigning a page for traffic that was never human. Roughly 68% of all "visitors" viewed one page for under ten seconds and never came back. Conversion against people who actually looked is **~7%**, not 2.3%. **Why this is not called a bot rule:** one false positive against 24 known-real visitors is enough to say the signal does not support the word, and asserting it anyway would repeat the exact over-claim this dashboard was full of. Naming it "engaged" claims only what the data shows — that a five-second single-page visit is a hit, not a read.
