  - Verification: `tsc --noEmit` exit 0. 55/55 tests green across 3 suites under `jest -c jest.ci.config.ts` (28 new in `certQuestionBankService.test.ts`).
  - Notes: **`toSafeItem` is an allow-list, not a delete-list**, and that direction is the whole point. Building the payload by naming safe fields means a future answer-bearing column is simply omitted; a `{...revision, correct_keys: undefined}` spread would start leaking the day someone adds one, silently. A regression test plants `is_correct: true` on an *option* and asserts it does not survive — that is the exact leak a spread-based implementation would miss, and it is the same "spread of a Sequelize instance" family of bug that bit this repo on 2026-09-02. **Scoring is set equality with no partial credit**: a two-answer item is correct only when both are right. Partial credit would inflate the readiness number the badge rests on, and the real exam does not award it; duplicate/out-of-order selections normalise so a client quirk cannot change a result. **Approval requires a named reviewer** (`setReviewStatus` throws `CERT_APPROVAL_NEEDS_REVIEWER` without one) and there is NO code path that writes an approved revision directly — everything lands as `draft`, AI-drafted items included, because a wrong answer key is worse than no practice at all. **`loadServableRevisions` enforces the gate in the QUERY** (`review_status: 'approved'`, `is_retired: false`), not only in memory, so a caller cannot accidentally widen it; a key with no servable revision is absent from the result and callers must handle a short form rather than substitute an unapproved item. It also drops any question whose `provenance` is not `colaberry_authored` — the bank is Colaberry-authored against the public blueprint, and a row claiming otherwise is a bug to investigate, not content to serve. `validateRevision` catches the failure mode most likely from generated drafts: `select_count` disagreeing with the number of correct keys, which makes an item unanswerable and marks everyone wrong. Not wired to any route yet; no student can reach this code.

- [x] **The scoring core, and an honest 0–1000 number**
  - Date: 2026-09-03
  - Session: CC-20260903-7t4k
  - What changed: `services/certPrep/certScoring.ts` — the pure scoring core, deliberately separate from any DB write so every boundary case is testable in isolation: `toScaledScore`, `passingProportion`, `rollUpDomains`, `scoreSession`, `buildFormPlan`, `isExpired`, plus the `SCORING_POLICY_VERSION` that every session and readiness snapshot records.
  - Verification: `tsc --noEmit` exit 0. 20/20 new tests green; 100 Cert Prep tests total under `jest -c jest.ci.config.ts`.
  - Notes: **The 0–1000 number is honest about what it is not.** Anthropic produces CCAR-F's scaled score through criterion-referenced equating we do not have and cannot reproduce. Ours is a published LINEAR transform so a practice result sits on the same axis and can be compared to the same 720 line, and the file header states it must never be captioned as a predicted Anthropic score. The consequence is documented rather than buried: under a linear map **720 lands at 68.9% correct** — a reasonable working bar and an assumption, not a fact about the real exam. Being linear and published means a student who asks "why 640?" gets an answer; an opaque curve could not give one. **An unanswered question is not a wrong answer** — skipped items are excluded from both numerator and denominator in the per-domain roll-up, because counting them wrong makes an abandoned session look like a failed one and someone who ran out of time has not demonstrated they do not know the material. Session totals still score out of items SERVED, since that is what running out of time on the real exam produces; `answered_count` is reported alongside so "got half wrong" and "answered half" stay distinguishable. **An empty attempt scores null, not 100** — zero questions answered is "no measurement", not "scored at the floor", and showing a floor score to someone who answered nothing is a lie the UI would then have to explain away. **`buildFormPlan` uses largest-remainder apportionment**: naive rounding of five weights lands on 59 or 61 for a 60-item form routinely, and a mock quietly serving 59 items is not the exam shape it claims to be. A test asserts the slots sum exactly across eight form sizes; the official weights produce 16/11/12/12/9 = 60. Unweighted domains are DROPPED rather than given an equal share — inventing a share is exactly the false precision the nullable schema exists to prevent, so the caller checks `weightsAreUsable` and offers unweighted practice instead of a weighted mock. No write path yet; nothing calls this.

- [x] **Cert Prep session lifecycle: start, resume, submit, complete**
  - Date: 2026-09-03
  - Session: CC-20260903-7t4k
  - What changed: `services/certPrep/certSessionService.ts` — the write path for a diagnostic, practice or mock sitting, plus `listApprovedKeysByDomain` added to the question-bank service for form construction. Every operation is guarded in order by ownership, the Week 7 fence, and expiry.
  - Verification: `tsc --noEmit` exit 0. 23 new tests; **123 tests green across 7 suites** under `jest -c jest.ci.config.ts`.
  - Notes: **Correctness is computed from the revision the session SERVED, never the question's current revision.** `cert_sessions.question_keys` stores `[{question_key, revision}]`, and submit looks up exactly that pair — so approving a revised question mid-session cannot retroactively change whether an answer already given was right. **Idempotency is structural, not defensive**: start dedupes on `idempotency_key`, submit uses `findOrCreate` on the unique `(session_id, question_key)` index, and completing an already-complete session returns the stored result without rescoring. Each is enforced by a DB constraint, so a race between two tabs loses at the database rather than in a check-then-write window a retry can slip through — a double-tapped Finish cannot produce two different scores. **Another student's session is indistinguishable from a missing one**: both raise the identical 404 `CERT_SESSION_NOT_FOUND`, so probing session ids reveals nothing about what exists. **Recently-seen questions are DEPRIORITISED, not banned.** Banning them would silently produce a short form against a small bank, and a 40-item "mock" claiming to be 60 is worse than a repeat; fresh keys lead and seen ones backfill only if a domain would otherwise come up short. A test asserts exactly that trade. `startSession` refuses rather than degrading when the bank has no approved questions (`CERT_NO_APPROVED_QUESTIONS`) or no blueprint is configured (`CERT_NO_BLUEPRINT`) — an empty session is not a session. Mode defaults are configuration, not scattered magic numbers: diagnostic 15 items / 25 min, practice 10 / untimed, mock 60 / 120 min to match the real exam shape. **A test-suite failure worth recording:** the first run failed at suite level, not assertion level — `jest.requireActual('../certQuestionBankService')` pulled in the real `CertQuestion` model, whose `Model.init()` runs at import time against the stubbed sequelize. Mocking that model too fixed it. Any future service test that requireActuals a module importing a model needs the same treatment.
