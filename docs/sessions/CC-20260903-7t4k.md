- [x] **Cert Prep models and the governed question-bank serving path**
  - Date: 2026-09-03
  - Session: CC-20260903-7t4k
  - What changed: 8 Sequelize models (`CertTrack`, `CertDomain`, `CertQuestion`, `CertQuestionRevision`, `CertSession`, `CertResponse`, `CertReadinessSnapshot`, `CertEvidenceMapping`) matching `ensureCertPrepSchema.ts` column for column, registered in `models/index.ts` via the existing import + export-block pattern. Plus `services/certPrep/certQuestionBankService.ts`, which is where acceptance criteria 6 (only approved revisions reach students) and 7 (no answer data before submission) are actually enforced: `toSafeItem` / `toRevealedItem` / `scoreSelection` / `isRevisionServable` / `pickServableRevision` as a pure, DB-free core, then `loadServableRevisions`, `loadServedItems`, `createDraftRevision`, `validateRevision` and `setReviewStatus` over the models.
  - Verification: `tsc --noEmit` exit 0. 55/55 tests green across 3 suites under `jest -c jest.ci.config.ts` (28 new in `certQuestionBankService.test.ts`).
  - Notes: **`toSafeItem` is an allow-list, not a delete-list**, and that direction is the whole point. Building the payload by naming safe fields means a future answer-bearing column is simply omitted; a `{...revision, correct_keys: undefined}` spread would start leaking the day someone adds one, silently. A regression test plants `is_correct: true` on an *option* and asserts it does not survive — that is the exact leak a spread-based implementation would miss, and it is the same "spread of a Sequelize instance" family of bug that bit this repo on 2026-09-02. **Scoring is set equality with no partial credit**: a two-answer item is correct only when both are right. Partial credit would inflate the readiness number the badge rests on, and the real exam does not award it; duplicate/out-of-order selections normalise so a client quirk cannot change a result. **Approval requires a named reviewer** (`setReviewStatus` throws `CERT_APPROVAL_NEEDS_REVIEWER` without one) and there is NO code path that writes an approved revision directly — everything lands as `draft`, AI-drafted items included, because a wrong answer key is worse than no practice at all. **`loadServableRevisions` enforces the gate in the QUERY** (`review_status: 'approved'`, `is_retired: false`), not only in memory, so a caller cannot accidentally widen it; a key with no servable revision is absent from the result and callers must handle a short form rather than substitute an unapproved item. It also drops any question whose `provenance` is not `colaberry_authored` — the bank is Colaberry-authored against the public blueprint, and a row claiming otherwise is a bug to investigate, not content to serve. `validateRevision` catches the failure mode most likely from generated drafts: `select_count` disagreeing with the number of correct keys, which makes an item unanswerable and marks everyone wrong. Not wired to any route yet; no student can reach this code.
