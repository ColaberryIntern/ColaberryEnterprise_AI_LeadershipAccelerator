## Two method notes, both bought with a near-miss

**A measurement that encodes a guess about shape can report a defect as absent.** The
first query written to size the matcher collision used `base || ':R%'` and returned **0
rows, "unreachable"**. The real suffix is `.autonomy:Rn`, so the `LIKE` never matched and
the zero was an artifact of the pattern. A second query that asserted no shape at all —
testing only the condition `\b` actually applies, "the next character is a non-word
character" — returned **964**. The shipped guard therefore also asserts no shape: it
strips whatever ids the plan actually contains rather than anything matching `:Rn`.

**n=1 is not a control.** A full-suite run with this change showed 2 failures in
`buildVerificationService.test.ts`; the same suite passed 28/28 in isolation, and one
pristine control run passed. That looked like causation. Running both sides three times
instead:

| | run 1 | run 2 | run 3 |
|---|---|---|---|
| pristine | pass | timeout | timeout |
| with this change | timeout | timeout | timeout |

The failures are `Exceeded timeout of 5000 ms` on the suite's first test — pre-existing
marginality at jest's default on this filesystem, not a regression. Neither
`jest.config.ts` nor `jest.ci.config.ts` raises `testTimeout`, and that suite is not on
the CI ignore list, so it is marginal in CI too and merely fast enough there. Left alone
as out of scope, but recorded: it is a flake waiting to be blamed on an innocent change.

## A performance defect in the first draft of this fix

The first version recomputed the extending-id scan and rebuilt a `RegExp` per extending id
on **every** call, inside a loop that runs roughly `2 x stories x commits` times. On the
plans AF12.7 is about that is ~37,800 calls each scanning 189 ids, on the path a student
hits when they press Sync. `storyCommitMatcher` compiles per story instead; the equivalence
test pins the compiled and one-shot forms to agree, and deliberately reuses one matcher
across several messages because the compiled regexes carry `g` and a stale `lastIndex` is
how that kind of cache goes wrong.

## AF12.7 investigation, recorded because the ticket's premise was wrong twice

Nothing was republished and no config was changed. These are findings, not changes.

**The ticket said the plan generator still emits base ids.** It does not.
`buildPlanFromTasks` does `id: String(t.story_id)` — a verbatim pass-through of
`student_tasks.story_id`. It emitted base ids in October only because it ran before the
rung rows existed. A re-derive alone emits them; no generator change is needed.

**The scope is 991 stories across all ten domains, not ~460 across four.** The ticket's
figure was a sample and understated it by more than half.

**What actually blocks the republish** is `if (proj.published > 0) … skipped` in
`synthesizeDomainBuildPlans.js`. Lifting it naively would insert a second published row
and violate the partial unique index `build_plans_one_published_per_project`. The correct
path is `savePlanDraft` + `planStore.publishPlan`, which supersedes inside a transaction
with `FOR UPDATE`. **Verified that `planStore.publishPlan` does not touch `student_tasks`
at all** — the script's header warns that "the publish path rewrites every task row", but
that is `publishBuild` the service, not `publishPlan` the store. Using the store primitive
preserves the 503 stories' acceptance criteria and due dates.

**Pre-flight, measured:** 1,477 task rows and 1,477 distinct story ids across the ten
domains, so a re-derive would not hit `buildPlanFromTasks`' duplicate-id guard.

**A second defect, found by the same query:** 17 ids in the published plans match no task
row — the truncation casualties of the old `varchar(60)` `story_id` column. They cannot
verify either, and today they log `sbp_verification_task_missing` and continue silently.

### The story-points consequence, corrected

`storyPoints.ts` divides a budget by the plan's story count, and the budget is the single
global `points_config` row `project_story_verified` (`award_model: budget_per_build`,
`builder_xp` = **800**, last edited 2026-08-15).

This was first reported as "republishing cuts the per-story rate 3x, so raise the budget to
protect it". That framing was incomplete in a way that inverted the answer, and the record
should say so:

- **`budget_per_build` exists precisely so plan size does not change what a build pays.**
  The seeder comment records that Ali chose it over a flat rate "so that a student is not
  rewarded for their plan happening to decompose into more pieces". Total for finishing a
  whole build is 800 XP before and after the republish. The per-story number falls only
  because the story count rises.
- **The row is global and cannot be raised narrowly.** `getBudgetPerUnitXp` looks up
  `scope: 'type_default'` only, so there is no per-project override. Raising it to hold the
  agent-domain rate would also reprice **53 other published builds** (student capstones,
  currently 26–160 XP/story) by the same multiple.
- **Banked XP is immune either way.** `xp_awarded` is read back from the frozen
  `evidence_records` row, not recomputed — 459 awards, 24 enrollments, 22,851 XP, window
  2026-08-16 to 2026-11-07. Nobody loses what they already earned.

So the republish needs no budget change, and raising the budget would be a platform-wide 3x
XP inflation. Left with Ali as a decision rather than acted on.

  - Notes: the ticket's premise was false; see below. Nothing about enforcement behaviour
    changed — this reports the truth, it does not alter it.

### The ticket's premise did not survive contact with the code

AF12.8 says directives are "read at runtime for Dara and Reese only... for every other agent,
Ellis included, a directive is recorded but enforced nowhere." Verified by reading both read
sites:

- **False half.** `agentBlueprint/agentManagerConversationPrompt.ts:114` calls
  `getActiveDirectiveTexts(agentId)` **unconditionally** — no name check, no slug list, no
  enabled gate. A directive on any agent reaches that agent's manager conversation today.
- **True half.** `agentSystemPrompt.ts:117` gates its read behind `if (options?.agentId)`, and
  only `curriculum/daraSystemPrompt.ts:34,56` and `reese/reeseSystemPrompt.ts:96` pass it.

### The real gap is one agent, not eight, and it is live

Seven of the eight have no reply runtime for a directive to miss — `domainAgentIdentitySeed.ts`
leaves them disabled, at observe, with no capability. **Maya is the exception and she is
talking to people:** `maya/mayaReplyService.ts` answers DMs (reached from
`communityRooms/dmService.ts:251`) through `maya/mayaPortalPrompt.ts`, and neither of her prompt
builders reads a directive. Positive-controlled both files before claiming the absence.

### And "enforced" is the wrong word for all ten

Every read site injects directives as **prompt text**. No code path reads a directive to grant a
tool, raise autonomy or block an action — `models/ManagerDirective.ts:18-26` says so outright.
The restrict-only property holds *by construction*, not because directive text is validated. So
the honest answer is **advisory for every agent, Dara and Reese included**, and what differs
between agents is only which surfaces inject.

That means the decision the ticket offers — "enforce for all ten, or label advisory for the
eight" — rests on the false premise. The choice that actually exists is to wire Maya's one live
surface and label the mechanism honestly, which is one integration rather than eight.

### Why this is derived rather than asserted, which the acceptance demands

Identity is resolved through the same `get*AgentId()` functions the prompt builders use, so the
posture cannot disagree with them about which row is Dara, Reese or Maya. And five tests **read
the prompt-builder sources** and fail if the wiring stops matching — including one that pins
Maya's gap so that closing it breaks the test rather than leaving a stale claim. Mutation-proved
in both directions: making Maya's source mention the reader fails exactly the pin, and making
the module claim she injects fails exactly her unit test.

A hand-maintained list with no such check would be precisely the asserted answer the acceptance
rules out.

### Method note

A count-mode ripgrep over `backend/src` returned 26 files and **omitted the two files holding
the entire answer**, while content-mode grep over the same path found them and `grep -rl`
returned 143. A short, confident file list from a count-mode search is not evidence of absence

inside `@types/d3-dispatch` before reaching any source of mine.

  - Notes: the old comment claimed "other checks will catch it". They do not — see below.

### Why the original comment was wrong on both counts

The code read `} catch { /* Fail open for pause check — if DB is down, other checks will
catch it */ }`. Neither half of that holds:

- **The other checks do not catch it.** `checkLeadSendable` and `checkCampaignSendable` do
  fail closed, but on *their own* errors. A pause is not a lead fact or a campaign fact, so
  a readable lead plus a readable campaign sent the mail with the pause never examined.
- **A safety flag that fails open stops working exactly when the system is already in
  trouble**, which is the one moment it exists for.

This file's own header says "Enforces: test mode (fail-closed)", and two of its four checks
already fail closed. The pause was the inconsistent one, not the fix.

### The thing that could have made this fix an outage, checked first

Failing closed is only safe if "unreadable" is distinguishable from "never set". It is, and
it was verified rather than assumed: `getSetting` returns `DEFAULTS[key] ?? null` for a key
with no row, and `scheduler_paused` is **absent from DEFAULTS** — so an untouched flag is a
*successful* read returning `null`, and only a genuine database failure throws. A third test
(`still SENDS when the pause flag has simply never been set`) pins that, and it passes both
with and without the fix, which is correct for a control.

Also checked: every consumer of `blockedReason` logs it or interpolates it into a message.
Nothing switches on the value, so adding a reason is non-breaking.

### The ticket's second finding, verified and NOT fixed here

Quincy also reported that nothing which *runs* a timer reads `scheduler_paused` — it gates
sends only. Confirmed: the flag is read in exactly four places (`adminSchedulerController`
twice for the UI, `communicationSafetyService` to block sends, `campaignActivationAuditService`
to audit). No scheduler or worker consults it. So telling someone "the scheduler is paused"
describes a send block, not a stopped job. Left as its own finding because AF12.5's acceptance
covers the fail-open defect only, and Quincy was explicitly told not to widen his story.
