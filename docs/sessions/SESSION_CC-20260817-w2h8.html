What changedQuincy Nkwain Ninying (`qninying@gmail.com`, enrollment `acda8718-806c-4d51-b266-ce85cd8e4b56`, project CoreOps `48f67531-dbbe-4176-b20c-29d4603fa802`) reported twice that he could not see STORY-000. He was right both times. **Root cause: `overlayCompletions` in `frontend/src/pages/portal/projects/projectHydrate.ts` — the ONLY path a device that already holds a project ever takes — could update task STATE, adopt the server's NAME, and record the Command Center URL, and nothing else. A task the server had and the browser did not was never noticed, so `reconcileProjects` reported `noop` while the two sides disagreed about what exists.** His cached card was short by exactly STORY-000 because the Command Center story is deliberately kept out of `plan.stories` (backend `commandCenterStory.ts`: it fulfils no requirement of the student's own system, so counting it would distort the traceability gate and release sizing) and exists only as a materialized task row prepended by `materializeTasks` — so anything cached from a plan-shaped payload is short by that one story, permanently. This is the same defect shape as the rename bug fixed two days earlier by `adoptServerIdentity`; that fix taught the overlay path to adopt a changed name, this one teaches it to adopt a changed task set. Added `adoptServerTasks(p, tree)` (adds missing tasks at the server's position, and whole missing lists; **adds and never removes**, so the student's local-only work and hand-ticked completions cannot be deleted by a merge), extracted the shared `taskFromServer` mapper so the hydrate and adopt paths cannot drift, and wired adoption into `overlayCompletions` ahead of the completion overlay. Also hardened `projectsStore.ts`: `write()` was `try { setItem } catch {}` — a silent swallow of `QuotaExceededError` that would leave the OLD value in localStorage while every caller carried on as if the new one had landed. It now logs a structured `error_class` event and returns success, and the unreadable-cache branch in `read()` logs instead of silently re-seeding. No backend change: the server was correct throughout.
