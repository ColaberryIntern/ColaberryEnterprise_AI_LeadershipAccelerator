# WIRING THE GATES THAT GUARDED NOTHING

Date: 2026-08-27 to 2026-08-30
Session: CC-20260823-r4k9

Three slices, same shape each time, and the shape is the finding.

## The pattern, stated once

Gates 9, 12, 13 and 14 shipped as pure logic with tests, and none of them had a single
production caller. The reason was identical in every case and it was not laziness: **the
table the gate reasons about did not exist.** `delivery_stories` did not exist, so there
was no story to gate. `delivery_releases` did not exist, so there was no release to
evaluate. `delivery_capacity_overrides` existed but had no model, so nothing could read
it.

Each gate was verified against hand-built fixtures that described the world the gate
expected. Every one of those test suites passed. Passing tests over invented inputs is
exactly what "built, tested, and called by nobody" looks like from the inside - which is
why none of the fifteen gate reviews caught it.

## Gate 12 - capacity (`builderAssignment.ts`)

Assignment now consults `assessOverload` with `activeProjects + 1` - the assignment being
*considered*, not the count as it stands. Asking about the current load answers the wrong
question: it would approve the assignment that causes the overload and then report the
overload afterwards.

Also added the `DeliveryCapacityOverride` model. The table had been created by Gate 12's
own DDL and then never given a model, so the override path was unreachable from code.

## Gate 9 - quality (`storyEvidence.ts`, PR #1940, merged)

`upsertStory`, `recordEvidence` (idempotent on `deliveryEvidenceKey`), `evaluateStoryGate`.

The load-bearing decision: **`evaluateStoryGate` reads evidence from the database and
takes no evidence parameter.** Letting a caller pass the evidence would let the caller
decide what the gate sees, which is the one thing a gate exists to prevent. It would also
have been the easier signature to write and to test.

Verified end to end against a running system, not just in unit tests - the gate refuses a
story with missing evidence and passes the same story once the evidence row exists.

## Gates 13 and 14 - profiles and release (`releaseManagement.ts`)

Gate 14 pulled Gate 13 in with it: the release gate derives its mandatory-check set from a
profile key, so profile resolution was unreachable for the same reason the gate was.

**A release here is a record, not a deployment.** `releaseGate.ts` already drew that line
itself - `evaluateReleaseGate` answers *readiness*, `assertDeploymentAuthorized` answers
*may this be deployed*. They are separate functions because they are separate questions.
Nothing in `releaseManagement.ts` can push code. That answered the product question I had
flagged before starting - what "cutting a release" means in this system - from the code
rather than from invention.

Four decisions worth arguing with:

- The **profile comes from the project, never the request.** A caller who could pass one
  could choose which mandatory checks apply to their own release, and picking
  `internal_tool` for a government engagement is precisely the move the gate exists to
  stop - while looking like an ordinary request.
- A project with **no profile is refused, not defaulted.** Guessing a profile guesses which
  checks are mandatory: the strict guess blocks ordinary internal work, the convenient one
  waves a regulated engagement through.
- `evaluateRelease` uses the **stored approver, never the caller.** Evaluating with the
  requester's id would make the gate's `approver_missing` rule unreachable - every
  evaluation would appear to have an approver simply because somebody asked.
- A **refused approval writes nothing.** One that still recorded an approver would show a
  person signing off on something that never passed.

Verification: 8 tests, weighted toward what is *not* written on a refusal.

## The recurring self-correction

Five times across these three slices a test failed on a name I had invented rather than
read: `riskLevel` (optional on the interface, blocking in the validator), `gate.passed`
(the real field is `passes`), and in the release fixture both `sandbox` (no such profile;
the real keys are `commercial_standard`, `internal_tool`, `government_public_sector`) and
`tests_pass` (the real check is `tests`).

Each was caught because these tests run against the **real** modules rather than
hand-rolled doubles of them. That is the same property the original gates lacked, and it
is the reason the wiring found the gap that fifteen gate reviews did not. Worth keeping
deliberately: a test that mocks the thing it is checking will pass over an invented world
indefinitely.

`delivery_releases` shipped with a model and a DDL group, and the DDL/model agreement test

# GATE 11 - the last gate, and why it could not be wired honestly

Date: 2026-08-30
Session: CC-20260823-r4k9

`mentorExceptions.ts` was referenced by **exactly one file in the repository: itself.** No
caller, and no test either - the only gate that shipped with neither.

The reason was not neglect. **Four of its eight inputs had no source in the schema**, so
there was no honest way to call it.

| Input | State found |
|---|---|
| `clientReviewPending` | sourceable from `delivery_client_acceptances` |
| `hasClientReviewExperience` | sourceable, project-scoped proxy |
| `releaseAwaitingApproval` | sourceable **only after Gate 14** shipped `delivery_releases` |
| `concurrentStories` | no builder on `delivery_stories` |
| `completedStories` | no builder on `delivery_stories` |
| `reworkedStories` | **"rework" appeared nowhere in the schema at all** |
| `trustOrSecurityGateFailing` | `delivery_agent_trust_requirements` keys on `agent_definition_id` |
| `architectureConcernRaised` | `decision_type` has no vocabulary; nothing writes the table |

`delivery_stories` had `created_by_identity_id` and nothing else naming a person. Using it
as "the builder" was available and wrong - it is who *filed* the story. Ali approved adding
`assigned_to_identity_id` and `rework_count`, which closed three of the four gaps.

## The design decision this turns on

The tempting signature is `assembleBuilderState(): BuilderState` - every field populated,
unavailable ones defaulted to `false`. That produces a mentor queue saying *"this builder
has no problems"* for a builder whose problems are merely unrecorded, **with exactly the
same confidence as a real all-clear.**

So the assembler returns `{ state, unsourceable }` and the endpoint returns the
`unsourceable` list in the response body. Six answers are never presented as eight. The two
structurally blind fields are reported on every single call.

There is a second guard behind it. `delivery_stories.status` is a free `VARCHAR(30)` with
**no vocabulary defined anywhere** - `'proposed'` is the only value anything writes. The
in-flight and completed sets are therefore a stated assumption, and if the vocabulary ever
moves, every count silently becomes zero, which renders as a builder in perfect health. So
the assembler detects it: stories present but none classified means the three counts are
declared unsourceable, naming the statuses it actually saw.

## An existing test caught the schema change, correctly

`ensureRefactoredDeliverySchema.test.ts` asserted every `ALTER TABLE` matches
`/^ALTER TABLE organizations /`. My two ALTERs on `delivery_stories` failed it.

That assertion encoded the fact that ESC-1 was once the only ALTER, not the rule behind it.
The rule is **this module must not reach into tables it does not own**. Broadened to derive
the owned set from the `CREATE TABLE` statements in the same run, so a new table is covered
the moment it is added. Proved by injecting `ALTER TABLE enrollments` and watching it fail,
then removing it. The `SET NOT NULL` half is untouched and still the important one.

# E2E SCENARIOS A, D, E, G - four builds wearing test-shaped hats

| # | What had to be built before a line of the scenario could be written |
|---|---|
| A | `delivery_experience_claims` + `experienceClaims.ts` + 2 endpoints. `evaluateClaim` had no table, so no claim could ever be earned. |

## Two design rules worth keeping

**The caller never describes its own evidence.** `claimFromEvidence` reads `evidence_type`
and `outcome` from the `delivery_evidence` row and has **no parameter for them**. A caller
that can describe its own evidence can substantiate anything, and the ledger would be
recording claims about a world it was told existed rather than the one that does. Same rule
the quality gate follows, same reason.

**Silence is not an attestation.** `evaluateClaim` rejects `builderDidTheWork: false` - but
the field is optional on `ClaimCandidate`, so *omitting* it passes the check. That is credit
for attendance arriving through the one door the pure rule leaves open. The service requires
an explicit boolean and the column is `NOT NULL`.

## What the scenarios are careful about

**D** asserts the control, not just the failure: after recording every mandatory check
except accessibility, the ONLY remaining check blocker must be accessibility. Without it,
"not ready" could mean anything was missing and the test would pass even if the gate had
stopped looking at accessibility entirely. It also proves a recorded `not_run` does not
satisfy the gate, and that the waiver survives approval - folding it away would leave a
finished record claiming a clean government release that never had an a11y run.

**E** compares `row_to_json` of the whole student row as a string rather than the columns I
happened to think matter. `updated_at` is inside that JSON, so a bare touch fails. It uses
the OLDEST EXISTING student project, because a row the script created has no enrollment and
no progression and is a weak subject for a §24 non-regression claim.

**G** tests an absence, so it snapshots counts of every table a signal could have written to
plus the project row, before and after. A script asserting only "a candidate exists" would
pass on a system that also silently opened a story.

**A is PARTIAL and says so in its own output.** It does not cover the `-> Claude Code ->`
leg: evidence is recorded through the endpoint, not produced by an agent run.

### The finding

D failed 6 of 28 on the first run, one root cause: **`requireAdmin` populates `req.admin`,
and every actor lookup on these routes read `req.user`.** Approval 401'd because there was
no approving identity.

What that exposed matters more than the fix. `assignBuilderToProject` - shipped, merged,
and covered by the scenario C run recorded earlier in this log - had the identical
expression and had been passing `actorIdentityId: null` since it shipped. Nothing ever
failed, because `granted_by_identity_id` is nullable. Every assignment silently recorded no
granter, and scenario C passed against it because C never asserted who granted.

**Twenty unit tests covered that service and every one supplied the actor directly as a
parameter**, so none of them could see that the route never supplied one. The seam between
middleware and handler is precisely what a unit test cannot reach.

### Two fixture errors, both mine, both caught by running

  levels are `R0`-`R5`. Refused 422, correctly. The script now prints the validator's issues
  on failure.
- A `docker cp` into an existing `/app/e2e` left a stale copy, so the corrected script
  produced a **byte-identical** failure. The identical output was the tell: a real fix that
  changes nothing is evidence the fix never ran. Verified the new content was actually in
  the container before re-running.
