## Why the planning took four audit cycles

Worth recording, because the cost was real and the cause was mine.

The request asked for an in-app live player with a server-enforced 15-minute preview.
Discovery found that **live embedded playback was not reachable** with the services this
repo has: Zoom is Server-to-Server OAuth only, there is no Meeting/Video SDK credential
anywhere, no streaming stack of any kind, and no RTMP output configured. That was escalated
rather than worked around, and Ali approved a managed streaming provider on 2026-10-01.

Discovery also found three latent defects this feature depends on:

1. **Nothing ever writes `lobby_open` / `live` / `cooldown`.** `RoomBooking` declares twelve
   states and the transition table exists, but `roomBookingService` only ever writes
   `pending_approval`, `scheduled`, `completed`, `cancelled`. Controllers *read*
   `state IN ('live','lobby_open')`, so the "happening now" rail is permanently empty.
2. **`SessionWentLive` is dead vocabulary** — declared at `roomEvents.ts:14`, matched as a
   no-op handler, emitted nowhere.
3. **Every feed filters `starts_at >= now`**, so an event that has already begun is invisible
   by construction (`communityCalendarService.ts:93-95`).

Separately, the Zoom webhook **fails open** when its secret is unset and has **no replay
protection** — the repo's own test signs a November 2023 timestamp and asserts success.
That is a security fix queued as P2-06, justified independently of this feature.

The plan scored 14/20, then 17, 17, 17. No dimension ever scored zero, and in the later
cycles the losses were **my unverified repository claims**, not plan structure — five of
them, including an absence conclusion drawn from a grep piped through `head -12`. The
method correction is recorded in the run's `verification-log.md` and in memory: read the
file in-session before asserting anything about it, and never conclude absence from a
truncated or path-limited search.

    inserting an `ALTER TABLE live_sessions ...` statement failed *"every statement is
    CREATE ... IF NOT EXISTS"*, and changing the occurrence default to `'free'` failed
    *"defaults access_mode to the most restrictive value"* — both named, both reverted by
    edit rather than `git checkout`.
  - Notes: the mutation run caught a **test that could not fail**. The access-mode
    assertion originally matched `broadcast_series.default_access_mode`, which *ends with*
    `access_mode`, so it passed even with the occurrence default flipped to `'free'` —
    the same substring-false-positive family as `version` matching `conversion`. Fixed
    with a word boundary plus a negative assertion, and a separate test added for the
    series default. Design notes: editorial state and provider health are deliberately
    **separate columns** so a scheduled time or a stray webhook cannot publish backstage
    content; `content_started_at` is distinct from `scheduled_start_at` so a lobby
    countdown cannot consume preview time; `CHECK` constraints are inline rather than the
    `ALTER`-pair form, which keeps the additive-only guarantee literally true on new
    tables; and FKs point only at tables created in the same statement list — cross-epic
    links are plain columns per the house style, which is also what lets `source_id` hold
    a CCPP EventBrite string beside our UUIDs.
