### A student's second project was invisible because only the ACTIVE build could ever be hydrated (2026-08-25)

- [x] **Found the real root cause, ruled out the assumed one with evidence, unblocked Quincy with a backed-up one-row write, and opened PR #1833 with the permanent fix.**

  - What changed: Quincy Ninying, 2026-08-24: *"I am unable to see my Ambit project. I only see my current project and the training example."* Both projects are real rows on **his own** enrollment `acda8718`: `CoreOps` (`48f67531`, active, 28 tasks, 22 complete) and `Ambit` (`860288eb`, 13 tasks, published plan, created 2026-08-19). **The assumed cause was wrong and was disproved rather than worked around.** The known data defect on `860288eb` (`organization_name` still reading "Oklahoma Turnpike Authority") is carried by **both** of his projects, and the one carrying it renders perfectly, so the column cannot be what hides the other. `active_project_id` is not a filter either: `GET /api/portal/projects` was called against production as him and returned **200 with `Ambit` in the body** while the page drew one build. The server was sending it and the client was discarding it. **The defect is client-side.** `projectSync.reconcileFromBackend` hydrates from `/api/portal/projects/active`, which returns exactly ONE tree; the inventory from `/api/portal/projects` was consulted only to name the active id and to prune cards for deleted projects, and was never a source of new cards. A project live on the server but not active therefore had **no path onto the page at all**, and reloading could not help because the reload re-ran the same one-tree pull. `hydrateProjectById` already did the right thing and was wired only to archive-restore. The existing code comments name the hole exactly ("a project that is live on the server but not active has no path onto the page at all"). New `hydrateMissingProjects()` runs at the end of every pull and gives a card to each live server project the device lacks. **The guard that makes that safe:** "hydrate everything the server owns" points straight at `fcce50ef`, the platform's own ~144k-row record, which sits on Ali's real enrollment and has `name IS NULL`, so it would have rendered as a build called "Your build". The summary DTO now carries `is_protected` (derived from the existing `PROTECTED_PROJECT_IDS`, not a new list) and hydration skips those rows **while pruning still sees them**; `ServerInventory` gained a separate `hydratableIds` precisely so the two cannot be recollapsed, because narrowing `ids` would make pruning treat a live project as deleted and destroy its local card. Files: `frontend/src/pages/portal/projects/projectSync.ts`, `projectHydrate.ts`, `backend/src/services/projects/projectTreeDto.ts`, plus four test files. PR **#1833**, branch `fix/hydrate-non-active-projects`, SHA `00f641f8`.
