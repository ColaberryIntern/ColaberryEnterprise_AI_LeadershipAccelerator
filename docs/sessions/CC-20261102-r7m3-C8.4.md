### How a type and a table disagreed for seven months

Three things had to be true at once, and the mechanism is the lesson:

1. The column is a bare `STRING(30)` with **no database enum**, so Postgres accepted anything.
2. The one writer, `synthflowWebhookController`, called `create(... as any)`.
3. Nothing enumerated the legal values at runtime, so no validator could have caught it.

And the cast was not there to smuggle a bad outcome. It was there because **`step_index` was
declared required on the attributes interface while the column carries `defaultValue: 0`** — an
honest call could not compile. One cast silenced both problems. That is worth noticing in its
own right: a type that lies about what a caller must supply gets paid for in casts, and a cast
suppresses every other error in the same expression.

Corroborating detail: `funnelStages.ts` already lists `no_answer` among "the ten recorded
outcomes". The funnel documentation was right and the type was wrong.

## What changed

1. **`no_answer` added to `OutcomeType`**, with the measurement recorded in the comment.
2. **`InteractionOutcomeCreationAttributes`** — `Optional<..., 'id' | 'step_index' | 'created_at'>`,
   following the existing `RoutingRuleCreationAttributes` precedent. The database mints all
   three, so demanding them of a caller was the lie that forced the cast.
3. **The `as any` is gone** from the `InteractionOutcome.create` call in
   `synthflowWebhookController.ts`. The honest call now compiles, which means a wrong outcome
   value fails the build instead of landing in the table. (The other casts in that file are
   unrelated and untouched — blast radius kept local.)
4. **`OUTCOME_TYPES` and `isOutcomeType()`** — the union as data, so an inbound webhook value
   can actually be validated. A compile-time `AssertSameSet` makes the array and the union
   impossible to drift: adding to one without the other fails `tsc`.

## A defect I went looking for and did NOT find

Worth recording because the inference was reasonable and the rows refuted it.

`funnelStages.ts` stage 5 says: *"Nothing records a commercial meeting as HELD."* That looked
stale — `growth_journey_outcomes` declares a `meeting_completed` outcome type, fed from
`appointments.status` and `strategy_calls.status` through `APPOINTMENT_STATUS_MAP`. So the
schema to record a held meeting plainly exists, and I was ready to correct the text.

Production says otherwise. **`growth_journey_outcomes` holds zero rows**, and held meetings tied
to a lead at a strategic account come back **0**. The shipped claim is true in substance. I left
it alone.

Also confirmed accurate: the file says of `booked_meeting` "Nine exist." Production has exactly
**9 rows across 7 distinct leads**.

The new suite is **pure** — no database. The production values are written into it as a dated
fact with counts rather than queried, because a test that reads production cannot run in CI and
one that reads a dev database proves nothing about production. It carries a negative control
(`no_anwser` transposed, `SENT` miscased, non-strings) so that a guard returning `true` for
everything could not satisfy it, and an assertion that **every declared value is either observed
in production or on the written-by-nothing list** — which stops the union quietly accruing
aspirational members that readers mistake for live signals.
