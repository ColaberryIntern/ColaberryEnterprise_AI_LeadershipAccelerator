### The ticket's premise was right about the symptom and wrong about the cause

R11 reported 1,100 high-intent leads invisible to the scan, and attributed it to two stage
literals that do not exist. Both halves are true. Neither is why.

Measured in production 2026-11-12:

| stage | score ≥70 | score 1–69 | score 0 |
|---|---|---|---|
| new_lead | 161 | 108 | 16,686 |
| contacted | 939 | 963 | 6,548 |
| enrolled | 0 | 0 | 15 |
| meeting_scheduled | 0 | 1 | 5 |
| negotiation | 0 | 0 | 2 |
| proposal_sent | 0 | 0 | 1 |

**Every late-stage lead is unscored. Every scored lead is early-stage.** The old predicate
ANDed those two sets, so it could not match whatever the data did. Correcting the literals
alone still returns 0, which is the measurement that matters: the fix the ticket proposed
would have changed nothing and looked like a fix.

The cause is that scoring and staging are separate subsystems over separate rows: scoring
runs on inbound marketing leads, `pipeline_stage` is a hand-managed sales pipeline of about
two dozen people nobody scores.

### Four faults, three of them named in the ticket

1. **It could never run.** `revenueOpportunityAgent.ts` registers via a module-load side
   effect and nothing imports it. Now an entry in `SCHEDULE_REGISTRY`, and in
   `UNINSTRUMENTED_AGENTS` so `instrumentCronJob` makes run/error counts real.
2. **The predicate.** Score-led, with the table above written into the file.
3. **The seed row lied.** `trigger_type: cron` with `enabled: false`, run_count 0,
   error_count 0 — which reads as "configured, idle, healthy", because zero errors is what
   zero runs looks like.
4. **Not in the ticket: `limit: 20` with no `ORDER BY`.** A cap without an order is a random
   sample wearing a priority's clothes. Now ordered by score descending, capped at a named
   constant with its reason.

### Why it will actually fire

`enabled: false` on the `ai_agents` row does not gate the scheduler — the gate is
`cron_schedule_configs`, read by `resolveAllCronSchedules()`, and `enabled` defaults to
`true` when no row exists. There is no row for this agent, so the entry starts. The seed's
`enabled` is set to true anyway, so the row stops contradicting what happens.

### The guards are mutation-tested, because the first attempt did not prove anything

Reintroducing the dead predicate fails 2 tests. Removing the `ORDER BY` fails 2 tests. The
first run of that second mutation *passed*, which looked like a weak test — the substitution
had silently been a no-op. Repeating it with a verified removal failed correctly. A guard
that has not been seen to fail is not yet a guard.

### One ratchet fired, correctly

`cronRegistryBaseline` listed `RevenueOpportunityAgent` as `confirmed_dead`. Bringing it to
life healed that entry and the reconciliation suite failed, which is the ratchet working.
Entry removed. A sixth failure was a positive-control sentinel pinned to the registry's
first element; the new entry had been inserted at the top, so it moved down.
