Both directions are pinned by tests, not assumed.

**The dev environment can no longer mail a real person — enforced in code, not a settings row**

2026-08-13
What changedThe durable backstop (option 2 from the entry above) for the `accelerator-dev-backend` hazard, built at Ali's go-ahead after option 1 was applied. Restating the risk: that container runs `NODE_ENV=production` with a **live `MANDRILL_API_KEY`**, `SMTP_HOST=smtp.mandrillapp.com`, `EMAIL_FROM=info@colaberry.com` and the **same schedulers as production**, against `accelerator_dev1` — a database of real names and real addresses. An email from dev is byte-identical to one from prod: same branded sender, same domain. Option 1 (`test_mode_enabled=true` on dev1) is **one row in a table** — a refresh from a prod snapshot, a settings-screen edit, or a fresh dev DB removes it silently and nothing warns anyone. New `backend/src/services/devEmailGuard.ts` holds the routing rules as a **pure function**; it is applied inside `guardedSendMail()`, which **all ~28 sends in `emailService` funnel through** (verified by grep — only one line touches the transporter directly), so the property holds for the entire service rather than one sender. The property: **when `APP_ENV=dev`, an address that is not the configured sink either gets rewritten to the sink or the send is blocked.** Sink precedence is `DEV_EMAIL_SINK` env var → the `test_email` setting → nothing, and **nothing means BLOCK**. Fail-closed is deliberate and is the whole point: in dev, not sending is recoverable and mailing a student is not, so a settings-table outage now *closes* the door instead of opening it. `cc`/`bcc` are **dropped rather than rewritten** — each would otherwise be a live delivery — but are still named in the `[DEV → …]` subject tag so a dev tester can see who production would have copied. **Production is untouched by construction**: `isDev` is `APP_ENV === 'dev'` and **prod has `APP_ENV` unset** (checked on the running prod container *before* writing any code — had prod looked like dev, this change would have blocked all production email). The rules take `devMode` as an explicit argument rather than reading an ambient global, so prod behavior is a single literal `false`. **Also fixed an accounting bug this work exposed:** `guardedSendMail` resolves with an empty `messageId` rather than throwing when a guard stops a send, so `sendSessionReminder` logged `"sent"` **and wrote `status:'sent'` to `communication_logs`** for a message never handed to the transport — with 55 recipients that is 55 phantom deliveries in the audit trail added hours earlier. Blocked sends now record `status:'blocked'`, a third outcome distinct from `'failed'` (which would imply something went wrong when the block was deliberate), using the same `Boolean(info.messageId)` test the training-welcome sender already established.
Verification**21 new tests** — 13 pure routing tests plus 8 exercising the real `sendSessionReminder` → `guardedSendMail` path, including the production-unchanged case, env-sink-beats-DB-setting precedence, block-when-the-settings-lookup-itself-throws, and a **sweep asserting that across every nodemailer recipient shape** (bare string, `Name <addr>`, `{address}` object, arrays, comma-joined, sink-in-`to`-with-real-address-in-`cc`/`bcc`) **either the send is blocked or every surviving recipient is the sink**. Three further tests pin the blocked-vs-sent audit accounting. Full email surface green: **9 suites / 72 tests**. `tsc --noEmit` (5.7.3) clean on all changed files.
