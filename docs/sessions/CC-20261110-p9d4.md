# CC-20261110-p9d4

## The task board had no "in progress", so every working builder read as a zero

### What changed

- **`backend/src/services/sbp/verification/boardStatus.ts`** (new, pure). Maps a
  story's `StoryVerificationState` onto a `student_tasks.status`. `in_progress`
  and `submitted` both become `in_progress`; `not_started` stays; `verified`
  returns `null`, meaning "not mine to set".
- **`backend/src/services/sbp/verification/__tests__/boardStatus.test.ts`**
  (new). Six cases. The load-bearing one asserts no input ever yields
  `complete`.
- **`backend/src/services/sbp/verification/buildVerificationService.ts`**
  (modified, 2 hunks, +13 lines). The existing `StudentTask.update` now also
  writes `status` when the task is not already verified.

### Why

`buildVerificationService` has always computed `stories_in_progress` — it is
right there in `summary.rollup` on every run — but that number never left the
response body. Nothing wrote it to `student_tasks.status`.

Measured against production on 2026-11-10, before this change:

| status | rows |
|---|---|
| `not_started` | 2235 |
| `complete` | 537 |
| `in_progress` | **0** |
| `blocked` | 0 |

Zero, across every project and every builder, for the life of the system. The
column is a Postgres enum that has always accepted the value, and
`projectWriteService.CLIENT_SETTABLE_STATUSES` has always permitted a client to
set it. Nothing ever did.

The effect is that a builder mid-flight is indistinguishable from one who has
not started. Victoria Spencer-Auber's sales project holds 124 tasks: 8 complete,
116 `not_started`, and her own `.colaberry/progress.json` reports 37 stories in
progress. Fifteen commits in four days rendered as a zero next to her name, and
she was asked to account for it.

### Verification

- `boardStatus.test.ts`: 6 cases, all pure, no database and no mocks.
- Diff reviewed against `origin/main`: 2 hunks in the service, both at the
  single existing `StudentTask.update` call site.
- Production read-only probes (SELECT only) established the counts above, that
  `story_id` is unique per task for the affected project (124 distinct for 124
  rows, so the service's `findOne` is correct and not silently partial), and
  that `sales.RESEARCH-1-SYSTEM-CLASSES` is already `complete` and verified.
- **NOT verified:** this has not been deployed, so no production behaviour has
  changed yet. The backfill question below is open.

### Failure-first notes

- **What happens if it fails?** The update is the same single call that already
  ran; adding a column to its payload cannot fail independently of the write
  that was already happening.
- **Can it demote a verified task?** No, two ways. `record` is post-latch, and
  the `task.verified_at` guard short-circuits before `boardStatusFor` is
  consulted.
- **Can it award completion?** No. `BoardStatus` excludes `complete` at the type
  level and a test asserts it for every member of the state union.
- **Not handled:** existing rows. Tasks already sitting at `not_started` only
  move when the next verification run reads that story. There is no backfill in
  this change, deliberately — a backfill writes to every builder's board at once
  and should be a decision, not a side effect.

### Deliberately NOT done

1. **No backfill.** See above.
2. **No split of `buildVerificationService.ts`.** It is 715 lines, over
   CLAUDE.md's 500-line hard ceiling, and the rule says the next change must
   split it first. The new logic went into its own module rather than growing
   the file, and the call site grew by 13 lines. A genuine split of a 715-line
   service is a large refactor and an escalation, not something to do inside a
   bug fix. **Flagged for a decision.**
3. **No fifth task status.** `submitted` maps onto `in_progress` rather than
   getting its own value, because a new value means a database enum migration,
   which is an escalated decision. The precise state stays in
   `verification_json.state`.

### Runbook updated, because CI requires it

`skillRunbookCoverage.test.ts` enforces that every module under `services/sbp`
is named in `.claude/skills/build-student-project/SKILL.md` or its references,
or else listed in `NOT_IN_RUNBOOK` with a reason. `boardStatus` was neither, so
the first CI run failed on exactly that — 1 failed of 42632, and the failure was
this gate doing its job.

Rule 7 (`complete` cannot be set by the client) now carries the `in_progress`
half of the same story: the measured zero, the failure it produces when triaging
a builder on a low number, what `boardStatus` guarantees, and the absence of a
backfill. Re-ran the test's own logic against the branch before pushing: 94
modules, 3 reference files, 0 missing.
