## The code change

`coraAutoReplySkipReason()` treated `Precedence: list` as bulk mail. `support@colaberry.com`
is a Google Group, and Google stamps `Precedence: list` on everything it fans out, so **the
group that delivers Cora her mail was the thing making her refuse to answer it.**

Verified against production headers before writing a line of it:

```
precedence  : list
list-id     : <Support.colaberry.com>
mailing-list: list Support@colaberry.com; contact Support+owners@colaberry.com
delivered-to: ali@colaberry.com
```

Every one of those rows is an individual person writing in — "Tuition fee", "Deployment",
"Getting all the software downloaded", Kes's "Question" on 13 Nov.

The split:

- `bulk` / `junk` / `auto_reply` → still `bulk_precedence`, always refused.
- `list` → refused as `foreign_list_precedence` **only when the list is not ours**.

A new `isOwnDistributionList()` identifies our own group from `List-Id` or `Mailing-list`.
Replying is safe because Cora replies to `from_address`, never to the list address, so there
is no fan-out and no loop; `self_address`, the thread dedup log and the circuit breaker all
stay in front of it unchanged.

**Matched as a whole token, not a substring.** The first draft used `.includes()`, and the
test written against it caught that `<support.colaberry.com.evil.example>` would have passed
as ours — a way past the guard by naming a list after ours. Now `List-Id` is parsed out of
its angle brackets and compared exactly.

Also widened the dry-run audit metadata: it logged only `body_preview` (300 chars), which
cuts off before the part carrying the risk. Shadow mode exists so a human can read what would
have been sent, so the dry-run row now also carries `body_full` (8000 chars). The live-send
path keeps the short preview.

## The shadow replay — what Ali asked to see

Replayed all 42 support emails the guard refused in the last 30 days through the **compiled
production** `generateCoraReply()` inside `accelerator-backend`. No sends, no audit writes, no
DB changes; `CORA_DRY_RUN=true` untouched. The guard fix changes only *which* emails reach
that function, never what it writes, so the review is valid without deploying it.

| Measure | Result |
|---|---|
| Emails replayed | 42 (0 generation errors) |
| Came back `needs_human = true` | **42 of 42** |
| Replies that echo the sender's own letter back | **5** |
| Replies that tell the sender she has no access | 2 |
| Replies that promise a hand-off | 23 |
| Real students / cold vendor mail / internal | 20 / 19 / 3 |

**Verdict: do not arm her.** Not one of the 42 gets resolved. With no knowledge base, the
service falls back to a prompt that instructs her to acknowledge and route the sender to
support@colaberry.com — the inbox they just wrote to.

The worst case is concrete. A student wrote asking us to contact TFC and delay her tuition
payments because she has not found a job yet. Cora's reply was that student's own letter,
restated, **re-signed with the student's own name**. Live, she would have received her own
plea for help back from support, apparently written by herself.

## Not done, and why

- **Lock 2 (`CORA_DRY_RUN`) left at `true`.** Arming live sending is the exact path that
  produced the 2026-07-14 mail loop (3,209 `cora_send_failed`, all Gmail
  `"User-rate limit exceeded ... (Mail sending)"`). The replay above says it should stay off
  regardless until lock 3 is cleared.
- **Lock 3 (empty knowledge base) not seeded.** Seeding it decides what an automated agent
  tells students about tuition, deadlines and deletion requests. That is a governance
  boundary, not an implementation detail. `backend/src/seeds/` holds the seed path and
  `coraKnowledgeBase.ts` still holds the pre-DB static content.
- **Spam exposure flagged, not solved.** 19 of the 42 are cold vendor mail. Arming her would
  have support@ replying to sales prospecting, confirming the address is live. Worth a sender
  gate before any live send, and the dry run is what made it measurable.
- **A separate finding, logged not fixed:** 166 support-group emails arrived in 30 days and
  Cora was invoked on only 42. The other 124 are the group's own echo copies (`from:
  support@colaberry.com`, caught correctly by `isFromCoraHerself`) and `school.colaberry.com`
  forum notifications, archived by the `List-Unsubscribe` rule. Checked, not a defect.
- **Unanswered support mail still sitting at INBOX**, oldest first: "Colaberry - Formal
  Deletion Request" (28 Oct), "Im Stuck" (31 Oct), "Unable to Access Power BI Desktop Class
  Video" (2 Nov), "Tuition fee" (10 Nov), "Getting all the software downloaded" (12 Nov),
  "Deployment" (12 Nov), Kes's "Question" (13 Nov), "Deactivate and Delete my info" (14 Nov).
  Two of those are privacy deletion requests that have gone weeks without acknowledgement.

## Reproduce the replay

Read-only against production; the only outbound call is to OpenAI.

```bash
# 1. extract the refused emails (psql, no \pset lines - they contaminate the JSON)
docker exec accelerator-db psql -U accelerator -d accelerator_prod -t -A -q -f /tmp/coraextract.sql \
  > /root/cora_replay_in.json
# 2. replay inside the backend container
docker cp /root/cora_replay_in.json accelerator-backend:/tmp/
docker exec accelerator-backend node /tmp/coraReplay.js \
  /tmp/cora_replay_in.json /tmp/cora_replay_out.json --allow-fallback-prompt
```

`coraReplay.js` **refuses by default** when the knowledge-base prompt does not load, because a
review built on the fallback prompt would describe an agent nobody is running. That refusal is
what surfaced lock 3. `--allow-fallback-prompt` is the deliberate override used to capture
what production would really send today.
