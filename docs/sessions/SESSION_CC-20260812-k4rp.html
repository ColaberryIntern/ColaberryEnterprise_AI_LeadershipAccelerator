**PaySimple webhook: fix the signature check that was rejecting 100% of real deliveries (uppercase vs lowercase hex)**

2026-08-12
What changedInvestigating why Arinze Ohagwu's payment never linked (see the entry above) turned up a live outage: **every** PaySimple webhook was being rejected `400` with `[Webhook] PaySimple signature verification failed` — 11 deliveries between 17:12 and 18:51 UTC on 2026-08-12, all from PaySimple's `54.186.163.123`, zero successes. Ruled out the obvious causes with evidence: the signature header IS present (0 "no signature header" warnings), the secret IS configured (64 chars, and hashing the value across 5 `.env` backups to 2026-07-21 proved it **unchanged** — the 2026-08-10 21:56 `.env` edit only added `GITHUB_TOKEN` and two `SBP_*` keys). PaySimple exposes no webhook-config API (probed 11 candidate routes, all 404 / "route does not exist"), so I captured a real delivery off the internal docker bridge with `tcpdump` (read-only, no deploy) and tested it. **The digest was byte-identical to ours apart from letter case:** PaySimple sends `5F0738DD23FE...` while Node's `digest('hex')` returns `5f0738dd23fe...`, and `verifyWebhookSignature` compared the digest TEXT via `timingSafeEqual` (`'5F'` = 0x35,0x46 vs `'5f'` = 0x35,0x66), so it could never match. Fixed by comparing the raw 32 digest BYTES instead of the hex string, decoding the header as hex (either case) or base64 via a new `decodeDigest()` that returns null on a malformed header rather than comparing a truncated buffer. This is the **third** distinct cause of "every PaySimple webhook is rejected", after the `JSON.stringify(req.body)` raw-body bug (2026-07-30) and the `express.raw` Content-Type matcher (2026-07-31), which is why the fix is now encoding-agnostic rather than matching one more exact format.
Verificationproven against the real captured delivery before writing any code — 445-byte body, received `5F0738DD23FE5E19D28E1722F44FF6E8A6CD8CB39B18DD58450AF2B4ED75D233`, our HMAC over the same bytes with the configured secret `5f0738dd23fe5e19d28e1722f44ff6e8a6cd8cb39b18dd58450af2b4ed75d233`: exact-byte match **false**, case-insensitive match **true**, base64 match **false**. So the secret and the raw-body handling were already correct and case was the entire defect. 6 new unit tests; the load-bearing one asserts the UPPERCASE digest verifies, and it **fails against the unfixed code** (baseline run of the new tests against the old service: 4 failed / 18 passed; with the fix: 1 failed / 21 passed, the 1 being a pre-existing unrelated `findCustomerByEmail` fixture failure). Negative cases kept: right-length-but-not-hex, too-short, empty, wrong payload, and wrong secret all still reject. Full backend jest with normalized comparison of the failing-suite sets: **28 failing suites both with and without the change, zero regressions, zero newly-passing** (an intermediate run showed 29 — a timing-sensitive suite, not this change). `tsc --noEmit`: 15 errors with and without, none in `paysimpleService.ts`.
Notes**The existing test suite is exactly why this shipped.** `verifies valid HMAC signature` built its fixture with `digest('hex')`, i.e. lowercase, so it exercised a format PaySimple never sends and passed against broken code. A test that generates its own input in the wrong format proves nothing about the real integration; the new uppercase test is the one that would have caught it. **Not fixed here:** why Valentine Obiora (08-03) and ammar albazzaz (08-04) were missed — successful webhook activations sit on either side of them, so those look like individual missed deliveries rather than this total failure, and the container logs for those dates were lost to a redeploy before the investigation. **Also worth flagging:** PaySimple retries hard. The delivery I captured was an event first created **2026-08-01**, still being retried 11 days later, so once this is deployed the backlog should drain on its own; the reconciler is idempotent and `usedPids` prevents any double-link if both paths fire. Separately confirmed while investigating: across **all 16** payments the app has ever linked, **0** landed on the customer id we stored at checkout, so the reconciler's customer-id match path has never once worked in production — which makes the checkout-window path in the companion PR the only mechanism currently capable of linking a payment.
02

**Healed 3 unlinked $199 memberships and closed the two gaps that let them sit unnoticed**

2026-08-12
What changedTaiwo reported one student (Arinze Ohagwu) whose PaySimple payment was missing from the enterprise dashboard. Confirmed and root-caused, then found two more with the same signature. **The defect:** PaySimple's *hosted* payment page mints its **own** customer record for the payer, so the charge's `CustomerId` is not the one our app pre-created at checkout — Arinze's checkout created customer `43728423`, his settled $199 (payment `155621427`) landed on `43728431`, minted by the hosted page 4 minutes later. Activation normally comes from the webhook matching `order_external_id` → `subscriptions.payment_ref`, which works (13 subscriptions activated fine); when a delivery is missed, `appPaymentReconcileService` is the safety net — and it could never heal these, for two reasons. (1) It drew candidates from `enrollments.paysimple_customer_id`, but `startCheckout` wrote the customer id **only onto the subscription row**, so 62 of 86 pending checkouts were invisible to it (the candidate query saw **8** rows where the corrected one sees **31**). (2) Even reading the subscription's id would not have matched, because the charge carries the hosted page's customer, not ours. Fixes: `startCheckout` now reuses a customer id we already stored (enrollment, then prior subscription) before minting a new one — `findCustomerByEmail` can only ever return null because PaySimple ignores its own `?email=` filter (probed live: **200 rows returned, 0 with a matching email**), which had turned `findOrCreateCustomer` into create-every-time and gave Arinze's four attempts four duplicate customers — and mirrors that id onto the enrollment (best-effort; the payment link is already valid, so bookkeeping must never fail a live checkout). `reconcileAppPayments` gains a second match path, `matchesAppCheckout`, for the hosted-customer case.
Verification`tsc --noEmit` — **15 errors with the change, 15 on an unmodified `origin/main` baseline, none in either changed file** (the 15 are pre-existing: `axios`/`playwright` are imported but absent from `package.json`). Full backend jest: **28 failed suites / 41 failed tests both with and without the change** (same pre-existing missing-module failures), **7253 passing with vs 7239 baseline — +14, exactly the tests added**, 0 regressions. New scope-guard tests assert the safety-critical negatives: a same-amount charge from a different payer, an amount we never asked for (bootcamp $250), a charge outside the window, and a person with no app-originated checkout are all **rejected**. New checkout tests cover customer reuse, the enrollment mirror, and that checkout still returns `ok` when the mirror write throws. The corrected candidate SQL was executed read-only against the live prod schema before shipping (31 candidates / 24 with pending checkouts). Data heal ran on prod through the normal `activateByRef` path: all 3 now `paid` / `standard` / `member`, routed into "Cohort - July 2026", subscriptions `active` with payment ids linked and billing anchored to the real payment date (Arinze 2026-08-11 → 2026-09-11); his 3 duplicate checkouts canceled. A re-run of the detection sweep afterwards returned **0 remaining, $0.00**.
Notes**Scope doctrine preserved and deliberately reasoned about.** Revenue counts only app-originated payments, and the standing rule forbids matching PaySimple charges by amount/email — that rule exists because an earlier amount-matching ledger over-counted $6,664 against a true $3,038. The new path B does **not** relax it: the thing that brings a payment into scope is still **our own pending subscription row** (our app recorded that it started that checkout, for that exact amount, minutes earlier); the payer email only decides *which* of our pending checkouts a charge belongs to, and never qualifies a payment on its own. Both the file header and the tests state this explicitly so it is not misread later as a regression to email matching. **Revenue impact:** the dashboard was understating by **$398** — Arinze ($199, `payment_status` still `pending`) and ammar albazzaz ($199, marked paid but `amount_paid` NULL, which fails the `amount_paid > 0` filter in `revenuePaymentsService`); Valentine Obiora's $199 was already counted and only needed the payment id linked. **Only Arinze suffered real customer harm** — he paid on 08/10 and was still an Explorer being prompted to subscribe two days later, which is why he retried checkout three times. He was charged exactly **once**; there is no double-billing to refund. **What is not fixed:** the missed webhook deliveries themselves. Container logs for 08/10-08/11 were lost to a redeploy before this investigation, so the cause of the missed callbacks is unproven — the reconciler now heals them within 20 minutes either way, but if the miss rate is climbing, that is a separate investigation and this change would mask it. Worth adding a metric on `linkedByCheckoutWindow`, which is now counted separately in the summary precisely so a rising number is visible.
