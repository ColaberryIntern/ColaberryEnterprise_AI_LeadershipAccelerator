## What the ticket asked for

> When Ali chooses "assign this existing tool", the agent gains exactly that tool, the record names
> who approved it and against which request, and nothing else about the agent changes.

AF11.2 finds the candidate; AF11.3 lets him choose it; this is the write.

## The architecture was already decided, by two structural tests

Neither of these is a style preference. Each is a test that fails on the edit it forbids.

`toolRequestDecisionGrantsNothing.test.ts` reads the seven AF11.3 decision files by name and
asserts that none of them writes `tools_granted`, `autonomy_level`, `enabled` or
`abac_mode_override`, and that none imports a module that could. Its own header says what AF11.4
should do about that:

> AF11.4 will legitimately need to read a decision, and when it does it belongs on this list —
> which is the point. Widening the allowlist is a visible, reviewable line in a diff.

`agentToolGrantWritesOneColumn.test.ts` pins the importer set of AF3.5's grant service for the
converse reason.

So AF11.4 is **one new module that imports both**, and each allowlist gains exactly one line in
this change. Wiring the grant into the decision service instead would have broken the first pin
honestly; mounting the route on `toolRequestDecisionRoutes.ts` would have broken it *dishonestly* —
that pin matches module paths against a vocabulary, and `assignExistingToolController` does not
match it, so the test would have stayed green while the property it protects stopped holding.
Hence a route file of its own, and an assertion that the decision router never mentions this
handler.

## Three decisions worth stating

**The grant call carries no body.** Not even the tool name. The tool comes from the decision that
was just recorded, the agent and capability from the request the intern filed, the approver from
the verified token. So the console cannot record "assign A" and grant B. An empty `.strict()`
schema makes that impossible rather than merely unintended, and a body carrying `tool_name` or
`autonomy_level` is refused by name with a 400 instead of being silently dropped behind a 200.

**Two transactions, not one.** The decision commits first. If the grant is then refused — most
often an unconfirmed capability — the decision still stands and the refusal says why it could not
be carried out. Collapsing them would mean a refused grant erased a decision Ali did make, and the
console would invite him to make it again.

**The caller must be the person who decided.** The grant records one approving human. If anyone
who can reach the route could execute somebody else's decision, that record would name the decider
while a different person acted — and AF3.5's "the proposer does not approve their own grant" check
would then be applied to someone who did not act. One identity on both halves. Letting a second
person execute a decision is a real thing somebody may want later; it is a decision with an owner,
not a default.

## Acceptance criteria — 5 of 6 met, and the sixth is not meetable

1. **The grant writes `tools_granted` and nothing else, verified by reading the full row back and
   diffing it** — **MET**, and not by a test written here. AF3.5's service already does that
   read-back diff *in the production path*, inside the transaction, and throws
   `ToolGrantTouchedMoreThanToolsError` if anything else moved. This path reuses it, so the
   invariant holds for this caller by construction.
   `assignExistingToolGrantsOneThing.test.ts` additionally asserts that no AF11.4 file writes any
   of the four columns itself, names `ai_agents`, or calls a reclassifier.

2. **After the grant the resolver reports `usable: true`** — **NOT MET, and not meetable.**
   Measured, not assumed. `agentEffectiveAccessService.computeUsable` returns false immediately
   unless `registered` is true, and `registered` is the per-agent GRANTS table or the agent's own
   OpenAI tool-schema array — `toAgentKey` resolves exactly three names and
   `registeredHandlerToolNames` answers for exactly two. **`tools_granted` contributes to
   `grantedVia` and to nothing else.** So for all ten domain agents `usable` is false whatever is
   granted, and `send_email` — which has a real handler and a real gate — appears in no per-agent
   source at all, so it is unusable by this resolver's reckoning even for Reese. Asserted in
   `agentEffectiveAccessService.test.ts` with a positive control proving the resolver *can* say
   true. The service therefore **reports** the verdict rather than requiring it.

3. **Positive control: a neighbouring ungranted tool still reports unusable** — **MET**, against
   the real gate rather than the resolver. Ali's own correction named the right target:
   `agentEmailTool.readAgentGate` reads `tools_granted` and is a real check on a real action.
   `assignExistingToolMakesTheRealGateAnswer.test.ts` drives it: before the grant
   `reason: 'tool_not_granted'`; after it, `granted: true` and
   `reason: 'autonomy_insufficient:observe'`; granting the neighbour instead leaves `send_email`
   refused exactly as before.

4. **The record names the approving human, the request it answers and the tool** — **MET.** The
   new `change_request_id` column is what makes "which request did this settle" answerable. It is
   added by `ALTER TABLE ... ADD COLUMN IF NOT EXISTS`, because `CREATE TABLE IF NOT EXISTS` is a
   no-op against the table AF3.5 already created in production — and it is named in
   `REQUIRED_COLUMNS`, so a deploy where the ALTER did not run fails at boot rather than at the
   first assignment.

5. **Granting a tool for a capability in draft is refused** — **MET**, by AF3.5's contract
   (`capability_not_confirmed`), which already has both-direction coverage. This change asserts
   the propagation: the refusal reaches the console as a 409 with `code: grant_refused` in the
   grant's own vocabulary, not restated in a second one. **See the production caveat below.**

6. **Exactly one code path writes `tools_granted`** — superseded, which Ali's own 3 Nov correction
   did. There are **two** writers of `ai_agents.tools_granted` and there were two before this
   change: `agentToolGrantService.ts:228` and the boot seed at `agentRegistrySeed.ts` (which now
   unions in recorded grants through `seedToolPreservation`). The revised criterion — *the grant
   does not trigger reclassification, proven structurally* — is **MET**: AF3.5's structural test
   pins it, and AF11.4 adds no reclassifier call and no new writer.

## The finding that matters most for production

**Nothing can be granted through this path in production today, and the reason is not in this
code.** AF3.5's gate requires a *confirmed* capability. AF11.0 built the confirmation store, and
`capabilityConfirmationService` still has **no importer** — no route, no controller. So all 443
capabilities remain draft, `effectiveValidationState` returns `draft` for every one of them, and
every grant is refused with `capability_not_confirmed`.

That is a gap in AF11.0, not in AF11.4, and AF11.4 is correct to refuse: a tool is granted on the
strength of a capability somebody proved by hand and recorded. But it means the first real use of
this screen will be a refusal, and the sentence it shows will be the right one.

## AF12.10 - a WIP branch could turn main's secret scan red, and the gate had no proof it could fail

- [x] Secret scan: stop an unmerged branch reddening main, and make the gate prove it can fail
  - Date: 2026-11-07
  - Session: CC-20261106-r6k4
  - What changed: dropped `push` from the `full-history` job's condition, and wired the existing
    planted-secret self-test into both CI jobs as a new `scripts/secret-scan-selftest.js`
  - Verification: self-test exits 0 against the real `.gitleaks.toml` with 4/4 planted secrets
    detected; MUTATION-TESTED to exit 1 with 0/4 detected against a deliberately blinded config;
    workflow YAML parses and both job conditions read back correctly
  - Notes: see below - half of what the ticket asked for was already done by someone else, and
    one thing the ticket implied turned out to be false

**The ticket's own fix had already landed, by the right person.** AF12.10 proposed (1) an
allowlist entry, owned by PR 3669's author, and (2) narrowing the sweep. Option (1) shipped in
`8408d599` on 4 Nov ("clear the last scan hit") and PR 3669 merged on 5 Nov, so main's secret
scan has been green since. Verified: the last several `Secret scan` runs on main are SUCCESS, and
`texasFormsRules.ts` is now ON main with the statute identifiers still in it.

**But the structural cause was untouched, so it would have recurred.** `full-history` ran on
`push` to main while scanning `--log-opts="--all"`, i.e. every commit on EVERY REF. That is why an
unmerged branch's false positives failed main's check while the PR owning them was green. The
job's own comment already said it runs "on a schedule and on demand rather than per-PR" - the
condition contradicted the comment. Removing `push` makes the code match its documented intent.

**Coverage was deliberately NOT narrowed.** The ticket's option (2) was to scan fewer refs. That
would permanently lose the ability to find a secret sitting on a branch nobody merged, which on a
PUBLIC repository is still world-readable. Instead the sweep still walks every ref and simply
stops gating unrelated merges: it reports on the Monday schedule or on demand. Anything new
reaching main is still blocked by the `pull-request` job, which runs on push to main and scans
the pushed range. Logged as a deliberate deviation from the ticket's literal wording.

**The acceptance criterion's second half was unmet, and is now automated.** The ticket required
"a deliberately planted test secret still fails it". `scripts/lib/gitleaksSelfTest.js` already
existed with exactly those fixtures, but was only ever called by the INTERN-REPO audit
(`internRepoSecretScan.js`) - this repository's own gate had no such control. Both CI jobs now run
it first, including the scheduled sweep, because a scheduled "clean" from a blind detector is the
most dangerous result of all: nobody is watching a green cron run.

**A suspicion I had was WRONG, and measuring is what caught it.** The self-test's header warns
that this repo allowlists `process\.env\.[A-Z0-9_]+`, which on a line like
`const key = process.env.OPENAI_API_KEY || '<a real key>'` would suppress the finding AND the live
key beside it. I expected that fixture to be missed under the current config and was ready to
report it as a hole. Measured instead: it is DETECTED, because the `colaberry-generic-assigned-secret`
rule (entropy 3.5) now catches it. No such hole exists today.

**The control is falsifiable, which is the only reason it is worth anything.** Against a config
with `useDefault = false` and one `(?s).*` allowlist regex, all four planted secrets go unseen and
the step exits 1 with an actionable message. The blinded config lives in the session scratchpad
and is NOT committed. `.gitleaks.toml` was restored from git afterwards and confirmed
byte-identical.
