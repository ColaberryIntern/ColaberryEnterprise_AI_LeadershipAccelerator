### Two decisions worth recording

**Measurability and health are two chips, not one.** A revenue bet has two independent
properties: whether the funnel can count it, and whether it is still alive. "Measured
zero" and "the pipe is empty, kill it in November" are different facts; a single chip
would silently pick one. So `status` answers "can I trust this number?" and `verdict`
answers "is this bet alive?". A bet can be measured and dying at once.

**The API is mounted under `/api/admin/commercialization/revenue-room`, not a new prefix.**
`mgmtSectionGate.ts` is deny-by-default: an unmapped prefix 403s a scoped revenue identity
with nothing in the response explaining why, and `adminNav.ts` carries a matching list a
test asserts agrees with it. Reusing the already-classified prefix avoided touching two
gates to add one read-only page. The page path is still `/admin/revenue-room`; the API
prefix and the page path do not have to match.

### Wiring that already existed

`getFunnelSnapshot()` had been built and tested since C8.4 but had **no route** — it was
observable only by inferring it from the hypothesis response, which reports verdicts
rather than stage counts. It now has one. A service readable only as a side effect of
another endpoint is one nobody can check against the database.

### The government card refuses to call itself a pipeline

Per the R2 diagnosis, `decision=approved_bid_pursuit AND status=active` flagged 12 rows
including a test row, a duplicated RFP and three rows with no project. The card therefore
reports the flag count as a **proxy** and states what the count contains: how many of the
distinct projects behind it hold a proposal document (counted DISTINCT, so a duplicated
RFP is not two opportunities), how many rows have no delivery project, and that
`gov_submission` is empty so nothing has ever been submitted. An assertion fails the build
if anyone promotes this card to `live` while no column records a human confirmation.

### A defect the gates caught that green tests hid

The first run of the test-file typecheck found **35 TS2339 errors in the new service
test**, from a single cause: a `find()` helper typed as
`{ cards: Array<{ key: string }> }`. ts-jest transpiles without typechecking, so all 36
tests passed while the compiler believed every card had only a `key` — the assertions ran
but were never type-checked. The helper now names the real `RevenueRoomBoard` and
`InitiativeCard` types.

This is the exact failure the test-typecheck gate exists for, and it would have shipped
green. Worth remembering that in this repo a passing jest suite is evidence about
behavior and says nothing at all about types.

### Local-environment traps hit on the way, for the next person

- **The root `node_modules/typescript` in a worktree is 4.9.5**, while `backend` declares
  `^5.7.3`. Running the backend typecheck with 4.9.5 yields **267 syntax errors inside
  `node_modules` type declarations and none in repo source**. That signature — all errors
  inside `node_modules`, all syntax-level — means the compiler is wrong, not the branch.
  Use `frontend/node_modules/typescript` (5.9.3).
- A worktree whose `node_modules` is junctioned from an older tree is missing dependencies
  that are declared on main. Here that was `@dnd-kit/*` (10 frontend errors) and
  `@anthropic-ai/sdk` (2 backend errors), all in untouched files. The `@anthropic-ai/sdk`
  pair is also the whole gap between the measured 402 and the frozen baseline of 400.
- `react-scripts` is hoisted to the **workspace root**, not `frontend/node_modules`. Run
  it as `node ../node_modules/react-scripts/bin/react-scripts.js`. Invoking it by bare
  name fails with "not recognized", and piped through `tail` that failure still reports
  exit 0 — a non-run reading as a pass.
