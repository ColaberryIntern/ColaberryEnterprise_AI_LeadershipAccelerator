**ESC-1: `organizations.owner_enrollment_id` relaxed to nullable**

2026-08-23
What changedone statement — `ALTER TABLE organizations ALTER COLUMN owner_enrollment_id DROP NOT NULL` — plus `organization_type` guaranteed present and backfilled to `management_account` for every existing row. `models/Organization.ts` updated to match (`allowNull: true`), because Sequelize enforces `allowNull` in application code and a model left at `false` would reject a client organization before the relaxed database column was ever reached.
Verification`deliveryModels.test.ts` — **29 tests**. A client organization with a null owner passes model validation; a management account with an owner still passes; and a **negative control** proves validation is real (a row missing a still-required field rejects), so the first two cannot pass vacuously.
Notes**Gate 0's C-02 recommendation was wrong on this and I corrected it mid-build.** It said to drop the unique constraint alongside `NOT NULL`. That was wrong twice over. First, PostgreSQL treats NULLs as distinct in a unique index, so any number of null-owner client organizations were *already* permitted — `NOT NULL` was the only thing blocking them. Second, the constraint is load-bearing: `orgService.registerManager()` is idempotent via `Organization.findOrCreate({ where: { owner_enrollment_id } })`, and findOrCreate is only race-safe because a concurrent duplicate insert hits a unique violation Sequelize catches and converts back into a find. Dropping it would have let two simultaneous registrations for one manager create two organizations — the "works once, breaks on the second run" class root `CLAUDE.md` calls a production defect. A test now pins that the constraint is **not** dropped. Related: the real index is named `organizations_owner_enrollment_unique` (created by the inline DDL in `server.ts`), not Sequelize's `_key` convention, so the drop I originally wrote would have missed anyway.
