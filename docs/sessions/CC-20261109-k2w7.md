## M20. Root-cause the parallel-load flake

Ticket: https://app.basecamp.com/3945211/buckets/7463955/todos/10411539488

Not a code change yet; recording the evidence because it contradicts the ticket's standing
hypothesis on three measurable points. The ticket forbids refactoring ahead of a reproduction,
so nothing has been refactored.

- **No timeout exists in CI history.** 67 `Backend unit tests` job logs from runs that FAILED
  were downloaded and searched across 2026-09-01 to 2026-11-09 — the ticket's entire lifetime.
  Zero contain jest's `Exceeded timeout of N ms`. Every failure is a named assertion failure
  in a named suite. A control string present in every backend job log was asserted in each
  scan (65/67; 2 logs had expired and are recorded as unknown, not clean), because a scan
  reading the wrong thing would otherwise report a reassuring zero. The first version of that
  scan DID report zero from 0 logs read, and the control is what caught it.
- **The runner is 4 vCPU, not 2.** The repo is public (`"private": false`), so GitHub's
  standard Linux runner gives 4. CI passes no `--maxWorkers`, so jest computes
  `max(availableParallelism() - 1, 1)` = **3**, not the 1 a 2-core box would give. This
  matters in both directions: at `maxWorkers <= 1` jest runs IN BAND
  (`testSchedulerHelper.js`, `oneWorkerOrLess`) and no two suites are ever concurrent, which
  would make a contention hypothesis impossible. At 3 it forks, so contention is available —
  but the ceiling on concurrent repo-wide greps is 3, the worker count, not the 5 the ticket's
  comment states.
- **The grep is not the expensive thing.** Running `personViewRoles` alone: the git-grep test
  took 128 ms warm, while a single pure-looking test, "gives one subject key for one anchor",
  took 4,156 ms cold and 1,467 ms warm. That is the first test to touch the real import graph,
  which is the eager-Sequelize mechanism the ticket names — attached to a different test than
  the comment supposed. The earlier 858-2,303 ms grep measurements were taken in the OneDrive
  working tree, which is not what CI uses.
- **The suite is 4x the size the config claims.** `jest.ci.config.ts`'s docblock says 588
  suites and 8,229 tests. A full local run measured **2,543 suites and 41,980 tests**.
- **Not reproduced locally.** Full CI-config suite, `--maxWorkers=3`: 284 s, 0 timeouts. Three
  consecutive runs under synthetic load (13 cores occupied, leaving ~3) are the remaining
  evidence. The only 3 local failures are Windows line-ending artifacts in byte-identical
  render checks, unrelated to timeouts.

Harness kept out of the repo, in the session scratchpad: `m20_repro.js`, `scan_ci_timeouts.js`.
