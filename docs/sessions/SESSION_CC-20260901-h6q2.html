Projects "next step" card: ship the stylesheet the route actually needs

2026-09-01
What changedOne import. `ProjectsNextStepHero.tsx` now imports `components/timeline/timeline.css` directly. Since 6c48a4d0 (2026-08-13) the card reuses the Classroom's `.tl-nextweek` markup, and every rule for it is written `.tl-de <selector>` in timeline.css. That commit correctly added a `.tl-de` wrapper — but `.tl-de` only matters if the stylesheet is loaded, and `/portal/projects` is its own `lazy()` chunk in `routes/portalRoutes.tsx` with nothing in it importing timeline.css. On a cold load the card had no rules at all. Same fix `CardComments.tsx` and `ReflectionReview.tsx` already carry for the same reason; webpack dedupes, so it costs nothing at runtime. Added `ProjectsPage.cssChunk.test.ts`, which walks relative imports from every lazy portal route and fails when a route renders `tl-`/`tld-` classes without timeline.css in its own graph.
Verification**Reproduced and fixed visually, not just asserted.** The real component was transpiled and server-rendered against the real `projects.css` / `TodayShell.css` / `timeline.css`, then screenshotted in Chromium. Without timeline.css the computed styles are `display:block`, rail `flex-basis:auto` and transparent, `Open` at the user-agent `rgb(240,240,240)`/black, progress bar `height:0px` — pixel-for-pixel Ali's production screenshot. With it: `display:flex`, a 240px `#F8F8F7` rail, `Open` at cherry `#FB2832` on white, an 8px progress bar. New test proven red before green: with the import commented out it reports `ProjectsPage renders pages/portal/projects/ProjectsNextStepHero.tsx but its chunk never imports timeline.css`. 29 suites / 359 tests pass across the projects suites. `tsc --noEmit` clean in `src` (9 errors, all `@types/d3-dispatch` parse noise from the local TS 4.9.5 junction — the documented artifact, not code).
Notes**Only one route is affected** — the new test's sweep across every lazy portal route named `ProjectsPage` and nothing else. Worth recording why review missed this: navigating to Projects *from the Classroom* loads timeline.css into the page and the card looks perfect, so the bug only appears on a cold load or a direct link. The existing `.tl-de` scope guard (`today/__tests__/TodayPlan.cssScope.test.tsx`, written after the CAPE black-block incident) could not have caught it either — it reads timeline.css off disk and injects it into jsdom, so it proves selector scoping while being blind by construction to whether the bundle ships the file. That is why this is a new test rather than an extension of that one. **CI does not run frontend jest tests** (only `frontend-typecheck` and `frontend-build`), so this guard only fires for someone running the frontend suite locally; making it a CI gate would mean touching the workflow and is out of scope here.
