- [x] The migration that moves the existing 513 stories onto the ladder
  - Date: 2026-10-31
  - Session: CC-20261028-w7k5
  - What changed: new `services/agentDomain/agentDomainAutonomyReleaseMigration.ts` decides the
    whole migration as a pure function of current state, and new
    `scripts/migrateAgentDomainAutonomyReleases.ts` applies it — `--apply` gated, one transaction
    per domain, four exported SQL statements. The two acceptance backfills had their
    `release_key IN ('r0','r1')` / `= 'r2'` predicates replaced with `story_kind` predicates that
    also accept the old release key where `story_kind` is null, so they stay correct whether or not
    the migration has run.
  - Verification: 24 unit tests (pure, no database) and 18 integration tests against a real
    Postgres 16, with a negative control per statement. **Then run against a read-only snapshot of
    the actual production rows**: 100 releases created, **513 re-parented, 964 inserted, 0
    unrecognised, all 56 verified rows accounted for**.
  - Notes: Three things only the production snapshot could have told me.

    **17 stories would have been orphaned.** The migration matches an existing row to a generated
    story by `story_id`, and 17 production rows hold a `story_id` truncated by the old
    `varchar(60)` column — `curriculum.CAP.certification_item_rubric_review_and_improvem` where the
    generator produces `..._improvement`. Every fixture in the test file generates its ids at
    today's width and therefore matches by construction, so the unit tier was green and would have
    stayed green. Against the real rows the planner reported 17 strangers: it would have left them
    under a superseded release and inserted a fresh duplicate of each beside them. The migration
    now matches the wide id first and the 60-character form second, and repairs the stored value as
    it re-parents. The checker that found it ships as
    `backend/src/scripts/checkLadderPlanAgainstSnapshot.ts`, because the next migration of this
    shape should start by running it.

    **The first version of that fix refused, correctly.** Four generated ids share the prefix
    `curriculum.CAP.module_and_artifact_drafting_for_human_approv` — a capability story and its R0,
    R1 and R4 rung stories. The ambiguity is only apparent, because the rung stories did not exist
    while the column was 60 wide, so candidates are narrowed to the kinds that did. The refusal
    stays for a genuine collision between two pre-ladder stories.

    **The `IS DISTINCT FROM` guard suppresses the type error that caught the Phase 1 defect.**
    Measured directly against Postgres 16: `UPDATE t SET vc = $2, tx = $2 WHERE id = $1` is refused
    with "inconsistent types deduced for parameter $2", but add `AND vc IS DISTINCT FROM $2` and it
    is **accepted** — comparing the parameter against a typed column pins its type, the
    contradiction resolves, and the statement writes one column's value into another and reports
    success. That guard is on every parameter of the re-parent statement because it is what makes
    it idempotent, so this statement gained replay safety at the cost of the gate that caught the
    same class of defect a fortnight ago. There is no way to have both. Both halves are now tests,
    and the protection is an assertion on each column's value rather than trust in the server.

  plan and not the SQL, which is why the integration tier exists.

  — are untouched. An owner decision, deliberately left open by the design.
- **Phase 3** (wiring `evaluatePromotion()`, 22 refusal codes and still zero callers, plus the tool
  grant endpoint in AF3.5) is not started. It needs a rung to be promoted from, which is what this
  phase creates.
