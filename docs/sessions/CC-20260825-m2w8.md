### Leads Export CSV: honor the filters the operator actually applied (2026-08-25)

  - Date: 2026-08-25
  - Session: CC-20260825-m2w8

On the page, **`buildFilterParams()`** is now the single source both `fetchLeads` and `handleExport` read. Also declared `temperature` on the params interface, which was being read through `(params as any)` and would have silently vanished the first time a typed object was spread into that call.

### Open-house and training-site leads never reach GHL: root caused, escalated, not fixed (2026-08-25)

- [ ] **Diagnosed why 490 leads are invisible to Cora Voice and admissions, and stopped short of the fix on purpose.**
  - Date: 2026-08-25
  - Session: CC-20260825-m2w8
  - What changed: **Nothing in code, deliberately.** Kes reported that leads from the open house and the training site never appear in the "Colaberry School of Data Analytics" GHL account, so neither Cora Voice nor the admissions team can reach them. Root caused to **two independent blockers**, and the second is the reason no code shipped. **(1) The sync is never invoked.** `enrollmentService.createExplorerEnrollment` writes the open-house lead with a raw `Lead.findOrCreate` and never calls `syncNewLeadToGhl`; `externalLeadIngestService.ingestExternalLead` does the same for the training site; and `leadService.createLead`, the shared helper the generic form ingest funnels through, has no GHL call either. So **inbound web forms are unsynced as an entire class**, not just these two sources. Every existing GHL call site is admin-add, calendar booking, Apollo, CSV import, Maya, the Synthflow webhook, campaigns, automation or the scheduler. **(2) The single stored key points at the wrong sub-account.** `ghlService` uses one global `ghl_api_key` and never reads a location id. Calling `GET /v1/locations/` with the live key returns exactly one location: `JFWwp8q7l6T12NWTIOKG`, **"Agent Cory AI"** - not School of Data Analytics. The `ghl_location_id` that `settingsService` writes is dead config, read by nothing. Escalation written to `tmp/escalation.json` (not committed; `/tmp` is scratch).
  - Verification: Production evidence rather than inference. `accelerator_prod.leads` grouped by source: **`open_house` = 490 rows, 0 with a `ghl_contact_id`**, newest one today. `training.colaberry.com` across its three spellings = 3 rows, 0 synced. The control group proves GHL itself is healthy and the failure is specific to these paths: `apollo` **1,981 / 2,102** synced, `ccpp_alumni` 679/689, `ai-pilot-cold` 99/99, `strategy_call` 4/4. `system_settings` reads `ghl_enabled = true`, `ghl_api_key` set, `test_mode_enabled = false`, which rules out the disabled-flag and test-mode-redirect hypotheses outright.
  - Notes: **Not fixed on purpose, and that is the substance of this entry.** Wiring the sync is a two-line change. But with blocker (2) unresolved it would create roughly 490 contacts in the wrong CRM sub-account, and those contacts feed Cora Voice outbound dialing. That is an irreversible, outward-facing write to a live CRM and a live dialer against a population nobody has reviewed, which CLAUDE.md puts on the escalate side of the line rather than the proceed side. Three decisions are needed before code: which sub-account is genuinely the intended destination; whether to build **per-source account routing** (recommended) rather than repointing the single key, since repointing would silently move Apollo, campaigns, Synthflow and calendar bookings into the new account alongside the open-house leads; and whether the 490 already-captured leads get backfilled or the fix is new-leads-only, with a dry-run count first either way. Worth adding `ghl_sync_status` / `ghl_synced_at` to `Lead` when this is built, because today the only sync signal is `ghl_contact_id` being non-null and a failure is otherwise invisible. **Incidental security finding:** GHL's `GET /v1/locations/` returns each location's **full `apiKey` in the response body**, so any script that logs that response leaks a live credential.
