## Findings

### 1. The brief was "sync more than once a night". Measured, frequency was never the problem.

There is no nightly sync and no scheduled verification job anywhere in the codebase. The live
cadence is per commit, through the GitHub push webhook, and it works: 2,473 deliveries since
16 August. Adding frequency to a mechanism that already fires on every push would have been
motion.

What the per-commit cadence cannot see is a push that never comes. A project whose hook fires
verifies dozens of times a week; a project whose hook was never registered verifies never, and
the platform could not distinguish that from a project with nothing to do. So this phase is a
floor and a detector, not a faster clock.

### 2. The "stale tail" is not a tail. It is two thirds of the cohort.

Measured on production 2026-11-18, of 43 projects bound to a connection and carrying a published
plan:

| Last delivery | Projects |
|---|---|
| Never | 3 |
| Over 60 days | 7 |
| 30 to 60 days | 14 |
| 14 to 30 days | 4 |
| Delivering | 15 |

**28 of 43 have not been heard from in 14 days.** The phase ticket described this as "a real stale
tail nobody was told about" and named three repositories; the real figure is the majority. Three
have never delivered a single webhook while bound to a project with a published plan:
`fbeig2020-cloud/kashmiri-islamic-hub`, `amr23-sudo/DataBuddy`,
`tanmayikatamaraja-web/architect-workspace`.

**Every one of the 28 is on an ACTIVE enrollment**, so scoping the finding to live enrollments
removes nothing, and it never could: the enrollment table holds 1,379 active against 64 withdrawn,
which makes `active` the default state rather than evidence that anybody is working. There is no
liveness signal there to lean on.

That changed what the report should say. A finding naming 28 projects every run is noise, and
noise gets tuned out inside a week, which is this workstream's own failure one level up: a report
that looks like oversight and produces none. Raised with Ali against these numbers rather than in
the abstract; he chose buckets plus the ratio, naming only the never-delivered, with the full list
behind an endpoint.

### 3. The sweep's obvious ordering column was stomped, and would have made it lie.

"Oldest pass first" wants a per-project timestamp of the last verification. `student_tasks.updated_at`
is the obvious column and is unusable: **93 production rows share one identical value**, and three
further groups of about 50 share theirs, because a bulk write overwrote them. Ordering by it would
have made the sweep pick near-arbitrary projects while reporting that it picked the stalest, which
is worse than not sweeping, because the log would have looked right.

The signal that is real is `verification_json ->> 'checked_at'`, written by the verifier itself on
every pass: genuinely distinct per-project values from 20 August to 18 November. **34 projects with
open stories have no value at all**, which is the true head of the queue, and `NULLS FIRST` puts
them there. The production run of the shipped query returned a first batch of 12 that were all
never-verified, one of them with 100 open stories.

Because the ordering lives in SQL, it is asserted **as text**. No behavioural test over mocked rows
can catch an `ORDER BY` that reads the wrong column, since the mock returns whatever order it is
given, and the mutation run confirms both the column and `NULLS FIRST` are watched.

### 4. A scheduled job in this repo must have a row to be tracked against.

`cronRegistryReconciliation` enforces that nothing a timer can fire runs without an `ai_agents`
seed row, and the new cron entry had none, so "every run is tracked against nothing". Seeded
ENABLED on the `DeptCampaignPerformanceAgent` reasoning rather than `MarketingPublishingWorker`'s:
there is no blast radius to hold for review, because the sweep's own flag is the gate and defaults
to off, so with `STORY_VERIFICATION_SWEEP` unset a tick returns before it queries anything. The
row makes the job trackable; it does not switch it on.

### 5. My own A0 tripwire pinned line numbers, and an unrelated edit broke it.

Adding an import to `healthReportService.ts` moved its `ArtifactDefinition` reader from line 49 to
50, and `artifactDefinitionReaderScope.test.ts` reported the shift as reader drift. A false drift
report on a gate like that is worse than no gate: the next person sees a red suite about twenty
readers and learns to re-run it with the numbers updated.

It now counts readers **per file**, which keeps every bit of signal that matters. A new unscoped
reader in a listed file still fails because the count rises; one in a new file still fails because
the key appears; scoping one still fails because the count drops. Only the line number, which
nothing depends on, may move, and the failure output still prints exact sites. Two `it.skip` blocks
I had added to keep the old pinned lists "for provenance" were deleted along with a test that
re-asserted the same count: a skipped test is one nobody maintains, which is the same dead-cover
habit this workstream has been removing elsewhere.

### 6. The runbook said there is deliberately no webhook. There has been one for three months.

`skillRunbookCoverage` requires the runbook a human reads to know about every module in the
pipeline, and the two new modules were in neither it nor its allowlist. Writing the entry turned up
something worse than the omission: the runbook still stated "There is deliberately **no webhook**",
and `githubPushVerification` has taken 2,473 deliveries since 16 August calling the same verifier.

A runbook that contradicts the live system on its central mechanism is exactly what the coverage
ratchet exists to prevent, and the ratchet could not see it, because that sentence names no module.
Corrected in place and marked as a correction, so a reader who remembers the old claim learns that
it changed rather than quietly reading different words.

### 7. Running the mutation suite beside a full test run produced 14 false failures.

The first `jest.ci.config.ts` run reported 18 failing suites. Run again with nothing else on the
machine, the same commit reported 4, and the extra 14 were long-running suites timing out under
contention (one took 98 seconds). Worth recording because the first number looked like a serious
regression and was an artefact of how it was measured.

## What A2b does not claim

- **Nothing was deployed. No row was written to any database.** Every production query in this
  session was a read-only SELECT with the pool closed.
- **Both halves are off by default.** The sweep does nothing until `STORY_VERIFICATION_SWEEP` is
  set, and its middle mode calls no verifier. The silence finding is a report and changes nothing.
- **The sweep has never actually run.** Its selection query was executed against production as a
  read, and its behaviour is covered by unit tests and mutations, but no tick has verified a real
  project. The ticket's acceptance, disabling a test repository's webhook and watching the sweep
  pick it up within the hour, needs the flag on and is a step for whoever enables it.
- **The 28 quiet projects are a finding, not a fix.** Nothing here contacts a student, re-registers
  a webhook, or repairs the three that never delivered. It makes the silence visible.
- `verifyBuildFromRepo` awards XP and latches stories complete, so switching the sweep to `on`
  will produce awards across projects dormant for weeks. That is why the middle mode exists and
  why the default is off.
