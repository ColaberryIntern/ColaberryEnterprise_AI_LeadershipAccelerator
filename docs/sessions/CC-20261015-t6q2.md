# CC-20261015-t6q2 — The first live airing, and the defect it found

## What happened

The first private airing of Colaberry Live ran in production on 15 October 2026, 10:05 to
10:25 AM Central. Live video travelled Zoom to Cloudflare to the Colaberry player, and two
colleagues watched it on their own machines.

**It found five defects in twenty minutes.** This commit fixes the one that made live viewing
unusable.

## The defect

Two viewers reported, independently, that the audio kept repeating. Swati: *"the last lines
keeps repeating."* Kesetebirhan: *"Yes, I just confirmed that."*

The cause was one line in `broadcastPlaybackAdapter.ts`:

```ts
const resumeAt = isRenewal ? media.currentTime : 0;
```

A playback credential lives 120 seconds, so the adapter renews it roughly every 100. Renewal
swaps `media.src`, which reloads the element, and the adapter then restores the viewer's
previous position on `loadedmetadata`.

**That is correct for a replay and wrong for live.** A replay has a stable timeline, so
restoring puts the viewer back where they were. A live manifest restarts its timeline on
reload, so restoring an old `currentTime` seeks *backwards* into the DVR buffer. Every
renewal. Forever. The viewer never reaches the live edge again.

## The fix

The server now says whether the stream is live, and the client stops guessing.

- `GrantResponse` gains `is_live`, set from `occurrence.editorial_state === 'live'` on both
  the Cloudflare and the replay branch of the playback grant.
- The adapter restores position only when `is_live !== true`. Live still resumes playback, it
  just resumes at the live edge, which is the only position on a live stream that means
  anything.

`is_live` is optional, so a client talking to an older server treats the stream as a replay —
the behavior that existed before this field. That is the safe direction: restoring on a
replay is redundant, while failing to restore one would lose the viewer's place.

**Liveness is deliberately not inferred from the url shape.** It would have been easy to check
for `cloudflarestream.com` and call it live, and it would have been wrong the first time a
provider changed or a replay was served from a CDN. The server knows the editorial state; the
client should not re-derive it.

## Evidence

- `a LIVE renewal does NOT seek backwards - the viewer stays at the live edge` — **confirmed
  able to fail.** With the fix reversed to `resumeAt > 0`, this test fails. That matters: the
  test and the fix were written together, so until it was seen to fail it proved nothing.
- The pre-existing `renews before expiry and puts the viewer back where they were` still
  passes. Both must: the replay case is genuinely different and its behavior is correct.
- 52 playback-adapter tests, 33 broadcast-controller tests, frontend `tsc --noEmit` clean.

**Honest note on one test.** I also added `a live viewer who PAUSED is still not un-paused by
a renewal`. It passes with the fix reversed, so it is *not* evidence for this change — it pins
the pause behavior, which is worth pinning, and nothing more. Counting it as proof of the fix
would have been padding.

## What this does NOT fix

Four other defects from the same airing, recorded on the L5.3 ticket and not addressed here:

1. **No audio or unmute controls** on the player. A viewer who lands muted with no unmute
   button leaves and reports the product as broken.
2. **Cloudflare's `/lifecycle` endpoint returns 401** once the input requires signed URLs and
   is broadcasting — it answers fine while idle. This breaks the L5.1 adapter's health check.
   The working alternative, used live during the airing, is
   `GET /accounts/{id}/stream/live_inputs/{uid}/videos`, where the active broadcast reports
   `status.state = "live-inprogress"`. Note the live input's own `status` field stayed `null`
   throughout, so it is not a usable readiness signal either.
3. **`ended_at` is never written** when an occurrence moves to `ended`.
4. **The entry point is not portal-wide** in practice. Testers found the stream through Rooms;
   the portal-wide badge is mounted in the layout route but was not what they noticed.

## The number nobody had

End-to-end latency, Ali speaking to a viewer hearing it: **about 20 seconds.**

This figure did not exist anywhere before. Zoom publishes ~20 seconds only for YouTube,
Facebook and Twitch, and attributes it to *those platforms'* processing time; for a custom
RTMP destination it publishes nothing, and neither does Cloudflare. Ours landing in the same
range is the useful part: the custom path is not materially worse than the named ones.

## Second fix: the health check that reported a live class as dead

The same airing turned up a second defect in the L5.1 Cloudflare adapter, and this one was
the more dangerous of the two because it failed silently in the safe-looking direction.

`readLiveLifecycle` asked Cloudflare whether an input was receiving video by calling
`/lifecycle` on the delivery domain — exactly as Cloudflare's own documentation shows. During
the airing that endpoint returned **401 Unauthorized** the moment the input was actually
broadcasting with `requireSignedURLs` on. It had answered perfectly a few minutes earlier,
when the same input was idle.

**Why that matters more than it sounds.** The adapter's job here is to tell the state machine
whether the provider is ready, and the state machine refuses `go_live` unless it is. So a
healthy class, airing perfectly, would be reported as not ready and refused. An outage reading
as "nothing is live" — the fabricated zero in a different costume.

Cloudflare documents nothing about this. The L5.1 research explicitly flagged it as an open
question: whether `/lifecycle` needs a signed token once signed URLs are required. The airing
answered it the hard way.

### What it reads now

`GET /accounts/{id}/stream/live_inputs/{uid}/videos` on the **API domain**, where an active
broadcast reports `status.state = "live-inprogress"`. That authenticates with the API token
and worked throughout the airing.

Two things are deliberately **not** used:

- **`/lifecycle`**, for the reason above. It is not kept as a fallback: two paths that answer
  the same question drift, and one of them is known to be wrong in our configuration.
- **The live input's own `status` field**, which stayed `null` for the entire broadcast. Its
  name suggests it is a readiness signal and it is not.

A finished recording (`state: "ready"`) is **not** live, and its uid is not returned. Handing
back the uid of a completed recording would invite a caller to treat a replay as a stream,
which is how last week's class ends up behind today's live badge.

### Evidence

Two mutations, both killed by the tests written for them:

| Mutation | Killed by |
|---|---|
| `live = !!first` — any video counts as live | `a FINISHED recording is not live...` plus the three not-ready cases |
| path back to `/lifecycle` | `hits the API host, NOT the delivery host - this is the 401 regression` |

449 tests across all 20 broadcast suites pass.

The response shape is checked rather than trusted: `GET /live_inputs/{uid}/videos` appears
only in Cloudflare's guide, not in its API reference, so it has no published schema.

## Third fix: the end instant nothing ever wrote

`ended_at` has existed on `BroadcastOccurrence` and in `ensureBroadcastSchema` from the
beginning. **Nothing ever wrote it.** Outside the model definition the column had zero
references in the codebase.

The first airing ended cleanly — editorial state moved to `ended`, discovery stopped
returning the occurrence, the live badge cleared for every viewer — and left `ended_at` null.
Any later report on broadcast duration, watch windows or replay availability would have had no
end instant to work from.

The state machine could not even have been idempotent about it: `OccurrenceState` did not
carry `ended_at`, so the pure function had no way to know whether one was already set.

### What changed

- `OccurrenceState` gains `ended_at`, and `toState()` carries it from the model.
- The `end` transition stamps `ended_at` from the injected clock, once.

**Only `ended`, deliberately not `cancelled`.** A cancelled occurrence never aired, and
stamping it with a time it "ended" would assert in the data that something ran and finished.
Cancellation is its own state and reads as one.

### Evidence

Removing the write fails `ending a live broadcast stamps ended_at from the injected clock`.

Stated plainly: the other three tests in that block — no-rewrite, cancel, go_live — **pass
under that mutation too**. They guard against writing the instant in the wrong places, which
is a different property and worth pinning, but they are not evidence that the write happens.
Only the first test is.

453 tests across all 20 broadcast suites pass.

## L4.6: the measurement path, and two artefacts that only claimed to exist

`broadcastTelemetryService` shipped with **no tests and nothing calling it**, flagged as such
in its own commit. L4.6 closes that: the tests, the heartbeat route, and the producer read.

Two things the existing code already claimed were there, and were not:

- `broadcastTelemetryQuery.test.ts` — the service comment read *"the two must agree, which is
  why `broadcastTelemetryQuery.test.ts` asserts the SQL text contains the window"*.
- `scripts/explainBroadcastTelemetry.js` — described as running the plan check *"at deploy
  time"*.

Both exist now. This is the second time on this project that a comment has described wiring
that was never built.

### The test suite I nearly fooled myself with

The service tests mock `sequelize` and match on SQL patterns. Twelve of them passed happily
while I re-keyed the anchor query from `enrollment_id` to `session_id` — a change that
**reverses the entire dedup rule** and would double every watch figure for anyone with two
tabs open.

They passed because the mock answers on `/FOR UPDATE/` regardless of what the `WHERE` says.
The suite was testing the plumbing, not the rule.

The fix was an assertion on the key itself: the anchor query must read
`FROM broadcast_viewer_people`, must filter on `enrollment_id`, and must not mention
`session_id` anywhere. That one test is what kills the mutation; the other twelve do not.

### The two required mutations

| Mutation | Killed by |
|---|---|
| anchor query re-keyed to the tab | `reads the anchor keyed on the PERSON, not on the tab` |
| collection failure renders as an empty room | `a COLLECTION FAILURE carries no count field at all - not zero, not null, absent` |

### Zero and "we do not know"

`GET /audience` answers **503 with no count field at all** when collection fails — not zero,
not null, absent. A client cannot render a number that is not there, which is a stronger
guarantee than asking it to check a flag first.

The metrics dictionary calls a fabricated zero a defect rather than a cosmetic issue, and it
is right: *"nobody watched"* is a verdict on the broadcast, *"collection is down"* is a
verdict on us. Showing the second as the first would have a producer stop a class people were
actually watching.

### The EXPLAIN, run against production

```
Index Scan using idx_bvs_active on broadcast_viewer_sessions s
  Index Cond: ((occurrence_id = $1) AND (last_beat_at >= $2))
Index Scan using idx_bvp_reportable on broadcast_viewer_people p
  Index Cond: ((occurrence_id = $1) AND (is_staff = false) AND (is_test = false))
```

The planner chose `idx_bvs_active` — the plan that index was built for — and a second index
on the people side. No sequential scan.

The script is deliberately honest about its own limits: on a small table a sequential scan
would be the *correct* choice, so it reports that case rather than failing on it. A plan over
0 rows proves the query is plannable and the index exists; it does not prove anything about
40,000 rows, and the script says so.

### Totals

484 tests across 22 broadcast suites. Backend `tsc --noEmit` clean.

## L7.1 — create a broadcast occurrence from the Accelerator session setup flow

**Date:** 2026-10-18 · **Session:** CC-20261015-t6q2 · **Branch:** `workstream/l71-session-occurrence`

### What changed

The session setup flow gained a "Broadcast this class on Colaberry Live" checkbox. Ticking it
creates the broadcast occurrence as a side effect of the session the admin was already
creating. No new route, no new page, no parallel creation path — the ticket is explicit that
building a second flow is the failure mode, and the existing `createSession` already had the
right hook: a flag-gated, best-effort, non-fatal block that calls `ensureRoomForSession`.

- `backend/src/services/broadcast/broadcastSessionOccurrence.ts` (new) — the first supported
  way to create an occurrence. Before this the only `BroadcastOccurrence.create` in the backend
  was inside the dry-run-by-default historical backfill, so nobody had a reachable path.
- `backend/src/services/acceleratorService.ts` — `resolveRoomId` now returns the room id the
  room block was already fetching and discarding; `enableLiveForSession` is the new side effect.
- `backend/src/controllers/acceleratorController.ts` — `live_enabled` is split OUT of the body
  rather than spread through, because there is no such column and a silently-dropped key is the
  failure the broadcast schemas' `.strict()` rule exists to prevent.
- `frontend/src/pages/admin/AdminAcceleratorPage.tsx` — one checkbox in the existing modal.

### Decisions worth recording

**The occurrence's existence IS the live flag.** No column was added to `live_sessions`. An
authoritative `broadcast_source_refs` row for `('live_session', session.id)` answers "is live
enabled", and `uq_broadcast_source_ref` is UNIQUE on that pair — so a second tick physically
cannot mint a second occurrence. Idempotency is the database's, not the code's.

**Re-timing happens whether or not the box is ticked again.** The occurrence key embeds the
start instant, so a rescheduled class whose occurrence is not moved keeps the old time — and
the preview window and the whole access decision are measured from it. `updateSession` re-runs
the ensure whenever live is already enabled.

**Creation is not gated on `BROADCAST_ENABLED`.** A private, scheduled occurrence is inert
while the flag is off. Gating it would force the feature on globally before a class could be
set up, which inverts the workflow.

**Nothing guesses a time.** `deriveStartInstant` reports `derived: false` for an unparseable
time while still returning a usable-looking Date (`classInstant` falls back to 10:00). The
ensure refuses on the flag, not the Date.

**Scope held:** one-to-many across time per Ali's option B on 18 Oct; turning live OFF is not a
checkbox, because cancelling a show is a producer command.

### Verification

- 318 tests across 19 suites, including every neighbouring broadcast suite — no regressions.
- Backend `tsc --noEmit` clean, against a baseline captured clean *before* any edit.
- **Four mutations, each killed by a named test:**
  - removed the explicit `access_mode` → `creation › creates the occurrence PRIVATE and SCHEDULED, with the room and the derived instant`
  - trusted the Date when `derived` was false → `refusals — nothing is ever guessed › refuses a time it could not parse, even though a usable-looking Date comes back`
  - allowed re-timing a live show → `an occurrence that already exists › refuses to move a show that has already gone live`
  - dropped the room id on the wiring → `createSession — Colaberry Live occurrence › creates an occurrence, with the room id, when live is enabled`

### Not done

**The screenshot of the real screen.** It is an acceptance criterion and it cannot be satisfied
before the change is deployed — a CSS mockup is explicitly not acceptable here. It is owed after
merge, and the ticket should not close without it.

## L4.9 — wire the player to the heartbeat endpoint

**Date:** 2026-10-20 · **Session:** CC-20261015-t6q2 · **Branch:** `workstream/l49-heartbeat-wiring`

### The defect

Test 2 aired for twenty minutes with real viewers in the portal and recorded **zero** telemetry
rows. Not a low number — zero, in both tables, while nginx logged 16 successful playback grants
and 103 discovery polls.

L4.6 had shipped the ingestion route, the schema, the bounded upsert, the
unavailable-never-zero audience read and thirteen tests. **Nothing on the client ever called
it.** A producer with no consumer. The only frontend matches for "heartbeat" were the
curriculum watch-gate and admin analytics, both unrelated systems; the control was that the
frontend *does* call `/playback`, from `LiveMiniPlayer.tsx`.

### What changed

- `frontend/src/services/broadcastHeartbeat.ts` (new) — the caller. Its own module rather than
  an addition to `broadcastPlaybackAdapter.ts`, which is already at 510 lines, the hard ceiling
  in CLAUDE.md, where the rule is that the next change splits before it adds.
- `frontend/src/components/portal/LiveMiniPlayer.tsx` — a second effect, separate from the
  adapter's, driven by the media element's own events.

### Decisions

**Measurement must never affect playback.** Every send is fire-and-forget; every failure is
swallowed after logging. A stream that stutters because a metric could not be recorded is a
far worse bug than the missing metric.

**Driven by media events, not adapter phase.** The question is "is a human watching right
now", and only the element knows whether pixels are moving.

**A hidden tab is not a viewer.** Checked at beat time, not only on the visibility event,
because a backgrounded tab keeps a `<video>` "playing" and counting it inflates the audience.

**15-second cadence**, matching the server's `playbackHeartbeatSeconds` default, inside its
120/min limiter and comfortably under the 45-second viewer-expiry window (two beats plus
margin). The cadence is operator-configurable server-side and is **not** published to the
client, so this is a duplicated constant. Publishing it on the grant response would remove the
duplication; that is a backend contract change and deliberately out of scope here.

**No unload hack for the final beat.** `stop()` makes a best-effort `ended` post; on a real page
close it will not arrive, and it does not need to — the server's expiry window is precisely the
mechanism for a viewer who vanishes.

### Verification

- 143 tests across 12 suites, including every neighbouring player suite — no regressions.
- Frontend `tsc --noEmit` clean, exit code read directly rather than through a pipe.
- **Two mutations, each killed by named tests:**
  - unwired the `play` listener (reproducing the shipped bug) → `posts a heartbeat when the
    video starts playing` and `reports pause, buffering and ended as distinct states`
  - counted hidden tabs as viewers → `does not beat while the tab is hidden, even though the
    element is still playing`

The first mutation is the point of the whole ticket: **it recreates exactly what shipped on
16 October, and the new tests fail against it.** Thirteen server-side tests could not see that,
because every one of them started a layer below the gap.

### Not done

Nothing here has been exercised against a real airing. The defect it fixes was invisible to a
full test suite and visible within minutes of a live stream, so the fix carries the same
caveat: it is proven by test and unproven in production until the next broadcast.
## L7.4 — end a broadcast without an engineer

**Date:** 2026-10-20 · **Session:** CC-20261015-t6q2 · **Branch:** `workstream/l74-end-control`

### Why

Ali, during Test 2: *"Can we just end it once the stream is done? I won't have you there every
time."* He stopped the Zoom stream at ~14:04 UTC; the occurrence stayed `live` until an engineer
ran a producer command at 14:09. For five minutes the portal advertised a broadcast over dead
air, and with nobody running scripts it would have stayed that way indefinitely.

### What changed

- `backend/src/controllers/broadcastController.ts` — the playback grant now returns
  `is_producer` and `version`, both server-decided, on both the live and replay branches.
- `frontend/src/services/broadcastProducer.ts` (new) — the end command, with 409 / 403 / failure
  as distinct outcomes rather than one error.
- `frontend/src/components/portal/LiveMiniPlayer.tsx` — a two-click End control, and a grant
  observer that reads capability and version from the response.

### Decisions

**The control lives in the portal, not the admin app.** The command route authenticates a
PARTICIPANT and derives producer rights from the staff context on that token. An admin-side
button would need either a participant token it does not have or a second command route — and a
parallel command path is exactly what this subsystem keeps being warned about.

**Capability is granted, never inferred.** `is_producer` absent means NO. The safe default is
deliberately the opposite of `is_live`'s, because the consequences are opposite: a missing
replay-restore loses a viewer's place, while a wrongly-offered End button ends a class in front
of everyone.

**Two clicks.** Ending is terminal; there is no un-end command.

**No version, no action.** Guessing a version would either be refused or act on a state the
producer has not seen.

**The observer lives in the component, not the adapter.** `broadcastPlaybackAdapter.ts` is at
510 lines — the CLAUDE.md hard ceiling, where the rule is that the next change splits before it
adds. The component owns the fetcher it injects, so observing the response costs nothing.

### Verification

- Frontend: 134 tests across 11 suites, `tsc --noEmit` clean.
- Backend: 46 tests in the controller suite, `tsc --noEmit` clean.
- **Two mutations, each killed by named tests:**
  - dropped the `is_producer` check → `is NOT offered when the server did not say is_producer`
    and `is NOT offered when the server omits is_producer entirely`
  - removed the version guard → `refuses to act at all when the server gave no version`
- The backend pair asserts BOTH polarities (`true` for staff, `false` for an ordinary viewer),
  so no hardcoded constant can satisfy both — mutation-equivalent by construction.

**Auto-end is NOT in this change.** It cannot be: scoping it found that `runProviderEvent` is
exported, tested and **called by nothing**, so `provider_health` is permanently `unknown` in

**Also note:** this branch and L4.9's both modify `LiveMiniPlayer.tsx`. Whichever merges second

## L5.5 — the provider health loop

**Date:** 2026-10-20 · **Session:** CC-20261015-t6q2 · **Branch:** `workstream/l55-provider-health`

### The defect

`runProviderEvent` was exported, tested, and **called by nothing** — verified with a control
(`runProducerCommand` has real callers; this had exactly one occurrence, its own definition).
So `provider_health` was permanently `unknown` in production, which meant three things:

- `go_live` was always refused with `ProviderNotReady`. During Test 2 it had to be hand-fed a
  provider event after reading Cloudflare directly. **Ali could not start a class unaided.**
- A dropped stream was never marked `reconnecting`. That state existed in the machine and was
  unreachable in production, so a class dropping mid-sentence looked perfectly healthy.
- Auto-end had nothing to trigger on.

The third producer-with-no-consumer found in this subsystem in a week.

### What changed

- `broadcastHealthPolicy.ts` (new) — pure decision: what to report given one observation.
- `broadcastHealthRunner.ts` (new) — one tick; no state rules of its own.
- `broadcastHealthLoop.ts` (new) — the wiring: the query, the provider call, the cron.
- `server.ts` — starts the loop.

### Decisions

**The rule that matters most is when to say NOTHING.** A single failed observation is not
evidence a class stopped, and reporting one would move a live occurrence to `reconnecting` in
front of its audience. Non-ready observations are held until they repeat (default 2).

**Backstage with no stream is EARLY, not broken.** Reporting down there would log a fault every
minute for every class set up in advance, and teach everyone to ignore the signal.

**`unreadable` reports `degraded`, never `down`.** Both move a live occurrence to
`reconnecting`, so the operational effect matches — but "the stream is gone" and "we could not
see the provider" are different facts, and the row should say which happened.

**No state rules were re-implemented.** `applyProviderEvent` already decides that health moves
freely, that only the live/reconnecting pair may be entered this way, that a webhook can never
publish or end, and that stale deliveries are ignored.

**Miss counts live in memory.** A restart costs at most one extra tick of patience, which errs
toward not flapping. Persisting them would be a write per occurrence per tick to buy nothing.

### The wiring test, and how it caught itself being worthless

A source-reading test asserts `server.ts` actually calls the loop — the only layer where
"nothing calls it" is visible, and the thing that would have caught all three prior defects.

**Its first version was useless, and mutation testing is what proved it.** Commenting out the
call in `server.ts` left the test GREEN: the regex matched the call *inside the comment*. A
test written to catch "imported but never called" accepted exactly that. It now strips comments
first, and the stripper has its own four tests, because an unverified helper would just move
the problem.

### Verification

- 319 tests across 20 broadcast suites; backend `tsc --noEmit` clean.
- **Three mutations, each killed by named tests:**
  - removed the hysteresis → 7 tests including `HOLDS on the first miss rather than reacting to
    a blip`
  - conflated unreadable with stream-gone → `reports DEGRADED, not down` and two others
  - commented out the call in `server.ts` → `server.ts CALLS it in live code, not in a comment`
    (**after** the test was fixed; the first version survived this and had to be rewritten)

### Not done

**Unproven against a real airing**, like every fix in this subsystem. The next broadcast should
show `provider_health` reaching `ready` with no human involvement, and `go_live` succeeding
without a hand-fed event.

**Auto-end (L7.4's second half) is still not built.** This unblocks it but does not deliver it.

**One-minute cadence** is node-cron's finest granularity and the house pattern. With a
two-miss threshold that means up to ~2 minutes before a drop shows as `reconnecting`. Acceptable
for a first version; if it proves too slow, a sub-minute timer is the follow-up.

## L5.4 — bind a new occurrence to a live input

**Date:** 2026-10-22 · **Session:** CC-20261015-t6q2 · **Branch:** `workstream/l54-input-binding`

### The defect

L7.1 made a broadcast creatable by ticking a box, and the occurrence it created carried no
`provider_session_id`. Nothing told playback which Cloudflare input to sign, so the occurrence
was real, correctly private, correctly roomed, correctly timed — and **unplayable**. During
Test 2 the field had to be set by hand before anyone could watch.

### The decision I made, and why I made it

The ticket carried a genuine product decision: one durable input for every class, one per
occurrence, or one per series. **Ali was asked three times across two days and the answer did
not come.** Rather than leave the critical path blocked eleven days from launch, I proceeded on
the recommendation — `shared` — logging the assumption here and in the code.

`shared` is the simplest, the most deterministic, has the smallest blast radius, and is what
both airings already used. Its accepted cost is that two classes cannot air simultaneously,
which is not a constraint before 31 October.

**The decision is cheap to reverse.** All three strategies are named; the two unbuilt ones are
**rejected at runtime with a clear reason** rather than silently falling back to `shared` — a
fallback would ignore an operator explicitly asking for isolation and quietly bind every class
to one input.

### Refusing is the feature

If no input resolves, creation fails **before anything is written**. An occurrence that looks
correct and cannot play is worse than no occurrence at all, because it is discovered by an
audience rather than by an admin. The resolver also refuses a malformed uid without echoing the
value, since it comes from the environment and an error string becomes a log line.

### Verification

- 330 tests across 21 broadcast suites; backend `tsc --noEmit` clean.
- **Two mutations, each killed by a named test:**
  - removed the `provider`/`provider_session_id` fields from create — **this recreates the
    L7.1 defect exactly** → `binds the occurrence to a live input, or playback has nothing to sign`
  - let creation proceed when no input resolves → `REFUSES when no input is configured, rather
    than creating an unplayable occurrence`

### Not done

**`CLOUDFLARE_STREAM_LIVE_INPUT_UID` is not set in production.** Until it is, creating a
broadcast from the UI refuses — loudly and safely, but it refuses. That is the one step between
this merging and a UI-created broadcast actually playing.

**Unproven against a real airing**, like everything else in this subsystem.

## L7.4 — a broadcast that ends itself when the stream is gone

**Date:** 2026-10-23 · **Session:** CC-20261015-t6q2 · **Branch:** `workstream/l74-auto-end`

Ali, during Test 2: *"Can we just end it once the stream is done? I won't have you there every
time."* He stopped the Zoom stream at 14:04 and the portal advertised a live broadcast over dead
air until an engineer ran a producer command at 14:09.

The producer End control shipped earlier and covers acceptance criterion 1. This is the second
half — the safety net.

### The rule it looks like it breaks, and does not

The state machine deliberately forbids a provider event from ending a broadcast: an arbitrary
webhook must not be able to kill a live class, and a ten-second blip must not end a session
mid-sentence. **That rule stays.** The safety net is a timeout with hysteresis that then issues a
*producer* command. Ending is still a producer decision; this stands in for the producer who has
gone home.

### The rule that matters most

**An `unreadable` provider never ends anything.** If our Cloudflare token lapses, every
observation becomes unreadable, and a naive implementation would end every live class on the
platform at once — while looking exactly like the feature working. So an end requires a
*positive* observation, right now, that the stream is absent, on top of the sustained window. The
consequence is deliberate: a permanently unreadable provider means a human ends the broadcast.
That is the correct failure direction.

### What was built

- `broadcastAutoEndPolicy.ts` (new, pure) — the decision, plus the clamped window resolver,
  reusing the telemetry `resolveSeconds` rather than repeating its NaN handling.
- `broadcastHealthRunner.ts` — evaluates the auto-end inside the existing tick. **Ending is
  considered BEFORE reporting health**, because reporting first bumps the row's version and
  every auto-end would then lose to its own health write with a 409.
- `end_reason` — new nullable column (`ensureBroadcastEndReasonSchema.ts`, wired into boot),
  through the model, the state machine and the command path. Nullable with no default on
  purpose: back-filling `producer` onto older rows would invent a fact.
- `.env.example` — `BROADCAST_AUTO_END_WINDOW_SECONDS`, clamped 60-3600, default 300.

### Verification

- **103 tests across 8 suites**, backend `tsc --noEmit` clean on the backend's own TypeScript.
- **8 of 8 mutations killed**, every file restored byte-for-byte: unreadable treated as proof of
  absence; the clock paused instead of cleared on reconnect; backstage allowed to auto-end; the
  window made unreachable; an unparseable window becoming NaN; health reported in the same tick
  as the end; the absence clock not forgotten after ending; and the safety net recorded as a
  person pressing End.

### Two things found along the way

**The runner's logger stamped `outcome: "success"` on its own failure lines**, so
`broadcast_health_apply_failed` was recorded as a success. A failure logged as a success is worse
than no log, because it gets believed. Fixed, with `error_class` and `level: warn`.

**`loadObservableOccurrences` ends in `return rows as ObservableOccurrence[]`**, and a cast is a
promise the compiler accepts without checking. Drop a column and the field is simply `undefined`
at runtime — for `version`, that means every auto-end refused as a version conflict, with no
symptom except broadcasts quietly not ending themselves. `broadcastHealthLoop.query.test.ts`
parses the field list out of the interface and asserts the SELECT asks for each one.

### A process note worth keeping

The first mutation run reported `SKIPPED (anchor not found)` for the two runner mutations,
because tracked files here are CRLF and the anchors used `\n`. **A skip is not a kill**, and the
harness counted them as survivors rather than banking them — which is the only reason the two
most important mutations were not silently claimed. Saved to memory.

### Not done

`end_reason` is answerable by query and by the structured log; nothing surfaces it in an admin
read path. The loop is gated on `BROADCAST_ENABLED`, so the safety net only runs when
broadcasting is on — correct, and worth knowing. And **this has never fired against a real
stream**: every proof here is a test.

## L8.4 — bind the recording, and stop signing a dead input

**Date:** 2026-10-23 · **Session:** CC-20261015-t6q2 · **Branch:** `workstream/l84-recording-binding`

### The ticket was the wrong shape, and Ali chose the other path

L8.4 asked for a resolver behind `/bm/`. But **a Cloudflare occurrence never reaches `/bm/`**:
the grant controller branches on `provider === 'cloudflare'` and returns a Cloudflare URL, and
`/bm/` serves bytes from local disk. Routing replay through it would mean downloading every
class to the VPS to re-serve what Cloudflare's edge already serves, signed. Ali chose: bind the
recording's video uid and sign that. `/bm/` is untouched.

### The defect, measured

For an ended occurrence the controller signed `provider_session_id` — the **live input** —
unconditionally. Proven on production with the real signer:

| signed uid | HTTP | manifest | variants |
|---|---|---|---|
| the recording `2a5e8e18…` | **200** | yes | **4** |
| the live input `ed843de3…` | **204** | no | 0 |

A viewer asking to replay Test 2 got a correctly signed, correctly expiring URL that returns
**204 No Content**. Well-formed and wrong, which is the hardest kind of broken to notice.

### The binding is observed, not inferred

`readLiveLifecycle` already returns a new video uid per broadcast, and the health loop already
calls it every minute for everything on air — then narrowed it to a boolean on the way out.
Widening that return captures the uid exactly, with **no extra provider call** and no matching
recordings to occurrences by timestamp.

**`provider_instance_uuid` has existed since the table was created and nothing ever wrote it.**
Both production occurrences carry null. Third declared-but-unwired field in this subsystem,
after `ended_at` (L7.4) and the heartbeat route (L4.6).

The capture runs **before** the health decision and before the auto-end, because the tick that
sees the stream gone is the LAST tick that can still see the uid. A capture after the auto-end
would miss every show that ended cleanly, which is all of them.

### Verification

- **74 tests across 3 suites**; **6 of 6 mutations killed**, all files restored byte-for-byte:
  an unbound recording falling back to the live input; every state treated as on air; a second
  recording overwriting the first; a malformed uid persisted; the capture running only while
  the stream still arrives; a failed bind logged as a success.
- Criterion 1 proven against the **real** Test 2 recording, not a fixture.

### What a failing test taught me

My first controller tests used `editorial_state: 'ended'` and came back 403. Entitlement's
`WATCHABLE` set is `live`, `reconnecting`, `replay_ready` — **an ended occurrence is refused
before any playback target is resolved.** The fixture was wrong, not the code.

### The remaining link, named

**Nothing promotes an occurrence to `replay_ready`.** `processing` and `replay_ready` appear in
the broadcast source only in the schema's allowed-values list. So the binding is correct and
currently unobservable: every replay still answers `not_watchable`.

Cloudflare already reports the recording's status as ready. The promotion is small — observe
ended occurrences that have a binding, promote when the recording is ready. Put to Ali as a
scope question rather than widened silently, because this ticket had already been redefined once.

### The promotion step (Ali approved finishing it)

`ended -> processing -> replay_ready` now happens, driven by Cloudflare's own report that the
recording is playable. **The two commands that reach those states did not exist** — the
transitions had been in the table since it was written with nothing able to trigger them, which
is why `processing` and `replay_ready` appeared in the broadcast source only in the schema's
allowed-values list.

Two rules carry the weight. **An unreachable provider is never read as a failed recording** — a
Cloudflare blip would otherwise mark replays permanently unavailable, a terminal verdict from a
transient fault. And **a show with no binding is never promoted**: `replay_ready` with nothing
bound advertises a replay and then refuses to play it, which is worse than staying honestly
ended. An undocumented provider state reads as unreadable rather than "still preparing", so a
future Cloudflare value cannot silently stall every replay with nothing in the logs.

### Final verification

- **610 tests across 35 suites**, backend `tsc --noEmit` clean.
- **12 of 12 mutations killed** across both halves, all files restored byte-for-byte.
- Criterion 1 proven on production against the real recording.

### The mistake worth recording

One edit script used a bare `\n` anchor against a CRLF file. Python's `str.replace` returns the
string unchanged on no-match — no exception — so the script reported success and changed
nothing. The `observe` contract ended up half-applied: implementation updated, interface not.

**81 tests passed anyway**, because ts-jest runs with `isolatedModules` and does not typecheck.
Only `tsc --noEmit` found it, three errors deep. Second time in one day the CRLF difference has

## L8.3 part two — the portal surface, and a defect the requirement itself caused

**Date:** 2026-10-27 · **Session:** CC-20261015-t6q2 · **Branch:** `workstream/l83-replay-surface`

PR 3409 merged the endpoint on 26 Oct. Re-reading the ticket against it found that the endpoint
was **half of one sentence**: the artifact line reads *"a replay list endpoint plus a portal
surface"*, and the success signal reads *"a student finds last week's class and plays it."*

Two acceptance criteria also had nothing to point at. There were **zero controller tests** for

### The defect: the requirement and the bug were the same case

The merged handler read `ended_at` by **position** out of the array it had just filtered:

```ts
replays: projectDiscovery(entries).map((item, i) => ({ ...item, ended_at: occurrences[i].ended_at … }))
```

`projectDiscovery` **omits** an occurrence the viewer may not know about, so the projected list

from the private class while Week 10 is dated from Week 9.**

No crash: a shorter list only ever reads lower indices, so nothing goes out of bounds. No failing
test either, because omission is the only thing that triggers it — and omission is precisely what
this ticket exists to do. The feature's headline requirement was the defect's precondition, which
is why the green query suite went straight past it. Now keyed by id.

## L8.3 retention — Ali's 25-day window

**Date:** 2026-10-27 · **Session:** CC-20261015-t6q2 · **Branch:** `workstream/l83-replay-retention`

PR 3431 merged and Ali answered the open question in three words: **25 days.** The ticket had
asked "what appears in the list and for how long"; the code answered only the first half, because
the 25-row cap bounds size, not age — a class from a year ago stayed listed until twenty-five
newer ones displaced it.

### What the window is, and where it lives

`REPLAY_RETENTION_DAYS = 25`, enforced as `ended_at >= cutoff` **in the query**. In the query
rather than after it, for the same reason the recording binding is: a row filtered afterwards has
still been read, still been sorted, and still counted against the limit, so twenty-five expired
classes could push every live one off the page.

The partial index needs no change, and it is worth knowing why. `ended_at >= cutoff` is a range
predicate on that index's leading and only key, so it is a range scan that stops at the cutoff.
The window is deliberately **not** in the index's own WHERE clause: a partial index predicate
containing a moving `NOW()` is not immutable, Postgres refuses it, and an accepted one would
silently stop matching the query as the clock moved.

**A null `ended_at` is excluded.** `Op.gte` against NULL is NULL, which is not true. A row that
cannot be aged cannot be shown to be inside a window that touches billing, so it fails closed.
Only concerns rows predating L7.4, of which production has none.

**A constant, not an env knob.** The poll cadence is env-tunable because an operator needs to
slow every client mid-incident without a deploy. Retention is not an incident lever; it is a
commitment to students, and it belongs where a diff records changing it.

### The number is sent, not written into the page

`retention_days` rides on the route payload and the surface renders it — the same arrangement as
`poll_after_ms` on the live route, and for the same reason. A hardcoded copy in the frontend is a
second source of truth that goes stale the first time the policy moves, leaving the page
promising a window nobody enforces. The page says *"Classes stay here for 25 days after they
air"*, shown on an empty shelf too, because "nothing here yet" and "this is how long things stay"
answer different questions and a student hunting an expired class needs the second. Absent means
silent: an older backend sends no window and the page invents nothing.

### Verification

- **Query suite 19, controller 60, frontend replay suites 28** — all green. Both `tsc --noEmit`
  clean.
- **8 of 8 mutations killed**, file restored byte-for-byte: the window ten times too long; days
  read as seconds; out by one day; the window dropped from the query; the operator INVERTED so
  only expired classes list; measured from `scheduled_start_at` so a moved class expires from a
  date it never aired on; the default instant set to the epoch, which retains everything and
  voids the policy; and the cutoff frozen at import so it drifts for every hour the process is up.
- The controller test proves **forwarding**, not a constant: its mock says 11 while the real
  policy says 25, so a hardcoded 25 in the route fails it.

### A test of mine that was decoration

I wrote `expect(true).toBe(true)` under the label CONTROL and removed it rather than shipping it.
The genuine control for that guard — "passes a sane window through" — was already the first test
in the block.

### What it costs, recorded because Ali should be able to revisit it

find it. The ticket's stated objective is learning continuity; this window serves "I missed last
week" rather than "let me rewatch the course". Changing it is one number in one file.

### The access audit

Ali mentioned in passing that the first event is tomorrow, which turned "set up Test 3" into an

## 2026-10-29 — Test 3, and the ordering nobody had written down

Ali asked the question that should have come first: shouldn't we rehearse the steps before the
event rather than discover them during it. Then, reading the draft: *"is it as easy as being in
a scheduled event and go live on the zoom? Anything else outside of that?"*

**No, and the gap between those two answers is where an event gets lost.** The stream and the
editorial state machine are independent systems, and the order between them is forced in both
directions:

- Starting Zoom alone changes nothing a viewer sees. The Events Hall, the popup and the player
  are all driven by `editorial_state`, which only a producer command moves. The state machine's
  own header is explicit that **no transition is driven by the clock** — a scheduled start time
  publishes nothing.
- The command alone is refused. `go_live` fails unless `provider_health` is `ready`, because
  "the producer said go" and "the feed is usable" are deliberately two columns.

**And the ordering detail that was in no document:** the health loop's `OBSERVED_STATES` are
`backstage`, `live`, `reconnecting`. A `scheduled` occurrence **is never polled**, so until it
is backstage, nothing is watching for the feed and health can never become `ready`. Entering
backstage is not a formality before going live — it is what makes going live reachable. Anyone
who started Zoom first and then worked down the command list would sit watching `go_live` refuse
and have no idea why.

The mirror image at the other end: **closing Zoom does not end a broadcast.** The occurrence
stays `live` over dead air until the safety net fires after the stream is continuously absent for
`BROADCAST_AUTO_END_WINDOW_SECONDS` (default 300, clamped 60–3600). That window is exactly the
five minutes of dead air on 2026-10-20 — not a bug that was fixed, a window that was chosen, and
long on purpose so a presenter restarting OBS comes back to a class still running.

**The rehearsal runs entirely from a browser**, which is the part I had assumed was impossible.
Two things made it work, both found by reading rather than guessing:

1. `GET /api/portal/broadcasts/active` already returns `room_id`, `access_mode` and
   `can_watch` + `reason` **evaluated for the calling viewer**. So the access question is
   answerable precisely, by the only account whose answer counts, in one line.
2. `isAdmin` short-circuits the watchable gate, so staff can mint a playback grant on an
   occurrence that is not live. That grant is the only place the client ever learns `version`,
   which every command requires — without it there is no way to issue the first command from a
   browser at all. The same call doubles as the playability check: a 503 `ProviderNotReady`
   means entitled, real, and silent.

Two details verified rather than assumed, both of which would have failed live with an audience
waiting: `playbackGrantSchema` requires `asset` with no default (`master.m3u8`), and the command
response is `{ ok, noop, occurrence: { … version } }` so versions chain from each response.

## 2026-10-31 — P4-02: a producer control, and the version that made it impossible

Ali merged 3512, then said "next". Items 1 and 2 of the recommended order need him (the Zoom
desktop-client check; five people for Test 2), so the next item that is mine is item 3 — the Go Live
/ End control. It is the only engineering on the critical path.

**THE PREREQUISITE WAS REAL, AND BIGGER THAN THE SPEC SAID.** The spec recorded that the playback
grant is the only endpoint returning `version` and that it answers 503 on a `scheduled` occurrence.
Reading the code for this build added the second half: **discovery could not fill the gap either.**
`ACTIVE_DISCOVERY_STATES` is `['live','reconnecting']` (`broadcastActiveQuery.ts:29`), so a scheduled
or backstage occurrence is not in discovery at all, and its `COLUMNS` never included `version`. So
the End control works only because the grant is available once live — `LiveMiniPlayer.tsx:117-134`
takes both `is_producer` and `version` off the grant — and nothing pre-air could.

**What I built, and why not either option the spec proposed.** The spec said "either staff discovery
must expose `version`, or the 503 must carry it." I took neither. Both bolt a lifecycle fact onto a
route that exists for something else, and the 503 option is worse than it looks: it puts the number a
producer needs most into an error body they only receive when the feed is *not* working. Instead a
dedicated `GET /api/portal/broadcasts/session/:sessionId/producer`, staff-only, keyed on the session
because that is what a producer holds.

Four decisions in it worth keeping:

1. **Availability is derived, not restated.** `describeProducerCommands` evaluates each command
   through `applyProducerCommand` itself. A second table of "Go Live needs provider health" would
   have been a second place to forget that going live takes two keys — the exact duplication this
   subsystem's own comments keep warning about.
2. **Not folded into the audience read**, the other producer-facing endpoint. It answers 503 with no
   count field when telemetry collection fails, deliberately. Sharing a request would take the
   control away at precisely the wrong moment.
3. **Its own rate limiter.** The command limiter is 30/min; a control polling every 2.5s would spend
   24 of those before issuing a single command. 60/min and a 5s poll instead.
4. **`SENDABLE_PRODUCER_COMMANDS` is now one list** feeding both the route's zod enum and the read's
   description. The enum accepts six of the machine's eight commands — `begin_processing` and
   `publish_replay` are issued only by `runReplayTick` — so without this the read would have offered
   two buttons the route answers 400 to.

**A latent defect found by reading the call site.** `broadcastProducer.ts` has read `res.data.version`
off a 409 since the End control shipped, and `postProducerCommand` never sent one — it answered
`{ error, reason }`. So `currentVersion` was *always* undefined and every conflict told the producer
"someone moved this" with no way forward but a reload. Refusals now carry the version, re-read after
a lost write race rather than echoing the number the database just rejected, and omitted rather than
guessed when the occurrence vanished mid-flight. Three tests pin all three paths.

**The strip renders nothing for a viewer**, and that is a security property rather than a nicety:
`/portal/live/:sessionId` is a PUBLIC route that students load. Producer capability is asserted by
the server (403 → `null`) and never inferred on the client. Two of the frontend tests are about what
is *not* rendered, for that reason.

typecheck: **0 errors across the whole frontend** — notable because `frontend/node_modules` is gutted
in this worktree, so I expected module-resolution noise and got none. Frontend component tests could
NOT be run here (no react-scripts in the worktree) and are left to CI; said so in the commit rather

### What CI caught that my local run could not, and one real bug among it

PR 3519's first run failed two jobs. Every typecheck gate passed, including test-file typecheck,
so both were assertion failures. Worth recording because one was a genuine defect and the other is
a trap this repo has now sprung four times on four different people.

**`broadcastRoutes.test.ts`: every test failed at module load.** That suite mocks the controller

**The real bug: the re-read wiped the notice the command had just set.** Three frontend tests failed,

airing moved under you (now at version 9)"* would have appeared and vanished within the same tick.
That is worse than never showing it: a producer sees a flicker and learns nothing, on the one refusal
they could actually have acted on. Command outcomes and read failures are now separate state —
a command's outcome survives until the next command, a read failure clears when a read succeeds —
and a test pins the message surviving the re-read that follows it.

### Ali: "Auto-hide cadence: hide silently — fix"

He was right, and it is the same defect class as the notice bug: the control re-decides whether to
exist on **every poll tick**, and the hide path was indiscriminate. `refresh()` preserved the last
good picture only on a `failed` read; a `forbidden` one replaced state outright and the strip
returned `null`.

A later poll can answer `forbidden` for reasons that have nothing to do with who is watching — the
participant token expires mid-class, the broadcast flag is switched off, staff context fails to
resolve. So the strip would vanish between one tick and the next, in the middle of an airing, with
no explanation and End being the thing most needed. **A control that disappears silently is
indistinguishable from one that was never there.**

Fixed with `everAuthorized`: the hide is silent only BEFORE the server has ever answered as a
producer. After that it renders what happened and what to do — re-authenticate, or reach for the
API fallback in the go-live directive — and offers no command buttons, since the server has stopped
authorizing the caller and every one of them would fail.

**The security property is untouched, and there is a control test for it.** A viewer who is not a
producer never gets a successful read, so `everAuthorized` never becomes true for them: no strip, no
message, no trace that a control exists. That test asserts `container.textContent` is empty rather
than merely that the strip is absent.

Also cleaned up on the way: the two guards had grown a pair of `state!.occurrence!` non-null
assertions. Replaced with a single resolved `live` value, so TypeScript narrows properly and neither
guard needs an assertion.

**A theory of mine that was wrong.** I expected `LiveSessionPage.test.tsx` to fail too, because it
mocks `portalApi.get` to reject unknown URLs and I had added an unmocked `ProducerStrip` that calls
one. It passed: the strip renders `null` on a failed read, which is the behavior I had built
deliberately and then forgotten I could rely on. I stubbed it anyway — that file stubs its children
on purpose, and the real strip polling inside a page test is noise — and added five tests for the

On top of that it is blocked on §10 decision 3 — how a recording reaches an external contractor
is an access-model decision, not an implementation detail, and every route in the system today
requires a portal participant JWT. Item 5 is Piyush's. So the highest-value unblocked engineering
was the risk sitting in plain sight: the busiest live surface in the subsystem had no coverage at
all, three weeks before it gets its hardest use.

**Two of my own earlier claims were wrong. Both corrected rather than built on.**

1. **§8 finding 4 was wider than the code.** It presented three pulse states as what the check-in
   page offers, full stop, with a line reference. The line reference was right; the scope was not.
   The page has TWO controllers. The default screen offered all four ("I'm here" · Building ·
   "I'm stuck" · Finished); only the **Build Mode** controller dropped `here`. So the
   under-reporting I warned about for Test 2 is real but confined to Build Mode, not the whole
   airing — a materially narrower caveat than the document gave, and one that would have had
   somebody discount good pulse data. The spec table now shows all three controllers separately
   and says plainly that the first version was over-broad.
2. **The page's header comment claimed "no hardcoded hex".** It has fifteen — thirteen of them
   `var(--token, #fallback)` fallbacks or `#fff` on a filled button, which are fine, plus the
   Prompt Drop box's terminal-dark `#0f1720`/`#26313f`/`#e7eef6`, which genuinely do not adapt to
   light mode. I nearly shipped a test asserting the file was hex-free, which would have failed in
   CI. Instead the test asserts what is true, the comment now says what is true, and the dark
   prompt box is recorded as a deliberate design choice left alone — restyling a student-facing
   code block is not a test cleanup.

**The three defects, in order of how much they cost.**

- **Build Mode dropped `here`.** During the one segment where an instructor most needs to know
  who is following rather than building, there was no button to say so — and a student who had
  already tapped it watched their own status disappear from the grid when the instructor moved to
  a prompt. Their `pulse` state survived; the button rendering it did not.
- **A question could be double-posted.** `sendQuestion` is bound to Enter as well as the button,
  and only the button carried a `disabled`. React batches, so two quick presses both read
  `qState === 'idle'` out of the same closure and both posted. Nothing downstream deduplicates a
  question, so the instructor's deck showed it twice. Same bug, same shape, as the one I fixed in
  `SessionChatPanel` an hour earlier — which is the argument for the ref-gate being a pattern here
  rather than a one-off.
- **Label drift between two surfaces asking the same question.** "I'm here" vs "Following",
  "I'm stuck" vs "Stuck". Cosmetic in isolation; not cosmetic when the answer is aggregated into
  a number an instructor acts on and Test 2 measures.

**The fix for drift is structural, not a find-and-replace.** DOC 04's set now lives in
`frontend/src/components/portal/livePulse.ts`, which both surfaces import — the check-in page
through one `PulseGrid` used by both of its controllers, and `CompanionDeck` in place of its own
copy. Markup is deliberately NOT shared: one is a one-thumb phone deck and the other a public
landing card, and forcing one component on both would mean a prop per visual difference. What must
not differ is the SET, so that is the only thing extracted.

**The pulse-set test exists because the surface tests are circular without it.** Both surfaces'
tests iterate `LIVE_PULSES` to check what they rendered. Drop a state from the module and every
one of those assertions still passes, having quietly checked one fewer thing. So `livePulse.test.ts`
pins the four states and their labels literally, and the surface tests are then free to iterate.

**The file also broke CLAUDE.md's 500-line ceiling, so it split.** It was 615 lines and my changes
took it to 644. About 250 of those were the CSS template string, so that moved to
`classCheckinStyles.ts` byte for byte — no rule changed, no class name moved — bringing the
component to roughly 470. The Modular Composition Rule says a file over the hard ceiling must be
split before more code is added to it; this is that, done at the moment the rule triggers rather
than deferred again.

**What the 25 tests actually cover,** chosen by what a class cannot start without rather than by
line coverage: attendance recorded exactly once and never for a signed-out visitor; the points
burst only when the server says points were awarded; a failed check-in offering both a retry and
a way into the class anyway; the sign-in round trip carrying `next` back to this exact URL (without
it the magic link lands on `/portal/today` and the QR appears to have done nothing); both pulse
controllers offering all four states; the wire value sent rather than the label; a poll vote
blocked once revealed or locked; and the 2026-08-20 lost-connection incident in **both** directions
— silent after one dropped request, "Reconnecting" after three, immediate on a 401, and clearing
itself when the class comes back.

**Still open here:** the QR still never reaches `/portal/live/<sessionId>/companion`; it remains
reachable only by typing it. Whether the two surfaces should converge is a product decision, not a
cleanup. They are now consistent in what they *ask*, which was the part corrupting a measurement.

## The producer gets a clock and a viewer count — P4-02, the rest of it

- Date: 2026-11-01
- Session: CC-20261015-t6q2
- What changed: the two things a producer asks out loud during a class — where am I in the hour,
  and is anyone there — were already on the wire and neither was rendered. Both now are, as
  `producerClock.ts` and a viewer-count chip on the producer strip.
- Verification: frontend `tsc --noEmit` clean; the four node lint gates pass locally; the 38 new
  frontend tests (24 pure clock + 14 strip) are verified by CI, the only place the frontend suite
  can run in this environment.
- Notes: see below.

**This closes the second of the three declared-but-unreachable features.** `GET
/api/portal/broadcasts/:id/audience` had no caller anywhere in `frontend/src` from the day it was
written, and `content_started_at` / `scheduled_start_at` came back on every producer read and went
unread. Spec §8 finding 2 is down to one instance — clip markers — and in both closed cases the
act of giving a feature a reader is what exposed what was wrong with it. Chat's defects were in the
response shape; this one's is a rate limit.

**The clock counts UP past a missed start, and that is the reason it is worth building.** The strip
could already show the server's *reason* for the pre-air wait — provider health not yet `ready` —
but never its cost. Four minutes past the hour with Go Live still blocked is a different situation
from thirty seconds early, and a countdown resting at 0:00 says nothing about which one you are in.
It also reports how long a finished airing ran, and ticks locally once a second rather than on the
5s poll, because a clock that advances in five-second jumps reads as broken.

**Two findings in the code changed the design.** `go_live` refuses with `ContentNotStarted` unless
`content_started_at` is already set (`broadcastStateMachine.ts:195`) — going live without it would
leave every viewer's free preview window unbounded — so an on-air clock always has an anchor, as a
guarantee from the state machine rather than an assumption in the client. And `ended_at` is null on
real production rows: the column existed from the start and nothing wrote it until recently, so the
first airing ended cleanly and left no end instant. Those get no final duration rather than one
measured against `now`, which would otherwise grow every time the page polled.

**The clock is the producer's laptop against the server's timestamps, and the module says so.** A
start instant slightly ahead clamps to 0:00; more than a minute ahead shows no clock at all,
because a wrong duration rendered confidently is worse than a blank. A clock skewed into the *past*
is **not** handled and cannot be from the client alone — nothing here can tell it from a class that
genuinely started earlier. If it ever matters, the fix is a server `now` on the producer read.

**Zero watchers and a broken counter had to stay different sentences, and the client is where that
would have collapsed.** The server answers 503 with no count field at all, specifically so no
client can print a fabricated zero; the usual `?? 0` on the way in would have undone all of it in
one character. The chip reads `0 watching`, `not measuring`, `no answer`, or a kept number marked
`not updating` — four readings, three of which are not numbers. One test asserts the `not
measuring` text contains no digit at all.

**The first caller found a rate limit.** The audience route carries the *command* limiter, 30/min,
shared with the producer's own commands — reasonable when it was written ("a producer looking at a
dashboard, not a player polling") with no caller to contradict it. A 5s poll would spend 12 of
those 30 a minute, and a go-live sequence that hit a version conflict could find its commands
throttled by a viewer counter nobody acts on. So the count polls at 15s and only while on air. A
test pins the cadence relationship — 2 audience reads to 4 state reads across 15s — which also
proves the effect keys on the occurrence **id** rather than the object; keyed on the object, each
5s poll would hand it a new one, tear the interval down and re-fire. The real fix is the route's
own limiter, which is now recorded in the spec so the next caller does not rediscover it.

**One defect in my own code, found during BREAK rather than by a failing test.** A session may have
more than one occurrence (DOC 03), and on a re-airing the chip would have shown the previous
airing's count for as long as the first request took. One request is a short window and a wrong
number all the same — which is the one thing this entire change is about. The count is dropped when
the occurrence id changes, and the test holds that window open with a promise that never resolves
so the assertion lands inside it.

**I was wrong about the line ceiling and corrected it rather than arguing.** At 484 lines I judged
a CSS split unnecessary and said so in plain terms. My own next two fixes took the file to 502 —
over CLAUDE.md's hard ceiling — so it split after all: `producerStripStyles.ts`, byte for byte, no
rule changed and no class name moved, component back to 453. The rule is that the change crossing
the ceiling splits the file, and that change was mine.

**Preview-vs-program should stop being listed as engineering scope.** There is exactly one provider
input (`cloudflareStreamProvider.ts`), so cutting between a preview bus and a program bus is a
vision-mixer function belonging to the studio in P4-01/R5, which is Piyush's. A software imitation
— a second player labelled "preview" fed from the same single input — would be worse than its
absence, because it would read as a monitor that is not monitoring anything. Note that `PreviewBound`
in `broadcastPlaybackGrant.ts` is not this: it is the paywall's free-preview window for an Explorer
and shares only the word. The spec now says both. **The segment rundown is the only P4-02 item
still open.**

## Cancel is a one-way door, and now it says so — plus a spec finding that was backwards

- Date: 2026-11-01
- Session: CC-20261015-t6q2
- What changed: §8 finding 3 claimed participation merges across re-airings; a UNIQUE index makes
  re-airing impossible, so the claim was inverted and is now corrected. Checking it turned up a
  real defect next to it: cancelling an airing permanently retires the class from Colaberry Live,
  the confirmation did not say so, and the backend reported the refusal as `already_aired` — the
  one thing untrue about a show cancelled before it ever aired.
- Verification: frontend `tsc --noEmit` exit 0 with zero diagnostics, and `tsconfig.test.json`
  covers `src` with no exclude, so the two new/changed test files typecheck there too; backend
  test-file typecheck run raw in this worktree reports 400 errors total — equal to the frozen
  ratchet — and **zero** in either backend file touched. Jest is installed in neither tree, so the
  new tests themselves are verified by CI only, which is stated rather than papered over.
- Notes: the fix stops at honesty on purpose. Re-opening the door is §10 decision 5.

**The finding I was sent to fix does not exist, and I checked before building.** §8 finding 3 said
a session may have more than one occurrence, so re-airing would merge participation across both
airings. `uq_broadcast_source_ref` is UNIQUE on `(source_type, source_id)`, so a live session holds
at most one occurrence by constraint; every session→occurrence lookup in the backend goes through
that ref; there is no second creation path outside the backfill runner; and the only
`DELETE FROM broadcast_occurrences` in the repo is that runner's batch reversal, which can only
touch rows carrying a `batch_id`. Nothing merges and no data needs repairing. What the finding
really describes is a **precondition**: eight tables key on the session and none on the airing, so
occurrence-keying has to land *before* re-airing is ever supported. Recorded in that order now.

**What the check turned up instead.** Three individually reasonable facts: `cancelled` has no
outbound transition (`cancelled: []`), a session holds at most one occurrence, and re-timing is
refused outside `scheduled`/`backstage`. Together, one confirmed click permanently retires a class
from Live. The producer strip offers **Cancel this airing** on any scheduled occurrence, which is
the right button to have — a class called off for weather is an ordinary Thursday. What follows is
not: the occurrence can never leave `cancelled`, no second occurrence can be minted, and
re-scheduling the class in the admin modal is accepted, writes nothing and reports nothing.
`enableLiveForSession` logs and returns void by design, and the admin page has no error surface at
all — no `setError`, no toast, nothing. The next signal anyone gets is an empty room at the hour.

**The refusal named the wrong reason, which is the part that was simply a bug.** Aired states and
`cancelled` both came back `already_aired`, sending whoever read the log looking for a recording of
something that never happened. `cancelled` is now its own reason, and the state matrix is a
`Record<EditorialState, …>` table test — the compiler refuses a missing state, so a ninth editorial
state cannot be dropped into the wrong bucket by default. That is the gate; the one-line split is
not the interesting half.

**The warning goes in front of the click, not after it.** The confirmation said "This cannot be
undone", which is a statement about the airing — a producer hears it as "so re-schedule the class",
which is precisely the move that silently fails. It now says the class cannot be put back on air and
that re-scheduling will not bring the broadcast back. A cancelled occurrence also stops answering
with "Nothing to do from here", which was the identical sentence shown for a class sitting quietly
in backstage; `replay_ready` gets its own line too, because nothing left to run is good news there.

**The copy left the component, and the ceiling is not the reason this time.** `producerStripCopy.ts`
holds the labels, the confirmations, the empty-state note and the badge. Two of those sentences
carry a consequence, and a sentence that carries a consequence should not be a string literal inside
a render where an assertion has to fish it out of `textContent`. `needsConfirm` is now derived from
the questions rather than listed separately, so a command can no longer be marked irreversible with
no question written for it. The component came down to 427 lines as a side effect.

**I did not take either fix that would re-open the door, and said why in the spec.** Making
`cancelled` non-terminal changes `TERMINAL_STATES`, which the health loop and discovery both read,
and needs a `content_started_at IS NULL` guard because `cancel` is reachable from `live` — reviving
one of those is exactly how an airing inherits the previous audience's participation. Re-pointing
the source ref to a fresh occurrence is the smaller diff and needs no schema change, but
`occurrence_key` is UNIQUE and embeds the start instant, so re-enabling a class at the same date and
time collides, and avoiding that means changing what an occurrence's identity is — the one thing the
backfill's convergence depends on. Both cross a governance boundary and both make finding 3
load-bearing the day they ship. A third answer is legitimate: leave it permanent and warn properly,
which is what shipped.

**No Basecamp ticket for this, same gap as the rest of the day.** The token lives only in the prod
backend container and reaching it is a production operation this environment refuses.

## The clip list gets a reader, and R7's first brick is one third laid

- Date: 2026-11-01
- Session: CC-20261015-t6q2
- What changed: clip markers were the last feature complete server-side with nothing reading it
  (§8 finding 2). They now have two readers — a panel on the Class Kit and a CSV an editor can
  open, which is also the clip-candidates third of R7's first brick (§9 item 6). Giving it a
  reader exposed four things, as it did for the chat thread and the audience count.
- Verification: frontend `tsc --noEmit` and the backend test-file typecheck both run on the final
  tree; four node lint gates pass. The 30-odd new tests are verified by CI only — jest is
  installed in neither tree.
- Notes: the file has never run against a real airing, and that is stated in the spec rather than
  glossed. Markers only exist since 2026-10-24, the one production airing was 2026-10-20, so
  Test 2 will produce the first real clip list.

**Markers are start points; an editor needs ranges.** One row per advance, no end. The out point
is the next marker's in point, which is derivable from rows already held, and for the last marker
it is the end of the recording — knowable only from `ended_at`, which is null on real production
rows. So the last clip legitimately has no end, and it is reported as unknown rather than measured
against `now`: a duration that grows every time the file is downloaded gives an editor two
different answers and no way to tell which was wrong. All of that lives in one pure module shared
by the JSON route and the CSV, so the UI never implements a second copy of the pairing rule.

**Every advance writes a marker, so most rows are not clip candidates.** A 38-minute class
produces dozens and a handful are worth cutting; forty undifferentiated rows leave the editor
scrubbing the video, which is the exact cost this feature exists to remove. The authored note is
recoverable because the policy's precedence is `publicValue || segmentLabel || slideTitle` — a
label equal to neither fallback can only be the authored sentence. One false negative is possible
and documented (an author writing a publicValue identical to the segment label), and the proper
fix is for the write path to store what it chose, which needs a column on a shipped table and
would only help markers recorded after it lands.

**A plain `<a href>` to the CSV route would have 401'd.** The admin JWT lives in `localStorage`
and is attached by the `api` interceptor as a Bearer header, so an anchor carries no
`Authorization` at all — the obvious implementation is a dead affordance, which is the defect
class this whole sequence has been closing. Fetched through `api` and saved client-side instead,
and the filename is read from the server's `Content-Disposition` rather than composed a second
time on the client.

**CSV escaping is the one thing here that corrupts a file silently.** Labels are a sentence a
human wrote, so commas and quotes are ordinary. RFC 4180 quoting, with a test showing that the
header has 11 columns while a naive comma split of a row with a quoted comma yields 12 — which is
precisely what an importer would read without the quotes, shifting every column after the label.
I deliberately did NOT neutralize leading `=`/`+`/`-`/`@` against Excel formula interpretation:
the content is authored by Colaberry staff rather than untrusted input, and mangling a legitimate
label that starts with a dash is a worse everyday cost than a hypothetical. Stated rather than
silently skipped.

**The download filename carries no free text, deliberately.** The obvious name includes the class
title, and a title containing a quote or a newline interpolated into `Content-Disposition` is
header injection. The id and the date are enough to tell two files apart and cannot contain
anything hostile after the filter.

**A class that never aired gets a refusal, not an empty file.** CSV has no room to say "this was
never broadcast", so a header-only file would assert that the class aired and nobody marked
anything — a different and wrong statement. A class that DID air with no markers gets the
header-only file, because that claim is true. The panel makes the same distinction visible: the
route sends `content_started_at` for exactly this reason, and "nobody pressed Mark content
started" is a fixable mistake while "aired with nothing worth marking" is not a mistake at all.
Showing the same blank for both is how the first one goes unnoticed for a term.

**The same unread-feature habit exists on the frontend, which the spec had only charged against
the backend.** Found while hunting for a host: `ClassDetailsModal.tsx` is 211 lines,
self-fetching, and its own header comment says it is opened by clicking a session's title in the
admin sessions table — and nothing imports it. Recorded, not fixed: wiring it up means editing
`AdminAcceleratorPage.tsx` at 1555 lines, and CLAUDE.md's ceiling rule makes splitting that page
the price of the next change to it. The same rule is why the clip panel is its own component
mounted from `ClassKitModal` in two lines rather than sixty lines added to a page.
