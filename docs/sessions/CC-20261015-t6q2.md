# CC-20261015-t6q2 — The first live airing, and the defect it found

## What happened

The first private airing of Colaberry Live ran in production on 15 October 2026, 10:05 to
10:25 AM Central. Live video travelled Zoom to Cloudflare to the Colaberry player, and two
colleagues watched it on their own machines.

**It found five defects in twenty minutes.** This commit fixes the one that made live viewing
unusable.

## The defect

Two viewers reported, independently, that the audio kept repeating. Swati: *"the last lines
keeps repeating."* Kesetebirhan: *"Yes, I just confirmed that."*

The cause was one line in `broadcastPlaybackAdapter.ts`:

```ts
const resumeAt = isRenewal ? media.currentTime : 0;
```

A playback credential lives 120 seconds, so the adapter renews it roughly every 100. Renewal
swaps `media.src`, which reloads the element, and the adapter then restores the viewer's
previous position on `loadedmetadata`.

**That is correct for a replay and wrong for live.** A replay has a stable timeline, so
restoring puts the viewer back where they were. A live manifest restarts its timeline on
reload, so restoring an old `currentTime` seeks *backwards* into the DVR buffer. Every
renewal. Forever. The viewer never reaches the live edge again.

## The fix

The server now says whether the stream is live, and the client stops guessing.

- `GrantResponse` gains `is_live`, set from `occurrence.editorial_state === 'live'` on both
  the Cloudflare and the replay branch of the playback grant.
- The adapter restores position only when `is_live !== true`. Live still resumes playback, it
  just resumes at the live edge, which is the only position on a live stream that means
  anything.

`is_live` is optional, so a client talking to an older server treats the stream as a replay —
the behaviour that existed before this field. That is the safe direction: restoring on a
replay is redundant, while failing to restore one would lose the viewer's place.

**Liveness is deliberately not inferred from the url shape.** It would have been easy to check
for `cloudflarestream.com` and call it live, and it would have been wrong the first time a
provider changed or a replay was served from a CDN. The server knows the editorial state; the
client should not re-derive it.

## Evidence

- `a LIVE renewal does NOT seek backwards - the viewer stays at the live edge` — **confirmed
  able to fail.** With the fix reversed to `resumeAt > 0`, this test fails. That matters: the
  test and the fix were written together, so until it was seen to fail it proved nothing.
- The pre-existing `renews before expiry and puts the viewer back where they were` still
  passes. Both must: the replay case is genuinely different and its behaviour is correct.
- 52 playback-adapter tests, 33 broadcast-controller tests, frontend `tsc --noEmit` clean.

**Honest note on one test.** I also added `a live viewer who PAUSED is still not un-paused by
a renewal`. It passes with the fix reversed, so it is *not* evidence for this change — it pins
the pause behaviour, which is worth pinning, and nothing more. Counting it as proof of the fix
would have been padding.

## What this does NOT fix

Four other defects from the same airing, recorded on the L5.3 ticket and not addressed here:

1. **No audio or unmute controls** on the player. A viewer who lands muted with no unmute
   button leaves and reports the product as broken.
2. **Cloudflare's `/lifecycle` endpoint returns 401** once the input requires signed URLs and
   is broadcasting — it answers fine while idle. This breaks the L5.1 adapter's health check.
   The working alternative, used live during the airing, is
   `GET /accounts/{id}/stream/live_inputs/{uid}/videos`, where the active broadcast reports
   `status.state = "live-inprogress"`. Note the live input's own `status` field stayed `null`
   throughout, so it is not a usable readiness signal either.
3. **`ended_at` is never written** when an occurrence moves to `ended`.
4. **The entry point is not portal-wide** in practice. Testers found the stream through Rooms;
   the portal-wide badge is mounted in the layout route but was not what they noticed.

## The number nobody had

End-to-end latency, Ali speaking to a viewer hearing it: **about 20 seconds.**

This figure did not exist anywhere before. Zoom publishes ~20 seconds only for YouTube,
Facebook and Twitch, and attributes it to *those platforms'* processing time; for a custom
RTMP destination it publishes nothing, and neither does Cloudflare. Ours landing in the same
range is the useful part: the custom path is not materially worse than the named ones.

## Second fix: the health check that reported a live class as dead

The same airing turned up a second defect in the L5.1 Cloudflare adapter, and this one was
the more dangerous of the two because it failed silently in the safe-looking direction.

`readLiveLifecycle` asked Cloudflare whether an input was receiving video by calling
`/lifecycle` on the delivery domain — exactly as Cloudflare's own documentation shows. During
the airing that endpoint returned **401 Unauthorized** the moment the input was actually
broadcasting with `requireSignedURLs` on. It had answered perfectly a few minutes earlier,
when the same input was idle.

**Why that matters more than it sounds.** The adapter's job here is to tell the state machine
whether the provider is ready, and the state machine refuses `go_live` unless it is. So a
healthy class, airing perfectly, would be reported as not ready and refused. An outage reading
as "nothing is live" — the fabricated zero in a different costume.

Cloudflare documents nothing about this. The L5.1 research explicitly flagged it as an open
question: whether `/lifecycle` needs a signed token once signed URLs are required. The airing
answered it the hard way.

### What it reads now

`GET /accounts/{id}/stream/live_inputs/{uid}/videos` on the **API domain**, where an active
broadcast reports `status.state = "live-inprogress"`. That authenticates with the API token
and worked throughout the airing.

Two things are deliberately **not** used:

- **`/lifecycle`**, for the reason above. It is not kept as a fallback: two paths that answer
  the same question drift, and one of them is known to be wrong in our configuration.
- **The live input's own `status` field**, which stayed `null` for the entire broadcast. Its
  name suggests it is a readiness signal and it is not.

A finished recording (`state: "ready"`) is **not** live, and its uid is not returned. Handing
back the uid of a completed recording would invite a caller to treat a replay as a stream,
which is how last week's class ends up behind today's live badge.

### Evidence

Two mutations, both killed by the tests written for them:

| Mutation | Killed by |
|---|---|
| `live = !!first` — any video counts as live | `a FINISHED recording is not live...` plus the three not-ready cases |
| path back to `/lifecycle` | `hits the API host, NOT the delivery host - this is the 401 regression` |

449 tests across all 20 broadcast suites pass.

The response shape is checked rather than trusted: `GET /live_inputs/{uid}/videos` appears
only in Cloudflare's guide, not in its API reference, so it has no published schema.

## Third fix: the end instant nothing ever wrote

`ended_at` has existed on `BroadcastOccurrence` and in `ensureBroadcastSchema` from the
beginning. **Nothing ever wrote it.** Outside the model definition the column had zero
references in the codebase.

The first airing ended cleanly — editorial state moved to `ended`, discovery stopped
returning the occurrence, the live badge cleared for every viewer — and left `ended_at` null.
Any later report on broadcast duration, watch windows or replay availability would have had no
end instant to work from.

The state machine could not even have been idempotent about it: `OccurrenceState` did not
carry `ended_at`, so the pure function had no way to know whether one was already set.

### What changed

- `OccurrenceState` gains `ended_at`, and `toState()` carries it from the model.
- The `end` transition stamps `ended_at` from the injected clock, once.

**Only `ended`, deliberately not `cancelled`.** A cancelled occurrence never aired, and
stamping it with a time it "ended" would assert in the data that something ran and finished.
Cancellation is its own state and reads as one.

### Evidence

Removing the write fails `ending a live broadcast stamps ended_at from the injected clock`.

Stated plainly: the other three tests in that block — no-rewrite, cancel, go_live — **pass
under that mutation too**. They guard against writing the instant in the wrong places, which
is a different property and worth pinning, but they are not evidence that the write happens.
Only the first test is.

453 tests across all 20 broadcast suites pass.

## L4.6: the measurement path, and two artefacts that only claimed to exist

`broadcastTelemetryService` shipped with **no tests and nothing calling it**, flagged as such
in its own commit. L4.6 closes that: the tests, the heartbeat route, and the producer read.

Two things the existing code already claimed were there, and were not:

- `broadcastTelemetryQuery.test.ts` — the service comment read *"the two must agree, which is
  why `broadcastTelemetryQuery.test.ts` asserts the SQL text contains the window"*.
- `scripts/explainBroadcastTelemetry.js` — described as running the plan check *"at deploy
  time"*.

Both exist now. This is the second time on this project that a comment has described wiring
that was never built.

### The test suite I nearly fooled myself with

The service tests mock `sequelize` and match on SQL patterns. Twelve of them passed happily
while I re-keyed the anchor query from `enrollment_id` to `session_id` — a change that
**reverses the entire dedup rule** and would double every watch figure for anyone with two
tabs open.

They passed because the mock answers on `/FOR UPDATE/` regardless of what the `WHERE` says.
The suite was testing the plumbing, not the rule.

The fix was an assertion on the key itself: the anchor query must read
`FROM broadcast_viewer_people`, must filter on `enrollment_id`, and must not mention
`session_id` anywhere. That one test is what kills the mutation; the other twelve do not.

### The two required mutations

| Mutation | Killed by |
|---|---|
| anchor query re-keyed to the tab | `reads the anchor keyed on the PERSON, not on the tab` |
| collection failure renders as an empty room | `a COLLECTION FAILURE carries no count field at all - not zero, not null, absent` |

### Zero and "we do not know"

`GET /audience` answers **503 with no count field at all** when collection fails — not zero,
not null, absent. A client cannot render a number that is not there, which is a stronger
guarantee than asking it to check a flag first.

The metrics dictionary calls a fabricated zero a defect rather than a cosmetic issue, and it
is right: *"nobody watched"* is a verdict on the broadcast, *"collection is down"* is a
verdict on us. Showing the second as the first would have a producer stop a class people were
actually watching.

### The EXPLAIN, run against production

```
Index Scan using idx_bvs_active on broadcast_viewer_sessions s
  Index Cond: ((occurrence_id = $1) AND (last_beat_at >= $2))
Index Scan using idx_bvp_reportable on broadcast_viewer_people p
  Index Cond: ((occurrence_id = $1) AND (is_staff = false) AND (is_test = false))
```

The planner chose `idx_bvs_active` — the plan that index was built for — and a second index
on the people side. No sequential scan.

The script is deliberately honest about its own limits: on a small table a sequential scan
would be the *correct* choice, so it reports that case rather than failing on it. A plan over
0 rows proves the query is plannable and the index exists; it does not prove anything about
40,000 rows, and the script says so.

### Totals

484 tests across 22 broadcast suites. Backend `tsc --noEmit` clean.

## L7.1 — create a broadcast occurrence from the Accelerator session setup flow

**Date:** 2026-10-18 · **Session:** CC-20261015-t6q2 · **Branch:** `workstream/l71-session-occurrence`

### What changed

The session setup flow gained a "Broadcast this class on Colaberry Live" checkbox. Ticking it
creates the broadcast occurrence as a side effect of the session the admin was already
creating. No new route, no new page, no parallel creation path — the ticket is explicit that
building a second flow is the failure mode, and the existing `createSession` already had the
right hook: a flag-gated, best-effort, non-fatal block that calls `ensureRoomForSession`.

- `backend/src/services/broadcast/broadcastSessionOccurrence.ts` (new) — the first supported
  way to create an occurrence. Before this the only `BroadcastOccurrence.create` in the backend
  was inside the dry-run-by-default historical backfill, so nobody had a reachable path.
- `backend/src/services/acceleratorService.ts` — `resolveRoomId` now returns the room id the
  room block was already fetching and discarding; `enableLiveForSession` is the new side effect.
- `backend/src/controllers/acceleratorController.ts` — `live_enabled` is split OUT of the body
  rather than spread through, because there is no such column and a silently-dropped key is the
  failure the broadcast schemas' `.strict()` rule exists to prevent.
- `frontend/src/pages/admin/AdminAcceleratorPage.tsx` — one checkbox in the existing modal.

### Decisions worth recording

**The occurrence's existence IS the live flag.** No column was added to `live_sessions`. An
authoritative `broadcast_source_refs` row for `('live_session', session.id)` answers "is live
enabled", and `uq_broadcast_source_ref` is UNIQUE on that pair — so a second tick physically
cannot mint a second occurrence. Idempotency is the database's, not the code's.

**Re-timing happens whether or not the box is ticked again.** The occurrence key embeds the
start instant, so a rescheduled class whose occurrence is not moved keeps the old time — and
the preview window and the whole access decision are measured from it. `updateSession` re-runs
the ensure whenever live is already enabled.

**Creation is not gated on `BROADCAST_ENABLED`.** A private, scheduled occurrence is inert
while the flag is off. Gating it would force the feature on globally before a class could be
set up, which inverts the workflow.

**Nothing guesses a time.** `deriveStartInstant` reports `derived: false` for an unparseable
time while still returning a usable-looking Date (`classInstant` falls back to 10:00). The
ensure refuses on the flag, not the Date.

**Scope held:** one-to-many across time per Ali's option B on 18 Oct; turning live OFF is not a
checkbox, because cancelling a show is a producer command.

### Verification

- 318 tests across 19 suites, including every neighbouring broadcast suite — no regressions.
- Backend `tsc --noEmit` clean, against a baseline captured clean *before* any edit.
- **Four mutations, each killed by a named test:**
  - removed the explicit `access_mode` → `creation › creates the occurrence PRIVATE and SCHEDULED, with the room and the derived instant`
  - trusted the Date when `derived` was false → `refusals — nothing is ever guessed › refuses a time it could not parse, even though a usable-looking Date comes back`
  - allowed re-timing a live show → `an occurrence that already exists › refuses to move a show that has already gone live`
  - dropped the room id on the wiring → `createSession — Colaberry Live occurrence › creates an occurrence, with the room id, when live is enabled`

### Not done

**The screenshot of the real screen.** It is an acceptance criterion and it cannot be satisfied
before the change is deployed — a CSS mockup is explicitly not acceptable here. It is owed after
merge, and the ticket should not close without it.

## L4.9 — wire the player to the heartbeat endpoint

**Date:** 2026-10-20 · **Session:** CC-20261015-t6q2 · **Branch:** `workstream/l49-heartbeat-wiring`

### The defect

Test 2 aired for twenty minutes with real viewers in the portal and recorded **zero** telemetry
rows. Not a low number — zero, in both tables, while nginx logged 16 successful playback grants
and 103 discovery polls.

L4.6 had shipped the ingestion route, the schema, the bounded upsert, the
unavailable-never-zero audience read and thirteen tests. **Nothing on the client ever called
it.** A producer with no consumer. The only frontend matches for "heartbeat" were the
curriculum watch-gate and admin analytics, both unrelated systems; the control was that the
frontend *does* call `/playback`, from `LiveMiniPlayer.tsx`.

### What changed

- `frontend/src/services/broadcastHeartbeat.ts` (new) — the caller. Its own module rather than
  an addition to `broadcastPlaybackAdapter.ts`, which is already at 510 lines, the hard ceiling
  in CLAUDE.md, where the rule is that the next change splits before it adds.
- `frontend/src/components/portal/LiveMiniPlayer.tsx` — a second effect, separate from the
  adapter's, driven by the media element's own events.

### Decisions

**Measurement must never affect playback.** Every send is fire-and-forget; every failure is
swallowed after logging. A stream that stutters because a metric could not be recorded is a
far worse bug than the missing metric.

**Driven by media events, not adapter phase.** The question is "is a human watching right
now", and only the element knows whether pixels are moving.

**A hidden tab is not a viewer.** Checked at beat time, not only on the visibility event,
because a backgrounded tab keeps a `<video>` "playing" and counting it inflates the audience.

**15-second cadence**, matching the server's `playbackHeartbeatSeconds` default, inside its
120/min limiter and comfortably under the 45-second viewer-expiry window (two beats plus
margin). The cadence is operator-configurable server-side and is **not** published to the
client, so this is a duplicated constant. Publishing it on the grant response would remove the
duplication; that is a backend contract change and deliberately out of scope here.

**No unload hack for the final beat.** `stop()` makes a best-effort `ended` post; on a real page
close it will not arrive, and it does not need to — the server's expiry window is precisely the
mechanism for a viewer who vanishes.

### Verification

- 143 tests across 12 suites, including every neighbouring player suite — no regressions.
- Frontend `tsc --noEmit` clean, exit code read directly rather than through a pipe.
- **Two mutations, each killed by named tests:**
  - unwired the `play` listener (reproducing the shipped bug) → `posts a heartbeat when the
    video starts playing` and `reports pause, buffering and ended as distinct states`
  - counted hidden tabs as viewers → `does not beat while the tab is hidden, even though the
    element is still playing`

The first mutation is the point of the whole ticket: **it recreates exactly what shipped on
16 October, and the new tests fail against it.** Thirteen server-side tests could not see that,
because every one of them started a layer below the gap.

### Not done

Nothing here has been exercised against a real airing. The defect it fixes was invisible to a
full test suite and visible within minutes of a live stream, so the fix carries the same
caveat: it is proven by test and unproven in production until the next broadcast.
## L7.4 — end a broadcast without an engineer

**Date:** 2026-10-20 · **Session:** CC-20261015-t6q2 · **Branch:** `workstream/l74-end-control`

### Why

Ali, during Test 2: *"Can we just end it once the stream is done? I won't have you there every
time."* He stopped the Zoom stream at ~14:04 UTC; the occurrence stayed `live` until an engineer
ran a producer command at 14:09. For five minutes the portal advertised a broadcast over dead
air, and with nobody running scripts it would have stayed that way indefinitely.

### What changed

- `backend/src/controllers/broadcastController.ts` — the playback grant now returns
  `is_producer` and `version`, both server-decided, on both the live and replay branches.
- `frontend/src/services/broadcastProducer.ts` (new) — the end command, with 409 / 403 / failure
  as distinct outcomes rather than one error.
- `frontend/src/components/portal/LiveMiniPlayer.tsx` — a two-click End control, and a grant
  observer that reads capability and version from the response.

### Decisions

**The control lives in the portal, not the admin app.** The command route authenticates a
PARTICIPANT and derives producer rights from the staff context on that token. An admin-side
button would need either a participant token it does not have or a second command route — and a
parallel command path is exactly what this subsystem keeps being warned about.

**Capability is granted, never inferred.** `is_producer` absent means NO. The safe default is
deliberately the opposite of `is_live`'s, because the consequences are opposite: a missing
replay-restore loses a viewer's place, while a wrongly-offered End button ends a class in front
of everyone.

**Two clicks.** Ending is terminal; there is no un-end command.

**No version, no action.** Guessing a version would either be refused or act on a state the
producer has not seen.

**The observer lives in the component, not the adapter.** `broadcastPlaybackAdapter.ts` is at
510 lines — the CLAUDE.md hard ceiling, where the rule is that the next change splits before it
adds. The component owns the fetcher it injects, so observing the response costs nothing.

### Verification

- Frontend: 134 tests across 11 suites, `tsc --noEmit` clean.
- Backend: 46 tests in the controller suite, `tsc --noEmit` clean.
- **Two mutations, each killed by named tests:**
  - dropped the `is_producer` check → `is NOT offered when the server did not say is_producer`
    and `is NOT offered when the server omits is_producer entirely`
  - removed the version guard → `refuses to act at all when the server gave no version`
- The backend pair asserts BOTH polarities (`true` for staff, `false` for an ordinary viewer),
  so no hardcoded constant can satisfy both — mutation-equivalent by construction.

### Not done, and it is the larger half

**Auto-end is NOT in this change.** It cannot be: scoping it found that `runProviderEvent` is
exported, tested and **called by nothing**, so `provider_health` is permanently `unknown` in
production. That is why `go_live` had to be hand-fed during Test 2, why a dropped stream is
never marked `reconnecting`, and why a safety net has nothing to watch. Raised as **L5.5**,
P0 — it blocks this ticket's second half and unattended operation generally.

**Also note:** this branch and L4.9's both modify `LiveMiniPlayer.tsx`. Whichever merges second
needs a small rebase. Kept as independent PRs so each reviews on its own.
