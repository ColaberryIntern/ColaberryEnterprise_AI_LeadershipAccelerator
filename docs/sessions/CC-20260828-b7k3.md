## The `trigger` enum: assessed, deliberately NOT changed

`METRIC_PROVENANCE_PIPELINE.md` §5.2 notes that `caseStudySyncService.ts:122` accepts
`manual | webhook | reconciliation | project_update` and rejects `'scheduled'`, while
`CaseStudySyncRun.ts:19` documents the value as valid.

**Decision: out of Stage 0, in both of its possible directions.**

1. **Widening the Zod enum to accept `'scheduled'` is refused outright.** The document's §10
   lists "any scheduled recompute of a published figure" under what it would say no to
   regardless of budget. Adding the value would admit a trigger that nothing in the codebase
   can produce — there is no cron entry for case study sync — so it is a contract widened
   toward a capability the scope declined, with no caller on the other side.

2. **Correcting the stale comment is defensible but does not belong in this diff.** Two of the
   three sources already agree: the Zod enum (`caseStudySyncService.ts:122`) and the exported
   type (`types/caseStudy.ts:226`) carry the same four values. Only the model's doc comment
   disagrees, and it is wrong in both directions — it names `scheduled`, which is rejected, and
   omits `reconciliation` and `project_update`, which are accepted.

   The inconsistency is also **larger than the document recorded**: the next line,
   `CaseStudySyncRun.ts:20`, documents `status` as `running | success | partial | failed` while
   `CaseStudySyncStatus` (`types/caseStudy.ts:229`) includes a fifth value, `unchanged` — the
   idempotent-rerun outcome. So this is a model-documentation correction spanning two contracts,
   not a one-line fix, and bundling it onto a DRI-gated schema change to a *different table*
   would ask the DRI to approve two things while reviewing one.

**Logged as a proposal, not done.** The correct fix direction is to make the comments match the
enum, never the reverse. That matters because the stale comment is the most plausible cause of
someone later "fixing" the Zod enum to match it, which would silently enable the exact thing
§10 forbids.

The realistic failure was never brief confusion — it was someone WIDENING THE WORKING ENUM to match the broken comment, because the comment sits beside the column and the enum lives two modules away. A previous investigation had already declined to add `scheduled` to the enum for exactly that reason; this closes the other half, and the rule is now directional and enforced: comments follow the union, never the reverse. **Two details in the test are the difference between a check and a decoration.** The doc-comment lookup anchors on the field declaration and reads BACKWARDS to the nearest comment, so a second field's comment can never satisfy the first — scanning the file for any pipe-separated run would pass if any comment anywhere happened to carry the right words. And a non-vacuity test asserts both unions were actually found, because a renamed union would otherwise make every comparison compare an empty list to an empty list and pass green. That is the same failure mode this session's own memory records twice: a check that iterates over extracted items must assert the extraction found something specific, not merely something. **Reading source text rather than a runtime value is not a shortcut here** — a comment has no runtime value to assert against, which is precisely why it drifted. Four suites in this repository already use the technique. A fifth test does assign `'reconciliation'` and `'unchanged'` to their union types so `tsc` corroborates that the file-read lists are the real unions rather than two strings that happen to match. **Adding a member to either union will now fail this test by design**; the failure names the file to update, and the alternative is a comment that silently stops being true. **NOT DEPLOYED** — this is a comment and a test, and neither is reachable at runtime.
