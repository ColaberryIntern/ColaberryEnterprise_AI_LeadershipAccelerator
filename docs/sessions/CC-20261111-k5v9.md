# CC-20261111-k5v9

## Revenue Room: give the evidence spine its own table name

- [x] Fix every Revenue Room drill-down returning "Could not build the drill-down."
  - Date: 2026-11-11
  - Session: CC-20261111-k5v9
  - What changed: renamed the R3 evidence spine's table from `evidence_links` to
    `revenue_evidence_links` across its seven files, because the original name was already
    owned by the ticket/evidence feature.
  - Verification: 101 tests pass across the four covering suites
    (`jest -c jest.ci.config.ts --ci`); backend `tsc --noEmit` exits 0, proved real by a
    planted control error that it caught at `evidenceLinkService.ts(430,7)` with exit 2.
  - Notes: see the diagnosis below. Production verification is still owed after deploy.

### The fault

`enterprise.colaberry.ai/admin/revenue-room/membership_subscriptions` returned
"Could not build the drill-down." The controller catches everything into that one string, so
the real error only appears in the container log:

```
revenue_room_drilldown_failed ... "column \"source_system\" does not exist"
```

Raised by `getEvidenceTimeline` (`evidenceLinkService.ts:276`) via `getDrilldown`
(`revenueRoomDrilldown.ts:179`).

### The cause: two features, one table name

`evidence_links` already existed in production, owned by the ticket/evidence feature:

| | columns | rows |
|---|---|---|
| in production | `id, evidence_id, ticket_id, link_role, created_at` | 6 |
| R3 expects | 18, incl. `source_system`, `initiative_type`, `initiative_key`, `observed_at`, `unlinked_at` | n/a |

Its owners are `db/ensureEvidenceSchema.ts`, `models/EvidenceLink.ts`,
`services/evidence/evidenceService.ts`, `workforce/liveAgentsService.ts` and
`workLedger/summaryGeneratorService.ts`. None of them were touched.

`CREATE TABLE IF NOT EXISTS evidence_links` found the table already there and did nothing.
Every statement after it then failed against the wrong columns, all ten logged at `warn` and
swallowed so the boot continued:

```
ensure_evidence_link_schema_statement_failed ... "column \"source_system\" does not exist"
ensure_evidence_link_schema_statement_failed ... "column \"initiative_type\" does not exist"
ensure_evidence_link_schema_statement_failed ... "column \"unlinked_at\" does not exist"
  ... 7 more, every restart
```

So the Revenue Room has been querying another feature's table since R3 shipped. **This broke
every drill-down, not only `membership_subscriptions`** — `getDrilldown` calls
`getEvidenceTimeline` for any card key.

`tableExists()` was never at fault: it correctly found a table called `evidence_links`, which
is precisely what made the failure confusing rather than obvious.

### The lesson, which outlives this table

`IF NOT EXISTS` guards against a **second run**. It does not guard against a **second owner**,
and it cannot tell the two apart. Where two features might reasonably pick the same noun,
namespace the table to the feature that owns it. This is recorded in the module header so the
next person meets it before they meet the bug.

### Scope

Seven files, all Revenue Room:

- `backend/src/db/ensureEvidenceLinkSchema.ts` (+ its test)
- `backend/src/services/revenueRoom/evidenceLinkService.ts` (+ its test)
- `backend/src/services/revenueRoom/govProposalEvidenceBackfill.ts` (+ its test)
- `backend/src/services/revenueRoom/revenueRoomDrilldown.ts`

Generated index and constraint names move with it
(`uq_revenue_evidence_links_source_initiative` and friends), all within Postgres's 63-character
identifier limit; the longest is 46.

### Safe before the table exists

`tableExists()` now asks for `revenue_evidence_links`, so until the next boot creates it the
drill-down takes the already-written `state: 'absent'` path and renders its own note — "a
missing source is not an empty one" — rather than throwing a 500. The fix therefore improves
the page before the schema catches up, and `ensureEvidenceLinkSchema` creates the table on the
first boot after deploy.
