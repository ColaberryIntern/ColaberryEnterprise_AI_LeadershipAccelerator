  - Notes: Two design decisions worth recording, both reversals of a first answer.
    **(1)** A `pull_request`-triggered GitHub Actions workflow was rejected on evidence, not
    preference: `.github/workflows/delivery-execution-runner.yml` states that workflows here are
    manual-dispatch only and that "a workflow that fires on push would be" an unauthorized
    production agent worker, and its preflight fails the run if `BASECAMP_TOKEN` is present. A
    workflow posting to Basecamp needs exactly the credential that gate forbids.
    **(2)** Extending the existing `/api/webhook/github` receiver is the better long-term answer
    and is recorded as the upgrade path in the runbook, but it is a per-student multi-tenant path
    keyed on `findRepoBinding(owner, repo)` → enrollment, this repository has no such binding, and
    no webhook is registered on it. It also needs an admin action on the GitHub repo that no code
    change can perform.
    The watcher reports **merged, never deployed**. "Deployed" and "production-verified" are not
    pull request fields and this stack deploys over ssh rather than through GitHub Deployments, so
    reporting them would mean inferring them. The merge comment says so in as many words.
    Initial reconnaissance was performed against the OneDrive working tree, which is **3,279
    commits behind `origin/main`**, and its central finding ("no GitHub Actions in this repo") was
    false. Every fact above was re-verified against `origin/main` before any code was written.
