# CC-20261012-w9k4 — L5.1: Cloudflare Stream behind the playback-grant contract

## What this ticket asked for, and what landed

L5.1 asked for a Cloudflare Stream provider adapter sitting **behind the playback-grant
contract that already exists**, so live media travels the same entitlement path that replay
already proved. The contract, the state machine and the player were to stay untouched.

What landed:

- `backend/src/services/broadcast/providers/cloudflareStreamProvider.ts` — create and read a
  live input, read whether it is actually broadcasting, mint a signing key, and convert an
  already-decided expiry into a signed Cloudflare HLS url in the grant shape the player
  already understands.
- A **provider branch** in `postPlaybackGrant`. Occurrences with `provider = 'cloudflare'`
  take the live path; everything else is byte-identical to before.
- `backend/.env.example` documents the credentials and what happens when they are absent.

`backend/src/services/broadcast/broadcastPlaybackGrant.ts` has **no diff**. That was an
acceptance criterion and the diff is the evidence.

## The finding that changed the design

The ticket named three credentials: `CLOUDFLARE_ACCOUNT_ID`, `CLOUDFLARE_STREAM_SUBDOMAIN`,
`CLOUDFLARE_STREAM_TOKEN`. Those three support Cloudflare's `POST /stream/{uid}/token`
endpoint, which mints a signed playback token server-side.

Cloudflare's own documentation (securing-your-stream, read 2026-10-12) rules that endpoint out
for us. Verbatim: it is "recommended for testing purposes or if you are generating less than
1,000 tokens per day" and "requires making an API call to Cloudflare for each token, *which is
subject to rate limiting*". Our grant TTL is 120 seconds, so **one** viewer needs about 30
tokens an hour, and the request's own 1,000-viewer planning scenario is roughly 30,000 an
hour. Cloudflare's stated alternative for that volume is a signing key, used offline.

So tokens are signed locally with RS256, which needs two more environment values:
`CLOUDFLARE_STREAM_SIGNING_KEY_ID` and `CLOUDFLARE_STREAM_SIGNING_KEY_PEM`. **This is not a new
vendor or a new cost** — the key is minted from the same account with the same API token, via
`createSigningKey()` in this adapter. It is one extra setup step, performed once.

Two further reasons it is the better answer regardless of volume: a network round trip inside
the grant path would put a Cloudflare API outage between a paying viewer and their video, and
Cloudflare's documentation does not actually confirm that the `/token` endpoint accepts a
*live input* uid at all.

## How the preview deadline survives crossing a vendor boundary

This was the part worth getting right. `computeGrantExpiry` already decides the instant a
viewer's access ends — `min(now + ttl, contentStartedAt + previewSeconds)` — and the 900-second
rule lives there. The adapter does **not** recompute it. The controller calls
`computeGrantExpiry`, hands the resulting instant to `signLivePlayback`, and that instant
becomes the JWT's `exp`. One piece of arithmetic, two media paths.

`exp` is seconds; our contract is milliseconds. The conversion is **floored**, which can only
move the deadline earlier, by under a second. Ceiling would hand a preview viewer up to 999ms
past a deadline the rest of the system enforces to the millisecond. Mutation M7 reverses it.

## Verification

- **Adapter suite: 56 tests, all passing.** Includes timeout, 401, 403, 404, 429, 5xx,
  non-JSON body, `success:false`, and a result missing required fields.
- **Controller provider branch: 4 tests.** The load-bearing one asserts that an unconfigured
  provider returns 503 with **no `url` field at all** — not a `/bm/` url, not an unsigned one.
- **Every broadcast suite: 20 suites, 446 tests, passing.**
- **Mutation testing: 13 mutations, 13 killed, 0 survivors.** Each killing test is named in
  the PR body.

Two honest notes on the evidence:

1. **The first mutation harness run was worthless and said so.** It reported 13 survivors.
   Its control run reported `compiled=false`, which is how I knew the harness — not the code —
   was broken: it looked for jest in `backend/node_modules` when jest is hoisted to the repo
   root. A mutation harness whose control does not go green is not evidence of anything. Fixed,
   re-run, and the control is now clean.

2. **M12 genuinely survived the first real run**, and the fix was a test, not the code. The
   envelope guard `success !== true` had a test that passed even with the guard deleted,
   because that test's payload also had a null `result` which failed the shape check further
   down. It proved the symptom, not the guard. The replacement sends `success: false` with a
   **perfectly valid** result underneath, so the guard is the only thing that can reject it.

3. **One flaky run, reported rather than buried.** A full `--testPathPattern broadcast` run
   reported 5 failures; an immediately following run on the same tree, with no source change
   between them, reported 446/446 passing. This matches previously recorded flakiness in this
   repo's larger suites. The five were not individually named before the re-run, so I cannot
   say which they were — only that the tree is green on repeat runs.

## What this does NOT establish

- **Nothing has been run against the real Cloudflare API.** Every test uses an injected fetch
  double, and the suite installs a throwing global `fetch` and asserts it was never called.
  The adapter is proven against the documented contract, not against the live service.
- **The playback token has never been presented to Cloudflare's edge.** Cloudflare publishes no
  4XX examples for any Stream endpoint and documents nothing about what the delivery domain
  returns for an invalid or expired token. That gap is real and belongs to the first live test.
- **The credentials are not in the production environment**, so the branch fails closed there
  today. That is the designed behaviour, not a defect.
- **`CLOUDFLARE_STREAM_SUBDOMAIN` is still incomplete** — the recorded value is truncated
  (`customer-keedfbz9hw…`). The full value has to come off the Stream dashboard page.
