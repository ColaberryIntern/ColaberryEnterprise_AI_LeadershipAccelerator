  - Notes: **NO NEW FLAG MECHANISM, WHICH M29 FORBIDS EXPLICITLY.** The ticket's out-of-scope
    line is "no second kill switch, no second flag registry". Nothing here stores state, reads
    an env var, or defines a switch. Every answer composes three existing gates:
    `isGrowthJourneyCapabilityEnabled` (which already ANDs the growth master, so this module
    never reads the master itself), `isExplorerFeatureEnabled`, and `isKillSwitchActiveStrict`.
    A consequence worth stating: adding a Maya capability adds no flag, so it needs no update to
    the hand-maintained flag pins in `config/__tests__`, which otherwise require a count bump in
    three places.
  - Notes: **THE KILL SWITCH IS CHECKED FIRST, AND THAT IS A DELIBERATE DEVIATION.** M29 says
    "system_kill_switch overrides everything". The existing precedent, `resolveStops()` in
    `growthJourney/execution/resolveExecutionMode.ts`, checks flags first and the switch at step
    5. The OUTCOME is identical either way, off is off, but the REASON differs: there a
    master-off answers `flag_master_off` without ever reading the switch. Here the switch wins
    the reason too, because somebody asking "why can Maya not act" during an incident should be
    told the incident, not a flag that also happens to be off. A test pins exactly that, and a
    Proxy that throws on any property read proves no flag is touched when the switch is active.
  - Notes: **THE STRICT READER, SO AN UNREADABLE SWITCH FAILS CLOSED.** `isKillSwitchActive`
    swallows a read error and returns false, which fails OPEN. For an agent that can contact a
    human that is the wrong default, so a throw becomes `kill_switch_unreadable` and the
    capability stays off. The resolver never throws: an unreadable switch is an answer, not an
    exception for every future caller to remember to handle.
  - Notes: **THE MAPPING IS THE REVIEWABLE DECISION, AND ONE ROW NEEDS ALI'S EYE.** No Maya
    capability flags exist today, so the four capabilities are mapped onto existing gates:
    `respondToExplorerDm` and `sendInAppWelcome` to `journeyExecution` plus Explorer's
    `inAppNudge`; `createJourneyHandoff` to `journeyHandoffs`, which is exactly that action; and
    `readPerson360` to `journeyDecisions`. That last one is a judgement. M34 calls Person 360
    "her eyes", and reading is not acting, so gating it on the decisions flag treats "Maya may
    form a view about a person" as the switch. Leaving reads ungated was rejected because M29's
    first criterion is that EVERY capability is off by default. If the mapping is wrong it is
    wrong in the safe direction: it makes Maya blind rather than talkative.
  - Notes: **A BOOLEAN WOULD HAVE BEEN THE WRONG RETURN TYPE.** The resolver returns
    `{ capability, enabled, reason }`. A bare boolean makes "stopped by an incident" and "never
    launched" indistinguishable, which is the same absence-versus-zero mistake the M24 fixes
    removed from the score's inputs, one layer up.
