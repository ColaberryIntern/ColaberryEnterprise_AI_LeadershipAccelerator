### The four-lens admin surface lab (2026-08-26)

- [x] **`sectionOrder` stopped being a mechanism that had never been given two different values: four differentiated lenses, an attribution floor that makes a truthfulness constraint structural rather than editorial, a segmented four-tab admin lab behind a default-closed server-side allowlist, and a preview surface that is deliberately not the publish surface.**

  - What changed: **NOT DEPLOYED — local only.**

    **(1) The four lenses actually differ.** `caseStudySurfaceProfiles.ts` passed one shared `SECTION_ORDER` constant to all four profiles, so a four-lens preview would have rendered four identical pages. `sectionOrder` is now a parameter and the four carry genuinely different values, each derived from its reader's question per `SURFACE_LENS_MODEL.md` §3. **Enterprise is deliberately unchanged** — it is the only publishable surface, so its order is what `/stories/:slug` renders today, and `STORY_STUDIO_PLAN.md` C-entry-2 blocks the proposed measurement-led order on the pilot's hero/measurement duplication (`heroMetrics[0]` and `measurement.metrics[0]` are the same metric, so leading with `measurement` prints the same card twice inside one screen). It is also the control: three lenses moving against a fixed fourth is how an operator can see the difference is the lens and not the record. Training leads `contributors` ahead of `build`; AI Flotation leads `architecture` and lifts `repositories` to fourth; Refactored leads `build`. **All four contain all ten keys and `hiddenSections` stays `[]` on all four** — a lens reorders, it does not drop, because a record's evidence is not audience-dependent.

    **(2) `requiredSections`, the attribution floor.** New field on `CaseStudySurfaceProfile`, `['contributors', 'repositories', 'cta']`, identical on all four surfaces, subtracted from `hiddenSections` in `visibleSections()` **before** the section walk. This is the change that turns `SURFACE_LENS_MODEL.md` §3.3's editorial intention into a property of the system. The concrete failure it makes unexpressible: an architecture-led page under an AI Flotation masthead with "who built it" suppressed implies an authorship the record explicitly denies (`builtBy` is `colaberry_team`; `ai_flotation_team` is a separate enum member) — **using nothing but section order, with no copy change anywhere.** The floor constrains the LENS, never the DATA: `isSectionSupported` still runs afterwards, so a record with no contributors is still allowed to be quiet. A lens may not choose to be silent about attribution; a record with nothing to say still may.

    **(3) `surface: PublicSurfaceView` on the admin preview response.** The whole client-side gap. `visibleSections()` takes a `PublicSurfaceView`; the preview returned a bare `surfaceKey` string, which carries neither the order, the hidden set, nor the floor. `PublicSurfaceView` and `surfaceView()` were **private to `routes/publicCaseStudyRoutes.ts`**, and importing a route module back from a service would close a routes → services → routes cycle and drag Express router construction into a service's import graph — so both moved to a new leaf module `services/caseStudy/caseStudySurfaceView.ts`, re-exported from the route file so no importer's path changed. `caseStudyAdminReview.ts` was at 497 of CLAUDE.md's 500 hard ceiling, so the `CaseStudySurfacePreview` interface moved to `caseStudyAdminPreview.ts` — the module that already owns the preview concept and whose own header records being extracted for exactly this reason — and is re-exported. Review is now 485 lines.

    **(4) Authorization: `CASE_STUDY_SURFACE_LAB_USER_IDS`, default `off`.** The `SBP_AGENT_SCOPING` pattern the product owner chose: parsed once in `config/env.ts` beside its precedent, `off` / `all` / comma-separated admin user ids, resolved by a pure predicate in a leaf module (`caseStudySurfaceLabAccess.ts`) so every boundary case is a one-line assertion rather than a router stand-up. **No hardcoded email or personal identifier anywhere** — the repo's `requireCoryAuthorized` bakes one person's address into two files and is the anti-pattern here; an identifier in a conditional is a permission that cannot be granted, revoked or audited without a deploy. **Mounted path-scoped in `adminRoutes.ts`**, on `/api/admin/case-studies/:id/preview`, above `router.use(caseStudyAdminRoutes)` — never as a bare `router.use` inside the sub-router, which applies to every later router's paths and has caused a production outage in this repo. `requireAdmin` is repeated on the same scoped mount because middleware there runs before the route's own guards and the gate needs `req.admin.sub`. **It refuses a REQUEST, not a route:** an `enterprise` preview and every other Case Study admin call pass through untouched, so the existing review desk is unchanged for every admin. Everything fails closed: unset, blank, unrecognised, a caller with no id, and a repeated `?surfaceKey=` query param (which arrives as an array, so anything that is not a plain string is refused).

    **(5) The segmented control.** New `frontend/src/pages/admin/CaseStudySurfaceLab.tsx` plus a pure `caseStudySurfaceLabModel.ts`. Four discrete `role="tab"` controls in a `role="tablist"` with arrow-key/Home/End navigation, 44px minimum targets, and the live surface marked in **text** (`↑ LIVE`) rather than by colour alone. Beneath it a `<dl>` in an `aria-live="polite"` region: **canonical truth first**, because it is the line that proves the lens did not change the facts; then the surface lens with its reader question; then the publication state beside the real gate verdict and its blocker codes; then draft state. Band composition comes from the same `visibleSections`/`isSectionSupported` the public page uses — a lab with its own idea of which bands render is a lab that agrees with itself and not with production. It also separates "this lens hid it" from "the record is silent", which look identical on a rendered page and are completely different problems.

    **(6) No draft change count, and it was not an oversight.** Nothing in this system computes one: snapshots are content-hashed wholes, no code compares two snapshots' contents, and a number here would be a number a reader trusts and nobody can derive — the exact failure the module exists to prevent. `draftState()` returns one of four **states** (`no-snapshot`, `not-published`, `live-matches-draft`, `draft-ahead`) and the panel says so on screen. There is a test asserting the label contains no `N changes`-shaped string, and the browser run asserts it against the live DOM.

    **(7) Preview surface split from publish surface, which is the safety item.** One `SURFACE = 'enterprise'` constant used to serve preview, publish, unpublish and the publication lookup. Preview now follows the tab; publish and unpublish read `PUBLISH_SURFACE`, a constant. **Wiring publish to the tab is the one genuinely dangerous version of this feature** — an operator idly exploring Training would be one click from publishing to a surface whose framing copy has never been reviewed and whose gate refuses it for a reason they would then be tempted to work around. The lab component contains no publish path at all: not a disabled one, not a confirm-guarded one, none.

    **(8) Two things found by building it.** The admin preview panel's left column is a verbatim snapshot dump that **names private repositories** by a disclosed §34 exception pinned in `AdminCaseStudies.states.test.tsx`. Auto-loading the lab on arrival would have put that on screen for anyone who merely navigated to the page, so the raw dump stays behind its own click (`rawPanelOpen`) while the lab auto-loads. And the auto-load fires for `PUBLISH_SURFACE` **only** — an admin who is not on the allowlist must never meet a 403 they did not ask for. Separately, `CaseStudySurfacePreview.projection` was typed as a loose `PublicCaseStudyProjection` with a `[key: string]: unknown` escape hatch, which cannot feed `isSectionSupported`; casting into the real type would have been asserting a shape rather than having one, so the admin client now references `PublicCaseStudyDetail` — the contract the backend actually sends.
