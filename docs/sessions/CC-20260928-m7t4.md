## The design

**Spine: "nobody told it no."** Every AI disaster is an action nobody said the system
could not take.

The lab is `./governance-lab/` — an agent that proposes real actions and a step that
carries them out, with a mode switch so it misbehaves on command:

| `AGENT_MODE` | Proposes |
|---|---|
| `normal` | refund $40, 2-year-old account, no prior refunds |
| `generous` | refund $2,400, account 6 minutes old, 4 refunds today, address changed after the order |
| `sloppy` | delete customer 8891 ("looks like a duplicate") — record has orders |
| `rogue` | export 40,000 customer rows **and** email every one of them |

The agent is never malicious. It is helpful in all four modes. That is the point.

### Monday (session 20) — 12 teach / 2 builds / 7 questions / 3 story beats

Build 1 builds the agent and the ledger **with no gate at all**, and the prompt
explicitly tells Claude Code not to add one or warn that one is missing. All four
modes succeed. $2,440 moves, a customer with orders is deleted, 40,000 people are
emailed, and every run exits zero.

Build 2 adds exactly **one rule** (`refund-limit`: over $500 → deny) plus a
**closed default** (no matching rule → deny). The result is the night's payoff:

> One rule you wrote stops one thing. The default you closed stops two more you never
> considered.

Nobody in the room writes a rule about deleting customers or exporting 40,000 rows.
`default-deny` catches both. That is fail-closed, run rather than asserted.

### Thursday (session 21) — 8 teach / 6 prompts / 7 questions / 3 story beats

Matches the non-overridable rail exactly: **CP0 Baseline · CP1 Policy blocks ·
CP2 Human gate · CP3 Auditable.**

- **CP0** — one prompt that verifies Monday's folder (~1 min) or rebuilds it (~4 min).
- **CP1** — five-factor ABAC with a computed risk score. The proof is the *same*
  $2,400 refund coming back **denied** in one context and **escalated** in another,
  from the same policy file, with reasons naming the rule and the deciding fact.
  Rule order is taught as a design decision: if `refund-large` (escalate) matched
  before `refund-suspect` (deny), a stolen card would reach a human instead of a wall.
- **CP2** — the human gate, and the three things that make escalation a control rather
  than paperwork: the facts travel with the request, the approval is **single-use**,
  and an unanswered request **expires as a denial**. Silence is not consent.
- **CP3** — one correlation id per decision, a **hash-chained** append-only audit log,
  a `why <correlationId>` replay, and `verify-audit`. Then every student edits one
  number in their own audit log on purpose and watches the verifier name the exact row.

Then BREAK (an `ungoverned/` copy under the same four actions) and HARDEN (the same
four governed, a side-by-side table, `GOVERNANCE.md`, one commit containing only the
folder).

### Participation, structurally

Ali asked for full class participation, so it is built into the run of show rather
than bolted on:

1. **The authority table.** While build 1 runs, the room writes the four action rows
   on the board and supplies each verdict. The instructor pushes once per row —
   *which fact would change your answer?* — and that second column is the context
   factor. The table becomes Thursday's policy file.
2. **The decision-theater poll.** The room *is* the approval queue. They vote on
   "refund $2,400 to order 7781, the customer says it never arrived" — and are only
   told afterwards that the account was 6 minutes old, had 4 refunds that day, and had
   its address changed after the order. All three facts were in the database while
   they voted. An approver without the facts is not a control; they are a signature.
3. **"Six days unanswered."** The most contested idea of the week, and the room splits.

World stories only, no program call-backs: the Hawaii false missile alert (2018),
Stanislav Petrov (1983), concentrated potassium chloride removed from ward stock,
the flight recorder, the ship's log kept in ink, and Knight Capital (2012).

## The trap this run hit

`kitSpecDaySlides.ts` builds every segment in a fixed order: generated opener →
teach slides (`<seg>-200+i`) → story beats (`<seg>-900+i`) → interactions
(`<seg>-950+i`). A story beat keyed to a segment therefore lands **after every teach
slide in it**, never between two of them.

Seven presenter notes were written against the order I intended rather than the order
the generator produces — "now run the decision-theater poll", "then straight into
demos", "then CP0", "then the roadmap slide with the timings". Every one of them was
wrong, and none of it is visible in the source.

This is the same failure Week 9 hit on 2026-09-21. It is only catchable by reading the
rendered order back out of the database, so this time the tool is **committed** rather
than left in the container:

```
node /app/dumpDeck.js <sessionId> [--notes]
```

It prints index, `kind:id`, SAY count, whether the tip is authored / generated
boilerplate / missing, and the title — then reports any `slideNotes` key that matched
no rendered slide (a silent failure: the note simply never appears). All seven notes
were corrected and re-applied.

## The from-scratch rule, made mechanical

Both composers carry their own lint (`--check` runs it with no database). It rejects:

- any reference to weeks 1–9, `W1`–`W9`, Orientation, the dragon, Intensives 1–4,
  the capstone, "last week", or the previous lab folder — anywhere in the deck text
- a build slide with no `⏱` estimate on both the eyebrow and the prompt label
- a prompt that does not name `governance-lab`
- a code block that is not a `paste` prompt, or any shell-shaped line inside one
- an untagged presenter line, or one missing SITUATION / ROOM / MOOD / OPEN
- Monday: more than 2 live builds or 14 teach slides
- Thursday: guided-build eyebrows that do not match the rail `CP0,CP1,CP2,CP3`
- Thursday: a `segment:readiness-0` note that does not tell the instructor to ignore
  the on-screen text
