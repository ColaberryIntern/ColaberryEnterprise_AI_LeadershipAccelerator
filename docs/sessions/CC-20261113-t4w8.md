## The colour work was measured, not chosen

Ali: "Every classification has a color so we can see anything that is happening that is tied
to the revenue."

Resolved the REAL token values from `src/colaberry/tokens/colors.css` rather than the
baseline-ui summary table — that skill's own header records that the table was wrong until
2026-08-25 and anything built from it "rendered in a colour scheme the product does not use".

Then ran the dataviz validator instead of eyeballing, which turned up two things.

### Finding 1: the design system ships a chart ramp, and I was about to not use it

`colors.css` carries `--chart-1` … `--chart-8` with an explicit instruction: *"Use --chart-N
in order. Never use raw brand ramps for series — these are tuned for charts."* I had been
planning to paint stream identity from the status palette, which would have violated it.

Corrected to a clean split, now enforced by a test:
- **Stream identity** (membership vs government) is CATEGORICAL → `--chart-1`, `--chart-2`,
  fixed order, never cycled, so filtering to one stream cannot repaint the other.
- **Event classification** is STATUS → the five reserved tones, always with a glyph and a
  label, never colour alone.

### Finding 2: the chart ramp's own colour-blind-safety claim is false at 3↔4

The ramp documents itself as *"ordered for max adjacent separation and color-blind safety"*.
Measured:

| pair | mode | ΔE (protan) |
|---|---|---|
| `--chart-3` #5BA63C ↔ `--chart-4` #E8920C | light | **1.8** |
| `--chart-3` #8AC759 ↔ `--chart-4` #F0A93A | dark | **4.3** |

The floor is 6-8 and the target is 8. At ΔE 1.8 a protanope cannot separate that green from
that amber **at all**. Normal vision sees ΔE 19.8, so it looks fine to anyone checking by
eye — which is why the reassuring comment is as much of a problem as the values.

This is not a problem I created and not one confined to this page: any chart in this repo
pairing those two slots has it. Filed as **R17** —
https://app.basecamp.com/3945211/buckets/7463955/todos/10506606119 — with three costed
options and a recommendation. I did not re-step the ramp: that is a design-system decision
with blast radius across every chart in the product, and R16 did not need it.

This page uses slots 1 and 2 only, which measured clean in both modes:

| | CVD ΔE (protan) | normal-vision ΔE | contrast vs surface |
|---|---|---|---|
| light #367895 / #FB2832 | 14.1 | 32.9 | both ≥3:1 |
| dark #5AA8C4 / #FF6B72 | 12.7 | 26.3 | both ≥3:1 |

### The contrast relief is an obligation, and it is tested

On the light surface `--status-success` is 2.94:1 and `--status-warning` is 2.39:1, both
under 3:1. The validator's wording is "relief required (visible labels or a table view)" and
that it "is not dismissable". Both reliefs ship, and both are asserted by tests, because
either one being removed looks like tidying and is actually an accessibility regression.

Fixing the contrast by inventing new hexes was the alternative and would have been worse: it
forks the brand palette, which is the failure the whole token layer exists to prevent.

### What the sparkline deliberately does not encode

A column is a day; its bands are the distinct classifications that occurred. Height is
**not** a count and **not** dollars. On this data a dollar-scaled bar would actively lie: the
membership stream's largest-value days are the ones where unbillable signups arrived, so
scaling by amount would make the worst days look like the best. Magnitude lives in the
funnel and the headline where it is labelled; the exact count is one hover away and in the
table view.

## The deploy decision, stated plainly

Phase 1 merged this morning and was deliberately **not** deployed on its own. It is a
backend-only table nothing reads yet; Phase 2 needs a deploy regardless; and `main` moved
twice more within minutes of the merge. Two deploys instead of one doubles the exposure to
the concurrent-deploy race that produces a Cloudflare 521, for no benefit.

So Phase 1 sits at **merged, not production-verified**, and the single deploy after Phase 2
merges is what will prove `gov_bid_values` exists and that `ensureGovBidValueSchema` ran
clean. That is the outstanding rung on the ladder and it is not being quietly counted as done.
