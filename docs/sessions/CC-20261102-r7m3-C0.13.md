## The red state, established before any code changed

On `origin/main`:

- `updateCampaign`'s allowlist contains **zero** occurrences of `tracking_link`,
  `approval_status` or `approved_by`.
- `campaignActivationGate.ts` reads all three: `approval_status` and `approved_by` at
  lines 184-188 as evidence of human sign-off, and `tracking_link` at line 238 in the
  `analytics_ready` check, which fails closed without it.

So the only surface that edits a campaign could not satisfy a gate requirement, and said
nothing about it.

## One ticket, two halves, opposite fixes

**`tracking_link` - allow it.** It is an analytics destination with no authorization
meaning, read nowhere except the `analytics_ready` check. Added to the allowlist.

**`approval_status` and `approved_by` - keep them unwritable.** Adding them would have
been the obvious reading of the ticket and it would have created the **first write path
for the approval record through a generic admin PATCH**, letting a campaign approve
itself. That is the one thing the gate exists to prevent. The allowlist's own comments say
it exists to stop a raw PATCH body reaching columns the logic later branches on, and the
marketing capability record states the requirement directly: the agent never appears as
`approved_by`, and no submission occurs without a recorded human action.

Confirmed before deciding: **nothing anywhere writes `campaigns.approval_status`.** Every
other `approval_status` writer in the codebase belongs to a different table
(`explorer_content_assets`, `growth_journey_content_rules`). So returning a 400 breaks no
existing caller.

**Therefore the defect fixed is the silence, not the dropping.** A caller that tries to
set an approval now gets a 400 naming the field instead of a 200 that quietly did nothing
-- which is the dangerous outcome, because it lets a caller believe an approval was
recorded when none was.

## Why the allowlist became a pure exported function

`filterCampaignUpdate` takes an update body and returns the writable subset, throwing on
an approval attempt. No model, no database, no clock. The allowlist was previously an
array inside an async function that needed a database to reach, which is why nothing could
see what it did or did not contain -- the direct cause of this ticket. A contract that
needs a database to test is a contract nobody tests.

Unknown fields are still ignored silently, deliberately: callers legitimately send whole
campaign objects back, so rejecting every unrecognized key would break them for no
security gain. The approval fields are the exception precisely because silence there is
the harm.

## What was deliberately not built

No approval write path. Had closing the gap required one, that is a compliance boundary
and the plan made it a hard stop with an escalation file rather than a thing to build. It
did not require one.
