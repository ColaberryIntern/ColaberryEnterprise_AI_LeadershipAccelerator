### Design decisions recorded in the code

- **`tenant_id` NOT NULL, `brand_id` nullable.** `campaignBrandAssignment.ts` deliberately
  refuses to guess a brand and leaves it null so it reads as "Unattributed". Forcing NOT NULL
  would push callers into inventing one — the exact failure that service exists to prevent.
- **`link_clicks.tracked_link_id` carries a real FK; cross-domain refs do not.** This was
  corrected mid-task, and the correction is the more interesting half — see below.
- **`utm_content` / `utm_term` and the four click IDs are real indexed columns**, with a
  JSONB overflow only for platforms not yet adopted. Burying them in JSONB is what was done
  to `strapi_attribution`, and it is why that data is unqueryable today.
- **Published links are immutable.** `superseded_by` points at a replacement, because editing
  a live link's UTMs would retroactively rewrite what already-recorded clicks meant.
- **Only `ip_hash` is stored**, never a raw address, matching `qrRedirectRoutes`. A test
  asserts no `ip_address`/`ip` column can appear.

### A trap worth knowing about, found while writing the parity test

Across this repo's model style — `Brand`, `BrandDomain`, `SenderProfile` and now these —
`timestamps: true` plus `underscored: true` means Sequelize names the **attribute**
`createdAt` while the **column** is `created_at`. The declared `created_at` property is
therefore `undefined` at runtime; the populated one is `createdAt`. The first parity-test run
failed on exactly this, and the failure was in the test (comparing attribute names against
column names), not the model. The convention is preserved for consistency and the access path
is documented in `TrackedLink.ts`.

### Two live-table hazards, both handled deliberately

`campaigns` has production rows, which makes two things load-bearing rather than stylistic:

1. **Boot ordering** — the call must run AFTER `ensureMultiTenantSchema()`, because the index
   is on `(tenant_id, utm_campaign_slug)` and that module is what adds `campaigns.tenant_id`.
   On a fresh database (preview stack, CI) built in the other order the index would never
   exist, and because the DDL loop only warns it would fail **silently**.
2. **The post-condition now verifies the INDEX, not only the columns.** A missing column is
   loud — Sequelize emits every declared attribute in every SELECT, so the next campaign read
   throws. A missing UNIQUE index is silent: every write succeeds, and the only symptom is
   that two campaigns in one tenant can share a `utm_campaign_slug`, at which point their
   clicks, sessions and leads merge into one bucket that cannot be untangled afterwards.
   Without the index check the function would have returned `ok: true` over exactly that
   state — the failure mode the module claims to guard against.

**A correction, recorded rather than quietly deleted.** An earlier version of this entry and
of the code comments justified the partial index by claiming that "every existing row is NULL,
so a plain unique index would collapse them into a single conflict." That is **wrong about
Postgres.** NULLs are treated as DISTINCT in a unique index, and a multicolumn unique index
only rejects a row when all key columns are equal — so `(tenant_id, NULL)` never conflicts
with `(tenant_id, NULL)`, and a non-partial index would have built fine. (`NULLS NOT DISTINCT`
is a PG15+ opt-in and is not used.) The partial predicate is still correct, for three real
reasons: index size, explicit intent, and not depending on NULL-distinctness semantics. The
claim was caught in review, and the reasoning is fixed in all three places it appeared.

The index is also per-tenant rather than global, mirroring `brands_tenant_slug_unique`:
separate legal entities may both legitimately run a `spring-openhouse` campaign.

### A parser bug this task exposed, and what it would have cost

The shared `parseCreatedTables` helper splits a `CREATE TABLE` body on top-level commas.
T001's and T002's DDL contain no `--` comments inside table bodies; the Content OS DDL has
several. Running the pre-fix parser against it does not merely mis-parse - it **silently
drops** the column following each comment: `revision` and `ai_model` from `content_items`,
eight columns from `content_variants` including `is_manually_edited` and `validation_state`,
`alt_text` and `rights_holder` from `media_assets`, and both revision columns from
`content_approval_requests`. Precisely the load-bearing ones. It also **invents** columns
named `so`, `not` and `and` out of comment prose.

The verifier found a second failure mode I had not spelled out: a comment containing
`operator's` flips the parser's quote-tracking flag, so stripping comments *before* the
quote-aware split is order-correct rather than incidental.

Both earlier suites are provably unaffected - neither DDL file contains `--` at all, so the
strip is a literal no-op on them, and their pinned counts (24/19) hold for the right reason
rather than by luck.

  - Date: 2026-09-09

**The defect being fixed is not a missing column.** `OpenclawTask.scheduled_for` already
exists and is indexed. Nothing writes it, and the worker that reads those tasks selects on
`status` + `priority` with **no time predicate**, so a future-dated task posts within thirty
minutes. A `publish_at` column with nothing filtering on it would be the identical bug wearing
a new name, and the schema would look correct either way. So the predicate is a pure function
with its own suite, and the first test in it is the one that would have caught the original:
*a job scheduled for the future is not due.*

Two idempotency guards rather than one - the application `idempotency_key`, and a separate
semantic key on `(item, revision, account, occurrence)`. The first catches a retry; the second
catches a bug in whatever computes the first. One guard is not enough when the failure mode is
a duplicate post, because a published post cannot be recalled.

Also the repo's first **jittered exponential backoff**. Every existing retry path is a fixed
+30 minutes or "next cron tick", and fixed delays synchronise: an outage fails every job at
once and they all retry at the same instant, which is how a recovering provider is knocked
over a second time.

### The defect review found: the scheduling gate FAILED OPEN

`toTime()` returns `NaN` for an unparseable date, and `NaN > nowMs` is `false` — so the
`publish_at > now` guard treated a malformed date as **due**, publishing immediately. That is
the precise outcome the module exists to prevent, and `publish_at` is typed `Date | string`
specifically because Sequelize returns string dates under some configurations, so the input
path was declared rather than hypothetical.

Every other unknown-input case in that module already failed closed — an unrecognised state is
not runnable, a null `next_retry_at` is not due. This one did not, and the asymmetry was the
bug. Fixed with an explicit `isUsableTime` guard on all three instants (`publish_at`,
`next_retry_at`, and `now` itself), plus seven regression tests.

### The deduction: an acceptance criterion that was not actually discharged

T005's criterion was "a test proves a duplicate idempotency key is **rejected by the unique
constraint**". Nothing exercised a constraint — the parity suite regex-matches
`CREATE UNIQUE INDEX` in the DDL string, and the post-condition suite proves a *missing* index
is detected at boot. Both are useful; neither proves rejection. A regex over DDL text shows the
statement was written, not that Postgres accepted it, nor that a second insert is refused.

The sharper half of the finding was that **the gap was nowhere disclosed** — the log listed
suite counts and `tsc exit 0` with no caveat, so the record read as though the criterion had
been met.

Closed by writing `ensurePublishingSchema.integration.test.ts`: an opt-in suite, gated on
`DATABASE_URL`, that inserts real rows and asserts both guards actually reject. It **skips**
without a database rather than passing vacuously (5 skipped, reported as skipped). CI collects
it and skips it, which is what CLAUDE.md's env-flagged integration-test allowance is for.

It also pins the known consequence of the partial semantic index rather than hiding it: while
T003 is gated and every `channel_account_id` is null, guard 2 is **dormant**, because NULLs are
distinct in a unique index. Without the partial predicate the index would exist and be equally
useless — so the predicate makes an unavoidable absence explicit rather than fake.

**Why destination validation is its own pure module.** `/r/:shortCode` is a PUBLIC endpoint
that 302s a visitor to a stored destination, which makes that stored value a redirect target
supplied at configuration time and executed at request time - the exact shape of an open
redirect. Get an arbitrary URL in and the platform becomes a redirector lending Colaberry's
domain reputation to a phishing page, with the victim seeing a legitimate colaberry.ai link.

So the whole decision lives in a function with no I/O, tested exhaustively, and applied at
**both** write time and redirect time. Validating only on write would grandfather every
existing row past any future tightening.

The tests that matter are the smuggles, not the parsing:

| Input | Why it is refused |
|---|---|
| `https://colaberry.ai@evil.test/` | Reads as colaberry.ai to a human; hostname is evil.test |
| `https://evil.test#@colaberry.ai` | Everything after `#` is a fragment |
| `https://colaberry.ai.evil.test/` | ENDS WITH an allowlisted string - a suffix check waves it through |
| Cyrillic homograph of colaberry.ai | Punycoded at parse, so it cannot match |
| `//evil.test/x` | No base URL is passed to `new URL` on purpose - supplying one would resolve this against our own origin and manufacture a valid absolute URL from input that was never absolute |

It fails CLOSED: an empty allowlist rejects everything, inheriting the behaviour
`getLinkableHostnames` already has, and reports that case with a distinct code from
"host not allowed" because the operator's next action differs.

**Short codes exclude I, L, O, U, 0 and 1.** They get read aloud, typed off printed QR cards
and dictated over the phone; `l` versus `1` in a URL that 404s is a support ticket nobody can
diagnose. Crypto randomness with rejection sampling, because a biased alphabet collides
measurably sooner and collisions are what this module works hardest to avoid.

**Collisions retry, never overwrite.** Overwriting would not error - it would silently repoint
an existing link, so every click already recorded against that code would be attributed to the
new campaign, unrecoverably.

Two type casts were removed during the typecheck rather than kept: `applyUtmParams` refused
the precisely-typed `UtmParams` because a `Record` parameter will not accept an interface
without an index signature. Adding one would have stopped TypeScript catching a typo like
`utm_sorce`; casting would have hidden the mismatch. Making the function generic and narrowing
at runtime keeps the caller's type precise and additionally rejects non-string values a cast
would have passed.

**The scope problem, and why it reuses the existing ramp.** Brand admin cannot build its scope

**zero rows** - so `tenantScopeWhere` returns `{ tenant_id: null }`, which matches nothing, and
every admin would open the brand page to an empty list. That is the correct STRICT answer and
the wrong answer for today.

`intelligenceScopeForAdmin` already solved exactly this with a three-step ramp, so
`adminTenantScope` rides the same one rather than inventing a second: scope to your memberships
if you have any; if NOBODY has any, open and logged; if memberships exist and you have none,
denied. Step two keys on the whole table being empty, not on your own rows, which is what makes
it **self-closing** - the first membership row anyone creates ends the open state for everybody
at once, with no flag to remember.

a single row anywhere flips `membershipSystemIsUnpopulated()` false for every admin

depends on the scope key being spelled `tenant_id` too and on it coming second. Rename one or
reorder the other and the caller's value silently becomes the effective filter - a 200 with
somebody else's brands in it.

competitor's brands. Any difference between the two responses IS the oracle.
