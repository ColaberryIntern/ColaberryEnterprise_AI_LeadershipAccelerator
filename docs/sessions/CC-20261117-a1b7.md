## Findings

### 1. The loop stop was a tenant of the trust line, so half the stories had no stop condition.

Before A1 the stop condition was rendered inside `if (s.trust)`:

```js
if (s.trust) rows.push(`...Trust (TBI): ${esc(s.trust)}   Loop stop: all acceptance scenarios pass.`);
```

A story with no `trust` field therefore showed **no stop condition at all**. The single sentence
that tells a builder when to stop was the easiest thing on the ticket to lose, and it was lost
silently, on exactly the stories nobody had written a trust note for. It is now rendered for
every story, with or without a contract.

This is asserted against the publisher's SOURCE, not by calling the renderer, because it is a
property of where the call sits: the test reads the file, finds the trust line, and requires that
it mention neither the loop stop nor the renderer, then requires the push to be unconditional on
its own line. No amount of calling a function proves where it is called from.

### 2. `StoryLikeForContract` type-rejected the objects it is documented to take.

The interface carried only `id?` and `artifacts?`. A real plan story has a title, a narrative,
acceptance scenarios and more, so an excess-property check refuses a story literal: the function
documented as taking plan stories would not compile against one. Found by the test typecheck
gate, on a test that passes `{ title: 'no id' }`. The fix widens the interface with an index
signature rather than trimming the test, because the test was passing the realistic shape and the
interface was wrong.

### 3. The skeleton the refusal prints cannot validate itself, on purpose.

Story ids come from the generated plan, so contracts cannot be authored before the generator
runs, and a hard gate with no help attached is a wall. The refusal therefore prints a paste-ready
`by_story` block for exactly the stories missing one.

That skeleton is deliberately unvalidatable: its `type` is `CHOOSE_ONE_OF: ...` and the schema
refuses it with `type_unknown`. Pasting it and publishing gets refused again, by name. A skeleton
that validated on paste would recreate this entire workstream's problem one level up, as a
declared contract nobody thought about, and a board that looks finished again. There is a test
whose only job is that the skeleton fails validation, and a mutation proving that test fails when
the placeholder is replaced with a real type.

The list of types in the skeleton is read from the catalog, not restated, so a type added to
`storyArtifactTypes.json` appears in the skeleton with no edit anywhere.

### 4. The hard gate belongs to the publisher, not to the platform, so parity needs both modes.

A1 makes a missing contract a refusal **when publishing**. The platform keeps the lenient
default, because it reads boards that predate the rule and refusing those would be refusing
history. That means the two implementations are only in step if they agree in both modes, so the
parity test now runs both over the same stories with `requireContract` absent, false and true,
and carries a control asserting the two modes actually produce different answers. Checking one
mode would let the hard gate drift on one side unnoticed.

### 5. Running it for real produced two changes that reading it would not have.

A twelve-story plan with no contracts printed the same 300-character paragraph twelve times,
which buried the skeleton underneath it: the only part of the output a person can act on. The
missing-contract refusal is now reported once, naming every story. And the acceptance heading
still read "Gherkin = demo script + loop stop" from a time when the loop stop had no line of its
own; it does now, so the heading no longer claims it.

## What A1 does not claim, and the one thing its ticket asked for that it did not do

- Nothing was deployed, no row was written to any database, and **no live Basecamp board was
  touched**. Every run was against a fixture with `fetch` replaced.
- No story on any live board has a contract yet. A5 retrofits the four live boards.
- Nothing yet verifies that a declared artifact actually exists. That is A2, which rides on the
  GitHub push webhook's existing verification pass.
- Quality is still a human judgement. The gate's job is to prove a document of the right kind
  exists at the right place; `evaluation_criteria` is the sentence a person judges it by.

**The L11.2 ticket's "Done when" cannot be met as written, and the reason is a mistake in the
ticket I wrote.** It says: *"A republish of one live board shows the contract on every story and
creates no duplicates. Idempotency is already proven in that script."*

Both halves are wrong. `publish_story_build.js` is **not idempotent**: every Basecamp call in it
is a bare POST, with no read-then-reuse anywhere except `/my/profile.json`. Re-running it against
the same bucket creates a second complete to-do list, with duplicate groups, duplicate to-dos and
duplicate documents. The idempotence I proved on 16 November was in `bc_create_group11.js`, my own
group-creation script for the L11 ladder, and the ticket conflated the two.

A republish of a live board therefore needs an UPDATE path the publisher does not have: find the
existing list, match each to-do, and PUT its description. That is a second substantial change, it
writes to live boards people are working from, and it is the stated job of A5 (retrofit the four
live boards) rather than of A1. It is also worth noting that no live board's config exists in
this repository at all; only `EXAMPLE.json` does. So A1's acceptance was demonstrated on a
fixture board end to end instead, and the live-board republish is named here and raised with Ali
rather than quietly redefined.
