## What B1 actually was

Every lifecycle authority check derived the actor's permissions as
`deliveryPermissionsFor([req.admin.role])`. `req.admin.role` is a value from the MANAGEMENT
vocabulary - `admin_users.role`, one of super_admin / admin / sales / ai_staff. `ROLE_GRANTS` in
`modules/delivery/deliveryRoles.ts` is keyed on the DELIVERY vocabulary. The two do not overlap at
a single point, so every lookup fell to the registry's fail-closed branch and returned `[]`.

Measured in the production bundle rather than argued from the source: the 13 delivery roles carry
**180 permissions** between them; all four admin roles carry **0**. Not few. Zero.

So `requestTransition` refused every transition, `requestBlueprintChanges` was an unconditional
403, `permittedActions` was empty on every status response, and `viewerPersonas` was empty for
everyone including the owner.

### This is not a dark feature

Checked rather than assumed, because it decides how much the finding matters:

| `ENABLE_PROJECT_LIFECYCLE` in production | **`true`** |

The surface is live and every action on it was dead for everybody. That is the same shape as the
condition the tenancy ramp comment in `lifecycleStatus.ts` records - "the feature was activated
and unusable" - reached by a different route.

## The design, and the premise that production disproved

The obvious fix is "stop reading the admin role as a delivery role; resolve the identity's real
delivery membership instead." That was the first design. Read-only counts on 2026-11-14 killed it:

| Measurement | Value | Why it matters |
|---|---|---|
| Lifecycle rows | 39 total: **28 student**, 11 delivery | `delivery_project_members` is keyed on `delivery_project_id`, so it cannot describe a student project at all. 72% of the rows this service governs are outside its reach by construction, not by emptiness. |
| Membership rows | 10, **every one `associate_builder`** (4 active, 6 revoked), 8 projects, 6 identities | `associate_builder` holds no approval permission whatsoever. The entire populated membership table is interns. |
| `admin_users` resolving to a `platform_identities` row | **1 of 50** | And only via the email fallback: `platform_identity_links` holds 0 rows, so the id path is dead. |
| admin to identity to active membership to a project with a lifecycle row | **0 complete chains** | Membership-first reaches the same zero as the bug, by a longer route. |

A ramp from the admin vocabulary is therefore not a shortcut around the authority. Today it is the
only thing that resolves to a non-empty answer for any caller on any project.

### What shipped

`backend/src/services/lifecycle/lifecycleActorRoles.ts`, one resolver with three branches:

1. **An active delivery membership on this project wins.** It is a deliberate per-project
   statement, which is the question `DeliveryProjectMember` exists to answer.
2. **Otherwise the admin identity is bridged** to exactly one delivery role.
3. **Otherwise nothing.** Fail closed, as the registry does.

Self-closing at the finest grain available: the condition is per actor, per project, so the bridge
stops firing for a person the moment a real membership is written for them. No flag, no global
ramp to remember to remove. Said plainly rather than buried: for the 28 student rows it can never
close, because membership cannot be expressed for them. There the bridge is the mechanism, not a
ramp.

### The bridge table

| Claim | Value | Bridged delivery role |
|---|---|---|
| `mgmt_role` | `owner` | `delivery_owner` |
| `mgmt_role` | `admin` | `delivery_lead` |
| `mgmt_role` | `curriculum` | `observer` |
| `mgmt_role` | anything else | nothing |
| no `mgmt_role`, `role` | `super_admin` | `delivery_owner` |
| no `mgmt_role`, `role` | `admin` | `delivery_lead` |
| anything else | | nothing |

`delivery_lead` and not `delivery_owner` for a plain admin, deliberately: `delivery_owner` is the
only role carrying `release.deploy` and `project.manage_authority`, and deploy authority should be
granted by name rather than inherited through a compatibility bridge.

### Why `mgmt_role` is read FIRST, which is the whole security content of this change

`mgmtBridgeService.mintMgmtAdminToken` sets the JWT's `role` to `'super_admin'` for the `owner`
management role and **`'admin'` for every other one**. A `curriculum` staff member therefore
arrives carrying `role: 'admin'`, and `curriculum` is one of only three management roles whose
sections include `program`, so they can reach these routes.

A bridge keyed on `role` alone would hand them `delivery_lead`: contract approval, architecture
approval, release approval and member management, acquired silently through a bug fix.
`mgmtRoles.ts` already names that failure mode - "another intern's entire domain, dressed up as
scoping". So the resolver reads `mgmt_role` first, exactly as `adminAllowedSections` does, and a
mutation that flips the order fails a test by name.

`AdminIdentity` and `adminOf` were widened to DECLARE `mgmt_role`. It was always present on
`req.admin` at runtime and simply absent from the type, and an undeclared claim is one a reader
has no reason to consult - which is how the derivation came to read the single claim that cannot
tell these identities apart.

## A test that was careful in the wrong vocabulary

`blueprintChangeRequest.test.ts` built its approver as
`{ role: rolesWithDeliveryPermission(CHANGE_REQUEST_PERMISSION)[0] }` - derived from the registry
rather than hardcoded, which is the right discipline. Applied to the wrong vocabulary. No mint
path issues an admin token whose `role` claim is `architect`, so the suite proved the gate admits
an approver who **cannot exist**, while in production the same gate refused everyone.

That is how B1 shipped green, and it is worth naming precisely because the test looked more
careful than it was. The fixture now builds the shapes the platform can actually mint, and which
of them approves is still derived - now through `bridgedDeliveryRole`.

### The integration tier caught a third fixture, and that is the gate earning its place

The first CI run on this branch went **red on `Integration tier (Postgres)`**, with
`stageCas.integration.test.ts` at 3 failed of 5 - including its own `APPARATUS` positive control.
Read from the job log rather than inferred from the tick.

It was the same defect a third time, and in a suite that reasoned about it carefully. It used
`role: 'observer'`, chosen deliberately because `observer` grants `project.read` and nothing more,
so the test could not pass by being over-privileged. But `observer` is a DELIVERY role in a claim
that carries a MANAGEMENT role, so the apparatus was proving a transition is permitted for an
identity that cannot exist.

The fixture is now a bridge-minted `curriculum` staff token - the mintable identity whose bridged
delivery role IS `observer` - so the minimum-privilege property is preserved exactly rather than
traded for a token that happens to work. Its negative control (`not_a_real_role`) keeps its
meaning, bridging to nothing and still being refused.

**Verified on the second CI run, from the job log rather than the green tick:**
`stageCas.integration.test.ts` **5 passed, 5 total** (4.4s), the `APPARATUS` positive control
among them. That control is the load-bearing one: without it every refusal in the suite could be
the authorization ramp or the permission check refusing, and the CAS it exists to test would never
be reached at all. So the fixture change did not merely stop the suite going red, it restored the
condition the suite needs in order to mean anything.

`projectLifecycleRoutes.test.ts` was fixed in the same pass: it stubbed `role: 'DELIVERY_OWNER'`,
the delivery constant's NAME rather than even its value, in a management-role claim. Harmless
there because every service is doubled and the derivation never runs - which is precisely what
made it a trap, since it reads as a valid admin token and is not one.

A sweep across `backend/src` and `frontend/src` for the same pattern found **no others**: every
remaining hit is `delivery_role` on a membership row or `mgmt_role` on a token, both correct.

Two things worth keeping from this:

1. **The unit tier could not have caught it.** `stageCas` is DB-gated, so it self-skips without
   `DATABASE_URL`, and this machine has no local Docker. The integration tier is the only place
   that failure was visible - and L7.6's own open recommendation is that the tier become a
   required check. It behaved exactly as a required check would have.
2. **Three suites, one fiction.** B1 was not a single mis-wiring. The vocabulary confusion had
   been written into three separate fixtures, each one carefully derived or commented, and every
   one of them passed. That is why the production measurement rather than the test suite is what
   settled it.

## What this does NOT do

- **B2 and B3 are untouched.** B2 (the gate satisfied by requester-supplied evidence) and B3 (the
  unregistered production project with no repair path) are unchanged, and Phase 7 exit stays
  REFUSED on both.
- **It does not gate blueprint approval.** `approveLifecycleBlueprint` still consults no
  permission at all and only records `approved_by_role` - L7.6's non-gating finding C4. This
  change makes that fixable, since there is now an actor role to gate on, but it does not fix it.
- **It is not a membership rollout.** `platform_identity_links` and `tenant_memberships` still
  hold zero rows, and the one admin that resolves to a platform identity does so by email.
- **The policy tradeoff is encoded, not settled.** A membership present on the project SHADOWS the
  bridge rather than being unioned with it, so someone who is both a platform admin and a named
  `associate_builder` on a project acts there as an associate builder and loses approval
  authority. That is 0 people today, and it is the narrower of the two readings, which is the
  right way to be wrong in an authorization change. The union is a one-line alternative in
  `resolveActorRoles` and is flagged in the PR for the DRI.
