## The question the screenshots were taken to answer

**Does the rendered preview match what a visitor actually receives?** Yes, exactly — and the
first answer this session produced was wrong, which is worth recording.

Harness: `.loop-architect/runs/20260822-casestudy-os/preview-render/capturePreviewRender.js`.
Proved it can fail first — `BASE_URL=http://localhost:59999` reports a red preflight and exits 1
without capturing anything.

There is **no production admin JWT on this machine** (`scripts/.ali_jwt.txt` absent, no
`STORY_STUDIO_TOKEN`), and the preview is uncommitted and undeployed, so the live admin surface
could not show it even with one. So the public page was captured from production unmodified over
the real network, and the admin preview ran against the local dev build with its `/api/admin/**`
calls fulfilled by Playwright carrying **the production public API's own payload** for this
record, plus the **real** surface views from the backend's own `surfaceView()` /
`getCaseStudySurfaceProfile()` (compiled out of `backend/src`, not reimplemented). On
`enterprise` both renderers therefore receive byte-identical `record` and `surface` objects.

| Comparison | bands | headings | visible text |
|---|---|---|---|
| preview frame vs **deployed** live page | same | same (9) | identical, 9310 chars |
| preview frame vs **this build's own** `/stories` page | same | same | identical, 9310 chars |

The second row is the control, and it is the one that matters: production runs an older commit,
so a difference against the live page alone could have been branch-vs-deployed rather than
frame-vs-page. Both are clean.

**The false finding, recorded because it nearly shipped as the headline.** The first run
reported a 361-character difference and the control failed too, which looked like a real
frame-vs-page defect in the architecture band. It was not. `StoryDiagram` renders through
`MermaidDiagram`, which fetches Mermaid from a CDN at runtime and swaps in an SVG whose node
labels are `<foreignObject>` HTML; the harness read the two public DOMs before that resolved and
the admin DOM after, and invented an 11-line difference out of the timing. Probing the live page
directly showed all 11 labels present after 2.5s. Every read is now gated on
`figure.cb-mermaid[data-state] !== 'loading'`, and the final `data-state` for all six reads is
recorded in the report as `ready` so the wait is evidence rather than an assurance. A comparison
harness that races the thing it compares will manufacture differences.

Not proven, stated plainly: the other three surfaces re-lens the **enterprise** projection
through their real surface view, so they prove the tab renders a real page per surface and that
band order follows the surface — they do **not** prove the per-surface content projection, which
needs an admin token. The `undefined` visible in the admin page header of the screenshots is the
harness's stub omitting `sourceType`, not a product defect.
