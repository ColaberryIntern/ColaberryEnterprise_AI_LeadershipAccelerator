## Precondition: attempted, and it proved my own gate unenforceable

The plan declared `verifyProjectLifecycleSchema.ts` exiting 0 a hard gate for all of Phase 3. I tried to discharge it against Postgres 15.16 in a disposable container and could not:

- The lifecycle DDL has FK prerequisites on `tenants`, `projects` and `delivery_projects`. On an empty database **all 12 statements warn-skip**, cascading from the first missing relation.
- Running `ensureMultiTenantSchema()` first — the real boot order — cleared `tenants` and exposed the next link, `relation "projects" does not exist`. Satisfying the chain needs the full boot sequence including the `sequelize.sync()` over the 200+ model graph. Stubbing the prerequisites would test a fake schema, which is a failure mode this repo already records.

Three things the failed attempt did establish, and they are worth more than a green tick:

1. **The verify script is falsifiable.** Against a database missing everything it exited **1** and reported `tables 0/4, indexes 0/5, constraints 0/2`, naming all eleven gaps plus the remedy. A check that only ever passes proves nothing.
2. **The assert caught exactly the silent failure it was built for.** Twelve DDL statements failed warn-only and the process would have continued happily; `assertProjectLifecycleSchema` returned `false` and said why. That is P2-T7's thesis observed rather than argued.
3. **The boot order in `server.ts` is correct** — `ensureMultiTenantSchema()` at `:2555` precedes `ensureProjectLifecycleSchema()` at `:2744`, so `tenants` exists before the FK needs it on a fresh environment.

**The gate was over-broad as written and is now narrowed in the plan itself, with the reason recorded rather than quietly dropped.** It was declared Phase-3-wide on the grounds that the tasks below it read tables they assume exist. That is false for T1 and T2, which are pure value transformations: `sourceHandoff.ts` imports only `sourceIdentity` and `projectUnderstanding` types, and nothing resembling `sequelize`, a model, or `config/database`. A schema gate could not have caught anything in T1. The gate now binds **T3 onward**, where DDL and table reads actually begin, and `plan-phase3.md` has been updated to say so — an earlier version of this log described the narrowing while the plan still read Phase-3-wide, so the governing artifact and the log disagreed.

**One documentation gap this surfaced, scheduled into P3-T3's commit** (same file): `ensureProjectLifecycleSchema.ts` does not document its ordering requirement, while the repo's own precedent does — `ensureGrowthJourneySchema.ts:22-24` states *"MUST BE CALLED AFTER `ensureMultiTenantSchema()`"* with line numbers. Today the order is right by position alone; reorder the boot loop and all four tables vanish on fresh databases, warn-only and silent.
