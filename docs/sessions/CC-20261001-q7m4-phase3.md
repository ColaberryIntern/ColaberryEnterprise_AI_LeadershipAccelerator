The plan declared `verifyProjectLifecycleSchema.ts` exiting 0 a hard gate for all of Phase 3. I tried to discharge it against Postgres 15.16 in a disposable container and could not:

- The lifecycle DDL has FK prerequisites on `tenants`, `projects` and `delivery_projects`. On an empty database **all 12 statements warn-skip**, cascading from the first missing relation.

Satisfying the chain needs the full boot sequence including the `sequelize.sync()` over the 200+ model graph. Three things the failed attempt did establish, and they are worth more than a green tick:

1. **The verify script is falsifiable.** Against a database missing everything it exited **1** and reported `tables 0/4, indexes 0/5, constraints 0/2`, naming all eleven gaps plus the remedy. A check that only ever passes proves nothing.

3. **The boot order in `server.ts` is correct** — `ensureMultiTenantSchema()` at `:2555` precedes `ensureProjectLifecycleSchema()` at `:2744`, so `tenants` exists before the FK needs it on a fresh environment.

**The gate was over-broad as written and is now narrowed, with the reason recorded rather than quietly dropped.** Its stated rationale was that "every task below reads tables it assumes exist" — which is false for T1 and T2, both pure value transformations that read no tables. The gate binds **T3 onward**, where DDL and table reads actually begin.

**One documentation gap this surfaced, scheduled into P3-T3's commit** (same file): `ensureProjectLifecycleSchema.ts` does not document its ordering requirement, while the repo's own precedent does — `ensureGrowthJourneySchema.ts:22-24` states *"MUST BE CALLED AFTER `ensureMultiTenantSchema()`"* with line numbers.
