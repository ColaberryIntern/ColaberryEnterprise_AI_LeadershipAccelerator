## The finding that forced this change

Part 2 ended with the knowledge base attached and 27 active answers on production. Two
defects survived, and they turned out to be the same defect:

1. Asked about refunds, Cora stated terms nobody wrote: *"we do not offer refunds for the
   membership fees once they have been paid."*
2. A knowledge base answer was edited to say Docker has **"no charge"**, specifically to
   remove the word "free". Her very next reply said Docker was **free**.

The second one settles the question the first one raises. **A knowledge base entry is
reference material the model rewrites in its own voice**, so a compliance rule written as
KB copy does not survive the paraphrase. Rules have to be instructions, above the
knowledge, saying that they override it.

`buildCoraSystemPromptFromDB` had no rules at all: a persona line, the cohort line, the
Q&A pairs, one closing sentence. The static prompt it replaced
(`coraKnowledgeBase.buildCoraSystemPrompt`, PR #25, June) had a scope section, response
rules and escalation triggers. The KB Ops migration dropped them and nothing replaced them.

## What shipped

**`backend/src/services/coraPromptRules.ts`** (new). Eight numbered rules plus a
`needs_human` definition, 3,768 characters, injected between the cohort line and the Q&A
block. Every rule is a reply that actually went out in shadow mode, named in the file:

| # | Rule | The reply that caused it |
|---|---|---|
| 1 | The word "free" must never appear, in any sense, including "feel free" | Docker described as free after the KB said "no charge" |
| 2 | Never state a policy the KB does not state | The invented refund terms |
| 3 | Never promise an outcome, and never say we do or do not guarantee employment | An unprompted placement disclaimer to a laid-off alum |
| 4 | Never name a person, team or address not in the KB | "our career coaching team", which does not exist |
| 5 | Never confirm an action was taken | "once your account has been permanently deleted" |
| 6 | The sender may already be a student | "once you're enrolled", to a student already in orientation |
| 7 | Answer only from the KB; never troubleshoot software from general knowledge | Step-by-step Power BI advice to a bootcamp student |
| 8 | When you decline, close the message | Thanking a marketing vendor and inviting more contact |

**Enforcement, in code.** `parseCoraReply()` now runs `findCoraReplyViolations()` over the
generated body and forces `needsHuman = true` when anything trips, whatever the model said
about itself. One-way: a violation can add a human, never remove one. The ids land in the
dry-run audit metadata as `rule_violations`, so a reviewer can sort the shadow log by the
drafts that need reading first, and a violation logs one structured
`cora_rule_violation` line with `error_class: ContractViolation`.

The prompt is what makes a violation rare. The check is what makes it visible. That split
is deliberate and is the reason the code change exists at all rather than just a longer
prompt: per CLAUDE.md's core principle, the probabilistic half cannot be the gate.

**Also fixed, same function:** the two degraded prompts in `getCoraSystemPrompt()` told the
sender to write to support@colaberry.com, which is the address they had just written to.
That is the "echo" reply this inbox produced for months. With no knowledge loaded there is
nothing Cora can answer, so the degraded prompt now acknowledges and hands off, and names
no address.

## Measured, on the same 20 real emails

The 20 unanswered support emails from the part-2 test, replayed three times through
`gpt-4o-mini` at the same temperature, with the live production knowledge base prompt read
out of the running container and the rules spliced in at the position the merged builder
puts them. Nothing sent, no DB row written, no production file changed.

| | No rules (production today) | Rules v1 | Rules v2 (shipped) |
|---|---|---|---|
| Replies tripping a compliance rule | **15 of 20** | 3 | **2** |
| Hand-offs (`needs_human`) | 10 | 16 | **17** |
| Generation errors | 0 | 0 | 0 |
| Prompt size | 10,166 | 13,454 | 13,993 |

Of the 15 in the baseline, 12 were "feel free to …" closings and 2 were genuine
advertising of a no-cost product. **An earlier note to Ali in this session said only one
reply contained the word; that was a spot check, and it was wrong. The detector found 15.**

The three replies named as unfixable from data in part 2 were re-checked specifically:

- **Saba** (Power BI dashboard) — **fixed.** Was confident step-by-step troubleshooting
  marked resolved; now declines to troubleshoot and hands off. Rule 7's general wording did
  *not* achieve this; naming the category did, which is why rule 7 names products.
- **Michael** (already in orientation) — **fixed.** "once you're enrolled" is gone and the
  email now routes to a person.
- **Genay** (new laptop, setup) — **partly.** The Docker and GitHub "free" is gone, but
  "once you are enrolled" survived, in a run where the rule quotes that exact phrase.

**The two survivors are the point, not the footnote.** One "feel free" and one "once you
are enrolled" each slipped once, in *different* runs, at the same temperature. The model is
probabilistic and no prompt wording will make it otherwise, which is the whole argument for
the parse-time check.

### A detector bug this found

The first version of the rule-6 check was `/\bonce you (are )?enroll(ed)?\b/i`, which
misses **"once you're enrolled"** — the exact phrasing that went to Michael. It was passing
replies as clean while the violation sat in the text. The pattern now covers the
contraction, the curly apostrophe, and "once you have enrolled", with a test for each.
Measuring with a check that cannot see the defect is worse than not measuring.

**The banned-word ratchet caught this file, correctly.** `coraPromptRules.ts` contains the
word twice, both inside rule 1, because a rule that forbids a word has to name it. That is
the same reasoning `services/mayaPersona.ts` already carries, and the entry follows its
precedent:

```
'services/coraPromptRules.ts': [2, "POLICY LIST: Cora's own rule 1 forbids the word and the phrase \"feel free\""],
```

Rewording the rule to dodge the scanner would disable the rule the line exists to enforce.

**Three suites failed in the local run and pass in CI**, so they are a local-environment
artifact, not breakage on main: `generateReeseToolInventory`,
`generateReeseBehaviourInventory` (both assert a committed Markdown file is byte-identical
to a fresh render) and `mountLearnerPortalRoutes`. None of those files is touched here, and
this branch differs from `origin/main` only by this docs file plus the Cora change.
CI's own backend unit-test job is green on all three. **Corrected from what I first wrote:
I called them "pre-existing failures on main" before CI had run them, which the local
result alone did not support.**

## Not in this change

- **`CORA_DRY_RUN` is still `true`.** Nothing was armed and nothing was sent. Arming is
  Ali's decision and this change does not move it.
- **Blocking a violating send.** A tripped rule forces a human, it does not stop the reply
  going out once live sending is armed. Whether a violation should block the send is a
  policy call, and shadow mode is the gate until it is made.
- **Four facts only Ali can supply**, one row each, still holding four answers inactive:
  next Open House date, cohort end date, Expo date, and a signed refund/cancellation policy.
- **Are `payments@colaberry.com` and `admissions@colaberry.com` monitored?** A routing test
  to admissions@ on 15 Nov was classified `SILENT_HOLD` and nothing answered it. The KB
  sends people to both.
