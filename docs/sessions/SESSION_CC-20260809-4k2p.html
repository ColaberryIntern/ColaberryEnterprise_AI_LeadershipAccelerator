**Fixed the sponsor magic-link flow silently sending nothing to a first-time manager, and gave link generation and access a durable audit trail**

2026-08-09
What changedSTORY-001 (REQ-001 `/sponsor/dashboard`, REQ-002 form-to-magic-link) was ~70% already on `main` — the route, the page, the `?token=` exchange, the 30-day TTL and the `sendSponsorMagicLink` email all existed. The defect was that `requestSponsorPortalLink()` returned silently unless a `Lead` **and** a `Sponsor` row with `contact_lead_id = lead.id` already existed, so a manager who had never been in the system submitted the form, saw "Check your email for your login link", and no mail was ever sent. Made it self-serve: `Lead.findOrCreate` on the normalized email then `Sponsor.findOrCreate` on `contact_lead_id`, with `company_name`/contact name derived from the address (`jordan.lee@acme-corp.com` → *Jordan Lee* / *Acme Corp*) when the form does not supply them, so the existing email-only login gate works unchanged. A still-live token is now **reused rather than rotated**, so a second submit cannot invalidate a link already sitting in the manager's inbox. The outbound send — an external boundary with no timeout anywhere on the shared nodemailer transport — is wrapped at this call site in a 10s timeout plus 3 capped attempts with 500/1500ms backoff; every attempt carries the same token, so a duplicated delivery is still one working link. All attempts failing throws a classified `EmailDeliveryError`, which the controller turns into a **503 with an honest message** instead of the previous false "check your email". Second half: new `sponsor_portal_audit_log` table (`SponsorPortalAuditLog` model + `sponsorAuditService`) writing `link_generated` on issue (before the send, so an undeliverable link is still on the record), and `link_accessed` / `link_rejected` on both outcomes of verify, each with correlation id, redacted email, client IP and user agent. Tokens are stored as a **SHA-256 fingerprint, never in plaintext**, so the audit table cannot be read as a credential store while still letting an access event be joined to the generation event that issued it. Audit writes are best-effort — a failed insert logs `sponsor_portal_audit_write_failed` and continues rather than locking a paying customer out of their dashboard. `ensureSponsorPortalAuditSchema()` added to the boot sequence, since boot runs no global sync and the table would otherwise never exist in prod. Frontend: optional Company field on the login gate posting `company_name`, and an expired-link notice with `role="status"` — a rejected `?token=` previously cleared the session and rendered a bare login form, so clicking a dead link looked like the button was broken.
Verification35 tests green across 3 suites. The load-bearing one is a new route-level end-to-end test (`src/__tests__/routes/sponsorMagicLinkFlow.e2e.test.ts`, 9 tests) that drives the real Express handlers with only nodemailer, the Sequelize models and the two DB-backed settings lookups stubbed — the **real** `emailService` executes, so the test extracts the magic link out of genuinely generated HTML rather than asserting a mock was called, confirms it is `https://enterprise.colaberry.ai/sponsor/dashboard?token=…`, feeds that exact token back to `GET /api/sponsor/verify` and gets a session. It covers all three acceptance lines plus the three named failure paths: malformed email → 400 and nothing sent, expired link → 401 + `link_rejected`, delivery failure → retries then 503. Idempotency proven against end state, not call counts: submitting twice yields one lead, one sponsor, one unchanged token, and an identical link both times. Credential safety asserted against the whole serialized audit row (`expect(serialized).not.toContain(token)`), so a token leaking into any field including `metadata` fails the test. Backend `tsc --noEmit` (TypeScript 5.9.3) and frontend `tsc --noEmit`: zero errors in all 10 changed files.
