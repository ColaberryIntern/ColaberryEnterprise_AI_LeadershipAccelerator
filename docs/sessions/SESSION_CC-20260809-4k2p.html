**Two live-only defects on the public sponsor surface, plus durable auditing for magic-link issue and access**

2026-08-10
What changedthree things, all on code already on `main`. (1) **`GET /api/sponsor/verify` returned 500 for an empty or non-UUID `?token=`, and wrote no audit record.** `sponsors.portal_token` is a `DataTypes.UUID` column, so Postgres raises a type error on a malformed literal instead of simply not matching, and the throw happened inside `Sponsor.findOne` before anything could be logged — so probing the endpoint with junk produced server errors and left no trace. A valid-shaped but unknown UUID behaved correctly; only malformed input was affected. Now guarded by a UUID shape test at the top of `verifySponsorPortalToken`: anything not UUID-shaped is a bad link, gets the same 401 as any other, and records `link_rejected` with reason `malformed_token`. (2) **New `sponsor_portal_audit_log`** (`SponsorPortalAuditLog` model + `sponsorAuditService`) recording `link_generated` on issue — written before the send, so a link that is minted but never delivered is still on record — and `link_accessed` / `link_rejected` on both outcomes of verify, each with a correlation id, redacted email, client IP and user agent. Tokens are stored as a **SHA-256 fingerprint, never plaintext**, so an access can be joined back to the generation event that issued it without the table becoming a credential store; a value that was never a token is not fingerprinted at all. Audit writes are best-effort — a failed insert logs `sponsor_portal_audit_write_failed` and continues rather than locking a customer out of their dashboard. `ensureSponsorPortalAuditSchema()` added to the boot sequence, since boot runs no global sync and the table would otherwise never exist in prod. (3) **`/sponsor/dashboard` rendered a heading beginning with a bare colon and four stat cards with labels but no numbers** once a real sponsor signed in. The page and `GET /api/sponsor/dashboard` were never reconciled: the endpoint sends `company_name` and a nested `seats{purchased,…}`, the page reads `company` and flat `seatsPurchased`; backend tiers are lowercase `bronze|silver|gold` while `tierTone()`/`progressTone()` key off `Gold|Silver|Bronze` and know an `Unranked` state the API never sends. The only boundary check was `Array.isArray(payload.participants)`, which an empty array satisfies — so a wrong-shaped payload was accepted as valid and `undefined` rendered into every other field instead of falling back to sample data. Replaced with an explicit `ApiSponsorDashboard` type, a mapper, and a check that validates the fields actually used. Two related defects fixed in passing: the React key was `p.email`, but the endpoint deliberately does not expose participant emails to the sponsor surface, so every live row would have keyed on `undefined` (participants now carry an `id`, `enrollment_id` for live data); and Demo Day membership now reads the server's own `demo_day_candidates` list rather than re-deriving the rule client-side, so the two cannot drift.
Verification23 tests green across 2 suites, including three regression cases (`''`, `'garbage'`, a truncated UUID) that assert the database is **never queried** for malformed input — checkable without a real Postgres, which is precisely what the original tests could not do. Backend and frontend `tsc --noEmit` both clean. Defect (1) was reproduced and then confirmed fixed against a **real Postgres on the dev stack** (`:9999`, `accelerator_dev1`): before, `?token=` empty / `garbage` / absent all returned 500; after, all four bad-token shapes return 401 and the previously-lost probes appear as three `malformed_token` rows in `sponsor_portal_audit_log`, while a genuine emailed link still returns 200. Defect (3) verified by serving the rebuilt bundle (`main.86117d95.js`) and confirming the mapper literals are present in the shipped JavaScript rather than trusting the build.
