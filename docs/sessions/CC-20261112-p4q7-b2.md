## What B2 actually was

`blueprintPersistence.buildRefs` built the manifest's ref set out of `input.project` - the HTTP
body. The compose route's Zod schema is deliberately shallow (`project: z.record(z.string(),
z.unknown())`) because each collection has a validator owning its deep contract, so nothing
checked it further. `factoryToManifestRefs` then honoured an explicitly empty `source_blocks: []`
as a MEASUREMENT - "there are no requirement blocks, therefore none are uncited" - and that
measurement satisfies the `source_block_uncited` prerequisite at `requirements_ready`.

So a caller could clear a governance gate for a project whose stored document holds requirement
blocks that no task cites, by posting two characters. Nothing compared the posted blocks against
`contract_process_documents`.

The caller must already be a trusted program-section admin, so this is **control integrity rather
than privilege escalation**. It is still a gate reading its own evidence out of the request it is
gating.

| Fact | State |
|---|---|
| `operating_blueprint_manifests` rows in production | **0** |

So B2 was **latent, not exercised**: no gate has yet been passed on requester-supplied evidence,
because nothing has composed. It is also the FIRST gate every project meets after `discovery`,
which is where all 39 of them sit. The zero carries a control: the same query against the same
table ran and returned a row count, so it is an empty table rather than a broken query.

## The fix was already half-built, and that is the finding

`gatherCompositionInput.loadFactoryProject` already reads the stored document, picks the track by
the rule `factoryRoutes` has always used, and carries a `sourceBlocksPresent` flag whose own
comment reads: *"Passed to `persistComposedBlueprint` only when true."*

`PersistComposedInput` has **no such field**. The flag is produced, documented, and asserted by a
test literally named *"carries sourceBlocksPresent out to the caller that has to pass it on"* -
and consumed by nobody. A producer with no consumer, which is the same shape as the three
producers L7.6's own ticket was opened about.

### What shipped

`backend/src/services/lifecycle/blueprintStoredCoverage.ts`. The coverage rule's inputs come from
`contract_process_documents`, never from the body.

**Both halves, because one would not close it.** The rule is "every source block of kind
`requirement` appears in at least one task's `source_evidence`". Taking the BLOCKS from storage
and leaving the TASKS in the body would leave the gate satisfiable by posting one task that cites
everything. So both come from the document, and the body's copies are ignored here.

**Consumed inside the persister, not threaded through the route.** A parameter can be omitted,
mis-set or forgotten by the next caller, and the value it carries is exactly the claim a caller
must not be trusted to make. The persister loads the document itself, so there is no argument
through which a false claim can arrive.

**Three fail-closed branches, all narrow:**

| Stored state | Coverage recorded | Gate |
|---|---|---|
| Document present, `source_blocks` key present | measured from the document | passes or names the uncited ids |
| Document present, key absent (pre-dates the field) | `null` | keeps blocking |
| No document | `null` | keeps blocking |
| Document unreadable (DB error, or malformed JSONB) | `null` | keeps blocking |

`no_stored_document` and `stored_document_unreadable` are kept apart in the log though they
produce identical refs: one is a project state, the other is an outage, and collapsing them would
make a database problem look like a project that has not been decomposed.

### What the fix does to the 11 real delivery projects

| | |
|---|---|
| Delivery projects with a lifecycle row | 11 |
| ...with a stored process document | **1** (`80b35be2`, the live client build) |
| That document | version 1, `draft`, 56 source blocks, 36 of kind `requirement`, 15 tasks |
| Its uncited requirement blocks | **0** |
| The other 10 | coverage `null`, so `source_block_uncited` keeps blocking until they are decomposed |

The live client project therefore measures CLEAN under the fix. The other ten stop passing a
check nobody had performed on them.

## The scope line, and the number that drew it

`loadFactoryProject` returns the stored REQUIREMENTS too, so sourcing those from storage as well
would have been a one-line extension. It would also block almost every delivery project at the
same gate under a different rule. Measured read-only on production, 2026-11-16:

| Measurement | Value |
|---|---|
| `contract_requirements` rows | 1,264 |
| Rows with no `source_document` (no provenance) | **1,241** |
| Delivery projects with a lifecycle row that would then be BLOCKED on `requirement_without_provenance` | **10 of 11** |
| Including `80b35be2`, the live client build | **yes - 56 of 56 rows unprovenanced** |
| CONTROL: rows that DO carry provenance | 23, across 3 projects, lengths 7 to 85 |

That control matters: without it, "1,241 have no provenance" is indistinguishable from a detector
that always reports null.

Blocking the live client build at its first gate is a decision with a cost attached to somebody
else's week, so under CLAUDE.md's scope lock it is **logged here for the DRI rather than folded
in**. B2 as the review wrote it is about the coverage gate, and the coverage gate is closed.

The STUDENT path is also unchanged: `sbpToManifestRefs` records coverage `[]` vacuously because
SBP has no source-block layer at all, which its own comment already documents as a limitation
rather than a pass. A test now pins that the student path does not consult the document.

## A test that certified the hole

`blueprintPersistence.test.ts` carried this, passing, under the heading *"an EMPTY source_blocks
array is honoured as a measurement of zero blocks"*:

```ts
await persistComposedBlueprint({ ..., project: project({ sourceBlocks: [] }) });
expect(persistedRefs().coverage.uncitedRequirementBlocks).toEqual([]);
```

True of the code and wrong of the gate. It is now the opposite test, named **"THE DEFECT: a body
claiming `source_blocks: []` no longer clears the gate"**, and it asserts that a body declaring no
blocks AND a task citing everything is ignored in favour of the stored document, which reports
`b-2` uncited.

That is the third time in this ticket that a careful-looking test had encoded the defect it was
meant to catch (B1 had three of them). The lesson stands: the production measurement, not the
suite, is what settles these.

## BREAK, then HARDEN

`doc_json` is `DataTypes.JSONB` typed `any`, validated by `factoryValidate` at write time and by
nothing at read time, and `reconstructFactoryProject` does `tasks: d.tasks ?? []` with no
`Array.isArray`. This path is its first reader, so its malformed shapes became newly reachable.

Run against the shipped adapter before any guard existed:

| Malformed stored document | Result |
|---|---|
| `tasks` is an object | `TypeError: tasks is not iterable` |
| `tasks` is a string | `TypeError: (input.tasks ?? []).map is not a function` |
| a `null` element in `tasks` | `TypeError: Cannot read properties of null (reading 'source_evidence')` |
| a `null` element in `source_blocks` | `TypeError: Cannot read properties of null (reading 'kind')` |
| CONTROL: a well-formed document | coverage `[]` |

Each one is a 500 from compose with nothing persisted. `readableCollection` now refuses them as
unmeasurable, logged `error_class: ContractViolation` with WHICH collections were malformed and
never their contents. One unreadable element makes the whole collection unreadable, matching
`readableSources` in `lifecycleEvidence`: measuring the remainder would publish a shorter uncited
list, and a shorter gap list reads as better news.

The read failure is also deliberately NOT rethrown. Returning a 500 would lose the composition
result the caller already has, and a manifest whose coverage is `null` is a true statement about
an unreadable document.

## What this does NOT do

- **B3 is untouched**, so Phase 7 exit stays REFUSED. Project `50a24430` still has no lifecycle
  row and there is still no repair path.
- **Requirements still come from the request body.** See the scope section: the measured cost of
  changing that is the live client build blocked at its first gate, which is the DRI's call.
- **It does not gate blueprint approval** (finding C4). `approveLifecycleBlueprint` still consults
  no permission at all.
- **It does not pin the refs at the document's version.** `factoryToManifestRefs` takes one
  `documentVersion` and applies it to every collection, including the requirement refs that still
  come from the body, so stamping the document's version there would pin a revision onto records
  not read at it. The version is carried to the log instead, and `revision: null` continues to say
  "unrecorded", which is true.
- **Nothing was deployed.** Merging is the DRI's click and deploying is a separate decision.
