# CC-20261112-p4q7 - L7.6 follow-up: the two suites that ran nowhere now run

Session `CC-20261112-p4q7`. Follow-up to the L7.6 review (PR #4021, merged as `04b9652f6`),
which found two lifecycle suites executing in no tier at all. This is the repair for both.

Ticket: **L7.6** (`10396178398`), which stays OPEN - this closes none of its three blockers.

`PROGRESS.md` is sealed; this file is the record.

---

## Why these two and not the blockers

L7.6 refused Phase 7 exit on three findings. All three are the DRI's: B1 is an authorization
policy question (which admin role should hold which lifecycle permission), B2 changes what a
governance gate accepts, and B3 needs a production write. None of them is mine to decide.

The two test-tier repairs are a different kind of thing entirely - reversible, local blast
radius, no governance boundary, and they make an existing claim checkable rather than changing
what the system does. So they are taken under the Autonomy Model's PROCEED tier while the
blockers wait.

---

## 1. `designPersistence` ran in no tier, and a bare rename would have made it fail

The suite is DB-gated, so the unit tier skips it. It was named `designPersistence.test.ts`, and
`scripts/ci/runIntegrationSuites.js` only discovers files ending `.integration.test.ts`, so the
job built for it never saw it. **Twelve assertions executing nowhere.** It was also absent from
the runner's exclusion list, which made it *invisible* rather than excluded - the worse of the
two, because the guard that fails when an exclusion rots cannot see a suite nobody listed.

**The obvious fix was the wrong one, and the repository already said so.**
`carried-forward-obligations.md` carries a section headed "KNOWN, not a defect: the lifecycle
suites cannot run on a TRULY empty database":

> A fresh, empty Postgres makes `designPersistence.test.ts` fail, and the failure LOOKS like a
> lifecycle regression. It is not. That suite needs the real multi-tenant base schema -
> `tenants(id, name)` - and **nothing in the lifecycle tree creates it**. [...] Two separate
> verifiers lost time to this; the second diagnosed it only after a 12-hour background job
> finished. Recorded so the third does not.

The integration tier gives each suite its own freshly created, empty database. So renaming the
file and stopping there would have moved it from "runs nowhere" to "fails red for a reason that
is not a defect" - and I would have been the third verifier.

**What shipped instead:** the suite now creates its own minimal `tenants`, `projects` and
`delivery_projects` stand-ins before calling `ensureProjectLifecycleSchema()`, which is exactly
the preamble `blueprintApproval.concurrency.integration.test.ts` and
`lifecycleAutoAdvance.integration.test.ts` already use for the same reason. `name` is included
because this suite inserts it and theirs do not. Then the rename.

Its header has also been corrected. It claimed "CI has no `DATABASE_URL`, and a Postgres
container there is deliberately a separate change", which was true when written and stopped
being true when the `integration-tier` job shipped with a `postgres:16-alpine` service.

## 2. `lifecyclePlanReads` lost seven good tests to one bad one

The runner excluded the whole file for a single test, `counts TWO published rows rather than
reporting the newest as healthy`, which forces a second `published` row into `build_plans` with
raw SQL to recreate a legacy state the partial unique index now refuses. That is a genuine
disagreement between the suite and the schema, not a flake.

But excluding the file to exclude the test took the other seven with it - including the JSONB
round trip, which the suite's own header calls "the one claim here that cannot be checked any
other way", and which `lifecycleEvidence.publishIntegrity.test.ts` delegates to by name.

The one test now lives in `lifecyclePlanReadsTwoPublished.integration.test.ts` and the runner's
exclusion names that file instead. Seven tests return to the tier; one stays excluded, with the
reason carried across and what would close it written down.
