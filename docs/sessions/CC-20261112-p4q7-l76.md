## 3. LC-01 is not met in production

This is the finding that refuses the phase.

`unregisteredStudentProjectsSince()` and `unregisteredDeliveryProjectsSince()` are exported
detectors that ask LC-01's actual question - "is there a project with no lifecycle row?" - rather
than checking the paths someone remembered to instrument. Run against production, read-only:

| | |
|---|---|
| Student projects created since the hook went live (2026-10-12) | 29 |
| Of those, registered | 28 |
| **Of those, NOT registered** | **1** |
| Delivery projects since 2026-10-09 | 11, of which 0 unregistered |

**The detectors were validated in both directions before being trusted.** Each was run twice: once
with its default `since`, and once reaching back to 2020-01-01, before the hook existed. The second
call returned **63** and **4** rows. A zero or a one from a detector never shown returning rows is
indistinguishable from a broken join, and the script was written to stop rather than publish an
uncontrolled figure.

The row: project `50a24430`, created **2026-11-11**, tenant `colaberry`, no name, no build, and its
enrollment's `active_project_id` never set. The enrollment is a real one on the "Explorer -
Prospects" cohort.

### How it got through, and why nothing fixed it

Not a bypass. The chain is written into the code and each step is deliberate:

1. `resolveStudentTenantId()` returns `null` on exactly two conditions, `configured_tenant_missing`
   and `unreadable`, both breakage rather than ambiguity. A transient read failure is enough.
2. On `null`, `studentProjectTenantHook` (beforeCreate) **returns**, leaving the row unattributed.
   Its comment says so: "the row is created unattributed and `studentProjectLifecycleHook` reports
   it as unregistered."
3. `studentProjectLifecycleHook` (afterCreate) sees no `tenant_id`, logs `error_class:
   ContractViolation` with `reason: tenant_unresolved`, and **declines to register**. By design: a
   data-layer module that threw here would refuse a student's project creation for a governance
   reason.
4. `ensureProjectTenantSchema` runs at boot and backfills `tenant_id` for every unattributed row.
   **This is why the project now looks ordinary.**
5. **Nothing registers the lifecycle afterwards.** The backfill repairs the cause and never the
   consequence.

`ENABLE_PROJECT_LIFECYCLE` reads `true` in the running container, and `storyAuthorization.ts`
treats a missing lifecycle row as absence of evidence, so this project is refused authorized
stories. No build has run for it, so nobody has hit the wall yet.

Detection exists and is wired into system health at **`severity: 'warning'`**, which is why five
weeks of it went unremarked. **Repair does not exist at all.**

### The log could not confirm it, and the control is what showed that

The retained container log holds **zero** occurrences of `student_project_lifecycle_unregistered`.
It also holds **zero** occurrences of the success event `project_lifecycle_registered`, although 28
projects did register. So the log window does not reach 11 November and cannot answer either way.
Without counting the success event alongside the failure event, that zero would have read as
evidence the failure never happened.

`featureFlags.ts` carries a figure measured 16 Oct: "11 of 48, p90 27,772". A review of evidence
should not reprint a month-old number as the current state of a live student path.

Re-measured today with the shipped `buildBriefText` over all 52 `build_intake` rows:

| | today | 16 Oct |
|---|---|---|
| rows | 52 | 48 |
| over the 20,000 cap | 11 | 11 |
| p95 | 28,844 | 28,844 |
| max | 41,679 | 41,679 |

**My first pass was wrong, and comparing against the prior figure is what caught it.** It
reconstructed the input from four columns and reported a maximum of 31,256 - *below* October's,
which is impossible without data loss. `buildBriefText` also reads `users`, `dataSources`,
`doneDefinition` and `targetWeeks` and appends a labelled line for each; 50 of the 52 rows carry at
least one. That is precisely the trap P7-T1.3 wrote down, and I walked into it anyway. The
corrected pass reproduces October's max and p95 exactly, which is what licenses the rest of the
figure.

**The new information is in the dates.** The newest clipped brief is **2026-09-26**. Five briefs
have been recorded since and all are under the cap. So October's present tense - "roughly a quarter
of real student briefs are clipped in production today" - was true of the corpus and reads as a
claim about the current rate. The current rate over the last seven weeks is 0 of 5, which is too
small a denominator to call the problem solved but changes the urgency of L9.6 without changing its
answer. `ENABLE_SBP_SOURCE_OVERFLOW_BLOCK` is not set in the container, so the flag is still off.
