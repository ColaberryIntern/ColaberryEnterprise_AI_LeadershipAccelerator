  - Verification: `npx jest -c jest.ci.config.ts --testPathPattern 'src/scripts/__tests__/prMergeWatcher'`
    -> **68 passed** (was 46), and **four mutation tests, 4 of 4 caught** - see below.
  - Notes: ticket https://app.basecamp.com/3945211/buckets/7463955/todos/10480871859

### Why it was needed, measured rather than assumed

Of the **222** open to-dos assigned to Ali in `Ali Personal`, **47 carried a merge notice from
this watcher and no deploy claim**; only 3 had ever got one, all written by hand. 44 of the 47
had shipped and were closed the same day. Recounting afterwards moved the overdue figure from
**233 to 213** - purely by ticking work that was already live. A watcher that can only say
"merged" manufactures a backlog of finished work, and the backlog reads as overdue.

The original refusal to report a deploy was correct in its reasoning ("a ticket that says
deployed because something merged is worse than a ticket that says nothing") and wrong in its
consequence. So the fix supplies a real signal instead of relaxing the standard.

### The signal, and the four ways it could have been wrong

The worker runs **on the host** from `scripts/cron-env-wrapper.sh`, which already shells out to
the container runtime, so the runtime is reachable. It inspects each container, reads the image
it was created from, and reads that image's build time.

1. **Bounds on the OLDEST running image, not the newest.** The API is in the backend image and
   the built frontend is in the nginx image; bounding on the backend alone would report frontend
   work live whenever the two drifted.
2. **Never reads `git HEAD` on the box.** Measured the same day: the host sat at `a29dfb24`
   (merged 13:16Z) while the running image had been built at 12:24:30Z, an hour behind. Registry
   deploys no-op when no image exists for main's tip, so the checkout moves on without the
   container.
3. **Four verdicts, not two.** `in_build` / `ambiguous` / `not_in_build` / `unknown`, and only
   `in_build` is ever posted. A build starts from the tip some minutes before its image is
   stamped, so a merge inside a 30-minute margin cannot be resolved by time alone.
4. **`state.deployAdoptedAt` stops a flood.** Every merge in the repository's history predates
   the running image, so without the stamp, switching this on would post a deploy notice on all
   of them.

Every constraint inherited from C0.4 still holds and is still asserted against the source text:
one comment per transition and nothing else written to Basecamp (exactly one `method: 'POST'`
line), GitHub reached only through the GET-only `ghGet()`, and the to-do never completed. A new
structural test asserts the container runtime is called **only** to inspect - `execFileSync` with
an argument array, never a shell string, and no `run`/`stop`/`rm`/`exec`/`compose` verb anywhere
in the source.

### Mutation testing, including one that failed first

A passing test that cannot fail proves nothing, so four mutants were introduced deliberately:

| Mutant | Caught by |
|---|---|
| bound on `Math.max` instead of `Math.min` | "bounds on the stalest running image, not the freshest" |
| backfill guard forced true | "announces nothing for merges that predate the deploy watch" |
| margin branch deleted | 3 tests |
| announce `!== 'not_in_build'` instead of `=== 'in_build'` | **survived at first** |

The fourth mutant - publishing an `ambiguous` verdict as a deploy, which is the exact failure
this whole design exists to prevent - **passed all 66 tests on the first attempt.** The
classifyDeploy unit test proved the verdict was `ambiguous`; nothing proved the watcher stayed
*silent* on it. Test "stays silent on an ambiguous verdict instead of rounding it up to
deployed" was added, and the mutant then died. Final: 68 tests, 4 of 4 mutants caught.

### Known limit, recorded rather than hidden

This is a **timestamp comparison, not a commit identity**. The running image carries no commit
label and no `GIT_COMMIT` variable, so "is this merge an ancestor of what is running" cannot be
answered directly - which is the only reason a margin and an `ambiguous` verdict are needed at
all. Stamping the commit SHA into the image at build time would replace the mechanism with an
exact ancestry check. That is a build-pipeline change and was deliberately not made here.

## 2026-11-05 - C10.1: checkout conversion, per person, split by product

- [x] Checkout funnel measurement, and the cause C10.1 asked for
  - Date: 2026-11-05

  - What changed: added `backend/src/services/checkoutFunnelService.ts` (pure) and

  - Notes: ticket https://app.basecamp.com/3945211/buckets/7463955/todos/10461566131

### The cause, which is not the one the ticket was built around

**The checkout does not leak. It converts 88 to 100 percent every month.** Measured per person,
split by `enrollment_type`:

| month | standard started -> paid | explorer started -> paid |
|---|---|---|
| 2026-07 | 37 -> **36 (97%)** | 10 -> **0** |
| 2026-08 | 17 -> **15 (88%)** | 2 -> **0** |
| 2026-09 | 14 -> **13 (93%)** | 2 -> **0** |
| 2026-10 | 2 -> **2 (100%)** | 12 -> **0** |
| 2026-11 | 1 -> **1 (100%)** | 3 -> **0** |

**Twenty-nine free Explorers have started checkout since July and not one has ever become a
paying member.** Meanwhile enrollments created per month went standard **195, 68, 19, 11, 0** and
explorer **122, 94, 76, 494, 87**. Of Explorers created each month, the share who ever start
checkout *fell* as volume rose: **9.0%, 4.3%, 2.6%, 2.2%, 1.1%**.

So C10.1's recorded decline - 51.4% in July to 14.3% in October - is a **mix shift**, not a
conversion problem. That series blends a product converting around 90% with a free tier
converting at zero; its July denominator (37) matches the standard-only population exactly while
its October denominator (14) matches the combined one. The paid product's rate never fell.

### Two wrong turns of my own on the way, both corrected at source

1. **"$9,950/month of unbilled membership."** Filtering the November cohort on `payment_status`
   and `portal_enabled` without `enrollment_type` counted 48 free Explorers as delinquent
   members. The cohort is 14 members, 12 paid (86%); real exposure is 2 people, about $398/month.
   Wrong by a factor of 25, in the alarming direction. Corrected on C9.13, on C10.1, in memory,
   and in C10.16's description so Jackie is not briefed from it.
2. **"Checkout arrival is unrecorded, criterion (2) is unbuildable."** Also wrong.
   `startCheckout` in `subscriptionService.ts` mints the payment link and then writes a
   `subscriptions` row with `status='pending'`, so the attempt *is* logged, keyed on
   `enrollment_id`. I had checked `enrollments.paysimple_customer_id` - genuinely unreliable at
   46 of 131 paid rows - and concluded from one bad column that the event existed nowhere.

### Why the module refuses to return a single number

`computeCheckoutFunnel` returns one row per (period, type) plus a `mix` block, and sets
`mixShiftWarning` when composition moves 25 points or more between the first and last period.
A blended rate is not merely less useful here; it is the thing that misdirected this ticket for
a month, so the composition travels in the same object as the rates.

The warning names the type with the **largest** shift, ties broken alphabetically. The first
version named whichever type appeared first in key order - and in the real data standard moves
-64.4 while explorer moves +64.4, exactly equal, so the message depended on insertion order. A
test caught it; a warning whose text changes between runs cannot be trusted or tested.

### The data-quality check that could have invalidated it

44 of the 248 attempt rows are stamped at exactly `14:00:0X` UTC - the signature of a scheduled
job, not a human clicking checkout. **0 of the 100 people have such a row as their *first*
attempt**, so the first-attempt rule makes the metric immune to them. Had even one person's first
row been machine-created, they would have counted as having started a checkout they never
started.

### Not done

Criterion (3), a measured rate on the next 40 first-time checkouts, cannot be met for a long
while at current volume: only **3 standard** people have started checkout since 1 October. The
report is also not yet scheduled anywhere - it is a script that must be run. C10.1 stays open.

## Two production data corrections to the batch model (2026-11-05)

Both authorized by Ali in session. Guarded, idempotent, verified by reading the row back.

### 1. November 2026 batch orientation date: 12 Nov -> 7 Dec

`cohorts.start_date` carries the batch's **orientation** date under the monthly batch model -
the first Monday of the month after the one you paid in. The November 2026 batch
(`fcb83a02-025e-43d5-b799-776cc56df3de`) still held `2026-11-12`, a date with no meaning under
the model.

The consequence of leaving it was not cosmetic: `schedulerService` stops chasing a batch for
payment once its `start_date` has passed, so on 12 November every unpaid person in that batch
would have silently dropped out of payment reminders. **48 of its 65 enrollments are free
Explorers**, so that is most of the batch.

Changed to `2026-12-07` - the first Monday of December. Verified by reading the row back.

Worth recording that the four batches created earlier in this session are all correctly dated
on the same rule: December 2026 -> 4 Jan 2027, January 2027 -> 1 Feb, February -> 1 Mar,
March -> 5 Apr. Each is the first Monday of the following month.

### 2. July 2026 batch closed, restoring the one-open-batch convention

Production had **two** open accelerator batches, July 2026 and November 2026. The directive
declares exactly one open batch load-bearing, so this was a live violation.

What I verified before writing, rather than assuming:

- `validateCohortAvailability` (`enrollmentService.ts:27`) is the **only** behavioral consumer
  of `cohort.status` outside open-filters. It rejects a *new* enrollment into a non-open cohort.
- Nothing under `backend/src/services/access` reads `cohort.status`. Existing members' access
  comes from `Enrollment.status` / `portal_enabled`. July's **56 members, 47 active, 44 paid,
  56 portal_enabled** are untouched by this write.
- Nothing reads a *cohort's* `'completed'` status anywhere - every hit for that string is a
  session, card, project or enrollment status. So `closed` and `completed` are behaviorally
  identical here; `closed` matches the resting state of the four future batches.
- `getDashboardStats` (`cohortService.ts:440`) sums `max_seats - seats_taken` over open
  cohorts. July is oversubscribed at 58/50, so it was contributing **-8** seats and
  understating seats remaining. Closing it fixes that number.
- Placement and the public picker do **not** change: `selectNextOpenCohort` already ignored
  July because its `start_date` is in the past, and `selectEnrollableCohorts` already excluded
  it on the seat check.

That last point is the uncomfortable one. July was invisible to the public cohort picker only
**because it was oversubscribed**, not because anything had closed it. A batch that had been
open five months past its start date was one seat-count correction away from being publicly
joinable. The convention was doing no work; the seat arithmetic was.

Reversible: set `status` back to `'open'`.

### Logged, not fixed: `seats_taken` is stale

November shows `seats_taken = 2` against 65 enrollments; July shows 58 against 56. Neither
matches the enrollment count or the paid count, so the column is simply drifting. It causes no
current harm - November's cap is 125, far above any count - but it is load-bearing in two
places (`validateCohortAvailability`'s full check, and the public picker's seat filter), and it
is what was accidentally hiding July.

Not fixed tonight because "correct" depends on an unanswered model question: does a seat count
every enrollment, or only paying ones? Under the batch model with free Explorers in every
batch, those are very different numbers. Belongs with C10.15 (the cohort resolver).

this phase deletes, on the one path where no payment justifies it. Writing `tier` alone leaves
the row at `explorer` + `member` + **unpaid**, which the Phase 1 paywall still gates — an admin
would "convert" somebody and leave them locked out of weeks 1-12, which is what this function
already was once before: a latent trap. Teaching the paywall to honour `tier` instead would
change access for rows that exist in production today (that is `freeAccountCoherenceBackfill`'s
Shape A, ~260 rows), which is a customer-visible decision for Ali, not a side effect of a
bookkeeping fix.

It had **no callers** — verified across `backend/src`, `frontend/src`, `/scripts` and `/tests`;
only its own definition and its own tests. The live admin "Convert to enrolled" buttons call
`grantFreeAccess`, which grants `tier` **and** `payment_status: 'paid'` through `grantMembership`
and records a comp subscription. Delegating to it was rejected rather than skipped:
`grantMembership` already calls `retireRedundantExplorerAccounts` from `enrollmentService`, so the
import would be circular, which CLAUDE.md forbids.

### The handoff's Shape A hazard was checked and is NOT real

The handoff said to retire or re-scope Shape A. Shape A is `explorer` + non-guest tier and its

It cannot. `exclusionsFor` pushes `paid_status` / `paid_amount` / `active_subscription`, and

correct code to match a prediction is how working guards get broken.

What *was* wrong:

- **The reasoning.** The docblock justified Shape A with "a Shape A row has already declared its

  **ordering is now recorded as load-bearing** — nothing in the `shapeA` predicate mentions
  payment, so an innocent-looking tidy-up that tests the cheap predicates first would turn the
  module into a tool that strips paid access.
- **The witness.** `SHAPE_COUNT_SQL` reported one `shape_a` number, so payers counted as pending

## C10.14 - one shared curriculum, and a room per batch

- Date: 2026-11-06
- Session: CC-20261104-m4k7
- Branch: `workstream/c1014-shared-curriculum-batch-rooms` off `origin/main` 4c0bead0

Ali settled both halves: *"We should not be holding curriculum per cohort - everyone can use
the same curriculum until future notice"* and *"Each batch should have their own room that only
they can see and staff. 1st meeting will be on their batch but after that they will use shared
rooms."*

### What the survey changed about the ticket

**The curriculum decision was already true of the live curriculum, and I had the wrong table.**
`services/timeline/curriculumScope.globalCurriculumWhere()` selects `cohort_id: null` and is
already the single source of truth for every student-facing reader; its header says "which
cards belong to the ONE shared student curriculum", and `acceleratorCohortCurriculumService`
states the rule outright. In production, 0 of 20 `curriculum_blueprints` rows carry a
`cohort_id` and 7 cohorts share one `program_id`. So nothing I did changes what a student is
taught, and claiming otherwise would have been the easiest wrong thing to report here.

What was real is the LEGACY authoring table. `curriculum_modules` holds 5 rows in all of
production, every one of them on the **completed** April 2026 cohort, under the retired
"Enterprise AI Leadership Accelerator" program. The repo already says so twice -
`acceleratorRoutes`: "the pre-Timeline authoring model and is empty for every live cohort";
`acceleratorCohortCurriculumService`: "effectively dead: nothing in the Composer writes it".
Against a NOT NULL `cohort_id`, that produced three things worth fixing:

1. `initializeParticipantCurriculum` threw for anyone in a batch without its own rows, which is
   every live batch. It is already why `/portal/curriculum` is a `<Navigate to="/portal/today">`:
   the page "500'd on every open (found 2026-07-30 via a real student report)".
2. `handleGetProgramModules` - a PROGRAM-wide admin endpoint behind four live Orchestration
   tabs - faked the global scope by filtering on whichever cohort was **oldest**
   (`getFirstCohortId`). It returned the right answer only because one cohort holds every row.
3. `directives/run-monthly-enrollment-batches.md` step A6 told the operator to materialize
   modules for each new batch. Twelve batches a year is twelve copies a year - exactly what
   Ali's decision rules out, written down as a procedure three weeks before the rollover.

**A claim of mine that was wrong, and is now corrected on the ticket.** I had posted that "the
only code writing `linked_cohort_id` is the DM service". There are three writers:
`ensureRoomForSession`, `createRoom` (which stamps `ctx.cohortId` onto **any** member-created
room) and `dmService`. Two consequences: a per-session cohort-private room already exists for
every live session, so the access model needed nothing; and `linked_cohort_id IS NOT NULL` is
**not** a usable "this is the batch's room" predicate, which is why the new room keys on a
deterministic slug instead.

### What I built

New `services/curriculumModuleScope.ts` - `findSharedModules`, `findSharedModuleByNumber`. Five
readers were rewired onto it (three in `curriculumService`, the progression unlock, and
`handleGetProgramModules`). It also absorbs a duplicated query that had already drifted four
ways: two sites ordered lessons in SQL, one sorted in JS afterwards, one did not order at all.
`cohort_id` stays in the schema - dropping a NOT NULL column is ESCALATE-tier and unnecessary,
and "until future notice" is reversible, so leaving it makes reversal a code change rather than
a migration.

New `services/communityRooms/cohortRoomService.ts` - the batch model's room policy, in its own
module because `roomService` already carries ten exports against the twelve the Modular
Composition Rule allows.

- `ensureRoomForCohort` - persistent, `privacy:'cohort'`, `category:'your_cohort'`, keyed on
  `cohort-<id>`. Minted from `createCohort`, flag-gated and non-fatal, same posture as
  `acceleratorService.resolveRoomId`. `room_type:'persistent'` is load-bearing:
  `listRoomsForViewer` excludes `['dm','scheduled']`, so a 'scheduled' batch room would exist
  and be unbrowsable - which is where the per-session rooms have always sat.
- `sessionRoomPrivacy` - the orientation's room is `'cohort'`, everything after it `'public'`.

### The thing that nearly went in backwards

`session_number === 1` is the obvious reading of "1st meeting" and is **wrong on the one batch
