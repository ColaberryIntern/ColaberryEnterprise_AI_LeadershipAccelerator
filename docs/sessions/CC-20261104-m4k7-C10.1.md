## What was actually missing

C10.1's criterion (2) is "checkout conversion instrumented per person and reported weekly as a
rate". Two PRs had already shipped and deployed the instrumentation (#3703, #3711). What had not
shipped was the cadence: `reportCheckoutFunnel.ts` has a `--weekly` flag and is registered in no
scheduler at all, so "reported weekly" depended on somebody remembering to run a script.

A capability is not a cadence. That was the whole gap.

## Why this hangs off the existing report rather than a new cron

`weeklyCommercialReport` (C8.8) already assembles outcomes weekly, already ships dark behind
`COMMERCIAL_WEEKLY_REPORT_ENABLED`, and already sends to the same `admin_notification_emails`
list. A second weekly cron would have told the same two people the same thing on a different
schedule, and added a second thing to register, seed and keep alive.

## The three rules the section is built around

Each one is a mistake this ticket actually made, so each is enforced rather than documented.

1. **Never a blended rate.** A blended number fell from 76.6% to 14.3% between July and October
   and sent this ticket hunting a broken payment page for a month. The page was fine; the
   population arriving had changed. `assertEveryRateNamesItsOrigin` fails the build on any line
   carrying a percentage that does not name the population it belongs to.
2. **A failed read is not a zero.** If the query cannot run, the section says so and prints no
   number. "0% converted" and "we could not look" are different weeks and only one is an
   emergency. The wording is also kept clear of `assertNoUnevidencedZero`'s trigger.
3. **The funnel's warnings travel with the number.** `originWarning` and `mixShiftWarning` become
   report caveats, computed and attached in the same place, because a caveat that is computed in
   one function and dropped in another is a caveat nobody reads.

## Two findings that changed the plan mid-build

- **A stale note nearly set the scope.** I came in believing free-to-paid was unmeasurable
  because the payment path rewrites `enrollment_type`, and had scoped a schema fix around it.
  C10.17 Phase 2 had already deleted those writes from `enrollmentService`, `subscriptionService`
  and `appPaymentReconcileService`. Reading the code before building saved a redundant PR. The
  origin markers stay in use anyway, for a reason worth keeping: Phase 2 is **not retroactive**,
  so every row that paid before it shipped already had its origin overwritten.
- **Local `tsc` here is a decoy.** `npx tsc` in this clone resolves TypeScript **4.9.5** from the
  hoisted root and reports **267 phantom errors**. The pinned compiler is at
  `backend/node_modules/typescript` (**5.9.3**), which `checkTestTypecheck.js` already uses by
  explicit path. The clean run was believed only after a planted control error came back, exactly
  one, from the directory under test.

## Deliberate choices

- The section reads the database through a **lazy import**. A static import of `config/database`
  pulls a live Sequelize instance into every suite touching the weekly report, and an unclosed
  instance leaks handles and force-exits a jest worker. Lazy also puts a module-load failure
  under the same guard as a query failure.
- `ReportSection` is imported **type-only**, so the two modules do not form a runtime cycle.
- The section counts as "movement" on exactly the condition that makes it non-empty, so the
  report headline and the section can never contradict each other.
- The existing `weeklyCommercialReport.test.ts` mocks only the **reader**, so the real section
  builder still runs there and the report is assembled from the shape production produces.

## Still open, honestly

Criterion (3), a measured rate on the next 40 first-time checkouts, cannot be met for a long
while: only a handful of never-Explorer people have started checkout since 1 October. The ticket
stays open on that criterion alone.

The report also still ships dark. `COMMERCIAL_WEEKLY_REPORT_ENABLED` is not set in production, so
this section exists and is tested but is not yet reaching anyone. Turning that flag on is Ali's
call and is the one thing standing between this and "reported weekly" being true in fact rather
than in code.
