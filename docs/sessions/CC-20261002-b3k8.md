## Why the planning took four audit cycles

Worth recording, because the cost was real and the cause was mine.

The request asked for an in-app live player with a server-enforced 15-minute preview.
Discovery found that **live embedded playback was not reachable** with the services this
repo has: Zoom is Server-to-Server OAuth only, there is no Meeting/Video SDK credential
anywhere, no streaming stack of any kind, and no RTMP output configured. That was escalated
rather than worked around, and Ali approved a managed streaming provider on 2026-10-01.

Discovery also found three latent defects this feature depends on:

1. **Nothing ever writes `lobby_open` / `live` / `cooldown`.** `RoomBooking` declares twelve
   states and the transition table exists, but `roomBookingService` only ever writes
   `pending_approval`, `scheduled`, `completed`, `cancelled`. Controllers *read*
   `state IN ('live','lobby_open')`, so the "happening now" rail is permanently empty.
2. **`SessionWentLive` is dead vocabulary** — declared at `roomEvents.ts:14`, matched as a
   no-op handler, emitted nowhere.
3. **Every feed filters `starts_at >= now`**, so an event that has already begun is invisible
   by construction (`communityCalendarService.ts:93-95`).

Separately, the Zoom webhook **fails open** when its secret is unset and has **no replay
protection** — the repo's own test signs a November 2023 timestamp and asserts success.
That is a security fix queued as P2-06, justified independently of this feature.

The plan scored 14/20, then 17, 17, 17. No dimension ever scored zero, and in the later
cycles the losses were **my unverified repository claims**, not plan structure — five of
them, including an absence conclusion drawn from a grep piped through `head -12`. The
method correction is recorded in the run's `verification-log.md` and in memory: read the
file in-session before asserting anything about it, and never conclude absence from a
truncated or path-limited search.

- [x] P2-05 — signed playback grant bounded by the preview deadline
  - Date: 2026-10-01
  - Session: CC-20261002-b3k8
  - What changed: added `backend/src/services/broadcast/broadcastPlaybackGrant.ts` — pure
    expiry computation, signing, and verification.
  - Verification: `jest -c jest.ci.config.ts` **138 passed / 138 total across 7 suites**.
    `tsc --noEmit` clean. **Proven by mutation:** removing the `Math.min(ttlExpiry,
    deadline)` bound failed **nine** tests by name, including *"caps the token at the
    deadline, NOT at the full TTL"*, *"refreshing does not extend it"* and *"grace never
    extends the GRANT itself"*. Reverted by edit.
  - Notes: this is where §4.2's hardest sentence — "prove the viewer cannot continue
    obtaining paid content after expiry" — is actually satisfied. A UI countdown proves
    nothing; the token is what holds the bytes back.
    **A preview grant is bounded by the deadline, not the TTL:** `min(now + ttl,
    contentStartedAt + previewSeconds)`. Refresh, a second tab, another device and a changed
    client clock all converge on the same server-side instant, so no sequence of renewals
    can mint a window outliving it — asserted by walking every renewal second from 600 to
    899 and checking the latest authorised instant is exactly the deadline.
    **The TTL is deliberately short (120s), not mediaStore's 15 minutes.** That TTL is sized
    for a provider fetching an image once; here it would leave a revoked viewer holding a
    valid token for a quarter of an hour. Revocation is only as fast as the shortest token.
    **Segment grace (10s) applies to the CHECK, never to the grant**, so the deadline is
    never extended — the most a viewer gains is one partly-buffered segment, and it cannot
    be chained because the next grant request is already refused. Tested.
    Signature is verified **before** expiry, so a 410 never leaks that a guessed key was
    once valid. Status classes mirror `mediaStore` exactly (404 InvalidKey, 403 Unsigned,
    410 Expired, 403 BadSignature) so the two media surfaces cannot drift.
    There is **no fallback** that returns an unsigned or long-lived URL on failure — §7
    forbids concealing a gap behind a public unlisted URL, and a fallback is how that
    happens. `signPlayback` returns null instead.
  - **A test of mine was wrong and the code was right.** *"gives a late joiner only the
    remainder"* asserted the token would span the viewer's remaining 300s of preview. It
    does not, and should not: the token is TTL-sized (120s) and renewed. I had conflated
    "remaining preview window" with "token lifetime". Rewritten to assert the property that
    actually matters — that no renewal ever passes the deadline.

- [x] P2-09 — observability: the five operational measures, stable error classes
  - Date: 2026-10-02
  - Session: CC-20261002-b3k8
  - What changed: added `backend/src/services/broadcast/broadcastMetrics.ts` — pure
    aggregation plus an emitter and a timing wrapper.
  - Verification: `jest -c jest.ci.config.ts` **238 passed / 238 total across 12 suites**.
    `tsc --noEmit` clean. **Proven by mutation:** reporting 0 instead of `null` for an empty
    sample failed *"returns null rates and null latencies for an empty sample"*, *"null is
    distinguishable from 0"* and *"reports all five paths…"*; making `observe` swallow
    instead of re-throw failed *"RE-THROWS after recording"*. Four named failures, reverted
    by edit.
  - Notes: §7 names five measures on five paths, and the acceptance bar I set was that each
    is asserted **equal to a hand-computed value** rather than merely present — a metric
    nobody can compute by hand in a test is one nobody can audit in production. Every
    expected number in the suite has its arithmetic in the comment beside it.
    **Zero observations yields `null`, not 0.** A `success_rate` of 0 means everything
    failed; `null` means nothing was measured. Collapsing them is how a dashboard reports a
    catastrophe during an outage *of the dashboard*. §4.7 forbids the fabricated zero, and a
    test asserts the two are distinguishable.
    **Percentiles are nearest-rank, and that choice is written down** rather than left to
    whichever library is installed — the definitions disagree on small samples. On N=5, p95
    and p99 are both the maximum, which is correct and worth knowing before someone
    over-reads a p99 over five events.
