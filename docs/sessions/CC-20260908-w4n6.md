  - What changed:
    **(1) THE COHORT THAT COULD NOT BE DELETED, AND WHY.** Ali could not delete `Cert Prep certprep-e2e open`. The admin UI already had a force-delete path and the service already returned "not blocked" for this cohort (`unsafeEnrollmentCount: 0, liveSessionCount: 0`), so the guard was never the problem. Running `deleteCohort` through its own code path on prod produced the real error: `update or delete on table "enrollments" violates foreign key constraint "student_architecture_skill_enrollment_id_fkey"`. **`cohorts.enrollments` is `ON DELETE CASCADE`, but 25 of the 44 FKs referencing `enrollments` are `NO ACTION`** — so the cascade dead-ends one level down the moment a student has done anything. This cohort's single enrollment held 56 such rows across `cert_responses` (31), `cert_sessions` (11), `student_architecture_skill` (10), `cert_readiness_snapshots` (2) and `reese_welcomes` (2). The UI reported only a generic "Failed to delete cohort". **This is a general defect, not a quirk of this row: any cohort whose students have used Cert Prep or accrued Architecture Skills is currently undeletable from the admin UI.** Deleted via a transaction-wrapped script that re-asserted both id and name, refused to proceed unless every enrollment was a `*.test` fixture, cleared the blocking child rows in dependency order, then deleted the cohort. **No schema change was made** — converting 25 FK delete rules is a governance-boundary call and is raised below rather than taken.
    **(2) NEW "RIGHT NOW" DASHBOARD above the Cohorts table** (`acceleratorCurrentClassesService.ts`, `CurrentClassesDashboard.tsx`, `GET /api/admin/accelerator/current-classes`). Answers "which classes are teaching today and how are those students doing" before the table answers anything else. Three selection rules, each pure and unit-tested, each present because the cohort row alone gets it wrong: a class must **have scheduled sessions** (without this the self-paced Explorer pool — 325 members, no sessions, open forever — dominates every average while teaching nobody), must **have started**, and must **not have finished**. Status cannot carry the last two: cohorts routinely teach out their final weeks still marked `open`, and are marked `completed` by hand, late. Headline averages are **weighted by head count**, so a 49-student class and a 2-student class do not move them equally, and cohorts with no score are excluded rather than counted as zero.
    **(3) THE CURRICULUM TAB WAS READING A DEAD TABLE.** It queried `curriculum_modules WHERE cohort_id = :id` — the pre-Timeline authoring model that nothing in the Composer writes — so it rendered "No curriculum modules found for this cohort" for *every* cohort. **The real defect is the join, not the data:** the live curriculum is `timeline_cards`, which is **course-scoped** (`program_id` set, `cohort_id` NULL, one curriculum shared across a course's cohorts). A cohort reaches its curriculum through `cohorts.program_id`, so the old cohort-id lookup could never have returned anything however much curriculum existed. Rebuilt against the Timeline (`acceleratorCohortCurriculumService.ts` + two routes), grouped by week, with per-participant progress from `timeline_card_progress`. Progress counts **published cards only** — a draft was never shown to the student, so counting it would report everyone as permanently behind. Two distinct empty states, because they need different fixes: "this cohort has no parent Course" versus "this Course has no cards yet".
    **(4) FIVE SURFACES FOLDED OFF THE SIDEBAR.** Community Roles became a section under the Cohorts tab; Cert Prep, Case Studies and Projects became program-level Accelerator tabs (lazy-loaded, rendering their existing pages unchanged); Feed Control Governance lost its nav entry because the Feed Control tab already links to it. **Every route and page stays live.** `Orchestration` was renamed `Curriculum` in the nav and page header, **path unchanged** so existing deep links and `?tab=` links keep working.
    **(4b) ARCHITECTURE SKILLS AND ENTERPRISE INTELLIGENCE, the two Ali asked about.** Both sat in the Program nav group, for opposite reasons. **Architecture Skills** (`/admin/cape-settings`) is the CAPE rubric — the 10 skill definitions and 4 evidence-band weights that produce the readiness and proficiency figures on Participants and Class Dashboard, writing `student_architecture_skill` per enrollment (the same table that blocked the cohort delete). That is curriculum *configuration*, so it became a tab on the Curriculum page beside Feed Control. **Enterprise Intelligence** (`/admin/brain`) is the Enterprise Memory Graph, spanning leads, agents, campaigns and projects with students as one node type among many; it was simply misfiled, and moved to the Intelligence group. **The Enterprise Intelligence move is presentation only and deliberately carries no access change:** its nav link keeps an explicit `section: 'program'` rather than inheriting the Intelligence group's `'intelligence'`, because the backend gate maps `/api/admin/brain` to `program`. Letting it inherit would have made the two gates disagree; changing both would have silently re-scoped who can open the page, which is an access decision rather than a nav tidy-up. This is the same split the Revenue group already uses for Leads and Pipeline.
    **(5) THE RBAC HALF OF (4), which is the part that silently breaks.** `sectionForPath()` derives a route's section from the nav list, so deleting a nav entry makes it return `null` — which makes `ProtectedRoute` bounce every scoped identity off a page the API would have served, while a legacy admin typing the URL still gets a working page. All five paths were therefore added to `UNLISTED_PATH_SECTIONS` as `program`, matching the backend gate. **Also found and closed a pre-existing latent 403:** `/api/admin/cape` was absent from `mgmtSectionGate`'s `PATH_SECTION` while both `/admin/cape-settings` (Architecture Skills) and `/admin/feed-control-governance` were live surfaces calling it — exactly the failure that file's own comments warn about twice. Removing the governance page's nav entry would have turned that gap from latent into live.
