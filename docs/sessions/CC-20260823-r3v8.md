### Curriculum video health: a card with no URL is reported, not silently healthy (2026-08-23)

- [x] **Select URL-less cards instead of filtering them out**
  - Date: 2026-08-23
  - Session: CC-20260823-r3v8
  - What changed: `loadVideoCards()` selected `WHERE metadata->'video'->>'url' IS NOT NULL`, so a card with no URL was never a row, was never probed, and could only ever read as healthy. The query now also selects cards whose type is one of `video`, `ai_video_stream`, `live_class` — the render-band-derived set of types whose player is fed from the card's own metadata. `podcast`, `testimonial` and `ai_video_feedback` are deliberately excluded: their media is resolved per student at runtime, so an empty `metadata.video.url` is their normal resting state and reporting it would be 100% false positives. The URL is still read only from `metadata->'video'->>'url'`, never from a whole-blob scan, so the `replaced_video.previous_url` tombstone that archived a healthy Week 3 card on 2026-08-21 still cannot match.
  - Verification: 158 tests across 6 suites green. Against unmodified `origin/main` the new SQL contract test prints the buggy clause verbatim as its received value — `WHERE metadata->'video'->>'url' IS NOT NULL` — against `Expected pattern: /type IN \(:cardOwnedVideoTypes\)/`.
  - Notes: `COALESCE` is load-bearing rather than defensive. `NOT (metadata->'video' ? 'url')` evaluates to NULL, not true, for a card whose metadata has no `video` key — the shape of all 21 such cards in production — so the naive predicate filters out precisely the rows it is meant to find. Measured against the live database: the naive form returns **0 rows** (a confident false all-clear), the COALESCE form returns **21**.

- [x] **Classify the absence rather than inferring it, alongside `classifyAbsent`**
  - Date: 2026-08-23
  - Session: CC-20260823-r3v8
  - What changed: new `classifyMissingUrl()` in `videoLinkClassifier.ts` and a new `URL_MISSING` member of `VideoState`. It sits beside `classifyAbsent()` on purpose: that one answers "the API omitted this id", this one answers "the card omitted the URL", and both exist so that a thing missing from a result set has to be classified deliberately instead of falling through as health. `ImpactCard` gained `video_url`, because `video_id` is null for two unrelated reasons — no URL at all, and a URL that is not YouTube — and collapsing them would turn a Loom link into a false content gap.
  - Verification: `classifyMissingUrl()` is asserted never to return `HEALTHY`, and the non-YouTube case is covered by a test asserting `missing_url` stays `[]` for a `loom.com` URL.
  - Notes: The run result gained `missing_url`, kept out of `failures` deliberately. A `VideoFailure` is keyed on a video_id and describes a link that broke; this has no video_id and describes a link never made. Merging them would spike the daily broken-video count by 21 without a single video having broken.

- [x] **Keep a content gap from reading like a sealed week**
  - Date: 2026-08-23
  - Session: CC-20260823-r3v8
  - What changed: new `assessMissingUrlCard()` in `videoLinkImpact.ts`, which always returns `seals_week: false`. Routing these cards through the existing `assessCard()` would have called them sealing — they are reachable, `learn`, completable and have a week, which is every condition the gate looks at — and raised a critical "seals week 3 for N students" alert against a live cohort for a card 15 students have already completed. Missing-URL alerts are `warning`/`low` at a fixed severity 3 that never scales with student count, because the finding never blocks a student.
  - Verification: the impact test asserts the contrast directly on one card: `assessCard(...).seals_week === true` while `assessMissingUrlCard(...).seals_week === false`. The service test asserts `missingUrlAlert.severity < deadAlert.severity` and that the dead-video alert is still `critical`.
  - Notes: The mechanism, confirmed in code and against production. `requiredWatchPct()` returns null unless `hasVideoMetadata()` finds a non-empty URL string, and `assertWatchRequirement()` returns immediately on null — so no URL means no watch gate is ever armed, and there is nothing to leave unsatisfied. A *dead* URL is the dangerous inverse: it satisfies `hasVideoMetadata`, arms a 75% gate, then emits no watch beats to satisfy it. Card `361ae8d3` bears this out: 15 completions, and Week 3's evaluation, survey and reflection each at 6.
