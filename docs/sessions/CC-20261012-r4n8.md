# CC-20261012-r4n8 — CB stops mentioning Ali six times a day, and stops blowing the context limit

## What was wrong

Two defects that fed each other on Basecamp recording `10049371244`
("[Tracking] Ali backlog status (auto from CB System enforcer)").

**1. The enforcer tagged on the level, not the edge.**
`backlog-enforcer.js` runs every 4 hours and decided:

```js
const shouldTag = overdue.length >= OVERDUE_TRIGGER || maxOverdueDays >= SINGLE_OLD_TRIGGER_DAYS || is9amTick;
```

Both the file header and the meta todo's own description say Ali is tagged when the backlog
*crosses* a threshold. This reads whether it *is above* one. `SINGLE_OLD_TRIGGER_DAYS` is 7
and one todo was 12 days overdue, so the condition was permanently true and could only become
more true as the todo aged. Ali was @mentioned on all six ticks a day, every day, and each
mention is a Basecamp notification email.

**2. The context walker caps every part but never the total.**
`cb-context-walker.js` caps documents at 60k bytes, external pages at 40k, and each comment at
4000 chars, and caps a *document's* comments at `.slice(-8)`. The main thread's comments have
no cap at all: LAYER 3 renders every one.

Together these compound. Defect 1 posts a comment every 4 hours, each comment grows the thread,
and when CB then tries to answer, the assembled walk exceeds gpt-4o's 128,000-token limit. The
API rejects the call before the model runs, so CB posts nothing but its "ran out of steps"
fallback, which is itself another comment on the same thread. Measured on prod: 381 comments,
LAYER 3 at 79,709 tokens and LAYER 4 at 49,647 (37 documents fetched from URLs inside those
comments), 129,471 tokens total. The audit log shows it climbing ~348 tokens per run across
100 failures: 178,679 on 10-11 to 181,115 by 10-12.

## What changed

- `scripts/ops-engine/backlog-enforcer.js` — `shouldTag` is now edge-triggered. It compares
  against the previous tick's counts, so a crossing tags once and a standing backlog stays
  quiet. `maxOverdueDays` is now persisted in `state.ticks[].counts`, without which the next
  tick cannot see an edge. Missing prior state is treated as "no crossing" rather than
  fabricating one; the 9am CT tick remains the floor that guarantees one nudge a day.
- `scripts/ops-engine/cb-context-budget.js` — new. `fitToBudget()` fits an assembled block to
  a token budget, keeping the head (LAYER 1/2, which name the task) and the tail (newest
  comments) and dropping the oldest middle, on line boundaries, leaving a visible marker so
  the model is told it is reading an excerpt.
- `scripts/ops-engine/cb-system-handler.js` — applies the budget to `walkedContext` after both
  the walked and the fallback path, and logs `context_trimmed_to_budget` when it bites.

Default budget 70,000 tokens, overridable with `CB_CONTEXT_BUDGET_TOKENS`. Derived from
measured overhead (SYSTEM_PROMPT 2,616 + lessons 289 + tools ~3,000, plus 4,000 for the reply),
and set well under the theoretical 118,100 ceiling because the observed failure reported
180,071 total against a 129,471-token walk and that gap is not yet explained. No model or
temperature change.

## Not done here

LAYER 4 fetched 37 documents (49,647 tokens) from URLs discovered in those 381 comments. The
budget trims the result, but the walk still makes those requests before anything is trimmed.
Capping document discovery is a larger change to the walker and is left out of this fix.

## Follow-up: the daily tick never fired, so the first fix would have silenced the enforcer

Found while verifying the deploy of the change above, not before it.

That change leaned on `is9amTick` as "the floor that still guarantees one daily nudge". It is
not a floor. It was `today.getUTCHours() === 14`, and cron runs this job at `0 */4`, so the
process only ever observes UTC hours 00, 04, 08, 12, 16 and 20. 14 is not among them. The state
file records 100 ticks and the hour histogram is `{00:17, 04:17, 08:17, 12:17, 16:16, 20:16}`:
it has been true exactly zero times since the file was written.

The hour was also wrong on its own terms, in the opposite direction to its comment
(`9am CT = 14 UTC (CST) / 13 UTC (CDT)`): 9am CST is 15 UTC and 9am CDT is 14 UTC.

Net effect if left alone: with tagging correctly edge-triggered and the only other path dead,
a standing backlog would never tag Ali again.

**Fix.** The daily nudge is now keyed to the Central calendar date rather than a UTC hour:
fire on the first tick at or after `DAILY_TICK_HOUR_CT` (08:00 CT) on a Central day that has
not already nudged, recorded as `state.last_daily_ct_date`. Resolving the date through
`Intl.DateTimeFormat` with `timeZone: 'America/Chicago'` is correct under both CST and CDT,
and keying off "at or after 8am" rather than an exact hour means it does not depend on how the
cron happens to be spaced. Under CDT the `0 */4` cron lands at Central hours 19, 23, 03, 07,
11 and 15, so the 11:00 CT tick carries the nudge.

17 assertions pass. Three further mutations, each caught by its named assertion:

| Mutation | Caught by |
|---|---|
| dead UTC-hour-14 tick restored | `cron runs 0 */4 ... that test never fired` |
| once-per-day guard removed | `must fire once per Central day` |
| stops recording the day it fired | `must record the day it fired` |

One note on the first of those: the assertion greps for the old expression, and it failed at
first against the *comment* I had written describing the old behaviour. The comment was
reworded rather than the assertion loosened.
