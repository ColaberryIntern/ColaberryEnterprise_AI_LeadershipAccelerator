them and enforced by the spine, which is the arrangement the earlier comment asked for.

### The four rules, and why each exists

1. **Linking is idempotent.** R5 and R8 are scheduled jobs. `ON CONFLICT DO NOTHING`
   against a unique index on `(source_system, source_id, initiative_type, initiative_key)`
   does this at the database, not in a read-then-write that two concurrent runs would both
   pass. `relation` is deliberately **out** of the key: if a classifier changes its mind,
   the right outcome is one row corrected, not two rows both claiming to be the document.

2. **Automation never overturns a human.** An unlink is soft, and the unique index covers
   unlinked rows, so the next ingestion run conflicts and does nothing — it cannot quietly
   resurrect a link Ali removed. `relinkEvidence` is the explicit human door, and it resets
   the row to `link_method = 'human'` with a null confidence, because a machine score must
   not survive a human overriding the machine. **This is the most important property here:
   a correction undone by a cron job teaches people to stop making corrections, and the
   failure is silent.**

3. **A missing table is not an empty one.** Reads check the table exists and return
   `state: 'absent'` with a note, distinct from `'ready'` with zero rows. The boot ensure
   warns and continues on failure, so this state can really occur, and an empty timeline
   rendered for a missing table reads as a quiet month rather than a broken deploy.

4. **An unknown initiative is rejected at write time.** There is no foreign key on
   `initiative_key`, because initiatives are heterogeneous — a hypothesis key is a register
   constant, a gov bid key is a `delivery_project_id` UUID. `validateLink` is therefore the
   whole guarantee, not a convenience. Without it a typo produces a link to an initiative
   nobody can see.

### Two decisions driven by this session's own findings

**`observed_at` is a separate column from `created_at`, and is never defaulted.**
`observed_at` is when the evidence happened; `created_at` is when we noticed. A timeline
built on the second is a history of our ingestion runs. This is not theoretical here: the
R2 diagnosis reported an explorer-to-paid conversion rate that was counting backwards,
because all 13 "conversions" had a paid row created *before* their explorer row.
Conflating when-recorded with when-happened produced a number that pointed the wrong way
down the funnel.

**The CHECK constraints are generated from the exported `as const` arrays.** The same
diagnosis found `revenueOpportunityService` filtering
`pipeline_stage IN ('qualified','proposal','negotiation')` when two of those three literals
had never been values of that column — a hardcoded list that drifted from what it
described, so the scan could never match, and 1,100 high-intent leads were invisible to it
(now R11). Generating the constraints from the TypeScript unions makes that drift
impossible, and a test asserts the generated SQL still lists exactly the declared values,
counting the quoted literals so an extra one is caught too.

### A test defect worth recording

Two schema tests failed on the first run by finding the wrong statement: every constraint
here is dropped and re-added for re-runnability, so
`S.find(x => x.includes('ck_evidence_links_confidence'))` matched the **DROP** line and
asserted nothing about the constraint body. Anchoring on `ADD CONSTRAINT` fixed it. The
vocabulary tests had already been written that way; these two had not.

Related: that jest run exited 1 while the task notification reported exit code 0, because
the command was piped through `tail` and the pipeline's status is the one reported.
Capturing `PIPESTATUS` is what surfaced the failures. Same class as the `react-scripts`
non-run in the R1 log.
