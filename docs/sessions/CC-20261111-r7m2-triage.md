# Session CC-20261111-r7m2 — the backlog triage board

Ali asked whether the daily "priority queue" email is legitimate, and what would make it more
useful. The answer to the first question turned out to decide the second.

## The audit: the email is honest, the backlog is not

The Ali Task Agent is **report-only and fail-closed**. `ATA_ENABLED` is unset, so it cannot act;
cron runs `ata-report-digest.sh` at `0 12,17,22 * * 1-6`. The email says so in its header, and its
section heading reads "I CAN HANDLE THESE **ONCE LIVE**". It is not claiming to have done anything
it did not do. Eight of the listed tasks were spot-checked against the mirror and all were genuinely
`active`. It also already carries a fail-open live-state guard that re-queries Basecamp and drops
tickets completed since sync, written after a run where the top four items were all already done.

So the machine is sound. **What it is pointed at is not.**

| Measured 2026-11-11 | |
|---|---|
| Active todos in the mirror | 4,070 |
| Overdue | 3,395 (83%) |
| More than 30 days overdue | 3,217 |
| More than 60 days overdue | **3,105 (76%)** |
| Of Ali's own assigned active set | **2,694 — of which 2,289 dormant (85%)**, oldest **1,069 days** |

## The defect, in one line of code

`queueBuilder.scoreTask` adds a **flat +40** for `dueIn < 0`. One day overdue and one thousand days
overdue score identically, and the stored `urgency_score` behaves the same way. The queue therefore
sorts by how long something has been ignored and labels the result urgency. That is how "Review
Women Applying AI Pilot draft", due 29 July, reaches the front page at urgency 85.

## Two things the charts had to be argued into

**Colour.** The first palette used amber / orange / red as a categorical set and **failed
validation**: amber against red is ΔE 2.9 under deuteranopia, which is to say indistinguishable.
That failure was the signal that the *form* was wrong — age is ordinal magnitude, not identity, so
it takes one hue varying in lightness, and lightness order survives every kind of colour blindness
while hue order does not. Final ramps are validated in both modes. Light passes every check with a
contrast WARN on the lightest step, relieved by direct labels and a table view. **Dormant is
deliberately neutral**: colouring the oldest items the most alarming shade would repeat the exact
error the board exists to correct.

**Overplotting.** The first production run fed 2,694 points into the scatter and produced an
unreadable slab in a 512KB file. It now samples evenly above 600 and **says so on the chart**,
because a sampled chart presented as a complete one is a lie told in pictures. 146KB after.

## A test that failed for the right reason

The assertion "a dormant task never appears in the live queue" failed on the first run. The board
was correct; the test sliced from the stat tile captioned "Live queue" and swept in the scatter,
which plots every task and names each in a hover title. Fixed by scoping to the section. The note
is kept in the test, because the scatter *should* span both sets — that span is the argument it
makes.

## Recommended next, in order of payoff

1. **Triage the dormant pile.** `ops_bc_todos` already has `is_dismissed`, `dismissed_at`,
   `dismissed_by`, `dismissed_reason`. The lever exists and is unused. This is the highest-value
   action and it costs decisions, not engineering.
2. **A claim marker, before `ATA_ENABLED` is ever set.** ATA's idempotency marker is a comment on
   the Basecamp thread, which is the right source of truth and completely blind to a Claude tab
   with a worktree open. A claim posted on the ticket, with an expiry, would let ATA and inbox-zero
   skip what is already being worked.
3. **One digest a day** rather than three.

## Failure-first notes

1. **What happens if this fails?** Nothing in production changes. These are new files; no existing
   renderer, scorer or scheduled job calls them. The board is generated on demand.
2. **Will it retry?** Not applicable — it is a pure render plus one read-only query.
3. **Recovery path:** delete the files. Nothing references them.
4. **Handled vs not handled.** Handled: an empty backlog, missing scores, missing due dates,
   hostile markup in a task title or project name, a backlog large enough to overplot, a failed
   Mermaid CDN (the written rule sits under the diagram). **Not** handled: the board reads the
   mirror, so a todo completed in Basecamp but not yet synced still shows. ATA's live-state guard
   covers that for the digest and is deliberately not duplicated here — the board is for deciding
   about old items, where a day of sync lag does not change the decision.
