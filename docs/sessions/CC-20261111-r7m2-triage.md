# Session CC-20261111-r7m2 — the backlog triage board

Ali asked whether the daily "priority queue" email is legitimate, and what would make it more
useful. The answer to the first question turned out to decide the second.

## The audit: the email is honest, the backlog is not

The Ali Task Agent is **report-only and fail-closed**. `ATA_ENABLED` is unset, so it cannot act;
cron runs `ata-report-digest.sh` at `0 12,17,22 * * 1-6`. The email says so in its header, and its
section heading reads "I CAN HANDLE THESE **ONCE LIVE**". It is not claiming to have done anything
it did not do. Eight of the listed tasks were spot-checked against the mirror and all were genuinely
`active`. It also already carries a fail-open live-state guard that re-queries Basecamp and drops
tickets completed since sync, written after a run where the top four items were all already done.

So the machine is sound. **What it is pointed at is not.**

| Measured 2026-11-11 | |
|---|---|
| Active todos in the mirror | 4,070 |
| Overdue | 3,395 (83%) |
| More than 30 days overdue | 3,217 |
| More than 60 days overdue | **3,105 (76%)** |
| Of Ali's own assigned active set | **2,694 — of which 2,289 dormant (85%)**, oldest **1,069 days** |

## The defect, in one line of code

`queueBuilder.scoreTask` adds a **flat +40** for `dueIn < 0`. One day overdue and one thousand days
overdue score identically, and the stored `urgency_score` behaves the same way. The queue therefore
sorts by how long something has been ignored and labels the result urgency. That is how "Review
Women Applying AI Pilot draft", due 29 July, reaches the front page at urgency 85.

## Two things the charts had to be argued into

**Colour.** The first palette used amber / orange / red as a categorical set and **failed
validation**: amber against red is ΔE 2.9 under deuteranopia, which is to say indistinguishable.
That failure was the signal that the *form* was wrong — age is ordinal magnitude, not identity, so
it takes one hue varying in lightness, and lightness order survives every kind of colour blindness
while hue order does not. Final ramps are validated in both modes. Light passes every check with a
contrast WARN on the lightest step, relieved by direct labels and a table view. **Dormant is
deliberately neutral**: colouring the oldest items the most alarming shade would repeat the exact
error the board exists to correct.

**Overplotting.** The first production run fed 2,694 points into the scatter and produced an
unreadable slab in a 512KB file. It now samples evenly above 600 and **says so on the chart**,
because a sampled chart presented as a complete one is a lie told in pictures. 146KB after.

## A test that failed for the right reason

The assertion "a dormant task never appears in the live queue" failed on the first run. The board
was correct; the test sliced from the stat tile captioned "Live queue" and swept in the scatter,
which plots every task and names each in a hover title. Fixed by scoping to the section. The note
is kept in the test, because the scatter *should* span both sets — that span is the argument it
makes.

## Recommended next, in order of payoff

1. **Triage the dormant pile.** `ops_bc_todos` already has `is_dismissed`, `dismissed_at`,
   `dismissed_by`, `dismissed_reason`. The lever exists and is unused. This is the highest-value
   action and it costs decisions, not engineering.
2. **A claim marker, before `ATA_ENABLED` is ever set.** ATA's idempotency marker is a comment on
   the Basecamp thread, which is the right source of truth and completely blind to a Claude tab
   with a worktree open. A claim posted on the ticket, with an expiry, would let ATA and inbox-zero
   skip what is already being worked.
3. **One digest a day** rather than three.

## Failure-first notes

1. **What happens if this fails?** Nothing in production changes. These are new files; no existing
   renderer, scorer or scheduled job calls them. The board is generated on demand.
2. **Will it retry?** Not applicable — it is a pure render plus one read-only query.
3. **Recovery path:** delete the files. Nothing references them.
4. **Handled vs not handled.** Handled: an empty backlog, missing scores, missing due dates,
   hostile markup in a task title or project name, a backlog large enough to overplot, a failed
   Mermaid CDN (the written rule sits under the diagram). **Not** handled: the board reads the
   mirror, so a todo completed in Basecamp but not yet synced still shows. ATA's live-state guard
   covers that for the digest and is deliberately not duplicated here — the board is for deciding
   about old items, where a day of sync lag does not change the decision.

## Not done

- **Not wired into the cron digest.** The daily email is unchanged. Wiring it in is a separate
  decision, and worth making after the dormant pile is triaged rather than before.
- **The flat +40 is still in `scoreTask`.** Partitioning sidesteps it; it does not fix it.
- **Not deployed.** Nothing to deploy — no runtime path imports these files yet.

## Second pass: making the report worth pairing with a session

Ali's follow-up: structure it so that pairing the email with a Claude Code session is an extreme
advantage, with the least human intervention, aimed at putting dropped work back in motion.

### The audit that reshaped the design

Three columns that should have carried the answer are dead:

| Signal | Fill rate on Ali's 2,694 active tasks |
|---|---|
| `last_human_action_at` | **0%** |
| `ai_opportunity_score` | **0%** |
| `downstream_blocked_count` | 100% populated, **zero for every row** |
| `category` | 100%, but **95% the single value `waiting_dependency`** |
| `description` | **100%, avg 648 chars, 2,652 of 2,694 distinct** |

So ranking by blast radius is impossible today, and `category` carries almost no information. The
description is not merely the best signal, it is very nearly the only one.

### What the descriptions turned out to contain

The tickets were authored to a house pattern and already carry labelled fields: `Decision owner:`,
`Decide by:`, `The decision.`, `Why.`, `Source of truth:`, `Canonical folder for this ticket's
artifact:`, and `Required skill:`. Those are exactly what a session spends its first ten minutes
rediscovering. **Parsing beats inferring**: it is free, reproducible, and cannot hallucinate an
owner or a deadline the ticket never stated.

- [x] Deterministic brief parser and work orders
  - Date: 2026-11-11 · Session: CC-20261111-r7m2
  - What changed: `briefParser.js` (HTML to text, labelled-field extraction, human-only detection,
    skill extraction) and `workOrder.js` (per-ticket work order, disposition proposal with a
    reason, plain-text render, one-line run command). The board gained a "Hand to Claude Code"
    section grouped by disposition with copy buttons, and the generator now emits a
    `.bundle.json` carrying every work order.
  - Verification: 92 tests across the aliTaskAgent suite. Fixtures are shortened from REAL
    production descriptions, because the premise is that the house pattern holds and a fixture
    invented to match the parser would prove nothing. Backend `tsc` 0 errors in `src/` with a
    planted control error; `checkTestTypecheck` matched both ways. Rendered against live data.

### Measured on 425 real work orders

| Field | Fill |
|---|---|
| summary | **100%** |
| sourceOfTruth | 17% |
| doneWhen | 17% |
| artifactFolder | 12% |
| why | 12% |
| blockedBy | 5% |
| owner | 3% |
| decideBy | 2% |

Dispositions after the fix: **act 275, draft 16, prep 49, ask 73, close 12 — 291 need no decision
from Ali at all.**

### The defect production found, which tests would not have

The first live render produced a work order reading **"proposal: Act now"** directly above a brief
reading **"Required skill: none - human task"**. The ticket stated the answer and the proposer
ignored it. **13 of 425 were wrong this way.** A confident wrong proposal is worse than none: it
sends a session to do work a person was meant to do.

Fixed by checking the ticket's own words FIRST, ahead of every inference, and adding a fifth
disposition, `prep` - a session cannot do a filing or a signature, but it can shorten the human
step by preparing it. Re-measured on the same 425: **0 wrong.**

The same pass found that **32 tickets name `/loop-architect` in a `Required skill:` line**, which
was being discarded. The work order now carries it, so the session is told the house approach
rather than choosing one.

### Still true, and still the bottleneck

- `doneWhen` is absent on 83% of tickets. A session told to "act" often will not know what done
  means, and the work order says so in those words rather than leaving a blank.
- The disposition is a PROPOSAL. Nothing in this change acts on anything.
- There is still no claim mechanism, so two sessions can still pick up the same ticket. That
  remains the next thing to build, and it should land before `ATA_ENABLED` is ever set.

## Third pass: the list is the unit of strategy

Ali: *"I love the idea of surfacing based on the List instead of the tasks... I want to make a
strategic decision that affects one or multiple tickets... I should have the option to do both."*

### Why the list turned out to be the right unit

| Measured on production | |
|---|---|
| Active tasks assigned to Ali | 2,696 |
| In ONE project (7463955), across 421 lists | **2,403 (89%)** |
| Carrying the generated shape (`Type:` + `Done when:`) | **1,386** |
| Carrying a real ladder title (C10.x, AF12.x, L11.x) | **109** |
| Top 10 lists | 270 tasks, **every one dormant** |

The biggest lists are "2. Matching Loads to Carriers", "1. Patient Self-Scheduling", "9. Ensuring
Data Security" - AI use-case scaffolding from demo projects, bulk-assigned. Working that per ticket
is roughly 76 hours. Deciding it per list is under an hour for a third of it.

And the lists are **numbered**, so a list is a phase of a program rather than a folder. That is
something a ticket can never carry: where it sits in a sequence, and therefore whether the whole
sequence is still live.

- [x] The list lens
  - Date: 2026-11-11 · Session: CC-20261111-r7m2
  - What changed: `listLens.js` (grouping, phase detection, spearhead selection, ranked strategic
    proposals) and `renderListLens.js` (one card per list: counts, band bar, phase position among
    its siblings, the spearhead, the moves, and a drill-down to every task). The bundle now carries
    the lists too, so a session can act per list rather than only per ticket.
  - Verification: 24 new cases, 126 across the aliTaskAgent and claims suites. Rendered against
    live production and inspected.

**The lens discriminates on real data, which is the only test that counts.** "9. Ensuring Data
Security" (100% generated, 56% human, all dormant) proposes *dismiss* or *give it to one owner*.
"Understanding Inputs and Outputs" (0% generated, 100% session work) proposes *re-date into a
window* and *run it unattended* - the guard against bulk-dismissing hand-authored work, firing by
itself.

Both modes are on every card, because Ali asked for both: the strategic moves first, and "work just
the lead task" always last and always present. A report that forces one mode makes the other
somebody else's problem.

- [x] Task claims, so two workers never take the same ticket
  - Date: 2026-11-11 · Session: CC-20261111-r7m2
  - What changed: `ensureTaskClaimSchema.ts` (one additive table, asserted on its COLUMNS not just
    its existence) and `services/ops/taskClaims.ts`. Wired into the boot sequence.
  - Verification: 15 cases. The SQL is asserted as a contract, not mocked away.
  - Notes: **the race is resolved in Postgres, not in application code.** The obvious
    implementation - read the claim, write if free - lets two workers interleave and both believe
    they won, and it would fail rarely enough to look like it works. `claim` is a single guarded
    upsert whose WHERE clause carries the whole condition, so the statement affects one row or
    none and there is no window. Expiry is mandatory: a lease without one is a lock, and a lock
    held by a session that died is a ticket nobody can ever work again.
  - `partitionByClaim` is **fail-open** by deliberate choice. If the claims table cannot be read,
    everything is treated as available. Treating it as all-claimed would empty the queue and look
    exactly like "no work today", which is the failure that wastes a day silently. Duplicated
    effort is visible and recoverable.

### Not done

- The commands the cards print (`/ata-list`, `/ata-work`, `/ata-work-task`) **do not exist yet**.
  The cards are a decision surface; executing them is the next build, and claims had to land first.
- Nothing bulk-acts. Every proposal carries its evidence and a command, and stops there.
- **One open question for Ali that no measurement can answer:** are the use-case projects dead
  scaffolding or live curriculum? That decides whether ~1,400 tickets are dismissed or whether he
  is simply removed as assignee.

## Fourth pass: making the moves executable

- [x] List action planners and executor
  - Date: 2026-11-11 · Session: CC-20261111-r7m2
  - What changed: `listActions.js` (plan dismiss / re-date / assign, each returning the exact
    changes, a summary and the reversal), `scripts/ataListAction.js` (dry-run by default) and the
    `ata-list` skill.
  - Verification: 24 new cases, **160 across the suite**. Dry-run against two real lists.

### The boundary the executor enforces

| Action | Reach | Applied here? |
|---|---|---|
| `--dismiss` | local mirror only | **yes** - reversible, and the ticket stays OPEN in Basecamp |
| `--redate-from` | Basecamp | **no** - plans it, writes the plan to a file, refuses |
| `--assign` | Basecamp | **no** - same |

Dismissal removes a task from Ali's queue. It does **not** close the ticket. That distinction is
load-bearing: most of the backlog is scaffolding bulk-assigned from projects other people may still
be running, so "stop showing this to me" must never become "this work is cancelled". The summary
says so in those words on every plan.

Re-dating and assignment reach Basecamp, where other people see the result, and bulk Basecamp
writes as Ali are gated in this environment. The script plans them and refuses to apply, saving the
plan rather than discarding the work. Routing around the gate would defeat it rather than satisfy
the request.

### The bug the dry run found, in the expensive direction

Re-dating "Understanding Inputs and Outputs" produced a plan whose task titles read
`[BREAK] 🤖 Implement validation...` and `[BUILD] 🧑 Document all expected inputs`. That is
story-build output - generated scaffolding - and the lens had scored the list **0% generated**,
because the detector only checked the description for `Type:` plus `Done when:`.

Measured: the narrow test caught **1,386 of 2,693 (51%)**; widened to include the `[BUILD]`,
`[BREAK]`, `[HARDEN]` prefixes and the 🤖 / 🧑 task-split emoji it catches **2,238 (83%)**. It was
missing **852 tasks**, and **two whole lists were being proposed for re-dating** when they should
have been proposed for dismissal.

Both failures are bad, but only one wastes the next three months: dismissing real work is noticed
immediately, whereas re-dating dead scaffolding quietly refills the calendar. After the fix both
lists propose dismissal, and the task-level `humanOnly` marker is unaffected because generated and
human-only are orthogonal.

### Not done

- `--redate` and `--assign` have never been applied, by anyone, anywhere. Only their plans exist.
- `/ata-work` and `/ata-work-task` still do not exist; the `ata-list` skill documents the
  per-ticket path using the work order and the claim API directly.
- Nothing has been dismissed. The question of whether the use-case projects are dead is still
  Ali's to answer, and it governs roughly 2,239 tasks.
