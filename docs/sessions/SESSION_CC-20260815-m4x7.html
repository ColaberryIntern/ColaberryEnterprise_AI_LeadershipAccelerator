**`read_attachments` tool built, granted to Cory and Reese, wired into all three chat surfaces with drag-drop and paste**

2026-08-15
What changedAli asked for Cory in the Project and Classroom workspaces to be able to consume screenshots alongside the text a student types, ideally drag-and-drop, and then specified it should be **a tool that agents can use**, assigned to Cory and Reese to start. Built as exactly that rather than as a chat feature, because three separate surfaces (`RuntimeWorkspace` -> `runtime/mentorService.coach()`, `ProjectWorkspacePage` -> `projects/projectMentorService.coachOnTask()`, `ChatDock` -> `reese/reeseReplyService`) call into the same coaching path, so a per-surface flag would have drifted within a release. **New `backend/src/services/agents/tools/`:** `agentToolRegistry.ts` holds the typed grant table (`cory` and `reese` both hold `read_attachments`) plus an `AGENT_TOOLS_DISABLED` env kill switch read fresh per call, so a vision-cost or provider incident can be stopped without a deploy; every call site asks the registry rather than assuming. `readAttachmentsTool.ts` resolves ids to owner-checked rows and returns provider-neutral content parts plus a named `skipped[]` list, so an unreadable file becomes something the agent can talk about instead of an error that costs the student their message. `imageNormalizer.ts` lifts `normalizeImageForVision` + `rasterizePdfFirstPage` out of `certificateService` — already production-proven there against the "You uploaded an unsupported image" rejections that screenshot tools cause — and `certificateService` now imports them (keeping its own 2000px edge, which it was tuned against, via an explicit argument). **Storage:** new `AgentAttachment` model + `ensureAgentAttachmentSchema()` (additive, no global sync), unique on `(enrollment_id, sha256)`, with its own multer instance and upload dir rather than reusing `communityMediaUpload` — these bytes go to a third-party vision model, so what is accepted must be decided by that fact alone. **LLM plumbing:** `runtimeAi.chatText` now takes `string | ContentPart[]` and pins a vision-capable model when a turn carries images (a text-only `DEFAULT_MODEL` 400s on image parts, which would take the turn down rather than degrade); `anthropicClient.toAnthropicContent()` converts OpenAI-shaped parts to Claude image blocks so the existing `MENTOR_LLM_PROVIDER` switch keeps working. **Frontend:** one shared `AgentAttachments.tsx` (hook + tray + paperclip + drop overlay) wired into all three composers — drag-and-drop onto the whole mentor rail, **Ctrl/Cmd+V paste** (the fastest path for a screen capture, which is the actual common case), and click-to-pick; files upload on selection so Send stays instant, and Send unlocks on text OR a finished upload but never mid-upload.

Two deliberate scope decisions worth recording. **(1) Images ride on the current turn only.** Prior turns replay as text (that is all `MentorTurn` stores), so a conversation containing a screenshot does not re-send it on every subsequent turn — otherwise vision cost would multiply by conversation length for context the model already has in words. Reese follows the same rule, reading only the triggering message's files out of its 20-message window. **(2) Sent thumbnails render from local object URLs, not the server URL.** The serve route is participant-authenticated and an `<img>` tag cannot carry a bearer token, so a server URL would render broken; the previews therefore cover the current session only, and a reload shows the message text. Making them survive a reload needs a signed-URL scheme and was not built here. Also: `POST /api/portal/dm/:roomId/send` now accepts an empty `content` when something is attached (a screenshot with no caption is a normal DM) and substitutes `(attached a file)` rather than loosening `postMessage`'s non-empty rule for every caller.
