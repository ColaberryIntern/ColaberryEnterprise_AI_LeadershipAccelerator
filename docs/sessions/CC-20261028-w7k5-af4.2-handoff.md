## What this does, in one paragraph

An intern opens **Change Requests** in the admin sidebar, picks one of their domains, says what
should change and why, and files it. It appears in your queue. You approve or decline it, and the
row records **your email and the time you decided**. Nothing is built as a result — an approved
request is a queue entry you triage, which is what the ticket's fourth acceptance criterion
requires.

## The two things only you can confirm

### 1. That the table landed, and nothing else moved

**There is no switch to throw.** The schema is created by an idempotent `ensure*` wired into
`server.ts`, so it appears the first time the backend boots after merge — a deploy, a restart, or a
crash recovery. An earlier draft of this work promised you a separate decision point; that was
wrong and is corrected.

After the first deploy, read-only:

```sql
SELECT column_name, data_type, is_nullable
  FROM information_schema.columns
 WHERE table_name = 'agent_domain_change_requests'
 ORDER BY ordinal_position;

-- Should be 0. The table is new; nothing writes to it until somebody files a request.
SELECT count(*) FROM agent_domain_change_requests;
```

The backend also checks this itself and throws `SchemaInvariantViolation` if a column is missing,
rather than warning. If the DDL silently did nothing, the logs will carry
`agent_domain_change_request_schema_unavailable` with an `error_class`.

### 2. The first real end-to-end pass

The ticket's own signal is *"An intern files a CR, Ali approves it, and the stored row names both
humans and the time."* That cannot be produced from a build session. Six steps:

1. Ask one intern — **Quincy** is the obvious choice, he is the most responsive — to open
   https://enterprise.colaberry.ai/admin/change-requests and file one request.
2. Confirm he can see the **Ask for a change** form and that it lists his domain. If his sidebar
   has no "Change Requests" entry, that is the section override having gone wrong and is worth
   telling me rather than working around.
3. Confirm he sees **no "Decide" section**. He must not be able to approve anything, including his
   own request.
4. Open the same URL yourself. You should see his request under **Decide**.
5. Approve it. The row should then read *"Approved by ali@colaberry.com on &lt;date&gt; CT"*.
6. Confirm **nothing started**. No build, no agent run, no email. If something did, that is a defect

Then one more worth doing once, because it is the constraint the ticket is built around: ask Quincy
to try approving his own request. He should be refused with *"The person who filed a change request
cannot be the person who approves it."*

## Limitations, stated plainly

- **An approval does nothing but record itself.** Deliberate — the ticket puts automating the build
  step explicitly out of scope. If you want approval to start work, that is a new ticket, and it is
  the decision the ticket flagged for you.
- **`dashboard` is the one section every mgmt role carries**, so a mentor, a support rep and a
  community organizer can all open this page. That is required: without the override all seven
  interns get a 403, which already happened once on 19 Oct. They can file; they cannot decide. The
  decide and queue routes carry `requireAdmin`, and the page renders the queue only when the API
  returns it, so its visibility is never the access control.
- **A decline needs a reason** and an approval refuses one. A decline the intern cannot read the
  reason for is how they learn to stop filing requests.
- **Withdrawal has no button yet.** The state exists and the gate allows it; no UI reaches it. An
  intern who wants a request gone should ask. Worth a follow-up if they do.

## Three latent defects found next door, not fixed here

All three are on the **fleet** approval path, a different blast radius, and belong in their own
ticket:

1. `approvalRequestController.ts` writes `req.admin?.email || 'unknown'` into `decided_by`, and
   `isNonHumanIdentity('unknown')` returns **false** — so that row claims a human decided something
   nobody did, permanently and undetectably.
2. **No test anywhere asserts `approveApprovalRequest` refuses a non-human `decidedBy`.**
3. `assertBuildAuthorized` in `factory/buildAuthorization.ts` would accept
   `system:auto_approve_timeout` as an approver today.

A fourth is a style hole worth one line: `err.name || err.constructor.name` logs the bare `Error`
that CLAUDE.md forbids in a production path, because `name` is inherited from `Error.prototype` and
short-circuits. Fixed in this ticket's controller; the same hole is in
`agentDisplayNameController.ts`.

## Rollback

One PR, one revert. The table is additive and referenced by nothing else, so reverting the code
leaves an empty table that nothing reads; dropping it is optional cleanup, not a recovery step:

```sql
DROP TABLE IF EXISTS agent_domain_change_requests;  -- only if you want it gone
```

No data migration, no backfill, nothing mutated, and the 106 existing `approval_requests` rows are
untouched. The two `PATH_SECTION` rows revert with the diff and cannot strand an identity, because
the paths disappear in the same commit. The nav and route rows revert together and the generated
Campus HQ tower follows them with no second edit.
