# Session CC-20260901-r3k7 — Make the automated billing messages tell the truth about auto-pay

**Date:** 2026-09-01
**Branch:** `fix/billing-messages-autopay-truth` (cut from `origin/main`)
**Scope:** On 2026-09-01, 20 members were migrated onto standing PaySimple schedules,
taking auto-pay from 1 member to 21. The renewal email was rewritten and deployed for
that in PR #1984. This session covers the rest of it: every other automated billing
message, and the documentation, still asserted "billing here is manual" as a universal
fact. That premise is now false for 21 people, and one automated message was acting on
it in a way that could have caused a double charge.

**NOT YET DEPLOYED.** Code and docs are committed and tested; the deploy entry will be
added when it ships.

- [x] Stop the billing watch chasing members whose schedule is about to collect
  - Date: 2026-09-01
  - Session: CC-20260901-r3k7
  - What changed: `checkLapsedWithoutFollowup` in
    `backend/src/services/billing/billingHealthCheck.ts` reads "period end is in the
    past" as "nobody is collecting". That was true while every term was a manual
    checkout. It stopped being true on 2026-09-01, because migrated members were
    promised auto-pay would begin at their **next** cycle rather than the one already
    collected by hand — so a member whose period ended 30 Aug has a schedule that first
    fires 30 Sep, and for a month they look exactly like someone who lapsed and was
    never chased. Added `AND s.paysimple_schedule_id IS NULL` and lifted the query into
    an exported `LAPSED_WITHOUT_FOLLOWUP_SQL` so the exclusion is a testable contract
    rather than a line that can be deleted while the suite stays green.
  - Verification: ran the **live** watch read-only against production before the fix.
    It reported `[act_now] lapsed_no_followup` for 2 members, one of whom —
    **VICTOR CHUKWUKERE, schedule 4511896, period ended 31 Aug** — is on a standing
    schedule that collects 30 Sep. The finding's stated action is "confirm these members
    were mailed", so acting on it meant sending a payment link to someone PaySimple is
    about to charge. With the guard the check returns only Kepha Ohanga, who is
    genuinely manual and awaiting ACH consent. 17 tests pass across both billing suites.
  - Notes: this is a money bug, not a noisy-email bug. It is the same class as the
    renewal-email defect fixed in #1984: an automated message applying manual-billing
    assumptions to auto-pay members.

## What this leaves open

- **New checkouts still create no schedule.** `subscriptionService.startCheckout` makes
  a one-time payment only, so every new paying member starts in the manual population
  and the 2026-09-01 backfill refills over time. This is now written down at the top of
  that file and in `BILLING_MODEL.md`; it is not fixed.
- **10 members hold two active subscription rows.** The watch reports it at `watch`
  severity. It is the reason row-level counting misreads the book.
- **$1,194/month** sits behind three ACH consent conversations, one current card, and
  the UK checkout bug that made Chukwuemeka Eneh borrow someone else's card.
