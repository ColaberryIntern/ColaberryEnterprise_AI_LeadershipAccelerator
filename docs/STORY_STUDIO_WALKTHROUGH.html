Story Studio — a production walkthrough of all seven tabs

Every tab of the Story Studio was opened against the live enterprise.colaberry.ai admin surface with a real admin session, and every control on it was used rather than photographed. This page reports what happened. Where a control did not work, it says so. Where something could not be tested honestly, it says that instead of guessing.

Nothing on this page has been deployed. The six defects below were observed on the production build that was live at 21:42 UTC on 2026-08-26. Five are fixed in the working tree on workstream/case-study-os and are proved by tests; none has shipped. Until a deploy happens, the live surface still behaves exactly as the screenshots show.

1 TRUTH 1 defect, fixed

“What is established about this record, who consented to what, and where did each value come from?”

What it is for

The canonical record and its consent axis. Four panels: the Storyline (editorial direction that aims the draft generator), Consent and privacy, Contributors, and Provenance.

What actually happened

Worked

  • Storyline save. Typed, saved, and read back from the server: the panel showed “Last written by <the signed-in admin>” and GET /storyline returned the same text. The disclaimer that this is editorial direction stored outside the snapshot is on screen, which is the right thing to say.
  • Consent fields rendered the record’s real values (named / Colaberry / public / role_only) and the save was accepted. Re-saving the same values left the record unchanged, confirmed through the API.
  • Contributors is empty and says so: “No contributors in this snapshot. The public page shows no credits section rather than an empty one.” A working empty state.
  • Provenance version switcher offered two versions and re-read without error.

Broken

  • Saving consent produced no visible response at all. Not a success banner, not an error. The success line and the failure line both render inside CaseStudyPublishPanel, which only reaches the screen on the PUBLISH tab. An operator whose consent save fails on this tab sees nothing happen.
  • Every provenance row read unknown / —. Fourteen rows, all blank, on the panel whose entire job is answering where each value came from. The payload behind them carried the tier, the actor, the note, the repository and the commit sha for every single row. The reader was looking for source/sourceRef, keys the server does not send.

2 SOURCES 1 defect, fixed

“What evidence exists, and what does each source actually prove?”

What it is for

Everything the record is built from: attached repositories and their roles, the read-only repository analyzer, the evidence table, sync, sync history, and the published-vs-draft diff.

What actually happened

Worked

  • Attach and detach round-tripped. A second repository was attached (1 → 2), appeared in the table, was detached, and the record came back to exactly the one repository it started with — verified through the API, not from the UI.
  • The analyzer reached GitHub and came back connected, listing both what the repository proves and what it cannot prove. Seven proof elements rendered.
  • Sync ran against the live repository and reported it in place: “1 of 1 repositories read, 156 facts, 0 candidate metrics. Snapshot created (v29).”
  • Sync history listed four real runs; the published-vs-draft diff rendered a table with ten diff elements.
  • Evidence rendered eight elements from the snapshot rather than a blank frame.

Broken

  • Two elements shared one test id. The Repository text input and the Analyze button both carried data-testid="cs-analyze-repo". Every lookup resolves the first match, which is the input — so the capability guard for “analyze repository” was asserting against a text box and would have stayed green with the button deleted. The walkthrough had to find the button by its accessible name instead, which is how it was noticed.
  • Sync, attach, detach and role changes report their errors to the PUBLISH tab — the same defect as consent, listed once above but felt here too. A failed sync on this tab surfaces nowhere on this tab.

Confusing rather than broken

“Attach repository” is styled btn-danger — solid red — for an additive, reversible action, and “Sync repositories” is btn-outline-danger. Red on this surface currently means “a button” rather than “careful”, which spends the one signal that should be reserved for Detach and Archive. Not fixed here: it is a design decision across the whole admin surface, not a defect in this tab.

3 STORY works as built

“What are we saying, in whose words, and has a human stood behind each sentence?”

What it is for

The prose and the figures it is allowed to state: draft generation and promotion, the narrative override fields, the metric table, and quotes.

What actually happened

Worked

  • Draft generation ran and produced four drafts (fourteen draft elements on screen) against the attached repository.
  • The generator names itself: “Last run by: deterministic”. It does not imply an LLM wrote it, because none did.
  • Every generated draft was rejected and the record was left with zero pending drafts, confirmed through the API.
  • Metrics rendered nine elements from the snapshot; quotes rendered its form plus a named empty state and its consent condition.

Not exercised on this record, deliberately

  • Promoting a draft and applying a narrative override both mint a new snapshot version, which would move a published record into “draft ahead”. Both were exercised on a throwaway record instead — see stop 8.
  • Suggested quote slots renders nothing: the page passes an empty list. The panel is wired for slot suggestions that nothing computes yet.

4 VISUALS 2 defects — 1 fixed, 1 left open

“What can be shown, and does every number in a picture come from a verified metric?”

What it is for

Artifact promotion — the control that moves a picture off candidate so a hero, carousel or figure can populate — and charts that reference verified metrics without ever carrying a number of their own.

What actually happened

Worked

  • The artifacts panel is honestly empty. This record has zero rows in case_study_artifacts, and the panel says “No artifacts on this record yet.” rather than rendering a blank table.
  • The chart disclaimer is on screen and is true: there is no field anywhere in the form into which a number could be typed.
  • Saving a chart worked and the chart persisted.
  • The chart told the truth about itself afterwards: “Renders: nothing — no metric it names is publishable and verified”, with the reason named per key. The honest-omission behaviour the panel promises is real.

Broken

  • The chart builder offers keys the chart resolver cannot resolve. The checkboxes are read from the snapshot; resolveChart resolves against the case_study_metrics table, which has zero rows for this record. So the form invites you to build a chart, accepts it, and then renders nothing. Left open — closing it needs a metric-listing endpoint the admin API does not have.
  • The same key was offered twice. verified_competencies appears in both heroMetrics and measurement.metrics, so two checkboxes rendered carrying one id and one test id — both labels pointed at the first input, and clicking the second label toggled the wrong box. Fixed.

Could not be exercised at all

Hero selection, the promote control and the derived evidence/atmosphere column. All three are per-artifact, and this record has no artifacts, so there was no row to press. They are unproven end to end — not observed working, and not observed broken.

The architecture diagram is not on this tab. It is rendered by the public story page (StoryDiagram.tsx, mermaid loaded from a CDN at runtime), and nothing in the admin VISUALS tab previews it. It was checked separately against the public page — see stop 7.

5 SURFACES works — and reveals a gate disagreement

“How does this one record read to four different audiences?”

What actually happened, and a correction

The four-lens switcher rendered, and it was expected not to. CASE_STUDY_SURFACE_LAB_USER_IDS is unset on the production backend — confirmed directly against the running container, where it reads (unset), which the config layer resolves to off. The strip rendered anyway, with four lens tabs and nine bands, because the gate refuses a request, not the component. Measured against production with this session’s admin token: GET /preview → 200, ?surfaceKey=enterprise → 200, ?surfaceKey=training → 403, ?surfaceKey=ai_flotation → 403. So the lab loads the Enterprise lens that every admin may preview, and the other three tabs are present but lead to a refusal. That is a switcher that looks available and is not, which is worth knowing before anyone reports it as broken.
  • The canonical truth line rendered — the line whose job is proving the lens changed no facts: title, “Built by: Colaberry team”, organization, “Verification: verified”, method.
  • The live surface is marked in text (↑ LIVE), not by colour alone.
  • The draft state is a state, never an invented count: “draft is ahead — draft v29 is not the published version”, followed by the panel explaining that snapshots are content-hashed wholes so no honest change count exists.
  • The note that exploring a lens never publishes is present.

Worth an operator’s attention

This tab reported gate: would publish while the PUBLISH tab reported five readiness gaps, two of them publication.surface_declared and publication.surface_publishable. Both are correct and they are answering different questions — readiness is advisory and scores the record, the gate decides publication — but a reader moving between the two tabs sees “would publish” and “five gaps” within one click of each other with nothing on screen reconciling them. Not a defect. Recorded because it is the most likely thing to be misread on this surface.

6 PREVIEW 1 defect, fixed

“What would a reader actually receive?”

What actually happened

Worked

  • The idle state is a sentence, not a blank frame: “Not previewed yet. The preview writes nothing…”
  • Pressing Preview rendered both halves — the raw snapshot beside the public projection — with 11,481 characters of projection JSON a reviewer can read.
  • The withholding narrative is specific: “1 of 2 metrics are not shown publicly. A metric that is not publishable, or whose verification is still pending, has no public shape at all.”

Broken

  • Rendering the preview blew the page 6,305px wide. Measured on the live page: documentElement.scrollWidth went from 1440 on every other tab to 7745 against a 1440px viewport the moment the projection rendered. The JSON <pre> grew to 3,686px inside a column whose min-width is auto, dragging the whole admin shell sideways with it. overflow: auto was already set and did not prevent it — a box has to be stopped from widening before it can be asked to scroll. Fixed, and the fix was verified by injecting exactly those two declarations into the live page and re-measuring: 7745 → 1440.

7 PUBLISH works — read-only paths only

“What does the gate refuse, and what happens when it stops refusing?”

What actually happened

  • Readiness declares itself advisory and named five gaps rather than a bare score: a missing standfirst or summary, a build timeline under three entries, no target surface declared, the declared surface not publishable in Phase 1, and no approved snapshot for the current draft. Each carries a “To close:” remedy.
  • The publication state rendered — published (8/25/2026, 5:13:23 PM).
  • The gate reported zero blockers and the band above the tabs said so in the words “Publish gate: no refusals… A clear gate is permission to publish, never an instruction to.”
  • All four lifecycle controls are present: approve, publish, unpublish, archive.

Not exercised on the live record, on purpose

Approve, publish, unpublish and archive were not pressed on the pilot. It is live on the Enterprise surface and unpublishing or archiving it would have taken a real page down. The refusal path was exercised on a throwaway record instead — see below.

8 A throwaway record — the acts the live one must not receive 1 defect, fixed

What actually happened

  • Create-from-repositories worked and said what it had and had not done: “…as a draft with 1 repository. Nothing is public until it is approved and published.”
  • A refused publish named every reason. The gate returned two refusals (case_study_not_approved, snapshot_not_approved) and the panel rendered both in full with field and remedy. This is the behaviour the whole gate design exists for, and it is real.
  • Archive worked and the record reported archived from the server, so the desk was left with no debris.
  • Defect: a fresh record has no snapshot, and the Narrative panel says so — “This candidate has no snapshot yet, so there is nothing to review” — and then renders three fully enabled “Apply override” buttons under that warning. Pressing one POSTs an override against nothing, gets a 404, and the operator is shown this override not found., on a different tab. The panel had already worked out the right answer and then did not act on it. Fixed.

Approve was correctly disabled on that record, because there was no snapshot to approve. That is right, and it is only discoverable from a title tooltip.

! What is not yet possible

This is the section to read before deciding what Story Studio can be used for. Everything below was observed, not inferred from a roadmap.

  • No LLM is wired to anything. The draft generator is deterministic and says so on screen: “Last run by: deterministic”. It is behind a seam, so a model can be dropped in later, but today nothing generates prose that a model wrote. Drafts are assembled from repository facts.
  • The four-lens switcher is gated off for non-default surfaces. CASE_STUDY_SURFACE_LAB_USER_IDS is unset on the production backend, which means off. The lab renders and the Enterprise lens loads (HTTP 200), but Training and AI Flotation return 403 for every admin — and three of the four surfaces are publishable: false anyway. Nothing in this walkthrough changed that environment variable, and nothing should: it is a production config decision, not a bug to work around.
  • External references were never built. There is no surface anywhere in the seven tabs for a customer reference, a testimonial from outside the platform, or a third-party citation. Quotes exist, but they are internal and consent-gated.
  • Charts are unproven end to end. A chart can be created and it correctly reports what it would render — which, on this record, is nothing. No chart has ever been seen resolving a real metric and appearing on a public page, because case_study_metrics is empty for the only record that exists. The chart subsystem is currently a form with an honest error message behind it.
  • Hero selection and artifact promotion are untested. Both are per-artifact controls and the pilot record has zero artifacts. Neither has been seen working or failing.
  • The architecture diagram has no admin preview. It renders on the public page from a CDN-loaded mermaid; to see whether a change to it worked, you visit /stories/:slug. The Story Studio never shows it.
  • Metrics cannot be created here. Nine metric elements render on STORY, all read from the snapshot, all overridable — but there is no control anywhere in Story Studio that adds a row to the metric table, which is what charts and the publish gate read.

⚠ What this walkthrough wrote to production

Stated in full, because a walkthrough that writes to a live record and does not say so is not a walkthrough.

  • A storyline on the pilot record. Editorial direction, stored outside the snapshot, unpublishable by construction.
  • A re-save of the consent fields with the values already on them. Verified unchanged afterwards.
  • One repository attached and then detached. The record ended with exactly the one repository it started with.
  • One manual sync, which created draft snapshot v29. The approved snapshot is still v28 and the publication still points at v28, so the public page did not move. The record now reads “draft ahead”, which is the normal state after any sync.
  • Four AI drafts generated and all four rejected. No pending drafts remain.
  • One chart, unapproved, which resolves nothing. It is the evidence for defect 6 and was left in place rather than quietly deleted.
  • One throwaway record, created and archived.

Never touched: the pilot was not approved, published, unpublished, archived or overridden. Its publication has been continuously live throughout.
