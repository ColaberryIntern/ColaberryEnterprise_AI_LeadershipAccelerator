Explorer Growth · Decision Logic

What the weekly digest actually chooses from

How the Governor picks one action per learner per night, what evidence it reads to do it, how “stage” and “audience” cross to decide what a person is allowed to receive, and why it sometimes declares that it has nothing to send.

Read this first: it is not weekly, and nothing sends it

explorer_weekly_digest is a real campaign with a real sequence and a real decision written for it most nights. But three separate facts in the code mean no Explorer learner has ever received it:

  • Its sequence ships is_active: false, re-asserted on every boot. The seed file calls this “the one thing that actually stops a send.” backend/src/seeds/explorerGrowth/seedExplorerGrowthCampaigns.ts:33, 73
  • Every decision row is written mode: 'shadow' and executed: false. backend/src/services/explorerGrowth/governor/runGovernor.ts:261, 293
  • Its sequence has one step at delay_days: 0, not a recurring seven-day step. Nothing re-enrolls anyone weekly. backend/src/seeds/explorerGrowth/explorerSequenceDefinitions.ts:137-147

So everything below describes a system that decides and records, and is deliberately not yet permitted to act. That is the point of shadow mode: you can audit the judgment before it reaches anybody.

1The nine things it can choose, and why the digest nearly always loses

The agent does not compose a digest out of parts. Each night it runs eight independent generators over one learner, each of which either proposes a single action or returns nothing. A referee then picks exactly one winner. The weekly digest is one of the nine possible outcomes, and deliberately the last one.

// governor/candidates/nurture.ts:80-97 — the entire digest generator
export function generalNurture(ctx) {
  if (ctx.contactability?.email?.eligible !== true) return null;
  return {
    action_type:      'SEND_EMAIL',
    campaign_key:     'explorer_weekly_digest',
    priority_tier:    9,
    intra_tier_score: 30,
    required_assets:  [{ asset_type: 'weekly_digest', state: ctx.primary_state, ... }],
    rationale:        ['general nurture — no higher-priority candidate applies'],
  };
}

How the referee ranks them

Four sort keys, in order:

  • priority_tier ascending — lower tier wins outright
  • intra_tier_score descending — breaks ties inside one tier
  • then action_type and campaign_key alphabetically

Those last two exist only to make the ordering total. The documented third and fourth keys (days in state, enrollment id) are constant for a single learner, so they cannot separate two of that learner's candidates. Without a final deterministic key the output would stop being reproducible, which would quietly destroy the idempotency the whole system rests on.

Every loser is recorded with the reason it lost. This is why the digest is usually the thing being suppressed rather than the thing suppressing: a real production row reads explorer_weekly_digest → "lower priority than tier 6 (SEND_EMAIL)".

2What information it looks at

Three cron jobs run in a deliberate order each night: content sync at 02:50, profile recompute at 03:20, then the decision at 03:50. By the time the agent chooses, this is everything on its desk.

Two name collisions worth knowing

  • There is a per-learner portal preference also called weekly digest (“A Monday summary of your progress, points, and what’s next”). The Governor does not read it. Different feature, same name.
  • The forecast service uses the word gap to mean a shortfall against a paid-learner target. Unrelated to content gaps in §4.

What is deliberately NOT on the desk

The generators are pure functions. The context handed to them has, in the code's own words, “no mailer, no queue, no campaign engine, no model client.” A test enforces an import whitelist and derives the forbidden send* function names from the mail service's own source, so the decision layer is structurally incapable of sending. A generator can propose; it cannot act.

3Stage × audience: the two questions that must both pass

This is the part most often misread as one idea. “Stage” and “audience” are two independent axes, written by different functions for different reasons, and a piece of content has to clear both before a learner can be sent it.

Axis two: content → week → stage and audience

Both tags are written by the 02:50 projection, from one field: the card’s week number.

// Where the content sits in the journey
week is null  → 'evergreen'
week <= 1     → 'activation'
otherwise     → 'learning'

// Who is allowed to open it — mirrors the portal's own gate exactly
week === 0    → ['free_preview', 'full_access']
otherwise     → ['full_access']

The trap. An undated card is evergreen, which sounds portable, but full_access only — because the portal’s rule is week === 0 and null is not 0. The two tags answer different questions, and the thresholds genuinely differ: week ≤ 1 for stage, week === 0 for audience.

Where they cross

At lookup time both become predicates in the same query. For a digest to an ACTIVATING free-preview learner: 

AND :tier = ANY(audience_tags)                                -- 'free_preview'
AND (:stage_tags IS NULL OR journey_stage_tags && :stage_tags)  -- '{activation}'
AND asset_type = ANY(:kinds)                                 -- '{LESSON}'
LIMIT :max_rows                                              -- 3, only for the digest

A stage of null means do not filter by stage, which is not the same as “match nothing.” The digest pins no stage of its own, so it follows the learner. Activation purposes do the opposite: they pin activation regardless of where the learner has drifted to, because the point is the first step.

The consequence, in one line

Of 585 synced cards only 23 are week 0, while 152 of 153 learners are free tier. Every one of the 206 learning-stage assets is full_access. So a free-tier learner past week 0 has an empty candidate set by construction — not because content is missing, but because none of it is theirs to see. Recommending anything else would send 96% of the audience to a paywall.

Zero cells are highlighted in the real UI with the tooltip “No asset a learner in this stage and tier could receive.” Do not sum the cells: 23 assets carry both audience tags, so the grid totals more than the catalog holds.

4Why something is declared a gap

A gap is a first-class outcome, not an error. The governing contract is that a missing asset is reported, never invented and never quietly substituted. There are three distinct kinds and they should not be merged.

Kind A  Declared gap — a purpose nothing can ever answer

Hand-written in source with a reason. The entire test is one field: supported: false. It is refused before any database query runs.

PurposeDeclared reason
community_digestCommunity posts are 100% cohort-scoped private discussion; no cohort-safe projection is defined. A privacy boundary, not a shortage — every post carries a cohort id, and a registry row is cohort-blind by construction.
friction_recoveryNo friction-recovery content exists; zero learners currently request it
enrollment_offerNo offer asset is projected yet; zero learners currently reach ENROLLMENT_READY
referral_inviteNo referral asset exists; zero learners currently reach REFERRAL_READY
Reported rather than filled. An invented “we noticed you got stuck” email nobody wrote is worse than an empty registry, because it looks ready. content/assetPurposeMap.ts:121-128

note  The weekly digest is not a declared gap. It is supported: true, kinds ['LESSON'], limit 3 — the only purpose allowed more than one asset, “because a digest of a single item is not a digest.”

Kind B  Named gap — this learner, this night, nothing to carry

An action was selected and no content could fill it. Two conditions produce one:

  • the purpose is a declared gap, so the reason above travels verbatim; or
  • the query ran and returned zero rows.

The second produces a token naming the purpose and the stage it looked in:

no_asset_for_purpose:lesson_recommendation:learning

There is no gap table and no gap type. A gap is a string segment inside the decision row’s reason column, alongside the rationale and the consent note: 

state=CONNECTED_TO_COMMUNITY | no affinity evidence yet
  | campaign=explorer_next_lesson | consent: can_spam_opt_out
  | asset gaps: no_asset_for_purpose:lesson_recommendation:learning

Two properties matter. A gap never drops the decision — the row is still written, so the review can say “these N have no asset behind them” instead of quietly showing fewer rows. And partial success stays partial: one gap does not discard the assets that did resolve, and one success does not hide the gap.

Kind C  Campaign gap — the message has nowhere to be sent from

The action named a campaign key that no campaign row answers, so the id stays null and the gap is named: no campaign for key: explorer_weekly_digest.

It never falls back to another campaign: the eight keys mean eight different messages, and substituting one for another would send a dormant learner an enrollment offer while every count still looked healthy. governor/runGovernor.ts:235-241

What a human is supposed to do about one

The admin Content tab carries the instruction itself, under the heading “What the Governor could not find”:

Before treating this as missing content, read the matrix below. A gap can mean the content exists but the learner’s tier cannot see it. components/explorerGrowth/ContentTab.tsx:118-141

So the loop is: read the token to learn which purpose and which stage, then use the stage × audience grid to decide which of three causes it is.

CauseWhat it meansAction
Content genuinely absentNothing exists for that purpose and stageAuthor or publish it; the 02:50 sync projects it the next night
Content exists, tier cannot see itThe entitlement filter excluded itA scope decision about the free tier, not a bug
Declared gapA deliberate, reasoned refusalChanging it means designing audience-scoped resolution — not filing a ticket
That is why 12 decisions reported a gap on 2026-09-02 and zero did on 08-31: the entitlement filter shipped on 09-01 and is working exactly as designed. It is a decision about what the free tier should include, not a bug — and the cross-tab is what makes that legible instead of alarming. components/explorerGrowth/ContentTab.tsx:20-23

5Everything that can stop the digest

The pipeline order is: freshness gate, hard stop, generate, arbitrate, contact policy, record. Note that contact policy runs after the winner is chosen, not before — so a blocked message is recorded as “chosen, then blocked, and here is why,” which is far more useful to a reviewer than never appearing.

One outcome that should never be mistaken for consent: when no consent record exists at all, the verdict is allowed with basis no_evidence, and that phrase is written onto the decision row. It is recorded precisely so nobody later reads silence as permission.

6Where the design document and the code disagree

Worth knowing before planning work against the plan rather than the code.

The plan specifiesWhat exists
One recurring step, 7-day delay, re-enrolled weeklyOne step, delay_days: 0, no re-enrollment absent
Three assembled slots: one thing to learn, one opportunity, one next actionNo slot concept anywhere in the subsystem. The digest asks for up to 3 LESSON assets and nothing else. absent
Guardrail: if fewer than 2 of 3 slots resolve, do not send — “a one-item digest is a newsletter”No such guardrail absent

The campaign-definitions file says so itself: it is keyed from the shipped governor rather than the plan document, because only 2 of the 8 campaign keys matched. The eight purposes were measured — read back out of real decision rows — not designed up front.

Every claim here was read from the code in backend/src/services/explorerGrowth/ and verified against source. Production counts (153 learners, 585 cards, 23 week-0, 206 learning assets, 12 gapped decisions) are figures recorded in code comments at the time they were written, not live queries — treat them as orders of magnitude, not today’s numbers.

The one thing to carry away: this system currently decides and records, and is not permitted to send. Shadow mode exists so the judgment can be audited before it reaches a learner.
