Gov Company Dossier · Needs restructure

From 100+ scattered asks to a handful of fillable groups

The dossier today lists every unanswered placeholder as its own row, so the same question appears a dozen times under slightly different wording. This plan adds a semantic grouping layer that reads what each ask actually wants, folds it into the same category and record groups the library already uses at the bottom, and grows new groups on its own when a new kind of information shows up. Ram fills one form per group, and the answer propagates to every bid that asked.

Why it looks like this today

Four causes, each in one place in the code.

1. Deduplication is literal, not semantic

mergeTenantNeeds dedupes only by an exact need.key, and that key is just the drafter's placeholder label, title-cased (cleanFactKey). "project name 1" and "specific project names" produce different keys, so they never merge into one row.

2. Needs are not folded into the library's groups

The needs section renders a flat <ul>. Only record-kind needs get a "Reference" / "Key person" tag. Plain fact-needs are never bucketed into the FACT_CATEGORIES the library below is grouped by, so the top and bottom of the page use two different structures.

3. The taxonomy is a hardcoded array

FACT_CATEGORIES is a fixed 7-item list in the frontend. It cannot grow, so anything that does not fit lands in "General". A brand-new kind of RFP demand has nowhere of its own to go.

4. Filling is one ask at a time

Each need is answered individually inside a single bid's Proposal Studio. There is no "fill this whole group for this company once" path, which is exactly what bulk entry by Ram needs.

Already solved and reused: the grouped record kind (one reference = client+scope+value+dates+contact as a unit), the tenant-wide needs union, and answer-once propagation across bids all exist and are live. This plan routes many atomic needs into those existing rails rather than rebuilding them.

How it gets smart, and grows

Every incoming ask runs through one classifier before it ever reaches the screen.

deterministic alias map AI classifier for the long tail
Place

File by group and by subject

Two tags: which group it belongs to, and what it is about (reporting, recruiting, data work). The subject is what stops records being swapped between unrelated requirements. If nothing fits, propose a new group.

subject tag new group, pending approval
Show

One card, every bid that asked

The group card carries a bid count and a single Fill form. Answering it resolves every atomic need mapped to it, across all bids.

Trust before intelligence. The classifier's mapping and any new category it proposes are shown with a confidence level and stay pending an admin's confirmation before they shape the drafter. The AI never silently invents a category or an answer; it proposes, a person approves, exactly like the dossier's existing approve-before-use gate. A deterministic alias map handles the recurring asks with no model call at all, so the common case is fast, free of AI cost, and auditable.

Same group, not interchangeable

A reference only answers a requirement it is actually relevant to.

Two past-performance references both live in the "Past projects & references" group, but they are not swappable. A requirement asking for reporting experience must not be answered with a recruiting project. So beyond its group, every requirement and every record carries a second tag: what it is about. The group decides the shape of the answer; the subject decides which record is allowed to fill it.

What this fixes today: right now every approved reference is handed to the drafter for every bid with no relevance filter, so a recruiting project can surface in a reporting proposal. Giving each record a capability tag (case studies already carry one) and matching it to the requirement's subject closes that. Answer-once reuse then means answer once per subject: a reporting reference clears the reporting need on every bid that asks for reporting, and leaves the recruiting needs untouched.

The build, phase by phase

Each phase is one PR, independently shippable. Ali merges; deploy is backend plus nginx.

0

Taxonomy becomes dataPR 0

  • Move FACT_CATEGORIES into a tenant-scoped gov_requirement_categories table, seeded with today's 7 categories plus the reference and personnel record groups.
  • Both the library and the needs surface read the taxonomy from one source. No behavior change yet, just the seam that lets it grow.

Reuses: the existing fact category column; DDL proven in accelerator_dev1 inside a rolled-back transaction first.

1

Canonical normalizer, deterministic corePR 1

  • A pure canonicalizeNeed(ask, key) with an alias table for the recurring asks: project name and details, client, due date, contact, past performance, pricing, certifications, registrations.
  • mergeTenantNeeds dedupes by canonical id instead of raw key. This alone collapses the 100+ to the true distinct set.

Reuses: the tenant needs union. Pure and fully unit-tested, no AI, no migration.

2

AI classifier for the long tail, adaptive categoriesPR 2

  • Asks that match no alias go to a classifier that maps to the nearest canonical and category with a confidence, or proposes a new category.
  • It also tags each requirement and record with a subject (reporting, recruiting, data work), so references stop being interchangeable. The drafter then cites a reference only when its subject matches the requirement, instead of offering every approved reference to every bid.
  • Results are cached per distinct label (classify once) and land as pending taxonomy rows an admin confirms. This is the "gets smarter and grows" behavior.

Reuses: the dossier approve-before-use gate and the grounding allow-list, so nothing unapproved reaches the drafter.

3

Grouped needs UI and the group fill formPR 3

  • Render needs grouped by category and record, one card per group with a bid count, matching the library's look below. Where a group spans subjects, the card splits by subject (reporting, recruiting) so each is filled on its own.
  • One Fill form per group collects the record and its subject at once, and resolves every atomic need mapped to that group and subject, across every bid asking for it.

Reuses: the grouped record form, resolveProjectNeed, and answer-once propagation. This is Ram's bulk-entry path.

4

Reclassify the live backlogPR 4

  • Run the normalizer over the open gaps already on the live tenant so the current 100+ collapse into the clean grouped view on day one.
  • Non-destructive: it only tags open needs with their canonical group; it never edits or deletes an answer.

Reuses: the Phase 1 and 2 classifier, run once as a backfill script.

6

What this gives Ram

A short list, not a wall

Roughly 8 to 12 group cards instead of 100-plus rows. Each says how many bids need it, most-shared first.

Fill once per subject

One form per group. The answer becomes a reusable fact or record and clears that question off every bid asking for the same thing, and only those, so a reporting reference never lands on a recruiting bid.

It keeps up with new RFPs

When a solicitation asks for something genuinely new, a new group appears for his review instead of the question hiding in "General".
