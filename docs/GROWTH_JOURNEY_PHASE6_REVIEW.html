What to look at

The dark state component

What an operator sees today, before anything is switched on.

Look at:
  • The banner names the flag, not a symptom. A dark system and a broken one look identical on every other screen, so this is the only thing that tells them apart.
  • It says the page is showing configuration rather than activity.
  • It does not also claim memberships are missing — two different problems, and showing both would send someone to run the wrong fix.

The unseeded state component

The other state that looks exactly like a working system.

Look at:
  • It names the seed script. In production tenant_memberships is empty, so this is the state you will actually meet first.
  • The runbook's §8 explains why: the journey reads do not use the tenancy migration ramp, so naming a brand before seeding is a hard 403 — fail-closed, not broken.

Overview — readiness with three states component

Where you start: is this on, and does it have anything in it?

Look at:
  • ready is three-state. tests_green is neither true nor false — "not readable from here, the suite's last result lives in CI" — and it counts neither as ready nor in the denominator.
  • Every blocked item names the next move, not just the problem.
  • Order is the product: next_move is the first blocked item in list order, so the list is worked top-down rather than by whatever looks easiest.
  • The three crons are shown disabled with last_run_at never — "never ran" and "ran and found nothing" are different facts.

Content — what may be said, and what may not component

The tab that enforces the brand boundary.

Look at:

The number to read is the lift, and the interval is the finding.

Look at:

Handoffs — the queue your staff will live in component

A handoff is the system saying a human should take this one.

Look at:
  • The first row has no ticket and says why: capacity_full. A blocked assignment is stated, never silently dropped.
  • The second row's reason reads redacted — the column held an address and the API masked it, with a separate flag saying which happened.
  • The caption says the ordering is not strictly highest-value-first and that paging is unstable. Both are true of the SQL, and a column labelled "highest value first" would be false exactly where it matters.
  • priority has its own column and is not what the list sorts by.

Performance — a null is never a zero component

The single most important distinction on the whole surface.

Look at:
  • Acceptance rate 0.0% "0 of 12" sits directly above expiry rate — "no handoff was created in this window". A real zero means every handoff was refused, which is a crisis. An absence means none existed, which is a quiet week. A screen printing 0% for both would say the opposite of the truth.
  • Every absence carries its own reason — "nothing was accepted, so no meeting could follow", "nothing reached qualified or converted". The API's bare no_denominator is not actionable; these are.
  • Medians distinguish "no samples yet" from "only 2 samples — a median needs 3".
  • The freshness badge is stale with the API's own sentence. This is the only journey read carrying a freshness verdict, so it is the only place a badge is a fact rather than a guess.
  • The bottom table shows AI Flotation Consulting as "Not running yet" — every figure absent rather than zero, "because nobody has arrived to count".

Controls — the only write surface component

Everything else on this workspace reads.

Look at:
  • An active pause is listed with its scope, its reason and who set it. Rows are cleared, never deleted, so the history of who stopped what survives.
  • A pause must name a brand, a programme, a channel or a subject. An all-wildcard pause is refused twice — by the schema and again in the service layer — because it would be a second global kill switch, and this system deliberately has exactly one.
  • ali_outreach can be paused here and cannot be started here. It is review-only by construction and has no rollout route.
