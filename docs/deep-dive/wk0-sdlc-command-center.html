Section 1 · Mission

Why modern software development exists

Software is how organizations deliver strategy — a bank's product is its app. "Software development" is the disciplined practice of turning business intent into a working, maintainable, trustworthy system, and keeping it healthy after launch. It exists because building software is a team sport with high failure cost: unmanaged, projects run late, drift from the need, and become unsafe to change.

Why organizations invest
  • Predictability — turn uncertainty into a plan with gates.
  • Quality & safety — catch defects before customers do.
  • Speed that lasts — ship fast and stay able to change.
  • Alignment — keep the build tied to the real need.
Common misconceptions
  • "Coding is software development." It's one phase of ten.
  • "More process = better software." Process serves outcomes.
  • "AI replaces the team." AI shifts humans from doing to directing.
  • "Done at launch." Most cost and risk live in operation.

The loops inside the lifecycle

Smaller cycles you'll meet

"Lifecycle" isn't one thing. The SDLC contains smaller cycles each Deep Dive revisits.

Repository

A project's memory: code, history, docs — all traceable to a commit.

Branch strategy

main stays shippable; work on feature branches; a PR is the review gate.

Documentation

Docs live beside code and update with it. Stale docs are a defect.

Change mgmt

Every change proposed, reviewed, approved, reversible.

Release

Build → release → run are separate. Always roll back to last good.

Project

Initiate → plan → execute → monitor → close, marked by gates.

Section 5 · Good vs Bad

Great vs poor delivery

Great looks like

  • Requirements trace to a business outcome.
  • Architecture decisions written with tradeoffs.
  • main always shippable; changes reviewed.
  • Tests cover failure paths, not just happy path.
  • Docs & runbooks current; on-call isn't guesswork.
  • AI output reviewed before it counts as done.

Poor looks like

  • "We'll figure out requirements as we build."
  • Architecture lives in one person's head.
  • Direct commits to main; no trail.
  • Only happy path tested; edge cases hit prod.
  • Docs months stale; every incident is archaeology.
  • Generated code merged unread "because AI wrote it."
Red flags that stop an approval: no traceability, no ADRs, no failure-path tests, no rollback, no risk owner, "works on my machine."

Section 9 · Architect Review

Questions before you approve

This lens repeats in every Deep Dive. Run AI-generated work through it before approving.

Business

  • Solves the real problem?
  • Scope right?
  • Traces to a need?

Technical

  • Scales & integrates?
  • Tradeoffs written?
  • What breaks, then what?

Operational

  • Deploy, monitor, roll back?
  • Who owns it after launch?
  • Security & compliance?

Maintainability

  • Can a newcomer follow it?
  • Tested & documented?
  • Cheap to change?
Approve only when: intent met, failure path handled, tested & documented, tradeoffs explicit, owner + rollback exist. Less than that is "send back with feedback."
