Overview · Mission

Why the Software Engineer exists

An approved design is a promise; code is the reality that either keeps it or breaks it. The Software Engineer implements the design, structures it so it can be understood and changed, and proves it works with tests. Skip the discipline and you still get code that runs once — then rots into something no one can safely touch. When a claim is filed at 2 a.m., the difference between a clean intake service and a fragile one is whether the customer's claim is captured or silently lost.

Business value
  • Turns a design into software that actually behaves as specified.
  • Keeps code changeable — most cost lands in the years after launch, not the first release.
  • Catches defects with tests before customers do.
  • Makes the codebase legible so the next engineer (or AI) can extend it safely.
Common misconceptions
  • "It compiles, so it's done." Done means designed, tested, reviewed, and shippable.
  • "Working code is good code." Code is read far more than it is written; readability is a feature.
  • "Tests slow us down." Untested code slows every future change.
  • "AI writes it, so we can skip review." AI writes fast and confidently — including confident mistakes.
How AI changes engineering. AI now writes most of the lines — scaffolding modules, boilerplate, and tests in seconds. What it does not own is architecture fit, correctness on the edge cases, security, and whether the code truly satisfies the design. You supply judgment and the standard; AI supplies the draft.

Ownership

What a Software Engineer actually does

The Software Engineer owns the path from an approved design to a merged, tested change.

  • Translate the design into a module breakdown with explicit interfaces and contracts.
  • Write code that is small, single-responsibility, and named to reveal intent.
  • Cover behavior with tests across the pyramid — unit, integration, and the critical end-to-end paths.
  • Handle failure explicitly: timeouts, retries, and errors that are logged and typed, never swallowed.
  • Keep changes in small, reviewable pull requests with a clear story.
  • Review peers' (and AI's) code against the checklist before it merges.
  • Track technical debt deliberately instead of letting it accrue silently.
  • Confirm every change meets the definition of done before calling it complete.

Section · Good vs Bad

Good vs bad code

Good code

  • Small, single-responsibility modules with explicit contracts.
  • Names that reveal intent — validateClaim, not doStuff.
  • Tested behavior, including failure and boundary paths.
  • Errors handled explicitly, logged, and typed.
  • Changed in small, reviewable pull requests.

Bad code

  • God functions that validate, save, notify, and format at once.
  • Vague names and copy-pasted logic in three places.
  • Happy-path only — no tests for what happens when it fails.
  • Empty catch blocks that hide the real error.
  • A 2,000-line pull request no one can truly review.
Red flags in AI-written code: confident code with no tests, a silently swallowed error, duplicated logic instead of a shared function, a plausible-looking function that never handles empty or malformed input, and a giant diff that "does everything."

Architect Review

Before you approve a change

Run every AI-generated change through this lens before it merges.

Correctness

  • Does it do what the design and acceptance criteria specify?
  • Are edge, empty, and malformed inputs handled?
  • Does it fail safely — logged, typed, no silent catch?

Design & structure

  • One responsibility per module, with a clear contract?
  • Any duplicated logic that should be shared?
  • Names that reveal intent without comments?

Tests

  • Do tests assert behavior, not just run the code?
  • Are failure and boundary paths covered?
  • Is the mix right — mostly fast unit tests?

Safety & change

  • Is untrusted input validated at the boundary?
  • Is the PR small enough to truly review?
  • Is any shortcut tracked as explicit debt?
Approve only when: the code meets the design, edge and failure paths are handled and tested, modules are single-responsibility with clear contracts, the change is small enough to review, and the definition of done is fully met.

Why review AI-written code if it compiles and the tests pass?
Compiling and green tests only prove what the tests check. AI writes confident code that can skip edge cases, security, and architecture fit — the things a review lens catches.
What is the single fastest signal of risky code?
A large pull request with no tests. Size hides defects, and no tests means nothing proves behavior — insist on small, tested changes.
Unit or end-to-end — which should there be most of?
Unit. They are fast, precise, and cheap. The pyramid wants many unit tests, fewer integration, and only the most critical end-to-end paths.

Why is a small pull request safer than a large one?
Small PRs can actually be reviewed — defects hide in large diffs. They also fail smaller and are easier to revert.
Name one thing tests should cover beyond the happy path.
Failure and boundary cases — empty, malformed, or oversized input, and what happens when a dependency is unavailable.
What does a good module contract specify?
Its inputs, its outputs, and its errors — so callers depend on the promise, not the internals.
